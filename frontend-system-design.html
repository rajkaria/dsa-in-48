How to run these two days

Every topic is a refresher plus a rapid-fire question set — and one running design (a photo-sharing feed) that each topic extends. The questions are the workout: cover the answer, say yours out loud, then reveal and compare. Out loud is non-negotiable; the round is a spoken performance.

01 · answer before you reveal

Every question hides its answer behind a click. Say your answer aloud first, then reveal. Reading answers feels like progress and trains nothing — the interview only grades production, not recognition.

02 · the shape of a good answer

Requirement → options → decision → tradeoff you just accepted. "Feed needs fast first paint on mobile → SSR the first page, hydrate, then client-fetch the rest → we pay server cost and hydration complexity." That shape scores in every frontend round.

Your whiteboard boxes are components, stores, and caches in the browser — SearchInput, ResultsList, a query cache, a WebSocket manager. One box on the far right says "API". If you're drawing load balancers, you're answering the wrong round.

The interview loop — RADIO

Frontend design rounds reward structure over brilliance. RADIO — Requirements, Architecture, Data model, Interface, Optimizations — is the script that keeps 45 minutes from dissolving into component trivia.

YOU ALREADY KNOW THIS

Every ticket you've ever refined is a mini-RADIO: clarify what "done" means, sketch which components change, agree the API shape, then argue about edge cases. The round is a 45-minute refinement session where you run the meeting.

// the idea

  • R — Requirements (5 min): split functional ("type → see suggestions → pick one") from non-functional (fast on mid-range mobile, works offline-ish, accessible, i18n?). Then scope down out loud: "I'll focus on the results list and caching; I'll treat auth as done." Interviewers grade the scoping itself.
  • A — Architecture (10 min): draw the component tree plus the client-side services around it — a query cache, a WebSocket manager, a router. Boxes = components/stores; arrows = data flow, props down, events up. Name where state lives before anyone asks.
  • D — Data model (10 min): the client-side entities and their shape: what's server state (posts, users — cached, refetchable), what's UI state (selected index, open modal), what's persisted (drafts in localStorage). Normalize entities by id; store lists as arrays of ids, never nested copies.
  • I — Interface (10 min): two contracts: the HTTP/WS API (endpoints, pagination params, error shape) and the component API (props for your reusable pieces — an <Autocomplete getSuggestions onSelect renderItem />). Senior candidates design the second one unprompted.
  • O — Optimizations (10 min): the depth showcase, themed: performance (debounce, cache, virtualize), resilience (retry, offline, race conditions), a11y (keyboard, ARIA), security (sanitize). Pick the two the product actually needs — that judgment is the signal.
  • Timebox out loud. "Five minutes on requirements, then architecture" tells the interviewer you've run real design meetings. Ask before going deep: "want me to go deeper on caching or move to offline?"

// rapid-fire — answer out loud, then reveal

How is the frontend system design round different from the backend one?

Backend rounds distribute load across machines; frontend rounds architect one browser session: rendering strategy, component boundaries, state ownership, data fetching, and failure UX. Capacity math mostly disappears; latency budgets, bundle size, and interaction design take its place. Saying this contrast in your opening minute signals you know which game you're playing.

What do you clarify in the requirements phase of "design an autocomplete"?

Functional: data source (static list vs API), single vs multi select, free text allowed? Non-functional: result latency target, mobile keyboards, expected list size (10 vs 10,000 — decides virtualization), a11y bar, i18n. Then scope: "I'll design the input, fetching, and list; ranking is server-side." Two minutes, huge signal.

What goes in your architecture diagram if not servers?

The component tree (App → page → sections → leaf components), the client services beside it (query cache, socket manager, router, analytics), and one box for the API. Arrows show data flow: props down, callbacks/events up, services accessed via hooks. State ownership gets written next to the box that owns it.

What's the difference between server state and UI state — and why does the split matter?

Server state is someone else's data you cache (posts, profiles) — it can be stale, refetched, shared across views. UI state is yours and ephemeral (open dropdown, input value). Mixing them — e.g. copying API data into useState — creates staleness bugs; the split tells you the tool: query cache for one, local state for the other.

Interviewer says "design the component API for a reusable modal." What are you actually being asked?

Props-as-contract design: controlled vs uncontrolled (open + onClose beats internal state), composition (children vs config props), escape hatches (initialFocusRef), and what you deliberately leave out. Mention focus trap and portal to show the a11y floor is built in, not bolted on.

How do you handle "we have 45 minutes" time pressure?

Announce the plan (RADIO with rough minutes), write requirements as bullets not prose, and at each transition ask "deeper here, or move on?" If you're behind, cut optimizations to one theme done well. Running the clock visibly IS senior behavior — meandering is what fails the round.

What are the classic frontend design prompts, and what's each secretly testing?

Autocomplete: debounce, caching, race conditions. News feed: pagination, virtualization, optimistic actions. Chat: real-time transport, offline queue, ordering. Photo carousel/editor: preloading, gestures. Collaborative doc: conflict handling (OT/CRDT at concept level). Design system component: prop API + a11y. Each is a lens on the same 12 topics in this course.

When should you bring up accessibility — end or start?

Start: it's a requirement ("target WCAG AA — keyboard and screen reader support for everything interactive"), then it shows up in the component API (ARIA roles, focus management) rather than as a guilty afterthought. "A11y as requirement, not optimization" is a line interviewers remember.

Rendering strategies

CSR, SSR, SSG, ISR, streaming, islands — six answers to one question: where does HTML come from, and when? Every frontend design opens here, so this vocabulary has to be reflex.

YOU ALREADY KNOW THIS

You've shipped a Vite SPA (that's CSR), waited for a Next.js page to build (SSG), and watched a dashboard show a spinner-then-content (client fetch after hydration). The strategies are just names for where you've already put the waiting.

// the idea

  • CSR (client-side rendering): server sends an empty div + JS bundle; the browser builds everything. Cheapest to host, great after load — but first paint waits on the whole bundle, and SEO needs extra work. Right for logged-in tools (dashboards, editors).
  • SSR (server-side rendering): server renders real HTML per request; browser paints it fast, then hydration attaches JS so it becomes interactive. Fast first paint + SEO; costs server compute and a "visible but dead" gap before hydration finishes.
  • SSG (static generation): HTML rendered once at build time, served from a CDN. Unbeatable speed and cost — for content that's the same for everyone and changes rarely (marketing, docs, blogs).
  • ISR (incremental static regeneration): SSG that re-renders a page in the background after a revalidate window — static speed with content that's at most N seconds stale. The product-catalog answer.
  • Streaming SSR + Suspense: server sends the shell immediately and streams slow sections as they're ready; React fills the Suspense holes. Kills the "slowest query decides first byte" problem. Server Components go further: those components' JS never ships to the client at all.
  • The decision inputs, said out loud: is content public (SEO) or behind auth? Personalized per user or same for everyone? How fresh must it be? How interaction-heavy after load? Answer those four and the strategy picks itself — that's the sentence interviewers wait for.

// rapid-fire — answer out loud, then reveal

What is hydration, and why can it hurt?

After SSR, the browser has HTML but no behavior; hydration is React rebuilding its tree over that HTML and attaching listeners. It hurts because the page looks ready but ignores clicks until it finishes — and it re-downloads-as-JS everything the server already rendered. Mitigations: less client JS (Server Components), streaming, selective/lazy hydration (islands).

SSR vs SSG vs ISR — pick for a news site's article page and defend it.

Articles are public (SEO matters), identical for every reader, written once and edited rarely — that's static. Pure SSG breaks on corrections and breaking news, so ISR with a short revalidate (say 60s) gives CDN speed plus bounded staleness. SSR would pay a server render per view for content that doesn't change per viewer. Naming the revalidate number makes it concrete.

When is plain CSR the RIGHT answer, not a cop-out?

Behind a login where SEO is irrelevant, for interaction-heavy tools where post-load snappiness beats first-paint (Figma, dashboards, editors) — hosting is a static bucket, the API is the only backend. Weakness to volunteer: cold first load and SEO; fix with a tiny SSR'd shell or just accept it.

What do Core Web Vitals have to do with rendering strategy?

Strategy largely decides them: SSR/SSG pull LCP earlier (HTML arrives ready); CSR pushes LCP behind the bundle; hydration cost shows up in INP (interaction readiness); streaming protects LCP when data is slow. "I'd pick SSR here mainly for LCP on mobile" connects the two like a senior.

What are React Server Components, in interview-sized form?

Components that run only on the server: they can read the DB directly and their code never joins the client bundle — the client receives their rendered output. Client components (marked "use client") still handle interactivity. Payoff: dramatically less JS shipped; cost: a mental model split and framework buy-in. One honest sentence of each is full marks.

Design a landing page + logged-in app in one product — one rendering strategy or two?

Two, split by route: SSG/ISR for the public marketing and pricing pages (SEO + CDN speed), CSR or light SSR for the app behind auth. Modern frameworks choose per route; saying "rendering strategy is a per-route decision, not per-app" is the differentiator sentence.

What's the islands architecture?

Serve mostly static HTML and hydrate only small interactive "islands" (the carousel, the buy button) — the rest ships zero JS. Astro popularized it; it's the content-site answer to hydration cost. Contrast: React's version of the same instinct is Server Components + selective hydration.

Interviewer: "our SSR page's time-to-first-byte is bad because one API is slow." Options?

Stream: send the shell immediately, wrap the slow section in Suspense so it arrives later. Or cache the slow call server-side, or degrade to skeleton + client fetch for that section. The wrong answer is "make the whole page CSR" — you'd trade one slow section for a slow everything.

Component architecture

Where do you draw the boundaries, who owns what, and what makes a component API good? This is the round's bread and butter — the diagram phase lives or dies here.

YOU ALREADY KNOW THIS

Every time you've split a 400-line component because it re-rendered too much, or extracted a <Button> because three pages styled it differently, you were doing component architecture. The interview just wants the reasoning before the pain, spoken aloud.

// the idea

  • Boundaries follow responsibility, not visuals: split where data needs differ (this section fetches, that one is pure), where update frequency differs (ticker vs static sidebar — isolate the fast one), and where reuse is real. "One component per rectangle in the mock" is the junior tell.
  • Container vs presentational, modernized: a thin layer of components that know about data (call hooks, pick stores) rendering a wide layer that just takes props. Presentational components are trivially testable and design-system-able; hooks replaced the old HOC plumbing.
  • Composition over configuration: a modal that takes children (and maybe Modal.Header/Modal.Body compound parts) beats one with 25 boolean props. Config props multiply combinatorially; slots let callers compose what you didn't foresee.
  • Controlled vs uncontrolled: controlled = parent owns the value (value+onChange) — composable, the default for design systems. Uncontrolled = component owns it (defaultValue, read via ref) — less wiring, fine for simple forms. The senior move: support both, controlled when value is passed.
  • Design systems at scale: tokens (color/space/type as variables) → primitives (Button, Input, Stack) → patterns (forms, tables) → product features. Versioned like a library, documented in Storybook, a11y baked into the primitives so product teams inherit it for free.
  • Prop drilling vs context: drilling two levels is honest and fine; five levels of pass-through means restructure — compose children higher up, or put stable, app-wide values (theme, current user) in context. Context is DI, not a state manager — every consumer re-renders when the value changes.

// rapid-fire — answer out loud, then reveal

How do you decide where one component ends and the next begins?

Three splits that pay rent: different data sources (fetching vs pure), different change rates (isolate the fast-updating part so it re-renders alone), and genuine reuse. Plus readability — a component should fit in your head. Splitting purely by visual rectangles or file size is the anti-pattern to name.

Design the props for a reusable <DataTable> — what shows senior judgment?

Data in (rows, columns with render functions), events out (onSort, onRowClick), render customization via functions/slots (renderCell, empty), controlled sort/selection state, and explicit non-goals said aloud ("fetching and pagination live outside — the table renders, the page owns data"). Owning the non-goals is the senior part.

When is React context the wrong tool?

For fast-changing or partial-read data: every consumer re-renders on any value change, and you can't subscribe to a slice. Wrong for form input state, live prices, drag positions. Right for stable app-wide values — theme, locale, current user, an injected API client. "Context is dependency injection, not a store" is the line.

What's a compound component, and when do you reach for it?

A family sharing implicit state via context under one parent — <Tabs><Tabs.List><Tabs.Tab><Tabs.Panel>. Reach for it when structure varies by caller but the parts must coordinate (tabs, accordions, menus, modals). It's the design-system alternative to a config-object prop.

Where does business logic live, if components should stay dumb?

Custom hooks for stateful logic (useCart(), useAutosave()), plain functions/modules for pure rules (pricing, validation) — components orchestrate and render. Payoff: testable without rendering, reusable across views, and swappable UIs. This is the modern answer to "container components".

How would you structure a design system for 10 product teams?

Layered: tokens → primitives → patterns, shipped as a versioned package with semver discipline (breaking prop changes = major), Storybook as the contract, a11y and theming solved once in primitives, codemods for migrations, and a contribution path so teams upstream fixes instead of forking. Governance is the part most candidates skip — say it.

One team's feature needs a variant your Button doesn't support. What happens?

Escape-hatch ladder: composition first (wrap it), then className/style passthrough if the system allows, then a proposal upstream — never a copy-pasted fork, which orphans a11y and future fixes. Knowing there IS a ladder is the answer; naming fork-rot is the bonus.

Error boundaries — where do they go in the architecture?

Per independent region, not one global: each route, each widget on a dashboard — so one crashed panel degrades to a fallback while the rest lives. Global one at the root as last resort. Remember what they miss (event handlers, async) — those need try/catch feeding an error store or toast.

State at scale

Four kinds of state, four different homes. The single highest-signal sentence in the round is naming which is which — most candidates lump it all into "the store".

YOU ALREADY KNOW THIS

You've lifted state up and regretted it (everything re-rendered), shoved it in Redux and regretted it (boilerplate for a checkbox), and finally learned some state just belongs in the URL. That scar tissue IS the taxonomy — this block names it.

// the idea

  • Four kinds, four homes. Local UI state (open dropdown, input value) → useState in the component. Shared app state (theme, cart, current user) → a small global store. Server state (posts, profiles) → a query cache (React Query/SWR). URL state (page, filters, selected tab) → the router. Misplacing one category causes most state pain.
  • Colocation rule: state lives with the lowest common ancestor of everything that reads it — no lower (prop chaos) and critically no higher (re-render blast radius, false coupling). "Lift state up" has a second half nobody quotes: and push it back down when only one subtree cares.
  • Server state is a cache, not state: it has staleness, refetching, deduping, invalidation — cache problems. React Query/SWR solve exactly these (stale-while-revalidate, retries, dedupe by key). Copying fetched data into Redux/useState hand-rolls a worse cache — the #1 modern anti-pattern to name.
  • URL as state: filters, search terms, pagination, selected item → query params. Free deep-linking, sharing, back-button behavior, and refresh-survival. In the interview say: "filters go in the URL so a shared link reproduces the view."
  • Global stores, right-sized: Redux Toolkit when you want devtools/middleware/time-travel and a big team's discipline; Zustand/Jotai when you want a 2KB store with selector-based subscriptions. Either way: keep it small — auth, theme, cart. If the query cache holds server data and the URL holds view state, the global store shrinks dramatically.
  • Derived state is computed, not stored: filtered lists, totals, validation — compute in render (memoize if hot). Storing derivations means synchronizing them; desync bugs are the tell. Same rule server-side of the boundary: normalize entities, derive views.

// URL state — filters survive refresh & share links
const [params, setParams] = useSearchParams();

// server state — a CACHE with a key, not useState

  queryKey: ['posts', filter],          // cache key = deps
  queryFn: () => api.posts.list(filter),
  staleTime: 30_000,                    // fresh for 30s
});

// local UI state — stays in the component that owns it
const [draft, setDraft] = useState('');

// shared app state — small selector-based store (Zustand)
const cartCount = useCartStore((s) => s.items.length);

// derived — computed, never stored
const visible = useMemo(
  () => posts?.filter((p) => !p.hidden) ?? [],
  [posts]

// rapid-fire — answer out loud, then reveal

Interviewer: "where does state live in your feed design?" — the model answer?

Split it: posts and profiles are server state in a query cache keyed by feed+cursor; scroll position and composer draft are local; auth/user is a tiny global store; active filter is a URL param. Four sentences, four homes — that taxonomy answer alone puts you ahead of most of the loop.

Why is copying API data into useState an anti-pattern?

You've created a second source of truth with no staleness tracking, no refetch-on-focus, no dedupe across components mounting the same data, and manual invalidation after every mutation. A query cache gives all of it declaratively. The interview phrase: "server state is a caching problem, not a state problem."

Redux vs Zustand vs Context — the calibrated answer?

Context: DI for stable values, not a store. Zustand: minimal global store with selectors — great default for the small residue of true app state. Redux Toolkit: when the team wants enforced patterns, middleware, devtools time-travel at org scale. And the reframe that shows depth: with React Query + URL state, most apps' "global state" shrinks to auth + theme + cart.

What is stale-while-revalidate?

Serve the cached (possibly stale) value instantly, refetch in the background, update when fresh data lands. The user sees content immediately and eventual correctness — the default UX of React Query/SWR and of HTTP caching with the same directive. Contrast: spinner-until-fresh, which trades perceived speed for guaranteed freshness.

How do you keep two open tabs of your app consistent?

Storage events (localStorage 'storage' event fires in OTHER tabs) or BroadcastChannel for direct messaging; for server data, refetch-on-focus from the query cache mostly solves it for free. Mention idempotent mutations so a double-submit across tabs is safe. Rarely asked head-on, devastating when you volunteer it.

When would you use useReducer over useState?

When several fields change together under named transitions — a multi-step form, a wizard, drag interactions: dispatch({type:'NEXT_STEP'}) centralizes transition rules and makes them testable as a pure function. It's local Redux without the library. Bonus: dispatch identity is stable — handy for memoized children.

The interviewer asks how undo/redo would work in your design.

Command pattern over state snapshots: keep past[]/present/future[] (or a list of inverse operations for memory efficiency); every mutation pushes to past and clears future. Works cleanly only if state transitions are centralized (reducer/store) and state is immutable — which is the real point of the question.

Forms: controlled everything, or something smarter?

Per-keystroke controlled state across 30 fields re-renders the world; React Hook Form keeps inputs uncontrolled (refs), re-renders only touched fields, layers validation on top. Small forms: controlled is fine and simpler. The senior sentence: "form state is local, ephemeral, and performance-sensitive — treat it as its own category."

Data fetching & caching

Pagination, race conditions, optimistic updates, invalidation — the follow-up questions that separate "drew nice boxes" from "has shipped this". This is where the interviewer probes hardest.

YOU ALREADY KNOW THIS

You've fixed the search box that showed results for the previous keystroke (a race), the like count that jumped back (failed optimistic update), and the list that duplicated page 2 (offset pagination during inserts). Those three bugs are this entire topic — and its three favorite questions.

// the idea

  • Cursor beats offset for feeds: ?offset=20 shifts when new items are inserted above (duplicates/skips); a cursor ("after post_id X" / opaque token) is stable under writes and cheaper for the DB. Offset is fine for page-numbered admin tables. Say the failure mode, not just the preference.
  • Races are the default, not the edge case: two in-flight requests resolve out of order and the old one wins. Fixes, in order of strength: cancel the stale request (AbortController), ignore stale responses (track latest request id / take-latest), and key caches so responses land under the right key. Autocomplete questions are secretly this.
  • Debounce the input, dedupe the cache: debounce (~200–300ms) cuts request volume; a query cache dedupes identical in-flight requests across components; both together make search cheap. Throttle is for continuous streams (scroll, resize) — know which you're naming.
  • Optimistic updates: apply the change locally, fire the request, roll back on failure (with a toast). Perfect for high-success ops with obvious next state (like, follow, todo-check). Skip when success is doubtful or the result is computed server-side (payment, search). Always mention rollback — that's the half candidates forget.
  • Invalidation strategy: after a mutation, either invalidate affected query keys (refetch — simple, correct, default) or write through to the cache from the mutation response (instant, no refetch — for the hot path). Offset vs cursor pagination — failure mode and when each?

Offset breaks under concurrent inserts — page 2 at offset 20 re-serves items that slid down (duplicates) or skips new ones; also OFFSET n scans n rows server-side. Cursors ("after id X", opaque) are stable and index-friendly — the feed answer. Offset survives where jump-to-page-7 matters and writes are rare: admin tables.

The search box shows results for a query the user already replaced. Diagnose + fix.

Race: earlier request resolved later and overwrote newer results. When are optimistic updates the WRONG choice?

When failure is likely or the result isn't locally computable: payments, seat/inventory reservation, anything with server-side validation or computed outcomes, bulk destructive actions. There, show pending state honestly. Optimism fits high-success idempotent toggles — like, follow, check-off. The judgment, not the mechanism, is what's being graded.

After the user posts a comment, how does the UI reflect it — refetch or cache write?

Both are defensible; know the trade. Invalidate + refetch the comments query: simple, guaranteed consistent, one extra round trip. Write-through: append the mutation response into the cached list — instant, no refetch, but you must match server ordering/shape. Common hybrid: write-through now, background refetch to reconcile.

What's a request waterfall and how do frameworks fix it?

Nested components each fetching after mount: serial round trips, latency = sum. Fixes: route-level loaders that fetch in parallel before render (Remix/React Router), Server Components fetching on the server near the data, hoisting queries to a common parent, or a BFF endpoint that aggregates. "Fetch at the route, not the leaf" is the quotable rule.

How would you make the feed feel instant on revisit?

Serve the cached page immediately (stale-while-revalidate), persist the query cache to storage (IndexedDB) so even a fresh session paints from cache, prefetch on link hover/viewport, and keep scroll position. Four cheap tricks that together read as "product care" — perceived performance is a design skill.

GraphQL vs REST from the FRONTEND's perspective?

GraphQL: client picks fields, one round trip for nested needs, typed schema — shines with many screens × many services; costs: cache complexity (normalized entity caches), query cost governance. REST: URL-cacheable, simple, but over/under-fetching pushes you toward BFF endpoints per screen. Frame it as "who controls the response shape" and you sound like you've lived both.

Performance & Core Web Vitals

LCP, INP, CLS — the three numbers Google grades the web on, plus the React-side discipline that keeps interactions fast. "How would you make it fast?" is guaranteed to be asked.

YOU ALREADY KNOW THIS

You've watched Lighthouse yell about your hero image, seen the layout jump as a banner popped in (that's CLS), and profiled a laggy input (that's INP). The vitals are just names and budgets for jank you've already fought.

// the idea

  • LCP (Largest Contentful Paint) ≤ 2.5s: when the biggest above-fold element paints. Levers: render strategy (SSR/SSG), priority-load the hero image (fetchpriority="high", no lazy-load above the fold), CDN, fonts that don't block (font-display: swap), less render-blocking CSS/JS.
  • INP (Interaction to Next Paint) ≤ 200ms: worst-case tap-to-pixel-change across the visit. Levers: less main-thread JS, break long tasks (startTransition, yielding), web workers for heavy compute, avoid giant re-renders on keystroke. INP replaced FID in 2024 — knowing that dates your knowledge as current.
  • CLS (Cumulative Layout Shift) ≤ 0.1: how much the page jumps. Levers: width/height (or aspect-ratio) on images/embeds, reserved space for ads/banners/skeletons, no content injected above existing content, transform animations instead of layout properties.
  • React render discipline: a re-render is a function call cascade — cheap until it isn't. Order of operations: colocate state (shrink the blast radius) → memo hot leaf components → useMemo/useCallback to keep prop identities stable → useTransition to deprioritize the expensive update. Measure with Profiler first; memo-everything is a smell.
  • Perceived beats actual: skeletons that match final layout (also a CLS fix), optimistic updates, prefetch on hover/viewport, cache-first paints, view transitions. Users grade responsiveness, not benchmark numbers — say "perceived performance" explicitly.
  • Measure in the field: lab (Lighthouse/DevTools) reproduces; field (RUM — CrUX, web-vitals library reporting real users at p75) tells the truth about mid-range Androids on 4G. Budgets in CI (bundle size, LCP) stop regressions before deploy.

Real-time & network resilience

WebSocket vs SSE vs polling, offline queues, retries, reconnection — how the app behaves when the network is slow, flaky, or gone. Chat and collaboration prompts are graded almost entirely on this.

YOU ALREADY KNOW THIS

The bug that "only happens on train wifi", the double-submitted form from an impatient double click, the tab left open overnight that stopped updating — you've met every villain in this topic. Now you'll name their defeats: idempotency, retry with backoff, reconnection with catch-up.

// the idea

  • Transport menu, by need: Polling — request on interval; simplest, fine for slow-changing data. Long-polling — server holds the request until news; near-real-time on plain HTTP. SSE — one-way server→client stream over HTTP; auto-reconnects, plays well with proxies/HTTP2 — the notifications/dashboard answer. WebSocket — full duplex; the chat/games/collab answer; you now own heartbeats, reconnection, and scaling fan-out.
  • Reconnection is the real design: detect drop (heartbeat/ping), reconnect with exponential backoff + jitter (thundering herd), then catch up: resume from last-seen event id / sequence number, or refetch snapshot then resubscribe. An answer without catch-up is a demo, not a design.
  • Ordering & dedupe: messages carry server-assigned sequence ids; client buffers out-of-order arrivals and dedupes by id (retries WILL duplicate). Client-generated temp ids reconcile optimistic sends with server echoes — the "message shows twice" bug, pre-empted.
  • Offline as a state, not an error: detect (navigator.onLine + failed fetches), show it honestly (banner, disabled sends or queued sends), queue mutations (IndexedDB) and replay on reconnect — idempotency keys make replay safe. Service worker caches make reads survive; queued writes make actions survive.
  • Retries need idempotency: retry safely only if the server dedupes (idempotency key per logical action) or the op is naturally idempotent (PUT absolute state, not "increment"). Retry budget: exponential backoff, cap, jitter, and give up into visible failure UX. Retrying a non-idempotent POST is how you double-charge cards — say that sentence.
  • Multi-tab reality: one WebSocket per tab wastes connections; SharedWorker (or leader election via Web Locks/BroadcastChannel) shares one socket across tabs. A volunteer-level detail that lands very well in chat designs.

// Reconnect with backoff + catch-up — the interview skeleton
class Feed {
  constructor(url) { this.url = url; this.lastSeq = 0; this.tries = 0; }
  connect() {
    this.ws = new WebSocket(`${this.url}?after=${this.lastSeq}`);
    this.ws.onmessage = (e) => {
      const msg = JSON.parse(e.data);
      if (msg.seq <= this.lastSeq) return;      // dedupe replays
      this.lastSeq = msg.seq;                    // ordering marker
      this.tries = 0;
      render(msg);
    };
    this.ws.onclose = () => this.retry();
  }
  retry() {
    const delay = Math.min(30_000, 500 * 2 ** this.tries++);
    setTimeout(() => this.connect(),
               delay + Math.random() * delay);   // jitter
  }
}

Your WebSocket dropped for 40 seconds. What must the client do on reconnect?

Reconnect (backoff+jitter already done), then close the gap: send last-received sequence id and receive the missed messages, or if the gap is too big/unknowable, refetch a fresh snapshot and resubscribe from its version. Exponential backoff with jitter — why each half?

Exponential: each failure doubles the wait — don't hammer a struggling server, cheap first retry for blips. Jitter: randomize the wait so a thousand clients that dropped together don't retry together (thundering herd; retry storms re-kill recovering servers). What makes a mutation safe to auto-retry?

Idempotency: the server must treat a repeat as a no-op — either the operation is naturally absolute ("set status=paid" via PUT) or the request carries an idempotency key the server dedupes on. Without that, a timeout (which might have succeeded!) + retry = double effect. This is why payment forms disable the button AND send a key.

How does the UI communicate offline without being annoying?

Passive banner ("offline — changes will sync"), keep reads working from cache, allow queueable writes with per-item pending badges, block only what's genuinely impossible, auto-sync + subtle confirmation on reconnect. Where does polling still win in 2026?

Low-freshness data (a badge count every 60s), environments hostile to streams (aggressive proxies), and as the degrade path when the socket can't connect. It's also the cheapest thing to operate — no connection state on servers. "Progressive enhancement: WS → SSE → polling" as a fallback chain is a strong closer.

// the idea

  • The DOM is the bottleneck: 100k rows = 100k×(nodes, listeners, style calc, layout) — scrolling dies long before rendering does. Rule of thumb to say: the DOM comfortably holds hundreds of complex rows, not tens of thousands.
  • Virtualization (windowing): render only what's visible + overscan buffer; absolutely position rows inside a spacer div sized to the full list height so the scrollbar stays honest.   • Infinite scroll: IntersectionObserver on a sentinel near the end → fetch next cursor page → append. Guards: in-flight flag (no double fires), retry affordance on failure, "you're all caught up" end state. Pair with virtualization or the DOM grows forever — infinite scroll without windowing is the classic partial answer.
  • Infinite scroll vs pagination is a product decision: feeds/discovery → scroll; goal-directed search/tables → pages (jump to page 7, shareable URLs, a findable footer). SEO and "back button returns to my spot" (restore scroll + cached pages) are the follow-ups to pre-empt.
  • Keep rows cheap: memoized row components keyed by stable id, fixed-size images (CLS inside the list!), no per-row inline handlers churning identity, content-visibility:auto as the CSS-only cousin for simpler cases.

// Virtualization in ~20 lines — the mechanism, not the library
function VirtualList({ items, rowH, height }) {
  const [top, setTop] = useState(0);
  const start = Math.max(0, Math.floor(top / rowH) - 5);   // overscan
  const end = Math.min(items.length,
                       Math.ceil((top + height) / rowH) + 5);
  return (
    <div style={{ height, overflow: 'auto' }}
         onScroll={(e) => setTop(e.currentTarget.scrollTop)}>
      {/* spacer keeps the scrollbar honest */}
      <div style={{ height: items.length * rowH,
                    position: 'relative' }}>
        {items.slice(start, end).map((item, i) => (
          <Row key={item.id} item={item}
               style={{ position: 'absolute',
                        top: (start + i) * rowH, height: rowH }} />
        ))}
      </div>
    </div>
  );
}

Why does a 10,000-row table kill the page — where exactly does the time go?

Node construction and memory first, then every scroll/resize triggers style recalculation and layout over the whole tree, plus paint for everything on screen-adjacent layers; listeners and React reconciliation multiply it. The fix isn't faster rows — it's fewer rows: virtualization caps live DOM at ~viewport+overscan regardless of data size.

Explain virtualization's three moving parts like I've never seen it.

(1) A spacer element as tall as ALL rows would be — so the scrollbar is truthful. (2) Math: scrollTop ÷ rowHeight = which slice is visible; render only that slice + a few overscan rows. (3) Absolute-position the rendered rows at their true offsets inside the spacer. Scroll updates the slice; the user can't tell 40 rows are impersonating 100k.

What breaks when rows have unknown heights, and how do libraries cope?

The offset math needs heights you don't know until render. Cope: estimated heights up front, measure real rows as they appear (ResizeObserver), patch the spacer height and subsequent offsets, cache measurements by item id. Symptoms of getting it wrong: scrollbar jumps and mis-anchored jumps to position. This is why "fixed row height if at all possible" is a real design recommendation.

Infinite scroll: what are the four states your sentinel logic must handle?

Loading (in-flight guard so the observer doesn't double-fire), success-with-more (append + new cursor), failure (visible retry, don't kill the observer), and end-of-data ("caught up" marker, unobserve). Chat renders newest at the bottom and loads history upward. What's special?

Prepending changes scroll height above the viewport — without anchoring, content the user is reading jumps. Fix: record scrollHeight before prepend and restore the delta after (or overflow-anchor/scroll anchoring where supported), keep the sentinel at the top, and pin "stick to bottom" only when the user is already at the bottom — never steal the scroll mid-read.

Product asks for infinite scroll on the orders table. Push back or comply?

Push back with reasons: tables are goal-directed — users need "jump to last month", shareable page URLs, and stable positions for comparison; infinite scroll breaks all three plus makes totals/footers unreachable. Offer: pagination with generous page size, or virtualized scroll WITH URL-synced position. Product judgment is part of the round's rubric.

How do you keep 60fps while scrolling an image-heavy feed?

Virtualize; fixed-dimension image slots (no CLS/laid-out-again); lazy decode (decoding="async", loading="lazy" below fold); low-res/BlurHash placeholders; memoized rows with stable keys; no scroll-driven JS beyond the window math (use passive listeners); avoid new layers per row. Frame budget is 16ms — say it.

Accessibility & i18n

Keyboard, screen readers, ARIA, focus management — plus shipping in 12 languages. The topics that make interviewers sit up when you raise them first.

YOU ALREADY KNOW THIS

You've tabbed through your own form to test it, added an aria-label when the linter complained, and hit the div-that-should-have-been-a-button bug. A11y is that instinct, systematized — and in the round it's a differentiator precisely because most candidates skip it.

// the idea

  • Semantic HTML is 80% of the work: button, a, label+input, nav, headings in order — each brings keyboard behavior, focus, and screen-reader semantics for free. Every <div onClick> is a small a11y debt: no focus, no Enter/Space, no role.
  • First rule of ARIA: prefer not to use it. ARIA adds vocabulary (roles/states like aria-expanded, aria-selected) but zero behavior — you still implement the keyboard. Follow the APG patterns (combobox, dialog, tabs) rather than inventing.
  • Focus management is where SPAs fail: route changes should move focus to the new heading (announce the "page" change); modals trap focus and restore it to the trigger on close; deleted items send focus somewhere sensible. Never outline: none without a visible replacement (:focus-visible).
  • Announce async politely: aria-live="polite" regions for toasts, "3 new posts", validation summaries; loading states with accessible names. Silent spinners are invisible to screen readers — the feed design that "announces new content" earns real credit.
  • i18n architecture: keys + ICU messages (plurals/genders differ by language — never string-concatenate translations), Intl for dates/numbers/currency (never hand-format), RTL via CSS logical properties (margin-inline-start), and layouts that survive German (+35% text) and compact scripts. Locale is state: in the URL for public pages (SEO per locale), profile for apps.
  • Enforcement: a11y lives in the design system (accessible primitives once, inherited everywhere), eslint-plugin-jsx-a11y + axe in CI, keyboard pass in code review, and real screen-reader smoke tests on critical flows. "Accessible by construction, verified by CI" — the systems answer.

Make the autocomplete accessible — what's the actual checklist?

APG combobox pattern: input with role="combobox", aria-expanded, aria-controls pointing at the listbox, aria-activedescendant tracking the highlighted option (focus stays in the input); full keyboard: arrows navigate, Enter selects, Escape closes; results count announced via live region. Why is a <div onClick> worse than it looks, and when is div+ARIA legitimate?

It's missing four free behaviors: tab focus, Enter/Space activation, the button role for AT, and form semantics — recreating them needs tabindex, key handlers, and role, all maintained forever. Legitimate: when semantics genuinely don't exist natively (a canvas-drawn grid cell, a tree view) — then follow the APG pattern completely, not just the role attribute.

What breaks for keyboard users in a typical SPA, route by route?

Navigation: focus stays on the clicked link while content swaps — screen readers announce nothing; fix: move focus to the new page's h1 (tabindex="-1") and announce via live region. Modals without traps: tab escapes into the background page. Custom dropdowns: no arrow keys. Infinite scroll: no way past it to the footer. Each has a named fix — listing them IS the answer.

What is WCAG AA in one breath, and which failures are most common?

The standard contract: perceivable, operable, understandable, robust at the AA level — contrast ≥ 4.5:1 for text, everything keyboard-operable, focus visible, labels on inputs, no info by color alone. Most common failures in audits: contrast, missing labels, focus management, and images without alt. Knowing the "usual suspects" signals you've run an audit.

Why does string concatenation break i18n even when every word is translated?

Word order differs by language ("red car" vs "car red"), plurals aren't binary (Polish has several forms; ICU plural rules exist for this), and gender agreement changes surrounding words. Translators need the full sentence with placeholders — t('cart.items', {count}) — never t('you.have') + count + t('items'). This one question exposes whether someone has actually shipped i18n.

What has to change for RTL support — is it just direction?

dir="rtl" flips text, but layout needs logical properties (margin-inline-start not margin-left), directional icons mirrored (back arrows, chevrons — but not logos/media controls), gestures re-mapped, and absolutely-positioned UI re-anchored. Modern answer: build LTR with logical properties from day one and RTL is nearly free.

Locale-aware dates, numbers, currency — what's the rule?

Never hand-format: Intl.DateTimeFormat, Intl.NumberFormat (currency mode with the currency code from data, not the locale!), Intl.RelativeTimeFormat for "2 hours ago". Store UTC + ISO 8601, format at the edge in the user's locale and timezone. "1.000,50 €" vs "€1,000.50" is the two-second example to give.

How do you make a11y stick org-wide rather than being one hero's crusade?

Push it into the platform: design-system primitives accessible by default, lint rules + axe checks in CI blocking regressions, keyboard-pass on the PR checklist, screen-reader smoke tests on the critical path, and audits with real AT users at milestones. Individual diligence decays; defaults and gates don't.

Frontend security

XSS, CSRF, CSP, and where tokens live. Unlike architecture questions, these have correct answers — fumbling them reads worse than any design disagreement.

YOU ALREADY KNOW THIS

React escaping your strings, the httpOnly cookie you couldn't read from JS (that's the point), the CORS error that ate an afternoon — you've been operating inside these defenses for years. This hour makes you able to explain the walls you've been standing behind.

// the idea

  • XSS is the frontend's #1: attacker-controlled content executing as script in victims' browsers. React auto-escapes text children — the doors that remain: dangerouslySetInnerHTML (sanitize with DOMPurify first, always), javascript: URLs in hrefs, and third-party scripts. Stored XSS (in your DB, served to everyone) is the nastiest flavor.
  • CSP is the backstop: a response header allowlisting where scripts/styles/images may load from — injected inline script dies even if XSS lands. Modern shape: nonce-based script-src, object-src 'none', report-only mode first to find breakage. Defense in depth: escape AND sanitize AND CSP.
  • Where tokens live decides your threat model: httpOnly SameSite cookie — JS can't read it (XSS can't exfiltrate), but it auto-sends (CSRF exists → SameSite=Lax + CSRF tokens for forms). localStorage JWT — no CSRF (nothing auto-sends), but any XSS reads it and walks away with the session. The calibrated answer: httpOnly cookies + SameSite, short-lived access tokens, refresh rotation.
  • CSRF in one breath: another origin triggers a state-changing request riding your auto-sent cookies. Defenses: SameSite=Lax default (kills most), CSRF token for anything cookie-authed and mutating, never mutate on GET.
  • CORS is protection FOR users, not an obstacle: the browser blocks cross-origin reads unless the server opts in (Access-Control-Allow-Origin); preflights (OPTIONS) gate non-simple requests. "Fixing" CORS with * + credentials is handing your API to every origin — the trap answer to avoid.
  • Supply chain & embedding: third-party scripts run with full page power — Subresource Integrity hashes for CDN scripts, sandboxed iframes for untrusted embeds, frame-ancestors (anti-clickjacking), and dependency auditing in CI. postMessage listeners must check event.origin — the widget-embedding question's key line.

// rapid-fire — answer out loud, then reveal

Stored vs reflected vs DOM XSS — thirty seconds.

Stored: payload saved server-side (a comment), served to every viewer — worst blast radius. Reflected: payload in the URL/request echoed back — needs a crafted link per victim. DOM-based: never touches the server; client JS reads attacker-controlled input (location.hash) into innerHTML. Same defense family: escape output, sanitize rich content, CSP as backstop.

"React prevents XSS" — where's the truth boundary?

True: JSX text interpolation escapes HTML entities, so {userInput} can't inject tags. False beyond: dangerouslySetInnerHTML, href/src accepting javascript: URLs, spreading user-controlled props, third-party scripts, and server-rendered templates outside React. The phrase: "React escapes by default; the escapes from the default are where audits look."

JWT in localStorage vs httpOnly cookie — give the verdict with reasoning.

Cookie wins for browser apps: httpOnly means XSS can't exfiltrate the token; SameSite=Lax plus CSRF tokens for forms covers the cookie's own weakness; add short-lived access + rotating refresh. localStorage's XSS exposure is unbounded — one injected script owns the account. Mention BFF/session pattern for SPAs as the increasingly standard shape.

What does CSP actually block, and what's a nonce doing in it?

CSP allowlists sources per resource type; script-src 'self' blocks inline and third-party script — which kills most injected XSS payloads even after they land in the DOM. A nonce is a per-response random value: only script tags carrying it execute, letting you keep necessary inline scripts without 'unsafe-inline'. Roll out report-only first; that operational note reads as experience.

Walk CSRF end to end with the fix stack.

Victim is logged into bank.com (cookie); evil.com auto-submits a form POST to bank.com/transfer; browser attaches the cookie; server can't tell it wasn't the user. Fixes: SameSite=Lax (cookie stays home on cross-site POSTs), CSRF token the attacker can't read (same-origin policy protects it), and GET never mutating. Header-token auth kills CSRF but reopens the XSS-storage question — say the loop.

Why does CORS exist — what would break without it?

Without same-origin policy + CORS, any site you visit could fetch your gmail with your cookies and read the response — cross-origin READS are the danger. CORS is servers opting specific origins in. Preflight (OPTIONS) checks before non-simple requests. And the classic correction: CORS protects users from evil sites, not your API from clients — API protection is auth and rate limiting.

You must embed a third-party widget. Containment checklist?

Sandboxed iframe (allow only what it needs — allow-scripts, not allow-same-origin unless unavoidable), communicate by postMessage with origin checks both ways, their origin gets no parent DOM access, CSP frame-src limits who can be embedded, and frame-ancestors on your own pages stops reverse clickjacking. SRI if you must inline their script instead. "Iframe as the trust boundary" is the phrase.

What can the frontend do about supply-chain risk?

Lockfiles + audited upgrades (no silent ranges in CI), SRI hashes on CDN scripts, minimal third-party scripts each justified (tag managers are root access to your page — say so), CSP restricting exfil destinations (connect-src), and dependency scanning gates. The honest kicker: an npm package compromise runs inside your bundle — CSP + least third-party is the only real blast-radius control.

Observability & errors

Error boundaries feeding error tracking, RUM, session replay, feature flags, safe rollouts — the production-maturity questions that close out senior loops.

YOU ALREADY KNOW THIS

You've squinted at a minified stack trace, added a Sentry DSN to a project, and shipped behind a feature flag. Observability design is those tools arranged into a system: detect → triage → reproduce → fix → verify, each step with a named tool.

// the idea

  • Catch at every layer: error boundaries per region (render errors → fallback UI + report), window.onerror / onunhandledrejection as the global net (async + handler errors that boundaries miss), fetch-layer interceptors logging failed requests with context. Every catch reports to one place.
  • Make reports debuggable: upload source maps per release (minified traces are useless), tag errors with release version, route, user segment, feature-flag state; breadcrumbs (recent clicks/navigations/requests) reconstruct the path. "Error + release + breadcrumbs" is the triage triad.
  • RUM completes the picture: web-vitals (LCP/INP/CLS at p75), custom timings (time-to-first-message for chat), by device/geo/release. Errors tell you it broke; RUM tells you it's slow — both are dashboards with alerts, not spreadsheets someone checks monthly.
  • Session replay, responsibly: DOM-event-based replay (rrweb-style) shows what the user actually did before the bug — with strict masking of inputs/PII and consent gating. The privacy caveat is part of a senior answer, not a footnote.
  • Deploys that can't take the site down: feature flags decouple deploy from release (ship dark, enable by cohort, kill switch — no redeploy); canary a release to 5% and watch error rate + vitals before 100%; instant rollback because assets are immutable and HTML re-points. Frontend rollback = repointing HTML at the previous hashes — cheap, say it.
  • Alert on symptoms users feel: error-rate spike per release, vitals regression, checkout-funnel drop — not CPU. Tie alerts to the release that caused them; the on-call story ("we saw the spike, flipped the flag, fixed forward") is the credibility close.

The rapid-fire bank

Forty-eight more questions grouped by theme — the cross-cutting ones that don't belong to a single topic. Same ritual: answer out loud, then reveal. These deliberately don't repeat the topic questions; together they're the full deck.

// the browser itself

What happens between "browser has HTML" and "pixels on screen"?

Parse HTML → DOM; CSS → CSSOM; both → render tree (visible nodes + styles); layout computes boxes; paint rasterizes into layers; compositing stacks layers on the GPU. Matters because: JS/CSS changes trigger different depths — transform/opacity re-composite only (cheap), width/top re-layout everything below (expensive).

Why do transform/opacity animations stay smooth when height animations jank?

transform and opacity run in the compositor — the GPU shifts already-painted layers, no layout or paint, even while the main thread is busy. Animating height/top/left re-runs layout + paint every frame on the main thread, competing with your JS. Rule: animate only compositor properties; use transform: scaleY over height tricks.

What is layout thrashing?

Interleaving style writes and layout reads (offsetHeight, getBoundingClientRect) in a loop — each read forces a synchronous reflow because the pending writes must be applied first. Fix: batch — read everything, then write everything; or use requestAnimationFrame phases / FastDOM patterns.

requestAnimationFrame vs setTimeout for animation?

rAF fires right before the next paint, once per frame, synced to the display and paused in background tabs — perfect cadence, no wasted frames. setTimeout(16) drifts, fires during frames, keeps running hidden, and tears. rAF for visual updates; timeouts for logic.

Where does IntersectionObserver beat scroll listeners, and why?

Lazy loading, infinite scroll sentinels, "in-viewport" analytics, scrollspy. It's asynchronous and engine-managed — no main-thread work per scroll tick, no getBoundingClientRect thrash, thresholds and rootMargin built in. A scroll listener doing rect math per event is the jank generator it replaced.

sessionStorage vs localStorage vs IndexedDB vs cookies — job of each?

Cookies: tiny, auto-sent to server, httpOnly-able — auth. localStorage: small sync KV, survives restarts — prefs, theme. sessionStorage: per-tab scratch. IndexedDB: async, large, structured — offline queues, cached entities, anything a service worker touches. Sync-vs-async and sent-vs-not are the axes to name.

What's a web worker good for on the frontend — and what can't it do?

CPU work off the main thread: parsing big files, diffing, search indexing, image processing — keeping INP healthy. Can't touch the DOM; communicates by postMessage (structured clone; Transferables/SharedArrayBuffer for big data). "Heavy compute goes to a worker" is the INP answer's last rung.

How does the back/forward cache (bfcache) change your app's behavior?

Eligible pages are frozen and restored instantly on back — JS state intact, no reload. Breaks assumptions: unload handlers prevent it (use pagehide), timers/sockets freeze, and you must revalidate data on pageshow (persisted flag). Free instant navigation if you don't fight it — a very 2026 detail to know.

// architecture at org scale

Micro-frontends — the honest tradeoff summary?

Independent deploys per team (the actual win) at the cost of: duplicated dependencies, cross-app consistency work (design system discipline becomes mandatory), routing/shell coordination, and a harder perf story. Right at many-teams-one-surface scale; wrong as a fashion choice. "Team topology problem, not a tech problem" is the frame.

What is a BFF (backend-for-frontend) and when do you add one?

A thin server owned by the frontend team that aggregates/reshapes service APIs per screen — collapsing waterfalls, hiding service churn, handling auth/cookies (the SPA session pattern), and trimming payloads for mobile. Add when screens need N services or response shapes whiplash per client. It's also where SSR naturally lives.

Monorepo for frontend — why do big orgs bother?

Atomic changes across app + design system + utils (one PR, no version dance), single toolchain, shared CI caching (Turborepo/Nx), and visible consumers for every shared package. Costs: tooling investment, CI scale, ownership boundaries needing enforcement (CODEOWNERS). The alternative — versioned internal packages — trades atomicity for isolation.

How do 10 teams keep one product feeling like one product?

Design system with tokens + primitives (visual consistency), shared UX patterns documented (interaction consistency), platform team owning routing/auth/telemetry shells, contribution model so teams extend rather than fork, and design + a11y review gates. The system is social as much as technical — saying that is the point.

Where does TypeScript pay off most in large frontends?

API boundaries (generated types from OpenAPI/GraphQL schemas — server changes surface as compile errors), design-system prop contracts, discriminated unions for state machines (loading/error/success can't be mixed up), and refactors at scale. "Types are enforced documentation at the seams" — seams is the word that lands.

How would you migrate a huge jQuery/legacy app to React without stopping shipping?

Strangler pattern: new shell (or embed islands) rendering legacy inside; every new feature in React; migrate route by route with shared session/design tokens; delete legacy as routes flip. No big-bang rewrite — the business keeps shipping. Bonus: metrics comparing old-vs-new routes to prove the migration pays.

SPA vs MPA in 2026 — is the pendulum swinging?

Yes, toward hybrid: server-first frameworks (RSC, Astro, HTMX-ish patterns) ship less JS for content surfaces, while true app surfaces (editors, dashboards) stay SPA-shaped. View Transitions API gave MPAs SPA-feeling navigation. The answer: per-surface choice, not ideology — same muscle as the rendering topic.

How do you sunset a deprecated component API across 40 repos?

Deprecation with codemods (automate the mechanical part), usage telemetry to find holdouts, versioned releases with a support window, lint rules failing new uses, and comms + office hours for the long tail. "Codemod + telemetry" is the pair that turns this from nagging into engineering.

// api & contract design

Design the API contract for the feed — what does the frontend actually need?

Cursor pagination ({items, nextCursor}), stable ids, ISO timestamps (client formats), image variants or a sizing CDN convention, embedded author objects (or ids + a batch endpoint — say which and why), consistent error envelope, and idempotent mutations with client keys. Designing the contract FROM the UI's needs is the point being tested.

The mobile team wants smaller payloads than web. Options?

Sparse fieldsets (?fields=), GraphQL field selection, a BFF per client shaping responses, or protocol-level wins (compression, HTTP/2). Plus image variants per DPR/viewport. The wrong answer is one bloated endpoint serving everyone's union — name it as the anti-pattern.

How should API errors reach users?

Contract: machine-readable code + human-safe message + correlation id, mapped client-side to UX by category — validation errors inline at fields, auth errors to re-login flow, 5xx/network to retryable banners, permissions to explanatory empty states. Never raw server messages in the UI; always log the correlation id with the report.

What's optimistic concurrency for edits — the version-number dance?

Reads carry a version (ETag/updatedAt); writes send it back (If-Match); server rejects stale writes with 409/412; client then merges or prompts. Prevents silent last-write-wins clobbering on shared resources — the "two admins edit the same record" question, and the lightweight cousin of CRDT answers.

Polling an expensive endpoint every 5s across 10k clients — how do you not DDoS yourself?

Client side: jittered intervals, backoff when idle/hidden (Page Visibility), ETag/304 so unchanged polls are cheap. Server side: cache the hot response, or replace with push (SSE) which is exactly one connection per client instead of N requests. Recognizing polling AS load is the check.

When is client-side data denormalization the right call?

Normalized entity cache (posts by id, feeds as id lists) is the default — one update fans out everywhere. Denormalize (embed snapshots) when consistency is intentionally point-in-time (an order's price at purchase) or entities are never updated in-session. Mirror of the DB question — same reasoning, one layer up.

How do you version a public component library / SDK without breaking consumers?

Semver honestly (breaking = major), deprecate-then-remove across majors with codemods, changelogs + migration guides, integration tests against real consumer patterns, and beta/canary dist-tags for early adopters. For hosted SDKs: runtime version pinning and long support windows. Trust is the product.

What belongs in the "contract" between design and engineering for a component?

Tokens used (no raw hex), all states enumerated (hover/focus/disabled/loading/error/empty), responsive behavior, motion specs, a11y annotations (roles, focus order, announcements), and content guidelines (truncation, i18n length). Figma-to-code drift dies when states are the contract, not the happy-path mock.

// css & layout, design-round sized

Flexbox vs Grid — the one-sentence-each answer that ends the question?

Flex lays out along one axis and lets content size drive distribution — toolbars, nav rows, centering. Grid places into two-dimensional tracks you define — page scaffolds, card galleries, anything aligned in both directions. "Flex for components, grid for layouts" plus "they compose" is the complete answer.

How would you architect the CSS for a 40-team product?

Design tokens as variables (the themable core), a constrained styling system (CSS Modules, vanilla-extract, Tailwind, or CSS-in-JS — pick one, enforce it), co-located styles per component, no global cascade dependency beyond reset + tokens, and lint against raw hex/px drift. The war being prevented: specificity fights and unreviewable global changes.

What are container queries, and what did they fix?

Styles responding to the CONTAINER's width instead of the viewport's — a card can be compact in a sidebar and full in the main column, same component. Before them, "responsive" components needed viewport hacks or JS measurement. For design systems they're the missing piece: components adapt to wherever they're dropped.

Dark mode across a big app — architecture, not vibes?

Semantic tokens (--surface, --text-primary) mapped per theme — components never reference raw colors; theme switch = swapping one attribute/class at the root; prefers-color-scheme as default with user override persisted; images/embeds handled (color-scheme, picture sources); and an anti-flash inline script setting the attribute before first paint. That last detail separates people who've shipped it.

Why is position: sticky the interview's favorite CSS property?

Sticky headers/toolbars in feeds and tables are ubiquitous, and its failure modes are diagnostic: it needs a scrolling ancestor without overflow:hidden between, a threshold (top:0), and the parent's height bounds it. Debugging "sticky doesn't stick" out loud shows real CSS mileage.

What is the stacking context, and why do z-index fights happen?

z-index only competes within the same stacking context; transforms, opacity<1, filters, and position+z-index each create new ones — so a modal's z-index 9999 loses to a sibling context above it. Fix architecturally: portal overlays to a top-level layer with a managed z-scale, not by escalating numbers.

Responsive strategy in 2026 — still breakpoints?

Mobile-first fluid layouts (grid/flex + clamp() for type), container queries for components, breakpoints only for genuine layout mode changes (sidebar collapses), logical properties for i18n, and testing at content extremes not device widths. "Design for content ranges, not devices" is the maturity line.

When does CSS become a performance problem?

Render-blocking stylesheets delaying first paint (inline critical CSS, defer the rest), huge selector-heavy sheets (style recalculation on big DOMs), layout-triggering animations, and @import chains serializing loads. Also unused CSS shipping forever — purge by component co-location. CSS is on the critical path; treat it like JS.

// mobile & the real world

What actually changes when you design for mid-range Android on 4G?

CPU is the bottleneck, not just bandwidth: JS parse/execute cost dominates (ship less), INP budgets get tight (long tasks hurt more), memory pressure kills heavy pages, and network is intermittent (resilience patterns stop being optional). "Test on a $200 phone with throttling" is the practice that proves you mean it.

Touch targets and gestures — the design-review checklist?

Targets ≥ 44px with spacing, no hover-dependent interactions (provide tap equivalents), passive scroll listeners, momentum/overscroll respected, pull-to-refresh not hijacked accidentally, and gesture conflicts resolved (carousel swipe vs page scroll — lock an axis after intent detection). Plus visible focus for keyboard-with-tablet users.

The virtual keyboard — what does it break?

It resizes or overlays the viewport: fixed bottom bars jump or cover inputs, 100vh lies (use dvh/svh units), focused inputs need scroll-into-view, and position:fixed elements float mid-screen on iOS. The VisualViewport API is the escape hatch. Naming dvh is the 2026 marker.

PWA vs native vs React Native — the frontend architect's framing?

PWA: one codebase, instant updates, install + offline via service worker — best when reach beats device integration. React Native: shared logic, native UI, app-store presence — best when you need native feel with web-team leverage. Full native: when platform APIs/performance are the product. Frame by distribution + team + integration depth, never ideology.

How do you handle a webview embed of your app inside someone else's native app?

Detect and adapt chrome (hide duplicate nav), bridge via postMessage-style contracts with the native shell (auth handoff, navigation intents), respect safe areas, and test the OS webview versions explicitly — they lag browsers. Auth is the landmine: cookies in webviews are restricted; token handoff from the shell is the pattern.

Data-saver users and expensive markets — what's respectful engineering?

Honor prefers-reduced-data and Save-Data hints: lower image quality tiers, no autoplay video, defer non-critical fetches; cap background polling; make heavy features opt-in. Also prefers-reduced-motion for animations. Adapting to user constraints is both a11y-adjacent and a differentiating answer almost nobody gives.

App works on wifi, "broken" on the commute — the systematic diagnosis?

It's latency + intermittency, not bandwidth: waterfalls amplify RTTs (collapse round trips), timeouts tuned for wifi fire spuriously (adaptive timeouts + retry with backoff), sockets drop per tunnel (reconnect + catch-up), and half-loaded states need skeletons not spinners-forever. Reproduce with DevTools throttling + offline toggling — say the repro step first.

What's different about forms on mobile that interviews probe?

Input modes and keyboards (inputmode, autocomplete attributes — the autofill answer), validation timing (on blur, not per keystroke — thumbs are slow), error visibility above the keyboard, draft persistence (backgrounding kills tabs), and payment/address autofill APIs. "The form is a resumable state machine" carries over from the wizard question.

// process & judgment

How do you evaluate "should we adopt this shiny library/framework"?

Problem-first (what measured pain does it solve?), then: bundle cost, maintenance health, team learning curve, migration path IN and OUT, and a time-boxed spike with success criteria. "We stayed on X because our pain didn't justify the migration" is a senior answer — adoption stories impress less than restraint stories.

Testing strategy for a large frontend — the pyramid answer that's actually current?

Static (TS + lint) → unit for pure logic → component tests with Testing Library (behavior, not internals) as the bulk → a thin set of E2E smoke flows (Playwright) on the critical path → visual regression for the design system. Plus a11y checks in CI. Confidence per maintenance dollar is the metric; 100% E2E coverage is the anti-pattern.

How do you review a frontend PR beyond "code looks fine"?

Run it (or preview deploy), keyboard pass, loading/error/empty states present, bundle diff checked, a11y lint clean, state placed at the right level, new deps justified, and screenshots/video in the PR for visual changes. A named checklist beats vibes — and mentioning preview deploys shows modern workflow.

Estimate: the PM wants infinite scroll, virtualized, with offline support — this sprint. Respond.

Slice by risk: cursor pagination + plain list ships this sprint (user value now); virtualization next (perf at scale); offline queue after (distinct, testable chunk). Offer the order with reasons and what each slice unlocks. The question tests decomposition under pressure, not heroism.

A designer hands you a mock that will be slow (100 images above the fold). What now?

Prototype the cost (numbers, not opinions), bring options: progressive loading with placeholders, fewer eager images, or a redesigned hierarchy — framed as protecting THEIR user experience (LCP = users see the design later). Design-eng negotiation with data is the skill on trial.

What do you do in your first month owning a legacy frontend?

Instrument before touching: error tracking, RUM, bundle analysis — get the truth. Map the risky zones (no tests + high churn), fix the top user-facing pain for credibility, set budgets/CI gates so it stops getting worse, and write the map you wish you'd been given. Measurement before opinions, always.

When is the "worse" technical option correct?

When the constraint is real: ship-by date (pagination now, virtualization later), team familiarity (boring stack the team can operate at 3am), or reversibility (the option you can undo beats the optimal one you can't). Engineering is optimization under constraints — name the constraint, own the debt, schedule the payoff.

Close the interview: "any questions for me?" — what do strong candidates ask?

Questions that show operating instincts: "how do frontend teams own metrics — do you have RUM/error budgets?", "who owns the design system and how do teams contribute?", "what does the deploy→rollback path look like?" You're demonstrating what you'll care about on the job — and actually qualifying them.

Real topics, honestly deprioritized for the 48 hours. Know the one-liner, spend the time on the spine.

  • Backend capacity math — QPS estimation and shard counts live in the System Design course. In the frontend round, the API is a box you define contracts with, not a fleet you size.
