// module 14 the type system your JS was missing

TypeScript, actually reasoned through.

You've read TypeScript for years — squiggles, generics, config folklore. This module rebuilds it from one idea: types describe the shapes values already have, and the compiler is a very fast, very pedantic reviewer who never gets tired. Learn what it checks, what it erases, and how to make it work for you instead of around you.

Prerequisite: JS Fundamentals — TypeScript is JavaScript with a proof layer; the runtime never changes. The compiler can't run on this page, so this module trades runners for predict-the-error quizzes — read sharply. The cats have opinions about type safety. 🐈

The mental model — structural typing & the eraser

beginner → duck typing with a proof, gone by runtime

Two ideas explain 90% of TypeScript's behavior. One: typing is structural. A type is a shape description — any value with the right shape fits, no declarations of allegiance needed. If a function wants { name: string }, every object with a string name qualifies, whatever it was called or however it was made. (Java/C# are the opposite — nominal: you must declare implements.) Two: types are erased. Compilation strips every annotation; the JavaScript that runs contains no trace of them. Types can't affect runtime behavior — no type-based branching, no runtime validation for free — which is precisely why the boundary sections (§11) exist.

PROFESSOR WHISKERS EXPLAINSThe shelter's "is it a cat?" test doesn't check papers — it checks the shape: four legs, whiskers, disdain. Anything matching the shape passes, pedigree or alley. That's structural typing. And the test happens at the door, before the party — during the party (runtime) there are no inspectors anywhere in the building. If a raccoon got past the door wearing whiskers (a lying as, a wild API response), the party has a raccoon in it. The door is the compiler; the party is production.

erasure.js — run it (the OUTPUT of tsc — note what's missing)
// this WAS TypeScript:  function weigh(cat: { name: string; kg: number }): string
// after tsc, what runs is just:
function weigh(cat) {
  return `${cat.name}: ${cat.kg}kg`;
}
console.log(weigh({ name: 'Mochi', kg: 4.2 }));

// erasure means NO runtime trace:
console.log('any type info on the function?',
  Object.keys(weigh).length === 0 ? 'none — annotations are gone' : '??');

// …so nothing stops a lying value AT RUNTIME:
const fromAPI = JSON.parse('{"name":"Raccoon","kg":"HEAVY"}');   // kg is a string!
console.log(weigh(fromAPI), ' ← ran fine, wrong silently');
console.log('typeof fromAPI.kg:', typeof fromAPI.kg);
console.log('\nthe compiler checks the door. JSON.parse climbs in a window.');
console.log('that gap is what §11 (validate at boundaries) exists to close.');
the only runner in this module — proving the types are truly gone

interface Cat { name: string } · const dog = { name: 'Rex', barks: true } · const c: Cat = dog — compile?

      

        
        
        
        
      

      
Why: Cat asks "do you have a string name?" — dog does; done. No nominal ceremony (A is the Java instinct), no property deletion (types never touch values — erasure). The wrinkle worth knowing: assigning a fresh object literal directly (const c: Cat = { name: 'Rex', barks: true }) DOES error — "excess property checking" flags probable typos on literals only. LEVEL UP — what interviewers listen for

      
    
        
  • The one-liner: "TypeScript checks shapes at compile time and vanishes at runtime — it's a linter with a PhD, not a guard dog."
    • 
        
  • Because types erase, instanceof MyInterface is impossible — runtime checks need real values (discriminants §03, classes §07, or validators §11).
    • 
        
  • Structural typing is why two identically-shaped types are interchangeable — and why branding (a phantom property) exists when you need UserId ≠ OrderId despite both being strings.
    • 
        
  • Enums and namespaces are the two exceptions that DO emit runtime code — one sentence of trivia that signals real mileage (and why as const unions are the modern preference).

    02
    

      
Annotations & inference — write less, know more

      
beginner → where annotations belong, and where they're noise

    

  

  

    
The compiler infers most types: let kg = 4.2 is a number — annotating it is noise. The discipline: annotate boundaries (function parameters and public return types — the contracts), infer internals (locals, obvious expressions). Two inference behaviors worth knowing cold: let widens (let s = 'tuna' is string — it could be reassigned) while const narrows to the literal (const s = 'tuna' is type 'tuna'); and as const freezes a whole structure into readonly literals — the idiomatic way to make a plain object behave like an enum.

    
The shapes toolbox: object types ({ name: string; kg?: number } — ? means may be absent), arrays (string[]), tuples ([number, number] — fixed length, per-position types; what useState returns), and readonly for immutability at the type level (a compile-door promise — erased like everything else, as js-fundamentals' Object.freeze discussion foreshadowed: freeze is runtime, readonly is compile-time; different layers, both useful).

    

      
// quiz — first pick is the one that counts

      
const MOODS = ['grumpy', 'aloof', 'feral'] as const; — what is MOODS[0]'s type, and why does anyone do this?

      

        
        
        
        
      

      
Why: without as const, TS widens to string[] (you might push to it). With it: readonly ['grumpy', 'aloof', 'feral'] — and the typeof MOODS[number] trick turns the VALUES into a TYPE, so the list exists exactly once (single source of truth: add 'zoomies' to the array, the union updates itself). Option D is a category error worth noticing: there are no types at runtime at all (§01) — the question doesn't parse.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • ? (absent) vs | undefined (present-but-undefined) differ under exactOptionalPropertyTypes — deep-cut flag knowledge, deploy sparingly.
    • 
        
  • Annotate return types on exported/public functions even when inferable — they pin the contract so a refactor's type-drift errors at the source, not at fifty call sites.
    • 
        
  • string[] vs [string] confusion is the classic screen-share tell — array vs one-element tuple; say it before they ask.
    • 
        
  • Inference quality is WHY strict mode matters: without noImplicitAny, un-inferable things silently become any and the checking quietly stops (§09's story).

    03
    

      
Unions & narrowing — the control-flow type system

      
beginner → the compiler reads your ifs; discriminated unions & never

    

  

  

    
A union (string | number, Cat | null) says "one of these" — and until you know which, you may only do what's legal for all of them. Narrowing is how you find out: the compiler reads your control flow — typeof x === 'string', x !== null, 'meow' in x, x instanceof Cat — and inside each branch, the type shrinks accordingly. This is the machinery that makes strictNullChecks livable: Cat | null forces the null-check the bug report would have demanded anyway, and after the check, it's just Cat.

    
The crown jewel is the discriminated union: variants sharing a literal tag field — { status: 'loading' } | { status: 'ready'; data: Cat[] } | { status: 'error'; error: string }. Switch on the tag and each case knows its exact shape (data only exists under 'ready' — impossible states unrepresentable, the pattern React state sections preach). The never finisher: a default case assigning to never makes the compiler error when a future variant is added but unhandled — exhaustiveness as a compile-time tripwire.

    

      
// quiz — first pick is the one that counts

      
Why does the fetch-state discriminated union beat { loading: boolean; data?: Cat[]; error?: string }?

      

        
        
        
        
      

      
Why: with flags, "can data and error both be set?" is answered by convention and prayer; with the union, by the type system: no. Every if (state.status === 'ready') is also documentation. (C is the §01 category error again — types cost nothing at runtime; D misses that erased types can't instanceof — the tag value is the runtime check.) "Make impossible states unrepresentable" is the sentence to carry into every interview.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Custom type guards — function isCat(x: unknown): x is Cat — extend narrowing to your own predicates; the x is return type is the magic (and a lying guard is a lying as: the compiler trusts you).
    • 
        
  • Narrowing doesn't survive callbacks or awaits on mutable bindings — "possibly null" after an if usually means the check and use are in different closures; capture to a const first.
    • 
        
  • satisfies (TS 4.9+) — validate against a type WITHOUT widening to it: config objects keep their literal keys AND get checked. Modern flex, one sentence.
    • 
        
  • Exhaustiveness via never is how unions scale in teams: adding a variant lights up every switch that needs updating — the compiler as a refactoring TODO list.

    04
    

      
Typing functions — parameters, returns & the void quirk

      
intermediate → contracts for the unit of work

    

  

  

    
Function types read as arrows: (cat: string, kg?: number) => string. The pieces that trip people: optional parameters (?) must trail required ones; rest parameters type as arrays (...names: string[]); callback parameters are where annotation pays most — onAdopt: (cat: Cat) => void gives the caller's arrow function full inference (you write c => …, c is Cat, free). The famous void quirk: a callback typed to return void accepts functions returning anything ("I promise to ignore your return value") — which is why arr.forEach(x => map.set(k, x)) compiles though set returns the Map. void means "not used", not "must be undefined".

    
Overloads declare multiple call shapes above one implementation — function find(id: number): Cat; function find(name: string): Cat[] — the implementation signature is invisible to callers and must handle every overload. Modern honesty: unions + conditional returns often replace overloads; reach for overloads when the return type depends on the argument type and a union return would force every caller to narrow.

    

      
// quiz — first pick is the one that counts

      
Two function types: f: () => void and g: () => undefined. You pass () => 42 to each. Verdicts?

      

        
        
        
        
      

      
Why: void in a callback position is a promise from the CALLER ("I won't look at what you return"), so any return value is safe to allow — banning them would break every terse arrow that happens to return something. undefined is an actual value type with actual checking. This asymmetry is deliberate design, not sloppiness — explaining the WHY (who consumes the value?) is what separates the answer from trivia.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Parameter counts are structurally forgiving too: (x) => … satisfies (x, i, arr) => … — callbacks may ignore trailing args (why map(x => x*2) works). Fewer is fine; more is not.
    • 
        
  • Type this for old-style APIs (function(this: Cat)) — rare, but naming it shows you've met legacy code.
    • 
        
  • Function type vs call signature vs constructor signature (new () => Cat) — one breath each; interfaces can hold all three.
    • 
        
  • Async functions: return Promise<T>, always — async (): Promise<void> for fire-and-forget handlers keeps the floating-promise lint (js-async §05) coherent.
    •

    05
    

      
Generics — type variables, not type magic

      
intermediate → the compiler solves for T; you just relate the parts

    

  

  

    
A generic is a type variable: function first<T>(arr: T[]): T says "whatever element type comes in, that's what comes out" — the relationship between input and output is the entire point. Without it: first(cats) returns any (checking off) or unknown (caller must cast). With it, the compiler infers T at each call site — you almost never write first<Cat>(cats); T is solved from the argument. When you catch yourself writing a generic the output doesn't use (function log<T>(x: T): void), delete it — unknown does that job; generics earn their keep only by connecting types.

    
Constraints bound the variable: <T extends { id: string }> means "any shape with an id" — inside, x.id is legal; outside, callers keep their full type (that's the win over just taking { id: string }: the return can be T, not the stripped-down shape). The keyof duet — <T, K extends keyof T>(obj: T, key: K): T[K] — types pluck(cat, 'kg') as number and rejects 'wings' at compile time: the whole "typed ORM/config accessor" genre in one signature.

    

      
// quiz — first pick is the one that counts

      
API helper: async function get(url: string): Promise<any> vs async function get<T>(url: string): Promise<T> — the honest difference?

      

        
        
        
        
      

      
Why: get<Cat[]>('/cats') is still a promise about the network the compiler can't verify — but it's a propagated, checkable promise: every use of the result is typed, and one validator at the fetch site makes it true. any is a contagion: everything it touches becomes unchecked without a squiggle anywhere. Options A and D are the erasure misunderstanding in two costumes — generics are compile-time only, always.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Read error messages inside-out: "T is not assignable to…" errors usually mean the RELATIONSHIP is wrong, not the annotation — re-derive what T should solve to.
    • 
        
  • Default type params (<T = unknown>) make generic containers ergonomic; constraints + defaults together cover the API-wrapper pattern.
    • 
        
  • Variance intuition without the jargon: producers of T are covariant (Cat[] fits Animal[] reads), consumers are contravariant (a handler of Animal accepts more than a handler of Cat) — strictFunctionTypes enforces the latter.
    • 
        
  • The "when would you NOT use a generic" question has a real answer: single fixed type (just name it), or T appearing once (unknown). Generics model relationships — no relationship, no generic.

    06
    

      
Utility & mapped types — types computed from types

      
intermediate → Partial to infer, and the loop that builds them all

    

  

  

    
The built-ins you'll use weekly, each one sentence: Partial<T> (all optional — update payloads), Required, Readonly, Pick<T, 'a' | 'b'> / Omit<T, 'password'> (API responses derived from DB rows — derive, don't duplicate is the whole philosophy), Record<K, V> (typed dictionaries), ReturnType<typeof fn> / Parameters (extract from existing functions — typing what you don't own). They're not magic: each is a mapped type, a for-loop over keys: Partial is literally { [K in keyof T]?: T[K] }. Read that once slowly — "for each key K in T, same value type, add ?" — and the standard library stops being incantations.

    
Conditional types add the if-statement: T extends U ? X : Y, with infer as the pattern-matcher — type Unwrap<T> = T extends Promise<infer U> ? U : T pulls the resolved type out of a promise. You'll read these in library types daily and write them rarely; the honest skill split is "fluent reader, occasional author" — say exactly that when asked how deep your type-level TypeScript goes.

    

      
// quiz — first pick is the one that counts

      
DB row: type CatRow = { id: string; name: string; passwordHash: string; vetNotes: string }. The API returns everything except the sensitive fields. The maintainable type?

      

        
        
        
        
      

      
Why: the hand-copy (A) silently drifts — add adoptedAt to the row and the API type forgets it exists; six months later the types lie. Omit inverts the maintenance: additions propagate, and the exclusion list is the security review. Partial (C) says "every field maybe" — a different, wrong claim. The meta-lesson interviewers fish for: types have DRY too — one source of truth, everything else derived. (And the runtime filtering still has to exist — types don't strip fields; §01 forever.)

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Template literal types (`cat:${string}`) type string patterns — event names, route params; one example earns the point.
    • 
        
  • keyof + mapped + as remapping renames keys in flight (getName from name) — recognize it in library code, don't author it under pressure.
    • 
        
  • Deep utility types (DeepPartial) are recursive conditionals with edge cases — "I'd take type-fest's, not write mine" is the senior answer.
    • 
        
  • When a type-level puzzle exceeds ~3 layers, the design is usually wrong one level up — simplify the VALUE model; the type model follows. Saying this aloud is rare and lands.

    07
    

      
Interfaces, types & classes — which keyword when

      
intermediate → the eternal interface-vs-type question, settled

    

  

  

    
The question every TS interview asks: interface vs type. The real differences are two: interfaces can be reopened (declaration merging — the mechanism that lets you augment a library's types, §08), and interfaces only describe object/function shapes while type aliases anything (unions, tuples, primitives, mapped/conditional constructions). Everything else is style. The defensible convention: interface for public object contracts (extendable, better error messages), type for unions and computed types (interfaces can't union at all) — then stop arguing about it, which is itself the senior answer.

    
Classes get a type-system twist: a class declaration creates both a value (the constructor) and a type (the instance shape) — Cat works after new and after :. implements Iface checks the shape but changes nothing structurally (any matching class passes anyway — §01); TS's private is compile-only politeness (erased!), while #private (js-fundamentals §07) is runtime-real — the interview one-liner: "private is a comment the compiler reads; # is a wall the runtime builds." abstract classes are interfaces that may also ship implementation — use when sharing code, not just shape.

    

      
// quiz — first pick is the one that counts

      
Which of these NEEDS type rather than interface?

      

        
        
        
        
      

      
Why: A, C and D all work as either (extends/intersections, call signatures — both keywords handle them). Unions are the hard boundary: "this OR that" has no interface syntax. Since discriminated unions (§03) are the workhorse pattern, type earns its place no matter how interface-flavored your codebase style is. Knowing the ONE real constraint beats reciting style-guide folklore.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Parameter properties (constructor(private readonly db: Db)) declare-and-assign in one stroke — the DI idiom every Nest/service codebase runs on.
    • 
        
  • "Should this be a class or a plain object + functions?" — same answer as js-fundamentals §07 (stateful identity vs data+transforms), now with "interfaces type both" appended.
    • 
        
  • Declaration merging on interfaces is why interface Window { myGlobal: string } works — the feature is the door §08 walks through.
    • 
        
  • satisfies vs implements vs : — three ways to check a value against a contract; satisfies keeps inference, the others widen. Modern, precise, two sentences.

    08
    

      
Declarations & @types — typing the code you didn't write

      
intermediate → .d.ts files, DefinitelyTyped & augmentation

    

  

  

    
A .d.ts file is types with no implementation — the shape of code that exists elsewhere. Three sources, in the order you'll meet them: bundled (modern packages ship their own — the types field in package.json), DefinitelyTyped (npm i -D @types/express — community-written declarations for packages that don't ship them; version-matched to the runtime package, and occasionally wrong: they're documentation someone wrote, not compiler-verified truth), and yours — declare module 'legacy-thing' to paper over the untyped, or declare global for window extensions.

    
Module augmentation is the pro move: reopening a library's interfaces to add your fields — the canonical example is Express: declare global { namespace Express { interface Request { user?: SessionUser } } } so req.user type-checks after your auth middleware (the node module's pattern, typed). It rides on interface merging (§07), and its power is also its warning: augmentations are global claims — one lying augmentation poisons the whole project's checking, quietly.

    

      
// quiz — first pick is the one that counts

      
npm i cool-lib → "Could not find a declaration file for module 'cool-lib'". Rank the responses.

      

        
        
        
        
      

      
Why: the escalation ladder is check-the-registry → type-what-you-touch → (if generous) contribute upstream. ts-ignore (A) suppresses this and future errors on that line; blanket-any (D) is the same surrender with extra steps — acceptable as a day-one wedge only if §12's ratchet retires it. The minimal-surface .d.ts is the underrated middle: eight lines that make YOUR call sites checked, which is all the checking you were owed.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • skipLibCheck: true (default in modern configs) means dependency .d.ts conflicts don't block your build — know that it's ON and what it silences.
    • 
        
  • Publishing a library? declaration: true emits your .d.ts from source — hand-maintained declaration files for your own code is a smell.
    • 
        
  • Augmentation files must be modules (an import/export) or they become scripts with different scoping — the "my augmentation isn't applying" bug, one sentence.
    • 
        
  • The trust model in one line: "@types is crowdsourced documentation the compiler enforces — usually right, verifiably wrong sometimes, and my validators (§11) don't care either way."

    09
    

      
tsconfig, strictly — the flags that are the product

      
advanced → strict mode is the type system; the rest is plumbing

    

  

  

    
"strict": true is not a preference; it's whether TypeScript works. The umbrella's heavy hitters: noImplicitAny (un-inferable types error instead of silently unchecking — without it, checking has invisible holes), strictNullChecks (the flag: null/undefined leave every type unless declared — the billion-dollar mistake, opted out of; off, every cat.name is a potential TypeError the compiler blessed), strictFunctionTypes (callback variance, §05), strictPropertyInitialization (class fields provably assigned). Beyond the umbrella, the two worth adding: noUncheckedIndexedAccess (arr[i] is T | undefined — honest about bounds) and exactOptionalPropertyTypes.

    
The plumbing tier, one line each: target (what JS syntax comes out), module/moduleResolution (how imports resolve — "bundler" for app code in 2026), esModuleInterop (CJS/ESM peace treaty — the js-fundamentals modules story, config edition), paths (import aliases — must agree with your bundler's, a classic two-config drift bug), incremental/project references (build speed at monorepo scale). Apps extend shared presets (@tsconfig/node20-style); the flags you deliberately set are the ones worth talking about.

    

      
// quiz — first pick is the one that counts

      
A team inherits a large codebase with strict: false and "we'll turn it on later". What's the honest cost of running non-strict meanwhile?

      

        
        
        
        
      

      
Why: non-strict TS is a costume: function greet(cat: Cat) accepts null happily, and the reader believes a check that isn't happening — arguably worse than JS because it looks verified. "Later" compounds daily. The workable path is the ratchet: strict flags on new directories, // TODO(strict) debt burned down file-by-file — §12's migration machinery pointed inward. Naming the false-confidence problem (not just "strict is better") is the depth marker.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • tsc as CI's --noEmit checker while the bundler (esbuild/swc — which skip checking entirely!) does the building — the standard split; knowing WHO checks and who compiles is real-project literacy.
    • 
        
  • verbatimModuleSyntax + import type keep type-only imports out of the runtime bundle — erasure hygiene meets tree-shaking.
    • 
        
  • Non-null assertion ! and as are strictNullChecks' escape valves — each one is a place the config's promise is manually overridden; lint-count them (§12).
    • 
        
  • The one-sentence philosophy: "the compiler is free code review on every save — strict mode is just refusing to mute the reviewer."
    •

    10
    

      
TS + React — props, hooks & events, idiomatically

      
advanced → the five patterns that type 95% of components

    

  

  

    
The working set: props are a type/interface, with children: React.ReactNode (the everything-renderable type — not JSX.Element, which bans strings/arrays/null; the distinction is a favorite probe). useState infers from the initial value; annotate only the union cases — useState<Cat | null>(null) (infer from null alone and the state is forever null). Events come typed from the handler position — inline handlers get inference free; extracted handlers name their type (React.ChangeEvent<HTMLInputElement>). useRef has two personalities: useRef<HTMLInputElement>(null) for DOM (readonly current, null until mount) vs useRef<number>(0) for the instance-variable box (react module §09, now typed). Generic components — function List<T>({ items, render }: Props<T>) — give render a typed item per call site: the select/table/list genre, solved.

    
The payoff pattern to name: discriminated union props — { variant: 'link'; href: string } | { variant: 'button'; onClick: () => void } makes "link without href" unrepresentable (§03 applied to component APIs — the fesd component-contract lesson, enforced by the compiler instead of the code review).

    

      
// quiz — first pick is the one that counts

      
const [cat, setCat] = useState(null) then later setCat(fetchedCat) errors: "Cat is not assignable to null". The diagnosis?

      

        
        
        
        
      

      
Why: inference is only as good as the evidence at the declaration site (§02), and null is thin evidence. The generic parameter states the full lifecycle: "starts null, becomes Cat" — and every consumer now null-checks (strictNullChecks doing its §09 job). Option C — asserting the VALUE to satisfy a wrong type — is exactly backwards, and recognizing that reflex as backwards is the actual lesson.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • ComponentProps<typeof Button> extracts another component's props — wrap/extend without importing its type, or spreading native button props (ComponentProps<'button'>) into yours.
    • 
        
  • Don't annotate React.FC — plain function + typed props is the modern idiom (FC's implicit children and awkward generics dated it); knowing WHY dates your knowledge correctly.
    • 
        
  • Custom hooks returning tuples need as const (or a tuple return type) — else [value, setter] widens to an array of unions; the five-second fix everyone learns the hard way.
    • 
        
  • Server/client boundary (react §14): props crossing it must be serializable — a type-level discipline no flag enforces; naming it connects the modules.
    •

    11
    

      
TS + Node — typing the boundaries that lie

      
advanced → parse, don't validate-by-vibes: env, requests & DB rows

    

  

  

    
Backend TypeScript is boundary management: everything entering the process — env vars (process.env.X is string | undefined, honestly), request bodies (any-shaped network input), DB rows, queue messages, third-party webhooks — arrives untyped, and §01 says annotations can't check it. The pattern that closes the gap: parse at the boundary — a schema validator (zod-style) that checks at runtime AND derives the static type from the same schema: const Env = z.object({ DATABASE_URL: z.string().url() }); Env.parse(process.env) crashes at boot with a named error (not at 3am with "undefined is not a function"), and z.infer<typeof Env> IS the type — one source of truth, both worlds (the node module's validation section, upgraded from discipline to machinery).

    
Inside the boundary, types flow: typed request handlers (augmented req.user, §08), typed query builders (Kysely/Prisma derive row types from the schema — the pg module's tables, mirrored in types), and the rule that keeps it honest: validated once at the edge, trusted everywhere inside — re-validating in every layer is noise; never validating is the raccoon at the party.

    

      
// quiz — first pick is the one that counts

      
const user = req.body as User in a handler. What did as actually do, and what's the correct line?

      

        
        
        
        
      

      
Why: as is a promise, and at a network boundary it's a promise about OTHER PEOPLE'S data — the one thing you can't promise. The erased assertion means the first wrong payload detonates wherever user.email.toLowerCase() happens to live, stack-traced far from the cause. Parse-at-the-edge relocates the failure to the boundary with a client-blameable error. "as means the compiler stops looking — use it where YOU know more, never where the network knows more" is the whole section in a sentence.

    

    

      
LEVEL UP — what interviewers listen for

Migration & escape hatches — any, unknown, as & the ratchet

      
advanced → moving a living codebase without stopping the ship

    

  

  

    
The escape hatches, ranked by danger: unknown (safe — "no idea, so you must narrow before using"), as (a scoped claim — legitimate when you truly know more than the compiler: after a filter, a DOM lookup you control; illegitimate at boundaries, §11), ! (non-null assertion — a tiny as, same rules), any (checking OFF, contagiously — every expression it touches unchecks silently), and @ts-ignore (suppresses whatever the NEXT line's error is, including future different ones — prefer @ts-expect-error, which errors when the error disappears: self-cleaning). The honest hierarchy: reach for unknown first, as with a comment second, any never-without-a-TODO.

    
Migrating a JS codebase is a ratchet, not a rewrite: allowJs so both languages coexist → rename files leaf-first (utilities before entry points — fewer dependents, faster wins) → strict on for new code immediately (a lenient global config teaches the team non-strict habits — §09's false-confidence trap) → burn down the any-count with a lint budget that only shrinks (the "ratchet": CI fails if escapes increase). Six weeks of file-by-file beats a six-month branch nobody can merge — the pg zero-downtime migration philosophy (expand → migrate → contract), applied to a type system.

    

      
// quiz — first pick is the one that counts

      
Mid-migration, a util throws: catch (e) and you need e.message. Rank: catch (e: any) vs catch (e: unknown) + narrowing.

      

        
        
        
        
      

      
Why: js-fundamentals §10 taught that throw accepts any value — the type system just made that fact unignorable. unknown is the honest type for "the language guarantees nothing here", and the two-line narrow is the entire cost. This tiny case IS the migration philosophy: unknown forces the check you needed anyway; any defers it to an incident. (And useUnknownInCatchVariables — in strict — makes unknown the default: the config agreeing with the answer.)

The error gauntlet — predict the compiler, three for three

      
advanced → the module's ideas, disguised as squiggles

    

  

  

    
Reading compiler errors before the compiler produces them is the fluency test — and the interview format ("what does TypeScript say about this?") is exactly these three. No hints beyond everything above.

    

      
// gauntlet 1 of 3

      
function pet(cat?: { name: string }) { console.log(cat.name) } — strict mode says?

      

        
        
        
        
      

      
Why: cat? is sugar for cat: { name: string } | undefined — and strictNullChecks (§09) refuses property access until the undefined arm is eliminated. The fix menu, each with different semantics: cat?.name (undefined flows on), if (!cat) return (early exit), a default parameter (changes the contract). Compilers don't warn (D) — TypeScript errors or it doesn't.

    

    

      
// gauntlet 2 of 3

      
const ids = cats.map(c => c.id).filter(id => id !== undefined) where id: string | undefined. What's ids' type, disappointingly, and the fix?

      

        
        
        
        
      

      
Why: filter's signature only knows the callback returns boolean — WHAT it tested is invisible unless the callback's type says id is string (§03's custom guards, in the one place everyone actually needs them). The 5.5 note is the current-knowledge flourish: inferred type predicates fixed the most-googled TS annoyance — knowing both the old pain and the new fix dates you as active.

    

    

      
// gauntlet 3 of 3

      
type Keys = keyof { name: string; kg: number } and const k: Keys = 'tail' — verdict, and what IS Keys?

      

        
        
        
        
      

      
Why: keyof produces the union of the ACTUAL keys as literal types (§02's literals doing structural work) — not the vague string. That precision cascades: pluck(cat, 'tail') failing at compile time, typed routers, typed translations — half the "how does the library know?" magic is keyof + literals. Three for three means the model stuck: shapes, narrowed by evidence, erased at runtime, precise to the literal.
