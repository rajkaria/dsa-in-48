01

RADIO, practiced — a full pass, annotated

the walkthrough with the "why" behind every move

The course gives you RADIO's phases; here's a full annotated pass on "design an autocomplete", with the meta-commentary an interviewer never says out loud. R (5'): the questions you ask ARE the evaluation — "data source? result count? mobile? a11y bar?" each signals a dimension you know exists. Scope cuts signal senior-ness: "ranking is server-side; I'll design the client." A (10'): draw SearchInput → useAutocomplete() → ResultsList with a query cache beside it — and say WHY the hook exists (testable logic, swappable UI — the React module's §05 talking). D (10'): server state = suggestions keyed by query; UI state = highlighted index, open/closed; URL state = none (ephemeral) — the taxonomy said aloud is worth more than any single choice.

I (10'): two contracts: HTTP (GET /suggest?q=&limit=, ordered, with an id per suggestion) and the component's props (getSuggestions, onSelect, renderItem, minChars) — designing the second unprompted is the differentiator. O (10'): pick TWO themes and go deep: races + cancellation (Async §07 verbatim), and a11y (the APG combobox from the course). Close with the ritual: failure modes, what you'd build first, what you deferred. Practice this exact pass out loud three times this week — it transfers to every prompt.

// quiz — first pick is the one that counts

The interviewer interrupts your architecture phase: "actually, let's talk about how you'd cache suggestions." The right move?

Why: RADIO is your default itinerary, not a contract — interviewers redirect toward their rubric's meat, and following smoothly (while parking the open thread aloud) shows exactly the meeting-running skill the structure was proving anyway. Refusing the redirect to protect your script is the inverted failure: the structure mattering more than the collaboration. "Loose grip on the map, firm grip on the thread" is the sentence.

LEVEL UP — what interviewers listen for
  • Time your practice passes: 40 minutes wall-clock, phone timer per phase. Fluency under a clock is a trained skill, not a personality trait.
  • Three prompts cover the space: autocomplete (data flow), feed (lists + optimism), chat (real-time). One full pass each = 2 hours that upgrades every future round.

03

Component APIs — contracts you design on purpose

the DataTable worked example, decision by decision

Let's design <CatTable> the way the round wants — narrating each decision's why. Data in: rows + columns where each column is {key, header, render?} — the render function is the extensibility valve (custom cells without new props). Events out: onSort, onRowClick — the table reports, the page decides (containers stay thin). Controlled where shared: sortState + onSortChange lives with the caller because the URL wants it (State §04's taxonomy deciding a props question — the modules compound). Slots for variation: empty, loading render props. Stated non-goals: fetching and pagination live outside — "the table renders; the page owns data." Five moves, five reasons — that's a complete senior answer.

The compound-component upgrade (Table.Head, Table.Row) earns its complexity when callers need structural freedom — mention it as the escalation path, not the default. And the a11y floor is part of the API: sortable headers are <button aria-sort>, row click targets are real interactive elements — accessible by construction, inherited by every consumer.

// quiz — first pick is the one that counts

Product asks CatTable to support "click a row to expand details". Two teams want different expansion content. The API move?

Why: the enum prop (option 1) couples the design system to product features — every new use case is a PR to the table; the fork (3) orphans a11y and fixes. The render prop inverts the dependency: the table provides the mechanism (expansion, animation, aria-expanded), callers provide meaning. Option 4 is legitimate but changes the UX (modal ≠ inline). "Mechanism in the system, meaning in the product" is the design-system sentence worth memorizing.

LEVEL UP — what interviewers listen for
  • Prop-count as a smell metric: past ~10, look for config objects that should be composition.
  • The escape-hatch ladder (compose → className passthrough → upstream proposal → never fork) from the course's Q&A — recite it when "what if the system doesn't support X" appears.

04

State architecture — the audit ritual

the four-kinds taxonomy as a practiced skill

The course names the taxonomy (server / UI / app / URL); the skill is auditing a real screen fast. The ritual, on the cat feed: list every piece of state the screen touches, then home each one with a reason. Posts + profiles → server state (query cache; it's a cache problem — staleness, dedupe, invalidation). Composer draft → local UI… except drafts should survive refresh → persisted local (localStorage), a deliberate exception you say out loud. Auth/user → app state (tiny store). Active filter + scroll cursor → URL (shareable, back-button-correct). Like-in-flight → server-state mutation metadata (the query cache's job, not yours). Two minutes, five homes, every choice reasoned — that audit IS the interview answer.

The advanced layer: state machines for multi-step flows. The composer (idle → editing → uploading → posted | failed) as a reducer with named transitions kills the boolean soup (isUploading && !hasFailed && …) that breeds impossible states. "I'd model this as a state machine" + drawing the transition diagram is a senior move that costs 30 seconds.

// quiz — first pick is the one that counts

The feed's "3 new posts — tap to show" pill: where does the count of pending-unseen posts live, and why?

Why: the pill is a view of data-layer reality (posts fetched but held back to avoid yanking the scroll — the frontend course's lists topic). Deriving beats duplicating: a separate counter drifts the moment merge logic changes. Refresh (option 4) SHOULD reset it — after reload the feed is fresh. This question rewards the derived-state instinct from JS Fundamentals §07 and React §03, at design altitude — three modules, one answer.

LEVEL UP — what interviewers listen for
  • Practice the two-minute audit on three screens of your real app this week — the ritual, not the taxonomy, is what performs under pressure.
  • Undo/redo, offline queues, and optimistic rollbacks all get trivial when transitions are centralized — the payoff sentence for the state-machine investment.

05

Data & caching — the five-layer answer

where every deep-dive request eventually lands

When the interviewer says "go deeper on data", they want the layered story, and you now own every layer from three modules. Layer 1 — the contract: cursor pagination, stable ids, an error envelope (node-backend §04). Layer 2 — the transport: dedupe + abort in-flight duplicates (async §07). Layer 3 — the cache: normalized entities, lists as id arrays, stale-while-revalidate with per-key staleness budgets. Layer 4 — mutations: optimistic for high-success toggles with rollback; invalidate-vs-write-through as a stated choice per mutation. Layer 5 — persistence: cache snapshot to IndexedDB for instant revisit paint + the offline read story.

The worked detail that impresses: the like button's full journey. Tap → cache updates optimistically (count+1, filled heart) → request fires with idempotency key → success confirms silently / failure rolls back + toast → a background refetch reconciles eventually. Six beats, four modules' worth of machinery, told in twenty seconds — rehearse it verbatim.

// quiz — first pick is the one that counts

Feed post appears in the timeline, the user's profile grid, and a "trending" rail — the user likes it from the rail. What must be true of the cache for all three views to update?

Why: this is the postgres module's "one card per cat" — in the browser. Normalization isn't a server-only idea: entity-by-id + lists-of-ids is how client caches (React Query's structural sharing, Apollo's normalized store) make one update omnipresent. Options 1/3 work but are the hand-rolled, drift-prone versions of what normalization gives structurally. Saying "same normalization argument as the database, one layer up" connects two modules in one sentence — interviewers visibly enjoy that.

LEVEL UP — what interviewers listen for
  • Staleness budgets per data type, stated like SLOs: profile 5 min, feed 30 s, unread badge 5 s, price 0 — "freshness is a product decision expressed in cache config".
  • Prefetch on hover/viewport + cache persistence = the "instant app" feel — cheap tricks, name them together.

06

Performance budgets — numbers you commit to

turning "make it fast" into an engineering plan

The senior move in the perf deep-dive is converting vibes into budgets: LCP ≤ 2.5s on a mid-range Android over 4G; INP ≤ 200ms; initial route JS ≤ 200KB gz; images ≤ 200KB above the fold; then defending each budget in CI (size-limit, Lighthouse CI) and watching it in RUM at p75. With budgets stated, every technique becomes a line item with an owner: route-split the bundle (assets topic), stream the shell (rendering), virtualize the list (lists), transition the heavy updates (React §06), lazy-decode the images. The plan writes itself once the numbers exist — which is why you state numbers first.

And the diagnosis ladder when a budget's blown, in strict order: field data first (which users, which metric), then the trace (Lighthouse/Profiler on a throttled device), then the fix targeting the dominant term — never the reverse. "We optimized what the RUM said, not what annoyed us locally" is a sentence that carries a whole round.

// quiz — first pick is the one that counts

RUM says p75 LCP is 4.1s on mobile but 1.9s on desktop. Lab runs on your machine show 1.6s everywhere. First move?

Why: the lab/field gap is the classic tell that your test conditions flatter you — mobile CPUs execute your JS 4–6× slower and 4G round-trips stack. Segmenting RUM tells you WHERE the 4.1s lives (device class? one geo's CDN gap? one route?); throttled traces then show WHY. Options 1 and 4 are measurement-denial in different hats. "Debug in lab, decide in field — and make the lab lie less" wraps it.

LEVEL UP — what interviewers listen for
  • Budgets are per-route, not per-app — the checkout can spend more JS than the landing page. Saying so shows you've operated them.
  • The full drills: course topics perf + assets — this section is their planning layer.

07

Resilience & a11y — the requirements that upgrade your level

designing the unhappy paths first

The strongest closing habit in frontend rounds: design the unhappy paths as requirements, not patches. For every surface, four questions asked in the same breath as the feature itself: What renders while loading (skeletons matching final layout — CLS!)? What renders on failure (retryable error states per region, error boundaries containing the blast)? What happens offline (reads from cache, writes queued with pending badges — the network topic's full story)? What happens for keyboard and screen-reader users (focus management on every transition, live-region announcements for async results)?

The interview mechanics: raise a11y in the requirements phase ("targeting WCAG AA — it'll shape the component APIs"), then let it surface naturally in each design decision (the combobox's aria-activedescendant, the modal's focus trap, the feed's announced updates). One requirements-phase sentence + two concrete mechanisms later = the a11y box checked at senior level, without a dedicated lecture. Resilience gets the same treatment: "every fetch in this design has a retry policy and a visible failure state" stated once, then honored visibly.

// quiz — first pick is the one that counts

The infinite feed hits a fetch error on page 4. Grade these UX options, best first?

Why: the loaded content is still VALID — nuking it (option 3) punishes the user for your pagination hiccup; silent-forever (1) strands them wondering; killing the mechanism (4) turns a blip into a session-long downgrade. The inline boundary row preserves everything, communicates honestly, retries ambiently, and stays accessible. "Degrade the smallest possible region, keep what works, offer the retry where the failure lives" — that's the resilience design principle in one sentence, and it applies to every surface in the round.

LEVEL UP — what interviewers listen for
  • The unhappy-path grid (loading/error/offline/a11y × each surface) makes a great literal whiteboard artifact — draw it and fill it live.
  • This module + the course = both altitudes covered. Final step: the interview kit's mock-loop run sheets, where you perform all of it under a clock.
