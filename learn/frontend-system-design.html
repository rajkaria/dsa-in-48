RADIO, practiced — a full pass, annotated

the walkthrough with the "why" behind every move

The course gives you RADIO's phases; here's a full annotated pass on "design an autocomplete", with the meta-commentary an interviewer never says out loud. R (5'): the questions you ask ARE the evaluation — "data source? result count? mobile? a11y bar?" each signals a dimension you know exists. Scope cuts signal senior-ness: "ranking is server-side; I'll design the client." A (10'): draw SearchInput → useAutocomplete() → ResultsList with a query cache beside it — and say WHY the hook exists (testable logic, swappable UI — the React module's §05 talking). D (10'): server state = suggestions keyed by query; UI state = highlighted index, open/closed; URL state = none (ephemeral) — the taxonomy said aloud is worth more than any single choice.

I (10'): two contracts: HTTP (GET /suggest?q=&limit=, ordered, with an id per suggestion) and the component's props (getSuggestions, onSelect, renderItem, minChars) — designing the second unprompted is the differentiator. O (10'): pick TWO themes and go deep: races + cancellation (Async §07 verbatim), and a11y (the APG combobox from the course). Close with the ritual: failure modes, what you'd build first, what you deferred. Practice this exact pass out loud three times this week — it transfers to every prompt.

// quiz — first pick is the one that counts

The interviewer interrupts your architecture phase: "actually, let's talk about how you'd cache suggestions." The right move?

Why: RADIO is your default itinerary, not a contract — interviewers redirect toward their rubric's meat, and following smoothly (while parking the open thread aloud) shows exactly the meeting-running skill the structure was proving anyway. Refusing the redirect to protect your script is the inverted failure: the structure mattering more than the collaboration. "Loose grip on the map, firm grip on the thread" is the sentence.

LEVEL UP — what interviewers listen for
  • Time your practice passes: 40 minutes wall-clock, phone timer per phase. Fluency under a clock is a trained skill, not a personality trait.
  • Three prompts cover the space: autocomplete (data flow), feed (lists + optimism), chat (real-time). One full pass each = 2 hours that upgrades every future round.

03

Component APIs — contracts you design on purpose

the DataTable worked example, decision by decision

Let's design <CatTable> the way the round wants — narrating each decision's why. Data in: rows + columns where each column is {key, header, render?} — the render function is the extensibility valve (custom cells without new props). Events out: onSort, onRowClick — the table reports, the page decides (containers stay thin). Controlled where shared: sortState + onSortChange lives with the caller because the URL wants it (State §04's taxonomy deciding a props question — the modules compound). Slots for variation: empty, loading render props. Stated non-goals: fetching and pagination live outside — "the table renders; the page owns data." Five moves, five reasons — that's a complete senior answer.

The compound-component upgrade (Table.Head, Table.Row) earns its complexity when callers need structural freedom — mention it as the escalation path, not the default. And the a11y floor is part of the API: sortable headers are <button aria-sort>, row click targets are real interactive elements — accessible by construction, inherited by every consumer.

// quiz — first pick is the one that counts

Product asks CatTable to support "click a row to expand details". Two teams want different expansion content. The API move?

Why: the enum prop (option 1) couples the design system to product features — every new use case is a PR to the table; the fork (3) orphans a11y and fixes. The render prop inverts the dependency: the table provides the mechanism (expansion, animation, aria-expanded), callers provide meaning. Option 4 is legitimate but changes the UX (modal ≠ inline). "Mechanism in the system, meaning in the product" is the design-system sentence worth memorizing.

LEVEL UP — what interviewers listen for
  • Prop-count as a smell metric: past ~10, look for config objects that should be composition.
  • The escape-hatch ladder (compose → className passthrough → upstream proposal → never fork) from the course's Q&A — recite it when "what if the system doesn't support X" appears.

04

State architecture — the audit ritual

the four-kinds taxonomy as a practiced skill

The course names the taxonomy (server / UI / app / URL); the skill is auditing a real screen fast. The ritual, on the cat feed: list every piece of state the screen touches, then home each one with a reason. Posts + profiles → server state (query cache; it's a cache problem — staleness, dedupe, invalidation). Composer draft → local UI… except drafts should survive refresh → persisted local (localStorage), a deliberate exception you say out loud. Auth/user → app state (tiny store). Active filter + scroll cursor → URL (shareable, back-button-correct). Like-in-flight → server-state mutation metadata (the query cache's job, not yours). Two minutes, five homes, every choice reasoned — that audit IS the interview answer.

The advanced layer: state machines for multi-step flows. The composer (idle → editing → uploading → posted | failed) as a reducer with named transitions kills the boolean soup (isUploading && !hasFailed && …) that breeds impossible states. "I'd model this as a state machine" + drawing the transition diagram is a senior move that costs 30 seconds.

// quiz — first pick is the one that counts

The feed's "3 new posts — tap to show" pill: where does the count of pending-unseen posts live, and why?

Why: the pill is a view of data-layer reality (posts fetched but held back to avoid yanking the scroll — the frontend course's lists topic). Deriving beats duplicating: a separate counter drifts the moment merge logic changes. Refresh (option 4) SHOULD reset it — after reload the feed is fresh. This question rewards the derived-state instinct from JS Fundamentals §07 and React §03, at design altitude — three modules, one answer.

LEVEL UP — what interviewers listen for
  • Practice the two-minute audit on three screens of your real app this week — the ritual, not the taxonomy, is what performs under pressure.
  • Undo/redo, offline queues, and optimistic rollbacks all get trivial when transitions are centralized — the payoff sentence for the state-machine investment.

05

Data & caching — the five-layer answer

where every deep-dive request eventually lands

When the interviewer says "go deeper on data", they want the layered story, and you now own every layer from three modules. Layer 1 — the contract: cursor pagination, stable ids, an error envelope (node-backend §04). Layer 2 — the transport: dedupe + abort in-flight duplicates (async §07). Layer 3 — the cache: normalized entities, lists as id arrays, stale-while-revalidate with per-key staleness budgets. Layer 4 — mutations: optimistic for high-success toggles with rollback; invalidate-vs-write-through as a stated choice per mutation. Layer 5 — persistence: cache snapshot to IndexedDB for instant revisit paint + the offline read story.

The worked detail that impresses: the like button's full journey. Tap → cache updates optimistically (count+1, filled heart) → request fires with idempotency key → success confirms silently / failure rolls back + toast → a background refetch reconciles eventually. Six beats, four modules' worth of machinery, told in twenty seconds — rehearse it verbatim.

// quiz — first pick is the one that counts

Feed post appears in the timeline, the user's profile grid, and a "trending" rail — the user likes it from the rail. What must be true of the cache for all three views to update?

Why: this is the postgres module's "one card per cat" — in the browser. Normalization isn't a server-only idea: entity-by-id + lists-of-ids is how client caches (React Query's structural sharing, Apollo's normalized store) make one update omnipresent. Options 1/3 work but are the hand-rolled, drift-prone versions of what normalization gives structurally. Saying "same normalization argument as the database, one layer up" connects two modules in one sentence — interviewers visibly enjoy that.

LEVEL UP — what interviewers listen for
  • Staleness budgets per data type, stated like SLOs: profile 5 min, feed 30 s, unread badge 5 s, price 0 — "freshness is a product decision expressed in cache config".
  • Prefetch on hover/viewport + cache persistence = the "instant app" feel — cheap tricks, name them together.

06

The caching layer cake — HTTP, SW, memory & state

intermediate → four caches, one invalidation story, told in order

A browser request can be answered from four caches, and a design answer that names them in order sounds instantly senior. (1) HTTP cache — the browser's, governed by Cache-Control headers: immutable + hashed filenames for assets (cache forever, deploy new names — the CDN lesson's client half); no-cache (revalidate with ETag → 304) for HTML. (2) Service worker cache — programmable (§07 owns it). (3) In-memory app cache — your data layer's Map: React Query/SWR keyed by query, with staleness semantics (§05's layers, zoomed in): serve stale instantly, revalidate behind it, swap silently. (4) State itself — normalized entities already fetched (the "we have this user from the list page" case — cache by entity id, not by URL).

The design question is always invalidation scope: a mutation must invalidate exactly the affected keys across the layers it touched — the edit-profile call invalidates user:42 (memory), maybe a SW cache entry, never the immutable JS bundle. "Every cache in the stack answers two questions: what key, and who invalidates it" — say that sentence, then walk the cake.

// quiz — first pick is the one that counts

After deploy, users report the old UI until a hard refresh. Assets use hashed names with long max-age. What's actually stale?

Why: hashed bundles can't be stale — a new deploy is a new URL. The entry point that names them is the only mutable link in the chain, and giving it a long max-age freezes the whole app. The pattern generalizes: immutable content cached forever + one tiny always-fresh pointer — it's how CDNs, SWs, and even Docker layers work. (If a service worker is involved, the update lifecycle in §07 is the second suspect.)

LEVEL UP — what interviewers listen for
  • stale-while-revalidate exists at BOTH the HTTP layer (a Cache-Control extension) and the data layer (SWR's whole name) — same philosophy, two altitudes.
  • Cache keys must include what varies the response: auth state, locale (§09), variant flags (§10) — the CDN cache-key discipline, applied client-side.
  • Memory caches die on refresh — persisting the query cache (localStorage/IndexedDB) buys instant warm starts and buys the "how fresh is too stale?" conversation.
  • The interview close: draw the waterfall of one product screen and annotate which layer answers each request on a warm visit — 60 seconds, very few candidates can.

07

Offline-first & service workers — the app that survives a tunnel

intermediate → SW strategies, the update trap & the sync queue

A service worker is a programmable proxy between your app and the network — every fetch can be answered from its cache, the network, or a blend. The strategy menu, chosen per resource type: cache-first (app shell, fonts — instant, update in background), network-first with cache fallback (API data — fresh when online, stale beats blank offline), stale-while-revalidate (avatars, non-critical data). PWA = SW + manifest: installable, offline-capable, push-capable — "app-like" as a set of checkboxes rather than a vibe.

Two traps carry the interview. The update lifecycle: a new SW installs but waits until every tab from the old one closes — users can run week-old code despite your deploys ("why is the fix not live?" — it is; their SW isn't). The pattern: detect the waiting worker, show "update available", skipWaiting on click. Writes while offline: reads come from cache, but a POST needs a sync queue — persist the mutation (IndexedDB), show it optimistically (§04's optimistic state), replay on reconnection with idempotency keys (the backend module's §08 — the two halves of one contract), and design for the replay conflicting (server state moved on: last-write-wins, merge, or surface to the user — say which).

// quiz — first pick is the one that counts

A field-sales app must let reps edit customer notes in dead zones. The architecture sentence that covers it?

Why: the requirement is offline writes — blocking them (A) fails the brief. The outbox is the queue pattern from system design, living in the browser: durable, ordered, replayable, idempotent. The conflict policy is what separates a real answer from a happy-path one — two reps editing the same note offline WILL happen; "LWW with an audit trail, surface conflicts above N minutes of divergence" is a defensible line. localStorage (D) is synchronous, tiny, and string-only — name IndexedDB for anything structural.

LEVEL UP — what interviewers listen for
  • SWs are killable between events — no in-memory state survives; everything durable lives in Cache Storage/IndexedDB. "Stateless worker over durable stores" — the serverless mental model, in the browser.
  • Never cache-first the API without a freshness story — the support ticket is "my dashboard is from Tuesday". Reads: network-first or SWR; shell: cache-first. Per-type, always.
  • Background Sync API exists (replay even after tab close) but is Chromium-only — the honest answer replays on next open too.
  • Scope note: an SW only controls its scope path, HTTPS only, and the first visit is uncontrolled — three facts that date-stamp real experience.

08

Performance budgets — numbers you commit to

turning "make it fast" into an engineering plan

The senior move in the perf deep-dive is converting vibes into budgets: LCP ≤ 2.5s on a mid-range Android over 4G; INP ≤ 200ms; initial route JS ≤ 200KB gz; images ≤ 200KB above the fold; then defending each budget in CI (size-limit, Lighthouse CI) and watching it in RUM at p75. With budgets stated, every technique becomes a line item with an owner: route-split the bundle (assets topic), stream the shell (rendering), virtualize the list (lists), transition the heavy updates (React §06), lazy-decode the images. The plan writes itself once the numbers exist — which is why you state numbers first.

And the diagnosis ladder when a budget's blown, in strict order: field data first (which users, which metric), then the trace (Lighthouse/Profiler on a throttled device), then the fix targeting the dominant term — never the reverse. "We optimized what the RUM said, not what annoyed us locally" is a sentence that carries a whole round.

// quiz — first pick is the one that counts

RUM says p75 LCP is 4.1s on mobile but 1.9s on desktop. Lab runs on your machine show 1.6s everywhere. First move?

Why: the lab/field gap is the classic tell that your test conditions flatter you — mobile CPUs execute your JS 4–6× slower and 4G round-trips stack. Segmenting RUM tells you WHERE the 4.1s lives (device class? one geo's CDN gap? one route?); throttled traces then show WHY. Options 1 and 4 are measurement-denial in different hats. "Debug in lab, decide in field — and make the lab lie less" wraps it.

LEVEL UP — what interviewers listen for
  • Budgets are per-route, not per-app — the checkout can spend more JS than the landing page. Saying so shows you've operated them.
  • The full drills: course topics perf + assets — this section is their planning layer.

09

Internationalization — architecture, not string files

intermediate → locale as a first-class dimension of the system

i18n in a design round is an architecture dimension, not a library choice. The load-bearing decisions: locale detection & routing (URL-based /de/… beats cookie-sniffing: shareable, cacheable — the locale is part of the cache key everywhere, §06); bundle strategy (never ship all locales — lazy-load the active locale's messages as their own chunk; 40 locales in the main bundle is a perf-budget kill from §08); and message format (ICU MessageFormat, because pluralization is not count + "s" — Polish has four plural categories, Arabic six; the format encodes per-language rules your string-concatenation can't).

The layout half is what juniors miss: RTL (Arabic, Hebrew) is a mirrored world — CSS logical properties (margin-inline-start, not margin-left) make it nearly free if adopted early and a rewrite if not; text expansion (German labels run ~30% longer, Finnish worse) means fixed-width buttons truncate — design reviews need a long-locale pass; and dates/numbers/currency go through Intl.* (the platform already knows), never hand-formatting.

// quiz — first pick is the one that counts

The string "You have " + count + " item" + (count === 1 ? "" : "s") ships to 12 locales. What breaks, structurally?

Why: concatenation hard-codes English's grammar into the code. A translator given "You have ", "item", "s" cannot produce correct Polish (which needs different noun forms for 1, 2-4, 5+, and fractions) or reorder for Japanese. The ICU message is a tiny per-locale program — the translator owns the whole sentence including its branches. "Strings are per-locale functions, not fragments" is the mental model shift the question tests.

LEVEL UP — what interviewers listen for
  • Locale is a cache-key dimension end to end: CDN (Vary/key on locale), SW caches, query caches — miss one layer and German users get cached English (the §06/edge lesson, recurring).
  • Translation ops is a pipeline: keys extracted at build, missing-key reports, pseudo-localization in CI (l̂ön̂ĝ t̂ex̂t̂ catches truncation before Finnish users do).
  • SSR + i18n: the server must render the user's locale (detection before render) or hydration mismatches (react §14's bug) appear in translated text.
  • Scope honesty: "true i18n includes addresses, name order, phone formats, and legal text — I'd stage: UI strings → formats → RTL" — a rollout plan beats a library name.

Feature flags & experiments — shipping dark, deciding with data

intermediate → decouple deploy from release; kill switches & A/B rigor

Flags exist to decouple deploy from release: code ships dark (merged, deployed, off), then turns on by audience — internal → 1% → 50% → all — with a kill switch that reverts in seconds without a deploy (the cheapest incident response that exists). Architecture requirements the round expects: flags evaluate fast and local (bootstrap the user's flag set at page load / edge-inject it — a blocking flag-service call on the render path is a new SPOF), consistently (same user, same answer across pages and sessions: hash userId+flagName deterministically — no coin flips per render), and observably (every evaluation logged with the §12 telemetry, or you can't debug "which variant did this user see?").

Experiments are flags plus statistics: an A/B test is a flag whose variants are assigned by stable hash, exposure-logged, and judged on a pre-registered metric. The rigor that separates real answers: assignment ≠ exposure (only count users who actually saw the variant), don't peek-and-stop at the first significant wiggle, and mind the flicker bug — client-side flag resolution after first paint shows variant A for 200ms, then swaps to B: both branded into the user's retina and your metrics. SSR/edge evaluation kills the flicker.

// quiz — first pick is the one that counts

Checkout error rates spike 20 minutes after enabling a new payment-form flag at 50%. Walk the response.

Why: this is the entire ROI of flags condensed: rollback = a config change, blast radius was already capped at 50%, and telemetry segmented by variant (the observability requirement) turns "is it the flag?" from a debate into a graph. A code revert (A) costs a deploy cycle during an incident and un-ships code that was never the problem — the flag state was. "Deploys move code, flags move risk" is the sentence to leave behind.

LEVEL UP — what interviewers listen for
  • Flag debt is real: every flag is a fork in your test matrix — expiry dates, owners, and a cleanup ritual are part of the architecture answer, not ops trivia.
  • Long-lived flags are a cache-key dimension (§06, again): variant belongs in the key or users get each other's UI from the CDN.
  • Types of flags deserve different machinery: release flags (temporary), ops kill-switches (permanent, tested like circuit breakers), entitlements (billing — not flags at all, don't conflate).
  • The stats one-liner that lands: "I pre-register the metric and the sample size; the dashboard going green early is exactly when I don't stop."

Resilience & a11y — the requirements that upgrade your level

designing the unhappy paths first

The strongest closing habit in frontend rounds: design the unhappy paths as requirements, not patches. For every surface, four questions asked in the same breath as the feature itself: What renders while loading (skeletons matching final layout — CLS!)? What renders on failure (retryable error states per region, error boundaries containing the blast)? What happens offline (reads from cache, writes queued with pending badges — the network topic's full story)? What happens for keyboard and screen-reader users (focus management on every transition, live-region announcements for async results)?

The interview mechanics: raise a11y in the requirements phase ("targeting WCAG AA — it'll shape the component APIs"), then let it surface naturally in each design decision (the combobox's aria-activedescendant, the modal's focus trap, the feed's announced updates). One requirements-phase sentence + two concrete mechanisms later = the a11y box checked at senior level, without a dedicated lecture. Resilience gets the same treatment: "every fetch in this design has a retry policy and a visible failure state" stated once, then honored visibly.

// quiz — first pick is the one that counts

The infinite feed hits a fetch error on page 4. Grade these UX options, best first?

Why: the loaded content is still VALID — nuking it (option 3) punishes the user for your pagination hiccup; silent-forever (1) strands them wondering; killing the mechanism (4) turns a blip into a session-long downgrade. The inline boundary row preserves everything, communicates honestly, retries ambiently, and stays accessible. "Degrade the smallest possible region, keep what works, offer the retry where the failure lives" — that's the resilience design principle in one sentence, and it applies to every surface in the round.

LEVEL UP — what interviewers listen for
  • The unhappy-path grid (loading/error/offline/a11y × each surface) makes a great literal whiteboard artifact — draw it and fill it live.
  • This module + the course = both altitudes covered. Final step: the interview kit's mock-loop run sheets, where you perform all of it under a clock.

Frontend observability — RUM, error tracking & session context

advanced → the client is a fleet of production servers you don't control

Section 08 said "field decides, lab explains"; this section builds the field half. RUM (real-user monitoring) collects Web Vitals (LCP, INP, CLS) from actual sessions via PerformanceObserver, beaconed home (sendBeacon — survives tab close) and segmented: p75 by device class, country, connection — because your median MacBook user hides your p75 Android-on-3G reality, and Google's ranking reads the p75. Error tracking is the browser's version of the backend's structured logging: window.onerror + unhandledrejection, sourcemapped stacks (minified line 1 col 48291 is noise), grouped by fingerprint, with release + flag context attached — "did 2.3.1 introduce this? only under variant B?" is a query, not an investigation (the flags section's observability requirement, cashed in).

The discipline that makes it usable: sample (100% of errors, ~10% of session telemetry — volume is cost and privacy), scrub PII at the SDK level (URLs and breadcrumbs leak emails), and tie every beacon to a session id so one user's complaint becomes a replayable timeline — the nb request-id lesson, with the id living in the browser.

// quiz — first pick is the one that counts

Lighthouse scores 98 in CI, but conversion-critical pages feel slow to users in India. Where's the truth, and what do you instrument?

Why: lab is a controlled experiment (great for regressions, CI budgets); the field is the population (great for truth). The workflow is a loop: RUM finds the cohort and metric (LCP p75 = 6s on Android/4G in India — likely CDN distance §edge, image weight, or JS on the critical path), lab reproduces under those conditions, the fix ships behind a flag, and RUM confirms the p75 moved. "Field decides, lab explains" — now with the machinery attached.

LEVEL UP — what interviewers listen for
  • INP replaced FID (2024) — a stale metric name dates the whole answer; INP = worst interaction latency, the metric concurrent React (react §12) exists to improve.
  • Session replay is the heavy tool: powerful for "can't reproduce", radioactive for privacy — mask-by-default, consent-gated, sampled. Saying the caveats IS the answer.
  • Error budgets meet frontend: alert on error-rate per release (not raw counts — traffic varies), auto-halt rollouts (§10) when the canary cohort's rate diverges.
  • The closing move in any design: "and the observability section — vitals p75 by segment, error rate by release, one dashboard per critical journey" — 15 seconds, rarely said, always noticed.

Design systems at scale — tokens, theming & versioned UI

advanced → the component library as infrastructure with consumers

"Design a component library for 40 teams" is an infrastructure question wearing UI clothes. The layer cake: design tokens at the bottom — named decisions (--color-surface, --space-3) published as CSS variables, THE theming mechanism: dark mode/white-labeling = swap token values, zero component changes (this very page works that way — one --tint flip). Above them, primitives (Button, Input — a11y baked in: the resilience section's "mechanisms" argument for why a11y lives in the system, not in each product team's backlog). Above those, patterns (DatePicker, DataTable) composed from primitives, with the component-API lessons from §03 governing their props.

The at-scale part is versioning and migration: the system is a dependency with 40 consumers — semver religiously, breaking changes ship with codemods (a migration script beats a migration document), deprecations warn for N versions before removal, and adoption is measured (which teams, which versions, which raw-HTML escapes) because a design system nobody upgrades is a museum. Governance in one line: contribution RFC process + a core team — "product teams propose, the system curates" — or it forks into five dialects within a year.

// quiz — first pick is the one that counts

Marketing needs the whole product white-labeled per enterprise customer (colors, logos, radii). The design-system answer?

Why: override stylesheets (A) fight specificity forever and break on every library update; forks (C) are five museums. The token indirection is the whole trick: components bind to meaning (surface, accent, danger), themes bind meaning to values — the same indirection as env-config for backends. The senior details: semantic tokens (not --blue-500 — you can't theme a color named blue), and automated contrast validation per theme because customer-chosen yellows will fail WCAG (a11y as a mechanism again).

LEVEL UP — what interviewers listen for
  • Two token tiers: primitive (--gray-90) → semantic (--color-text) — themes remap the semantic tier; the primitive palette is shared vocabulary.
  • Distribution reality: tree-shakeable package, SSR-safe styles, and versioned docs with live examples (Storybook-class) — docs ARE the product; an undocumented system loses to copy-paste.
  • Measure "system health" like a platform: adoption %, version spread, override frequency (high overrides = the API is wrong — §03's listening-to-consumers lesson).
  • The one-liner: "a design system is an API with a visual surface — version it, deprecate it, and treat its consumers like customers."

14

Collaborative & multiplayer UI — presence, OT & CRDTs, honestly

advanced → the "design Figma/Docs" round, from the client side

Multiplayer features stack in difficulty, and pricing each tier correctly IS the interview. Tier 1 — presence (avatars, cursors): ephemeral state over the socket (async module's transport), throttled (cursor at ~30 msg/s max), interpolated for smoothness, expired by heartbeat — no persistence, no conflicts, ship it in a week. Tier 2 — live-updating shared data (dashboards, kanban): server-authoritative + optimistic local updates + last-write-wins per field — conflicts resolved by "someone wins", acceptable when edits rarely collide on the same field. Tier 3 — concurrent text editing: the hard one, because two people inserting at the same position must converge without losing either edit.

The two Tier-3 machines, one line each: OT (operational transforms) rewrites operations against concurrent ones ("your insert-at-5 becomes insert-at-9 because I inserted 4 chars before you") — needs a central sequencing server, powers Google Docs. CRDTs give every character a stable identity (fractional/tree positions) so concurrent inserts merge commutatively — order of arrival stops mattering, offline merges free, at the price of metadata overhead. The senior sentence: "I would not build either — Yjs/Automerge for the engine; my design work is the integration": local echo (§04 optimistic), the socket fan-out (backend's chat), snapshot + op-log persistence, undo that undoes my ops only (collaborative undo is famously its own problem).

// quiz — first pick is the one that counts

PM asks for "Google-Docs-style commenting" on report pages: threaded comments appearing live, occasionally two people editing the same comment draft. Which tier, and what do you NOT build?

Why: the feature description says "live", not "co-edited" — appending distinct comments never conflicts (server assigns order; optimistic UI makes it feel instant). The one edge (two people in one draft) is cheaper to prevent (advisory lock, presence hint) than to merge. Jumping to CRDTs is résumé-driven architecture — and the interviewer set that trap on purpose. Right-sizing the tier, then naming the escalation path if requirements grow, is the entire answer.

LEVEL UP — what interviewers listen for
  • Presence engineering has real numbers: throttle + batch cursor updates, interpolate between frames, expire on heartbeat loss (the nb websockets reaper, client-visible).
  • Optimistic + authoritative = client predicts, server sequences, client reconciles — say "local echo with server-assigned order" and both sides of the stack nod.
  • Offline + collaborative is where CRDTs genuinely earn it (merging divergent histories is their superpower) — tie to §07's outbox and the multiplayer story completes.
  • Collaborative undo: "undo MY last op, not the document's" — one sentence that proves you've actually thought about multiplayer editing.

The reasoning gym — nine questions, three tiers

all levels → transfer, not recall: every question is an inference

Nothing new past this line — this is where the module gets performed. Warm-up isolates one concept against its favorite misconceptions; apply hands you a snippet or a trace and makes you predict before you peek; stretch chains two or more sections under real constraints, the way the round does. First pick is the recorded one, and the "why" under each answer is the actual lesson — read it even when you're right. Professor Whiskers grades on reasoning shown, not phrases remembered. 🐾

// warm-up 1 of 3 — rendering choice under constraints

An internal admin console: behind SSO, a drag-and-drop pipeline builder, live per-user data, a three-person team, zero crawler traffic. Rendering strategy?

Why: run §02's four questions: no SEO pressure, personalized, live, app-grade interaction — that's the CSR corner of the tree, and "who operates the render servers" is a legitimate fifth input for a three-person team. The SSR distractor encodes "faster first paint is always the goal" — behind a login the product is the post-load feel, and SSR buys infra plus hydration cost for pixels no crawler will ever see. SSG can't bake per-user live data at build time, and streaming solves slow-data-blocking-the-shell, a problem this page doesn't have. Constraints pick strategies; defaults don't.

// warm-up 2 of 3 — symptom to metric to cause

Users report: "it loads fast, but as I start reading the page jumps and I tap the wrong button." Which vital captures this, and what's the usual culprit?

Why: the user handed you the diagnosis: content moved after paint — that's layout shift, and the mis-tap is CLS's signature injury (the target relocated between aim and tap). LCP tempts because "any complaint = slow = LCP", but they said it loads fast; INP tempts because a tap misbehaved, but the tap responded instantly — at a target that had moved, which is shift, not latency. TTFB can't move content that already painted. Mapping symptom → metric before touching tools is the whole skill §08 and §12 are building.

// warm-up 3 of 3 — homing state with reasons

The cat-adoption dashboard holds three things: the date-range filter, the export dropdown's open/closed flag, and the fetched report rows. Home each one.

Why: §04's audit, three rows deep. "Global because everything can reach it" is the reachability-equals-placement misconception — it makes every store a junk drawer. "Filter is UI so it stays local" feels right until a teammate pastes the link and sees different data: state that defines which view this is belongs to the URL. And rows-in-the-store is hand-rolled caching without staleness, dedupe, or invalidation — the query cache exists precisely so you don't rebuild those three hard things badly. Each home earns its tenant with a reason; that's the ritual.

// apply 1 of 3 — dependency graphs kill waterfalls

Profile page loader: const user = await getUser(id); const posts = await getPosts(id); const badges = await getBadges(user.role); — each call ≈ 300 ms. What's the real floor, and how?

Why: draw the dependency graph before touching syntax. getPosts needs only id — independent, so it runs beside getUser; getBadges consumes getUser's result, so that edge is real and must serialize. True dependencies define the floor; everything else is concurrency you left on the table — 900 ms becomes 600 ms. The Promise.all-everything instinct crashes into the dependency (user.role doesn't exist yet), the ~900 ms answer mistakes sequential syntax for required sequence, and browser "pipelining" that reorders your data dependencies is invented behavior. This is the waterfall-elimination move §05 assumes you can do cold.

// apply 2 of 3 — reading a vitals trace

Field p75 on the landing page: TTFB 200 ms, FCP 1.0 s, LCP 4.8 s — and the LCP element is the hero image. Most likely cause?

Why: read the three numbers as a timeline and let each one exonerate a suspect: TTFB 200 ms clears the server; FCP 1.0 s clears the critical rendering path (paint wasn't blocked, so option 3 is out); which leaves the 3.8-second FCP→LCP gap as the image's own story — it was requested late or fetched at low priority. The classic self-inflicted version is loading="lazy" on the LCP image: lazy is for below the fold, and lazying the hero tells the browser to deprioritize your most important pixel. CLS is a different metric measuring movement, not arrival. §08's ladder in action: the numbers name the dominant term before you touch anything.

// apply 3 of 3 — which response wins

Search-as-you-type: input.oninput = e => fetch('/search?q=' + e.target.value).then(r => r.json()).then(setResults); The user types "ca", then "cat" — and the "ca" response arrives last. What renders?

Why: two inference steps: every keystroke launches an independent request, and independent requests finish in any order — the shorter query can easily hit a slower path (bigger result set, cache miss). So the last .then to run wins the state, and here that's the stale "ca". Option 2 is the order-preserving-network misconception the bug feeds on; option 3 misapplies batching, which coalesces updates within one synchronous pass, not across async arrivals; option 4 imagines accumulation where setResults replaces. This is the async module's race, resurfacing exactly where §01's autocomplete said it would — cancellation is a design requirement, not a nicety.

// stretch 1 of 3 — find the false claim

Three of these claims are true. Which one is FALSE?

Why: post-paint client-side flag resolution is the cause of flicker, not its cure — variant A paints, then swaps to B in front of the user, branding both into their retina and contaminating the experiment's metrics; §10's fix is evaluating at the edge or during SSR, before any paint. The three true claims are load-bearing and worth having cold: hashed-immutable assets are §06's "immutable content + one fresh pointer" pattern, the waiting worker is §07's "why isn't my fix live" trap, and interval re-baking is §02's ISR contract. A FALSE-hunt rewards checking each claim against its section's mechanism rather than its plausible tone.

// stretch 2 of 3 — arithmetic vs accessibility

A moderation tool lists 10,000 flagged comments — ~10 DOM nodes per row, rows ~80 px, viewport ~800 px. Moderators Ctrl+F the list; screen-reader users audit it. Your call?

Why: the estimate decides the architecture: ~100k nodes means every scroll and every interaction pays layout tax against §08's INP budget, while a virtualized window is two orders of magnitude smaller. But virtualization deletes real behavior — off-screen rows don't exist, so find-in-page and screen-reader traversal silently break, and the stated requirements include both. Options 1 and 3 are mirror-image failures: one refuses the arithmetic, the other refuses the trade-off; option 4 dodges the requirement instead of meeting it. §08's numbers plus §11's a11y-as-requirement, in one decision — chaining them under constraints is exactly what the round grades.

// stretch 3 of 3 — cacheability vs personalization

An SSG marketing page lives on the CDN. Two new asks land: a locale-correct greeting and an A/B hero-copy experiment. Keep it fast AND cacheable — what's the shape of the answer?

Why: the cardinality math is the senior detail — locales × variants is a handful of cached copies (fine), while Vary: Cookie keys on a string that's unique per user, so the hit rate rounds to zero: caching, quietly off. Full SSR nukes the CDN win for two small slots — §02's decompose-first lesson applies to requirements, not just surfaces. Client-side resolution "works", but the greeting pops in and the experiment flickers post-paint (§10's bug, plus contaminated metrics) — "the CDN never notices" is true and is the smallest part of the problem. Four sections in one answer: §02's decomposition, §06's what-varies-goes-in-the-key, §09's locale dimension, §10's flicker.

LEVEL UP — how to read your score
  • Warm-up misses → reread the section the misconception lives in: "SSR is always faster" dies in §02's tree, "any complaint means LCP" dies in §08/§12's timeline reading, "reachable = global" dies in §04's audit. Name the misconception out loud — retirement requires an obituary.
  • Apply misses → adopt the tracing ritual: before answering anything with code in it, draw the timeline — one line per request, arrows only for TRUE data dependencies, and assume arrival order is adversarial. Thirty seconds of drawing beats any amount of squinting.
  • Stretch misses → the combinations were §06×§07×§10 (the false-claim sweep), §08×§11 (arithmetic against accessibility), and §02×§06×§09×§10 (the cache-key finale). Reread the pair, not one section — combining is the skill, and the round only asks combined questions.
  • Transferable: argue against your first answer before committing — every distractor above was built from somebody's confident first instinct, and interviewers build their follow-ups the same way.
