How the web actually works.

Between "user types a URL" and "pixels appear" sit a dozen systems you use daily and explain rarely: DNS, TLS, HTTP's three generations, the render pipeline, cache grammar, cookie attributes, the CORS dance. How browsers render — parse to pixels, five stages

beginner → and which CSS/JS moves re-trigger which stage

HTML bytes become pixels through a pipeline: parse (HTML → DOM tree; CSS → CSSOM — and a <script> without defer pauses parsing, which is the entire "scripts at the bottom / use defer" folklore, explained), style (match rules to nodes), layout (compute every box's geometry), paint (fill in pixels per layer), composite (GPU stacks the layers). The stages re-run from the point you dirty: change width → layout + paint + composite (expensive, everything downstream); change color → paint + composite; change transform/opacity → composite only — which is why performant animations use transforms: they skip the geometry math entirely (the fesd perf budgets, mechanically justified).

The other famous consequence: layout thrashing — JS that alternates reads (offsetHeight) and writes (style changes) forces a synchronous layout per pair (the browser must answer the read correctly, so it flushes). Batch reads, then writes — or let rAF (js-async §10) sequence them before the next paint.

// quiz — first pick is the one that counts

Two ways to animate a cat sliding across the screen: left: 0 → 500px vs transform: translateX(0 → 500px). Why is the second dramatically smoother on weak devices?

Why: the pipeline position determines the per-frame bill: layout properties re-run the three expensive stages; compositor properties re-run approximately none. "Animate transform and opacity; everything else is a performance decision" is the one-line rule — and knowing it's about which pipeline stage gets dirtied (not vibes) is what the question screens for. The off-main-thread bonus explains why compositor animations stay smooth even while JS jank happens.

LEVEL UP — what interviewers listen for
  • The critical rendering path in one sentence: "HTML and CSS both block first paint; JS blocks parsing unless deferred — hence: inline critical CSS, defer everything else."
  • will-change/layer promotion is a trade (memory per layer) — promoting everything is a real mobile OOM pattern; name the cost, not just the trick.
  • content-visibility: auto skips rendering offscreen sections — the platform's own virtualization (fesd's list lesson, one CSS property).
  • DevTools Performance panel's purple (layout) vs green (paint) bars map exactly to this section — "I read the flame chart by stage" is the practical flex.

URLs & encoding — anatomy, and the two escape functions

beginner → the address format everything else parses

Anatomy, left to right: scheme://user@host:port/path?query#fragment — with three details that decide real bugs: the origin is scheme+host+port exactly (the security boundary §08 and cookies §07 both hang off it), the fragment never leaves the browser (servers never see #… — why SPAs used hash routing, and why tokens-in-fragments was the implicit flow's trick), and query strings are percent-encoded — where the two escape functions earn their names: encodeURIComponent escapes everything reserved (use for VALUES going into a query), encodeURI preserves URL structure (use for whole URLs, rarely). Mixing them up either breaks the URL or injects into it.

const u = new URL('https://shelter.example.com:8443/cats/search?name=mochi&tags=tabby%20cat#results');
for (const part of ['origin', 'protocol', 'host', 'port', 'pathname', 'search', 'hash'])
  console.log(part.padEnd(9), '→', u[part]);

// searchParams: the RIGHT way to build queries (encoding handled)
const q = new URL('https://shelter.example.com/search');
q.searchParams.set('name', 'Mr. Whiskers & Co');       // spaces, &, . — all hostile
q.searchParams.set('mood', '100% feral');
console.log('\nbuilt safely:', q.toString());

// the two escape functions, compared on the same hostile value
const v = 'tuna&salmon=yes/no?';
console.log('\nencodeURIComponent(v):', encodeURIComponent(v), ' ← value-safe');
console.log('encodeURI(v):         ', encodeURI(v), ' ← & = ? survive: STRUCTURE preserved');

HTTP/1.1 → 2 → 3 — three fixes for one bottleneck

      
beginner → head-of-line blocking, chased down the stack

    

  

  

    
HTTP's evolution is one bottleneck being chased through three layers. HTTP/1.1: text protocol, one request at a time per connection — a slow response blocks everyone behind it (head-of-line blocking at the HTTP layer). Browsers coped with ~6 parallel connections per host, and we coped with sprite sheets, bundling, domain sharding — an entire folk-engineering era. HTTP/2: binary framing multiplexes many streams over ONE connection — HTTP-level HoL solved, and the old hacks became anti-patterns (bundle-splitting got cheap). But TCP underneath guarantees ordered delivery: one lost packet stalls every stream until retransmission — HoL moved down a layer. HTTP/3: replace TCP with QUIC over UDP — streams are independent at the transport level (a lost packet stalls only its stream), plus 0-RTT reconnection and connection migration (WiFi→5G without re-handshaking). Same verbs, same headers, same semantics — the fixes are all plumbing.

    

      
// quiz — first pick is the one that counts

      
Why did HTTP/2 make "bundle everything into one giant JS file" LESS optimal than it was under HTTP/1.1?

      

        
        
        
        
      

      
Why: every performance folk-practice encodes an era's constraints — bundling, spriting and sharding were all "requests are expensive" workarounds. Multiplexing deleted the constraint, so the trade rebalanced toward cache granularity (the immutable-hashed-chunks pattern from fesd/aws-edge). The honest coda: request count still isn't free (headers, scheduling), so the answer is "fewer, cache-aligned chunks", not "a thousand tiny files". Reasoning about WHY a practice existed is the senior move the question invites.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The "what happens when you hit enter" answer now has its spine: DNS (§04) → TCP or QUIC → TLS (§05) → HTTP request → render pipeline (§01) — five sections of this module in one breath.
    • 
        
  • Verbs + idempotency (GET safe, PUT/DELETE idempotent, POST neither) is HTTP semantics — unchanged across all three versions; the sd idempotency section builds on exactly this.
    • 
        
  • Status code fluency: 301 vs 302 (caching!), 304 (§06's revalidation), 401 vs 403, 429 (node's limiter), 503 + Retry-After — each code is a protocol-level contract.
    • 
        
  • HTTP/2 Server Push is deprecated/dead — replaced by 103 Early Hints and preload; knowing what DIDN'T survive dates your knowledge as current.

    04
    

      
DNS — the phonebook, its caches & its deploy lever

      
intermediate → resolution walk, record types, TTL strategy

    

  

  

    
Resolution walks a hierarchy: stub resolver (your OS) → recursive resolver (ISP or 1.1.1.1/8.8.8.8) → root servers ("ask .com") → TLD servers ("ask example.com's nameservers") → authoritative nameservers (the actual answer) — with caching at every hop, governed by each record's TTL. Records you'll actually touch: A/AAAA (name → IPv4/v6), CNAME (name → another name — how www and CDN onboarding work; illegal at the zone apex, hence ALIAS/ANAME workarounds), MX (mail), TXT (proofs: domain verification, SPF/DKIM), NS (delegation itself).

    
The operational insight: TTL is a deploy lever. Migrating providers? Drop TTL to 60s a day ahead (the old long-TTL answers must expire first!), flip the record, verify, raise TTL back. Forget the pre-drop and your "instant" cutover takes as long as the old TTL — a day of two-provider limbo. DNS is also availability's first domino: it's how failover actually redirects (health-checked DNS, low TTLs), and the sd multi-region section's traffic-shifting is mostly this record-flip, productized.

    

      
// quiz — first pick is the one that counts

      
You flip an A record to the new server; your machine sees it instantly, but users report the old site for hours. The mechanism, and what SHOULD have happened yesterday?

      

        
        
        
        
      

      
Why: "propagation" is a misleading word for expiry — DNS pushes nothing; a million independent caches simply count down TTLs they fetched at different moments. That reframe makes the whole playbook obvious: control the countdown (pre-drop TTL), don't wait on a myth. It also explains the long tail: a few resolvers ignore TTLs (misbehaving corporate caches) — why old-IP traffic trickles for days and you keep the old server answering during the overlap.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • DNS is the first latency in "hit enter" — and why dns-prefetch/preconnect hints exist for third-party origins (fesd perf, platform edition).
    • 
        
  • DoH/DoT (DNS over HTTPS/TLS) encrypt the query — the privacy story; and DNS is also an attack surface (spoofed answers) — DNSSEC signs records, adoption is honest-to-say patchy.
    • 
        
  • Round-robin DNS is the poor man's load balancer with no health checks — name why real LBs (aws §traffic) sit behind one stable record instead.
    • 
        
  • dig +trace walks the whole hierarchy visibly — the debugging tool that turns this section from theory into practice in five minutes.

    05
    

      
TLS & certificates — what the padlock actually proves

      
intermediate → the handshake, the chain of trust & the ops around it

    

  

  

    
TLS gives three guarantees: confidentiality (encrypted), integrity (tamper-evident), and authenticity (you're talking to who the certificate names — the one people forget, and the one that stops man-in-the-middle). The modern handshake (TLS 1.3, one round trip): client hello (supported ciphers + key share) → server hello (chosen cipher, its key share, its certificate) → both derive the same symmetric session key via ephemeral Diffie-Hellman — asymmetric crypto to agree on a secret over a public channel, then fast symmetric crypto for the actual data. Ephemeral keys buy forward secrecy: yesterday's recorded traffic stays unreadable even if the server's long-term key leaks later.

    
The chain of trust: the site's certificate is signed by an intermediate CA, signed by a root CA that ships in your OS/browser trust store — the padlock means "a CA your vendor trusts vouched that whoever controls this domain requested this cert" (domain validation — usually an ACME challenge proving DNS/HTTP control; Let's Encrypt automated it to free-and-90-days). It does NOT mean the site is honest — phishing sites have valid padlocks; the padlock authenticates the name, not the intent.

    

      
// quiz — first pick is the one that counts

      
Corporate laptops see no certificate warnings, but the security team can read employees' HTTPS traffic. How, and what does it teach about the trust model?

      

        
        
        
        
      

      
Why: TLS interception proxies are routine enterprise kit, and they work by the trust model's own rules — no math is broken; a new root is trusted, so freshly-minted certs for any domain verify. The lesson generalizes: the trust store is the root of everything (why malware wants to install CAs, why cert pinning exists for high-stakes apps, and why "valid cert" ≠ "no eavesdropper" on managed devices). Understanding the model's edges beats reciting the handshake.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Cert expiry is a top-five outage cause — automation (ACME renewal + monitoring days-remaining) is the answer; "we renew manually" is the confession.
    • 
        
  • HSTS (the header, §nb-11) pins HTTPS at the browser so the first insecure hop disappears; preload lists bake it into browsers themselves.
    • 
        
  • SNI is why one IP serves many certificates (the hostname travels in the client hello) — and Encrypted Client Hello is the current work to hide even that.
    • 
        
  • mTLS (client certificates both ways) is service-to-service auth in zero-trust setups — one sentence connects it to the aws IAM story.
    •

HTTP caching grammar — Cache-Control, parsed like a compiler

      
intermediate → the five directives that matter, and 304's little dance

    

  

  

    
The grammar: max-age=N (fresh for N seconds — no request at all while fresh), no-cache (store, but revalidate every use — the misnamed one), no-store (never write to disk — the actually-private one), private/public (may shared caches — CDNs — keep it?), immutable (skip revalidation even on refresh), stale-while-revalidate=N (serve stale instantly, refresh behind — the latency-hider fesd loves). Revalidation is the 304 dance: response carried ETag: "abc" → later, browser sends If-None-Match: "abc" → server answers 304 Not Modified, empty body — one cheap round trip instead of a re-download. The canonical pairing (every module keeps meeting it): hashed assets → max-age=1yr + immutable; HTML → no-cache — immutable content forever, one always-checked pointer.

    

      

        
cache-decider.js — run it (the browser's freshness algorithm)

        
// what the HTTP cache decides per request — the actual state machine
function decide(entry, now) {
  if (!entry) return 'MISS → full network request';
  const age = now - entry.storedAt;
  const cc = entry.cacheControl;
  if (cc.includes('no-store')) return 'never stored (how did we get here?)';
  if (cc.includes('no-cache')) return `stored but always revalidates → If-None-Match ${entry.etag}`;
  const maxAge = Number((cc.match(/max-age=(\d+)/) || [])[1] ?? 0);
  if (age <= maxAge) return `FRESH (${age}s ≤ ${maxAge}s) → served from disk, ZERO network`;
  const swr = Number((cc.match(/stale-while-revalidate=(\d+)/) || [])[1] ?? 0);
  if (age <= maxAge + swr) return `STALE-BUT-USABLE → serve stale NOW, revalidate in background`;
  return `STALE (${age}s > ${maxAge}s) → revalidate: If-None-Match ${entry.etag} (hope for 304)`;
}

const scenarios = [
  ['app.3f9c2.js (hashed)', { storedAt: 0, etag: '"x1"', cacheControl: 'public, max-age=31536000, immutable' }, 86400 * 30],
  ['index.html',            { storedAt: 0, etag: '"h7"', cacheControl: 'no-cache' },                             60],
  ['/api/cats',             { storedAt: 0, etag: '"c3"', cacheControl: 'private, max-age=30' },                  10],
  ['/api/cats (later)',     { storedAt: 0, etag: '"c3"', cacheControl: 'private, max-age=30, stale-while-revalidate=60' }, 45],
  ['first ever visit',      null, 0],
];
for (const [name, entry, now] of scenarios)
  console.log(name.padEnd(22), '→', decide(entry, now));
console.log('\nthe whole system: freshness answers "may I skip the network?",');
console.log('ETags answer "may I skip the DOWNLOAD?" — two different savings.');

      

      
five headers, five behaviors — this decision runs for every resource you ship

      

    

    

      
// quiz — first pick is the one that counts

      
An API sets Cache-Control: no-cache believing responses won't be stored, and a shared machine's disk cache turns out to contain users' account data. What went wrong?

      

        
        
        
        
      

      
Why: the two worst-named directives in the platform: no-cache = cache-but-verify; no-store = what everyone thinks no-cache means.     •

    • 
        
  • The layered answer ties it together: this section is layer 1 of fesd's cake — same grammar the CDN (aws edge) obeys, because the CDN is just a shared cache reading your headers.

Cookies & storage — attributes that are security decisions

      
intermediate → HttpOnly, Secure, SameSite: three flags, three attack classes

    

  

  

    
A cookie is a small key=value the browser attaches automatically to matching requests — that automation is both its power (sessions just work) and its danger (§10's CSRF is literally "the automation, abused"). Its attributes are security decisions, one attack each: HttpOnly — JS can't read it → stolen-by-XSS-script is off the table (the reason session tokens live in HttpOnly cookies, node §auth's rule); Secure — HTTPS only → no plaintext leak on hostile WiFi; SameSite — Lax (default: not sent on cross-site subrequests/POSTs; sent on top-level navigation) vs Strict vs None (sent always — third-party/embedded use, must pair with Secure) → CSRF's mitigation-by-default; plus Domain (share across subdomains — the wider, the riskier), Path, and Max-Age/Expires (session vs persistent).

    
The rest of the storage menu, priced: localStorage — synchronous (blocks the main thread!), ~5MB, string-only, per-origin, readable by any JS on the page (never tokens — XSS reads it trivially, the exact hole HttpOnly closes); sessionStorage — same but per-tab; IndexedDB — async, big, structured (the offline module's outbox lives here); and the fesd rule of thumb: cookies for what the SERVER needs on every request, storage for what the CLIENT needs between visits.

    

      
// quiz — first pick is the one that counts

      
A teammate moves the JWT from an HttpOnly cookie to localStorage "so the SPA can read the expiry". Grade the trade.

      

        
        
        
        
      

      
Why: the threat model decides: XSS-steals-token (catastrophic, silent, works offline) vs CSRF-rides-cookie (mitigated by SameSite=Lax + CSRF tokens, §10). Option C isn't wrong about the CSRF asymmetry — it's wrong about the exchange rate: trading a mitigated risk for an unmitigated worse one. The pattern that keeps both: HttpOnly cookie for the credential + a readable "session info" blob (expiry, username) for the UI. Needing app-visible expiry never requires app-visible secrets.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • __Host- cookie name prefix = Secure + no Domain + Path=/ enforced by the browser — the modern hardened session cookie; naming it is rare and lands.
    • 
        
  • Cookies travel on EVERY matching request (upload bandwidth per image request!) — why asset domains/CDN subdomains historically went cookieless; HTTP/2 header compression softened it, habit remains.
    • 
        
  • Third-party cookie deprecation reshaped the embedded world (CHIPS/partitioned cookies as the successor) — an honest "still settling" is the current answer.
    • 
        
  • localStorage is synchronous — a 2MB read during interaction is a main-thread stall (fesd's INP budget); IndexedDB or async wrappers for anything bulky.
    •

CORS, the whole dance — who's protected, who consents

      
intermediate → same-origin policy, preflights & the debugging playbook

    

  

  

    
Get the direction right and CORS stops being mysterious: the same-origin policy protects users — evil.com's JS must not read your bank's API using your cookies — so browsers block cross-origin reads by default. CORS is the server's consent mechanism: response headers (Access-Control-Allow-Origin et al.) telling the browser "this origin may read me". It protects nothing server-side (curl ignores it entirely — authorization is still your job, node §auth); it's the browser refusing to hand YOUR credentialed responses to OTHER people's pages.

    
The preflight: requests beyond "simple" (methods beyond GET/POST-with-simple-content-types, custom headers like Authorization, JSON content-type) trigger an OPTIONS ask-first — "may this origin send DELETE with these headers?" — answered with Allow-Methods/-Headers/Max-Age (cache the permission!). Credentialed requests tighten everything: credentials: 'include' requires Allow-Credentials: true AND an exact (never *) Allow-Origin.

    

      

        
preflight-decider.js — run it (the browser's CORS logic)

        
function cors(req, res) {
  const simpleMethod = ['GET', 'HEAD', 'POST'].includes(req.method);
  const simpleCT = !req.contentType || ['text/plain', 'application/x-www-form-urlencoded', 'multipart/form-data'].includes(req.contentType);
  const preflight = !(simpleMethod && simpleCT && !req.customHeaders);
  const steps = [preflight ? `preflight: OPTIONS first (Max-Age caches the yes)` : 'simple: request goes straight out'];
  const originOk = res.allowOrigin === req.origin || (res.allowOrigin === '*' && !req.credentials);
  if (!originOk) steps.push(`✗ BLOCKED reading: Allow-Origin is ${res.allowOrigin ?? 'missing'}${req.credentials && res.allowOrigin === '*' ? ' (wildcard + credentials = forbidden combo)' : ''}`);
  else if (req.credentials && !res.allowCreds) steps.push('✗ BLOCKED: credentials sent but no Allow-Credentials: true');
  else steps.push('✓ response readable');
  return steps.join('  →  ');
}

const api = { allowOrigin: 'https://app.example.com', allowCreds: true };
console.log('same-app JSON POST w/ cookie:\n ',
  cors({ origin: 'https://app.example.com', method: 'POST', contentType: 'application/json', credentials: true }, api));
console.log('form POST, no custom headers (the "simple" carve-out):\n ',
  cors({ origin: 'https://app.example.com', method: 'POST', contentType: 'application/x-www-form-urlencoded' }, api));
console.log('evil.com tries to read with the victim\'s cookie:\n ',
  cors({ origin: 'https://evil.example.net', method: 'GET', credentials: true }, api));
console.log('public API, wildcard, anonymous:\n ',
  cors({ origin: 'https://anyone.dev', method: 'GET' }, { allowOrigin: '*' }));
console.log('wildcard + credentials (the config that never works):\n ',
  cors({ origin: 'https://app.example.com', method: 'GET', credentials: true }, { allowOrigin: '*' }));
console.log('\nnote the form POST skipping preflight — that legacy carve-out is WHY CSRF (§10) exists.');

      

      
five configs, five verdicts — including the wildcard trap and the CSRF-shaped hole

      

    

    

      
// quiz — first pick is the one that counts

      
"CORS error in the console — so I'll bypass it by proxying through my own backend." When is that legitimate vs a smell?

      

        
        
        
        
      

      
Why: CORS guards the user's browser credentials, not the API — your server fetching a third-party API is the normal integration pattern (their key stays server-side, node §security's secrets rule). But proxying your OWN api-to-frontend gap means you didn't understand whose consent was missing — configure Allow-Origin for your known origins and keep the architecture flat. The question tests whether you know WHAT CORS protects; the answer's shape follows from that alone.

Forms & uploads — the platform's original POST

      
intermediate → encodings, multipart & the upload path

    

  

  

    
A native form POST sends one of two encodings: application/x-www-form-urlencoded (key=value&… — §02's percent-encoding as a body) or multipart/form-data (the one that carries files: each field its own part with headers, separated by a boundary string — inspect one in devtools once and uploads stop being magic). The modern JS side speaks the same language: new FormData(formEl) harvests a form (files included), fetch sends it — and the classic bug: manually setting Content-Type on a FormData fetch destroys the auto-generated boundary; let the browser write that header.

    
The upload path at scale is an architecture decision you've already met from two sides: small files can transit your server (multer-style streaming — node §backpressure applies); big files go direct-to-storage with a presigned URL (aws §s3 — your server issues the pass, bytes bypass it entirely), with resumable/chunked protocols (tus, multipart-upload) once networks get hostile. And native form behaviors worth keeping: a plain form POST works before JS loads (progressive enhancement — react §forms' actions lean into exactly this), and enctype/validation attributes are free behavior you'd otherwise rebuild.

    

      
// quiz — first pick is the one that counts

      
fetch('/upload', { method: 'POST', headers: { 'Content-Type': 'multipart/form-data' }, body: formData }) — the server says "no boundary" and parses nothing. Why?

      

        
        
        
        
      

      
Why: multipart's Content-Type is multipart/form-data; boundary=----Web…{random} — the boundary is generated per-request alongside the body; writing the header by hand ships a body whose separator the header doesn't name. It's the single most-Googled upload bug, and its lesson generalizes: some headers are owned by the payload encoder (Content-Length from node §buffers is the same family) — set the data, not the bookkeeping.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Upload UX needs progress — fetch can't report upload progress (streams landed partially); XHR's upload.onprogress or chunked uploads are still the honest answers.
    • 
        
  • Validate uploads server-side by CONTENT (magic bytes), never by extension or client MIME — the security module's boundary rule with a file-shaped payload.
    • 
        
  • File inputs are uncontrolled always (react §forms said it) — the platform forbids JS setting file values; a security boundary you design around, not against.
    • 
        
  • The "simple request" CORS carve-out (§08) exists BECAUSE forms could always POST cross-origin — the web's backward compatibility is the origin story of half its security quirks (§10 completes this thought).

XSS, CSRF & CSP — the web's three-body security problem

      
advanced → each attack, its mechanism, its layered defense

    

  

  

    
XSS — attacker's script runs in YOUR page's origin (reading storage, riding sessions, §07's nightmare). Mechanism: user data concatenated into HTML becomes markup (§02's injection family, HTML edition). Defenses in layers: output encoding by default (textContent, framework escaping — React does this unless you invoke the honestly-named dangerouslySetInnerHTML), sanitization (DOMPurify) for rich content, and CSP as the backstop: Content-Security-Policy: script-src 'self' means even injected <script> won't execute — the blast-radius cap for the day the first layers miss. CSRF — evil.com auto-submits a form to your bank; the browser attaches the session cookie (§07's automation, §09's legacy carve-out — the attack is the platform's own features composed). Defenses: SameSite=Lax (the default now — most CSRF died with it), CSRF tokens for what remains, and never mutating on GET. 

    

      

        
escape-or-execute.js — run it (XSS mechanics, safely inert)

        
// a "comment" from a hostile user
const comment = '<img src=x onerror="stealCookies()"> nice cat!';

// PATH 1 · innerHTML-style: data becomes MARKUP (simulated parse)
function naiveRender(html) {
  const tags = [...html.matchAll(/<(\w+)[^>]*?(onerror|onload|onclick)=/g)];
  return tags.length
    ? `parsed: <${tags[0][1]}> element WITH ${tags[0][2]} handler → attacker code runs in YOUR origin`
    : 'parsed: no executable content';
}
console.log('innerHTML path:  ', naiveRender(comment));

// PATH 2 · escape at output — the five characters that end XSS
const escapeHtml = (s) => s.replace(/[&<>"']/g, (c) =>
  ({ '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;' })[c]);
const escaped = escapeHtml(comment);
console.log('escaped output:  ', escaped);
console.log('re-parsed:       ', naiveRender(escaped), '(it renders as TEXT — the picture of an attack)');

// PATH 3 · CSP as the backstop, simulated
function csp(policy, scriptOrigin) {
  const allowed = policy['script-src'] ?? [];
  return allowed.includes(scriptOrigin) ? 'executes' : `BLOCKED by CSP (script-src ${allowed.join(' ')})`;
}
console.log('\ninjected inline script under CSP:', csp({ 'script-src': ["'self'"] }, "'unsafe-inline'"));
console.log('your own bundle under CSP:       ', csp({ 'script-src': ["'self'"] }, "'self'"));
console.log('\nlayered: escape by default, sanitize rich input, CSP for the miss you didn\'t see.');

      

      
the same string as markup vs text vs CSP-blocked — three layers, one attack

      

    

    

      
// quiz — first pick is the one that counts

      
With SameSite=Lax as the browser default, is CSRF "solved"? What's the honest residual?

      

        
        
        
        
      

      
Why: Lax's carve-out (cookies ride top-level navigations) is exactly why "GET /transfer?to=evil" is still a link away — the old "never mutate on GET" rule became a security invariant, not a style point. Defense-in-depth thinking (default + explicit token + method discipline) is what the question grades; "the browser fixed it" and "nothing changed" both fail it. Naming same-site vs same-origin as different boundaries is the bonus point.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • CSP rollout like a pro: Content-Security-Policy-Report-Only first, watch violation reports, then enforce — the flag-rollout pattern (fesd §10) for a header.
    • 
        
  • Clickjacking gets one line: frame-ancestors 'none' (CSP's successor to X-Frame-Options) — the invisible-iframe-over-the-button attack, deleted.
    • 
        
  • DOM XSS (source → sink inside JS: location.hash into innerHTML) never touches the server — Trusted Types is the platform's answer; naming it is current.
    • 
        
  • The unifying theory, once more: XSS = data becoming code (HTML), SQLi = data becoming code (SQL), param injection = data becoming code (URL) — "keep data and structure in separate channels" is the whole genre's cure.

Web auth flows — sessions, OAuth & passkeys, drawn once

      
advanced → the platform view of who-are-you

    

  

  

    
The platform's auth story in three eras, each solving the previous one's weakness. Sessions (the workhorse): credentials → server-side session → HttpOnly+Secure+SameSite cookie carries the id → §07's attributes ARE the security model (node §auth owns the server half). OAuth 2 + OIDC (delegation): "let Google vouch" — the authorization-code + PKCE dance (node §authplus walks it step by step); the platform-level insight is WHERE tokens may safely exist: codes in URLs (one-time, §02's fragment lesson), tokens in POST responses, credentials in HttpOnly cookies — each artifact placed by its leak-resistance. Passkeys/WebAuthn (the current shift): a keypair per site, private key in the device's secure enclave, login = signing a server challenge — phishing-resistant by construction (the signature binds to the origin §02 — a lookalike domain gets a useless signature; no shared secret exists to steal or reuse). Password reuse, credential stuffing (node §security's attack), and phishing all target the shared-secret model; passkeys delete the shared secret.

    

      
// quiz — first pick is the one that counts

      
Why can't a pixel-perfect phishing site at shelter-login.example.net steal a passkey login the way it steals passwords?

      

        
        
        
        
      

      
Why: passwords fail because humans authenticate the site by LOOKS while secrets work anywhere they're typed. WebAuthn moves the origin check from human eyes to the browser+authenticator (which never lie about §02's origin) — the phishing site can render anything it wants; it cannot make your device sign for an origin it didn't register. Biometrics (A) only unlock the local key — the anti-phishing property is the origin binding. This is THE modern auth question; the origin-scoping answer is the whole point.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The placement table, recited: session id → HttpOnly cookie; OAuth code → URL (once, short-lived); access token → memory; refresh token → HttpOnly cookie with rotation (node §authplus's tripwire). Every artifact, one home, one reason.
    • 
        
  • SSO ≠ OAuth: OIDC is the identity layer; SAML is its enterprise ancestor — one sentence each places you in bigger orgs.
    • 
        
  • Logout is a real design problem: cookie cleared ≠ session dead (server-side revocation), and OIDC single-logout is famously messy — honesty here reads as experience.
    • 
        
  • Password guidance is now boring on purpose: length over complexity rules, breach-list checks, rate limits (node §security) — and "we're rolling out passkeys alongside" is the 2026 answer.

Polling, SSE & WebSockets — the live-data decision, priced

      
advanced → pick by direction, frequency & infrastructure tax

    

  

  

    
The decision inputs: direction (server→client only, or both?), frequency (updates per minute or per second?), and infrastructure tax (what do proxies/LBs/serverless make hard?). The menu: polling — dumb, robust, cache-friendly, latency = interval (fine for "check every 30s"); long-polling — hold the request until data exists (low latency without new protocols — the compatibility champion); SSE — one HTTP response that never ends, text/event-stream, auto-reconnect with Last-Event-ID built into the browser's EventSource (server→client done RIGHT: notifications, feeds, AI token streams — the chat-UI standard); WebSockets — full duplex over one upgraded TCP connection (§nb-13 owns the server half: heartbeats, fan-out, per-connection memory) — earned only by bidirectional + frequent (chat typing, games, collaborative cursors).

    

      

        
transport-picker.js — run it (cost model per pattern)

        
// requests/hour + worst-case staleness per transport, for one client
function price(updatesPerHour, pollSeconds) {
  const polls = 3600 / pollSeconds;
  return {
    polling:  { reqPerHr: Math.round(polls), worstLagSec: pollSeconds, conns: 0 },
    longPoll: { reqPerHr: updatesPerHour + Math.ceil(updatesPerHour * .1), worstLagSec: '~0', conns: '1 held' },
    sse:      { reqPerHr: 1, worstLagSec: '~0', conns: '1 held' },
    ws:       { reqPerHr: 1, worstLagSec: '~0', conns: '1 held (duplex)' },
  };
}
console.log('scenario: order-status page, ~2 real updates/hour, 30s polling:');
Object.entries(price(2, 30)).forEach(([k, v]) => console.log(' ', k.padEnd(9), JSON.stringify(v)));

console.log('\n120 polls/hr to learn about 2 changes — 98% waste, but ZERO special infra.');
console.log('SSE: 1 connection, instant, auto-reconnecting — and it is "just HTTP" (CDN/proxy friendly-ish).');
console.log('WS earns its §nb-13 operational tax only when the CLIENT also talks constantly.');
console.log('\nthe senior answer names the escalation: poll → SSE when latency matters → WS when duplex does.');

      

      
98% waste vs 1 held connection — the whole trade in two numbers

      

    

    

      
// quiz — first pick is the one that counts

      
An AI chat UI streams tokens server→client. The team reaches for WebSockets "because it's real-time". The calibrated pushback?

      

        
        
        
        
      

      
Why: "real-time" isn't one requirement — direction and frequency are. Chat COMPLETIONS are a server monologue: the request goes up once (normal POST), tokens flow down (a stream) — which is why every major AI API ships SSE/readable streams, not sockets. Choosing the cheapest transport that satisfies the actual arrows is the fesd real-time lesson; knowing the industry converged the same way is the receipt.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • SSE's fine print: text-only, one direction, and (pre-HTTP/2) the 6-connection-per-host limit bit multi-tab apps — multiplexing (§03) mostly retired that footnote.
    • 
        
  • Resumability is the under-asked follow-up: Last-Event-ID (SSE) vs sequence numbers over WS (the fesd/chat catch-up pattern) — missed-message strategy IS the design.
    • 
        
  • Serverless changes the answer: held connections and function timeouts fight — managed layers (or SSE with re-request) are the workaround; naming the tension is the ops-aware move.
    • 
        
  • Escalation as architecture: ship polling day one, SSE when users notice lag, WS when the product grows a second direction — the "upgrade on pain" doctrine, transport edition.

The reasoning gym — nine questions, three tiers

      
all levels → transfer, not recall: every question is an inference

    

  

  

    
The gauntlet (§13) composed layers; the gym trains the reasoning moves themselves. Warm-up pits one concept against its favorite misconceptions, apply makes you trace timelines and predict verdicts before the network tab does, stretch chains sections under constraints — the cats will be counting round trips. First pick is the recorded one, and the "why" under each answer is the actual lesson: read it even when you're right.

    

      
// warm-up 1 of 3 — cache freshness verdicts

      
A cat-photo CDN serves mochi.jpg with Cache-Control: public, max-age=600. The user views the page, clicks away, and clicks back 300 seconds later. What does the browser do for mochi.jpg?

      

        
        
        
        
      

      
Why: §06's two savings, kept distinct: freshness answers "may I skip the network?", ETags answer "may I skip the download?" — and revalidation only starts once freshness runs out. Option A tempts because "check with the server first" feels safe, but that round trip is exactly what max-age exists to delete; D invents a HEAD-check dance the HTTP cache never performs; B underestimates the cache — it serves ordinary navigations all day. The honest footnote: a user-initiated reload revalidates even fresh entries, which is precisely the behavior immutable was invented to switch off.

    

    

      
// warm-up 2 of 3 — preflight or not

      
Four cross-origin requests leave https://app.shelter.example.com for https://api.example.net. Which ONE triggers a preflight OPTIONS first?

      

        
        
        
        
      

      
Why: the trigger test is "could a 1998 form or tag have sent this?" (§08, §09): simple methods + safelisted headers + form content types go straight out — that legacy carve-out is why CSRF exists (§10) — while anything beyond (custom headers like Authorization, JSON content-type, DELETE) needs consent first. B tempts because POST feels dangerous, but the urlencoded body is exactly the shape forms always sent; C confuses embedding (no CORS read involved) with reading; D confuses "cross-origin" with "non-simple" — cross-origin GETs fly without preflight and only the READ is gated. Method AND headers AND content-type decide — never the verb alone, never the origin alone.

    

    

      
// warm-up 3 of 3 — cookie flags vs attacks

      
A session cookie ships as session=…; Secure; SameSite=Strict — but someone forgot HttpOnly. Which attack does this configuration still leave wide open?

      

        
        
        
        
      

      
Why: §07's flags are not overlapping layers of the same strength — each closes exactly one door: Secure vs wiretaps, SameSite vs CSRF's cookie-riding (§10), HttpOnly vs script reads. A tempts because CSRF is the famous cookie attack — but Strict is the strongest anti-CSRF setting the platform has; B is Secure's whole job, already done; C is the deadly instinct that flags are fungible quantity rather than one-per-attack. Grade a cookie by which doors are still open, not by how many flags it wears.

    

    

      
// apply 1 of 3 — trace the cache timeline

      
/api/cats responds with Cache-Control: max-age=60, stale-while-revalidate=120 and ETag: "v1", stored at t=0. The page re-requests it at t=90 and again at t=200. What happens at each?

      

        
        
        
        
      

      
Why: two windows, three behaviors — §06's decider, replayed by hand: age ≤ 60 is fresh (skip the network), 60 < age ≤ 180 is stale-but-usable (skip the WAIT, not the request — the response is served now and the revalidation happens behind it), past 180 the latency-hider is gone and revalidation blocks. A collapses SWR into plain staleness, losing its entire point (instant response, paid for with a briefly stale one); C promotes SWR to freshness — but the background fetch at t=90 absolutely happens, that's the "revalidate" half — and ETags never expire, they get compared. D sells browsers short: they implement it, which is how the latency-hiding lands client-side at all.

    

    

      
// apply 2 of 3 — predict the CORS verdict

      
From https://app.shelter.example.com: fetch('https://api.example.net/cats/9', { method: 'DELETE', credentials: 'include' }). The API answers the preflight with Access-Control-Allow-Origin: *, Access-Control-Allow-Methods: DELETE, Access-Control-Allow-Credentials: true. What actually happens?

      

        
        
        
        
      

      
Why: two steps to the verdict: DELETE is non-simple, so OPTIONS goes first — and the answer contains the one forbidden combination, wildcard + credentials (§08's runner called it "the config that never works"), so the check dies at the preflight. B is the near-miss worth savoring: "the server executed it anyway" IS true for simple requests — there the browser blocks the read, not the send, which is the CSRF-shaped hole §10 lives in — but preflighted requests are stopped BEFORE sending; that asymmetry is the whole question. C reads headers as a checklist without knowing the wildcard rule; D invents a requirement — no custom headers were sent, so Allow-Headers has nothing to permit. The fix: echo the exact origin, keep Allow-Credentials, never *.

    

    

      
// apply 3 of 3 — order the cold load

      
First-ever visit to https://shelter.example.com — nothing cached at any layer. Which timeline is the physically possible one?

      

        
        
        
        
      

      
Why: each wrong order is impossible for a nameable reason: you can't handshake a connection that doesn't exist to an address you haven't resolved (A); sending the request before TLS completes would put the path, headers and cookies on the wire in plaintext — HTTPS never does request-then-encrypt (B); and parsing is STREAMING (§01) — the parser, plus the preload scanner running ahead of it, starts on the first chunks, which is why early <link> and <script> tags begin fetching while the HTML is still downloading. D's wait-for-the-whole-file throws away the network's best overlap. This is §13's five-word spine with every arrow justified — the version that survives follow-up questions.

    

    

      
// stretch 1 of 3 — spot the false claim

      
Four claims from four corners of the module. Exactly one is FALSE — which?

      

        
        
        
        
      

      
Why: HttpOnly hides the cookie from document.cookie — a defense against XSS theft (§10) — but the browser still attaches it to every matching request, cross-site ones included; attachment behavior belongs to SameSite. The claim seduces because both flags live in the same Set-Cookie line and both "restrict the cookie" — but they restrict different verbs: HttpOnly restricts READING, SameSite restricts SENDING. The other three are true and worth owning: 304's empty body is the entire economy of revalidation, CORS being browser-enforced is why it protects users rather than servers (curl was §08's proof), and private is exactly the browser/CDN split.

    

    

      
// stretch 2 of 3 — price the revalidation tax

      
A page ships 40 hashed assets (app.3f9c2.js-style). Config A: assets get max-age=31536000, immutable, HTML gets no-cache. Config B: everything gets no-cache. A user returns tomorrow; nothing was deployed. Roughly what does each config cost on the network?

      

        
        
        
        
      

      
Why: no-cache stores just fine (§06's misnomer, claiming its victim in B) but revalidates per use — and a 304 saves the DOWNLOAD, never the ROUND TRIP, which is the distinction A's "cached = free" instinct misses. That gap is the entire reason content hashing exists: move each asset's version into its NAME so one always-checked pointer can vouch for 40 never-checked files — C then overshoots by exempting the pointer itself, leaving users stuck on old HTML until the cache evicts it. HTTP/2 multiplexing (§03) softens B — the 41 requests share one connection — but header bytes, server hits and revalidation latency remain, multiplied by every return visit. Count the round trips before trusting the vibe: that's the estimation habit.

    

    

      
// stretch 3 of 3 — storage under constraints

      
Offline drafts for the shelter's volunteer notes: ~20MB of structured drafts per device, reads and writes must never stutter typing, and none of it should ride to the server on every request. Pick the store.

      

        
        
        
        
      

      
Why: run the constraints as a checklist against §07's priced menu: localStorage fails twice — its ~5MB-class quota can't hold 20MB, and every access is synchronous on the main thread, so bulk reads land exactly in the keystroke path (§01's jank, fesd's INP budget); cookies fail harder — a few KB apiece AND attached to every matching request, the "server needs it on each request" tool abused as a database; sessionStorage shares localStorage's quota class and its per-tab lifetime deletes the drafts with the tab. A and D tempt via API familiarity, C via the word "persistent" — but storage choice is constraint elimination, not API preference, and only one candidate survives all three cuts.
