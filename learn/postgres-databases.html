SQL from zero — describe the result, not the steps

beginner → the reading order that makes queries obvious

A table is a spreadsheet with rules: named, typed columns; one row per fact. SQL is declarative — you describe the result you want and the database plans how to get it. The unlock for reading any query is knowing the execution order, which is NOT the writing order: FROM (get the table) → WHERE (filter rows) → GROUP BY (bundle them) → HAVING (filter bundles) → SELECT (pick columns) → ORDER BY → LIMIT. Read in that order and every confusing query straightens out — including why you can't use a SELECT alias inside WHERE.

first-queries.sql.js — run it (in-page engine)
// the café's cats table — and a tiny engine that runs real clauses
const cats = [
  { id: 1, name: 'Mochi',   age: 4, breed: 'tabby',   visits: 31 },
  { id: 2, name: 'Biscuit', age: 7, breed: 'persian', visits: 12 },
  { id: 3, name: 'Clawdia', age: 2, breed: 'tabby',   visits: 44 },
  { id: 4, name: 'Tuft',    age: 5, breed: 'maine',   visits: 8  },
  { id: 5, name: 'Ziggy',   age: 1, breed: 'tabby',   visits: 27 },
];
const q = (rows) => ({
  where(f)   { return q(rows.filter(f)); },                 // WHERE
  orderBy(k, dir = 'asc') {
    return q([...rows].sort((a, b) =>
      dir === 'asc' ? a[k] - b[k] : b[k] - a[k])); },       // ORDER BY
  limit(n)   { return q(rows.slice(0, n)); },               // LIMIT
  select(...cols) {                                          // SELECT
    return rows.map(r => Object.fromEntries(cols.map(c => [c, r[c]]))); },
  groupBy(k, aggs) {                                         // GROUP BY
    const groups = new Map();
    rows.forEach(r => (groups.get(r[k]) ?? groups.set(r[k], []).get(r[k])).push(r));
    return [...groups].map(([key, rs]) => ({ [k]: key,
      ...Object.fromEntries(Object.entries(aggs).map(([name, f]) => [name, f(rs)])) }));
  },
});

// SELECT name, visits FROM cats WHERE age > 2 ORDER BY visits DESC LIMIT 2
console.log(q(cats).where(c => c.age > 2).orderBy('visits', 'desc')
  .limit(2).select('name', 'visits'));

// SELECT breed, COUNT(*), AVG(age) FROM cats GROUP BY breed
console.log(q(cats).groupBy('breed', {
  count: rs => rs.length,
  avgAge: rs => +(rs.reduce((s, r) => s + r.age, 0) / rs.length).toFixed(1),
}));
each method IS its clause — the pipeline is the execution order

    

    

      
// quiz — predict the result

      
SELECT breed, COUNT(*) FROM cats WHERE age > 1 GROUP BY breed HAVING COUNT(*) > 1; — with the table above, what comes back?

      

        
        
        
        
      

      
Why: execution order: WHERE filters ROWS before grouping (Ziggy the 1-year-old tabby is gone), GROUP BY bundles what's left (tabby×2, persian×1, maine×1), HAVING filters GROUPS (only tabby ≥ 2). "WHERE is for rows, HAVING is for groups" — the one-liner that answers a whole category of screen questions.

    • 
        
  • COUNT(*) counts rows; COUNT(col) counts non-null values; COUNT(DISTINCT col) counts distinct — a favorite rapid-fire triplet.
    • 
        
  • Window functions in one sentence for now: aggregates that DON'T collapse rows (ROW_NUMBER() OVER (PARTITION BY …)) — the "latest order per user" tool; the drills live in Full-Stack in 48 · PostgreSQL.

Modeling data — each fact lives in exactly one place

      
beginner → keys, relationships, and pragmatic normalization

    

  

  

    
Modeling is deciding what your tables ARE. The compass: every fact stored once, referenced everywhere else. A cat's name lives in cats; the adoption references cat_id — never a copied name that can drift. That's normalization's entire spirit; the numbered normal forms are just increasingly formal ways of saying it.

    
Relationships come in three shapes, and picking the shape IS the modeling: one-to-many (a cat has many vet visits → visits.cat_id foreign key), many-to-many (cats ↔ adopters both sides can have many → a junction table adoptions(cat_id, adopter_id, date) — which conveniently also holds facts about the relationship itself), one-to-one (rare; usually a column, split only for security or width). Foreign keys aren't decoration — the database enforces them: no adoption of cat 999 that doesn't exist, no deleting a cat that has records (unless you chose CASCADE deliberately).

    

      
      
PROFESSOR WHISKERS EXPLAINSThe shelter once wrote each cat's name on every form she ever touched. Mochi got renamed ("Mochi II, Destroyer of Couches") and eleven forms disagreed about who she was. New policy: every cat has ONE card in ONE drawer (her row); every form cites her card number (foreign key). Rename her once, every form is instantly right — because none of them ever held her name, just her number.

    

    

      
schema.sql — the adoption center, modeled

      
CREATE TABLE cats (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  breed      text,
  born_on    date,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE adopters (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE,          -- the referee from node-backend §07!
  name  text NOT NULL
);

-- many-to-many, with facts ABOUT the relationship on the junction row
CREATE TABLE adoptions (
  cat_id     bigint NOT NULL REFERENCES cats(id),
  adopter_id bigint NOT NULL REFERENCES adopters(id),
  adopted_on date NOT NULL DEFAULT CURRENT_DATE,
  fee_paise  integer NOT NULL CHECK (fee_paise >= 0),  -- money = integers!
  PRIMARY KEY (cat_id, adopter_id)
);

-- one-to-many: visits point at their cat
CREATE TABLE vet_visits (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  cat_id  bigint NOT NULL REFERENCES cats(id) ON DELETE CASCADE,
  note    text,
  at      timestamptz NOT NULL DEFAULT now()
);

    

    

      
// quiz — first pick is the one that counts

      
Orders show the price at purchase time. Product prices change. Where does the order's price live?

      

        
        
        
        
      

      
Why: "each fact once" — but the price today and the price you paid are two different facts. Joining to the live price silently rewrites history the day marketing runs a sale. Price-history tables (option 3) are legitimate for analytics but overkill for the receipt. Knowing WHEN copying is correct — snapshot facts vs living references — is the modeling judgment interviews actually probe, way more than reciting normal forms.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Money in integer minor units (paise/cents) or numeric — never float (JS Fundamentals' 0.1+0.2 lives in databases too). Timestamps as timestamptz, stored UTC.
    • 
        
  • UUIDv7 externally / bigint internally is the modern id calibration (the fullstack course's Q&A has the full trade).
    • 
        
  • jsonb is Postgres's escape hatch for genuinely-flexible attributes — "columns for what you query and constrain, jsonb for the ragged edge" is the balanced take.
    • 
        
  • CHECK constraints and NOT NULL are free tests running on every write, forever — model rules into the schema, not just the app.

Joins, finally clear — run the engine yourself

      
the concept everyone half-knows, made visible

    

  

  

    
A join answers "for each row here, which rows there belong to it?" — reuniting the facts that normalization filed in separate drawers. INNER JOIN: only rows with a match on both sides. LEFT JOIN: every left row, matched or not — unmatched ones carry NULLs on the right side (and WHERE right.id IS NULL finds the loners: "cats never adopted" — the anti-join idiom). RIGHT is LEFT mirrored; FULL keeps both sides' loners.

    
Below, a join engine you can read in one breath — nested loops, exactly how databases conceptually start (they upgrade to hash joins when the tables grow: build a Map on the small table, probe with the big one — the DSA cubby wall, again).

    

      

        
join-engine.js — run it

        
const cats = [
  { id: 1, name: 'Mochi' }, { id: 2, name: 'Biscuit' },
  { id: 3, name: 'Clawdia' }, { id: 4, name: 'Tuft' },
];
const adoptions = [
  { cat_id: 1, adopter: 'Prachi', on: '2026-07-01' },
  { cat_id: 3, adopter: 'Raj',    on: '2026-07-15' },
  { cat_id: 1, adopter: 'Amy',    on: '2026-08-01' },  // Mochi, twice? scandal
];

function innerJoin(left, right, match) {
  const out = [];
  for (const l of left)
    for (const r of right)              // nested loop join, honestly
      if (match(l, r)) out.push({ ...l, ...r });
  return out;
}
function leftJoin(left, right, match) {
  const out = [];
  for (const l of left) {
    const matches = right.filter(r => match(l, r));
    if (matches.length) matches.forEach(r => out.push({ ...l, ...r }));
    else out.push({ ...l, adopter: null, on: null });   // kept, with NULLs
  }
  return out;
}

const on = (c, a) => c.id === a.cat_id;
console.log('INNER (adopted cats only):');
console.table ? console.log(innerJoin(cats, adoptions, on)) : null;
console.log('LEFT (every cat, adopted or not):');
console.log(leftJoin(cats, adoptions, on));
console.log('anti-join — never adopted:',
  leftJoin(cats, adoptions, on).filter(r => r.adopter === null).map(r => r.name));
// note Mochi appears TWICE in the joins — one output row per match.
// that row multiplication is also why joining then COUNTing needs care.

      

      
watch Biscuit & Tuft survive only the LEFT join — as NULL rows

      

    

    

      
// quiz — first pick is the one that counts

      
"List every cat with their adoption count, including never-adopted cats as 0" — which query shape?

      

        
        
        
        
      

      
Why: two traps in one question. INNER drops never-adopted cats entirely (no row, not zero). And after LEFT JOIN, COUNT(*) counts the NULL row as 1 — you must count a right-side column (COUNT(a.cat_id)), because COUNT(col) skips NULLs (§01's triplet paying off). This exact query — with this exact bug — appears in real screens constantly.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Join algorithms in a sentence each: nested loop (small × indexed), hash join (big × big equality), merge join (both pre-sorted). You never pick — the planner does — but naming them explains EXPLAIN output.
    • 
        
  • Row multiplication discipline: joining one-to-many then aggregating the "one" side's numbers double-counts — aggregate in a subquery/CTE first, then join. War-story material.
    • 
        
  • Self-joins (employees → managers) and the N-versus-1 shape of every "…with their latest X" query (window function or lateral join) — recognize, don't fear.

    04
    

      
Indexes & EXPLAIN — seconds into milliseconds

      
the highest-leverage performance skill in your stack

    

  

  

    
Without an index, WHERE email = ? reads every row — a sequential scan, O(n) with disk I/O. An index is a B-tree (the BST from the DSA track, widened so each node fills a disk page — hundreds of keys per node, so a billion rows is ~4 hops) mapping column values → row locations. The same structure is why an index also accelerates ORDER BY, range scans, and (for a composite index on (a, b)) any query filtering on a or a AND b — but not b alone: it's a phone book sorted by last-then-first name, useless for finding all Rajs.

    
The price: every write updates every index on the table, and each one consumes cache. So: index your foreign keys and real query patterns; don't collect them. And the tool that ends guessing: EXPLAIN ANALYZE — it prints the plan (Seq Scan vs Index Scan, join algorithm, row estimates vs reality) and actual timings. The ritual: reproduce → EXPLAIN → look for Seq Scans on big tables and estimate-vs-actual gaps → index or rewrite → EXPLAIN again.

    

      

        
index-vs-scan.js — run it

        
// feel the difference an index makes — 200k row "table"
const N = 200_000;
const emails = Array.from({ length: N }, (_, i) => `cat${i}@cafe.example`);
const rows = emails.map((email, i) => ({ id: i, email, visits: i % 50 }));

// sequential scan: check every row
let t0 = performance.now();
let found;
for (const r of rows) if (r.email === 'cat173456@cafe.example') { found = r; break; }
const scanMs = (performance.now() - t0).toFixed(2);

// "CREATE INDEX ... ON (email)" — build the lookup structure once
t0 = performance.now();
const emailIndex = new Map(rows.map(r => [r.email, r]));   // stand-in for the B-tree
const buildMs = (performance.now() - t0).toFixed(1);

// indexed lookups: no scanning
t0 = performance.now();
for (let i = 0; i < 1_000; i++) emailIndex.get('cat173456@cafe.example');
const lookupMs = ((performance.now() - t0) / 1000).toFixed(4);

console.log(`seq scan, one lookup:  ${scanMs}ms`);
console.log(`build index once:      ${buildMs}ms   ← the write-side cost, paid upfront`);
console.log(`indexed, per lookup:   ${lookupMs}ms  (×1000 runs)`);
console.log('\\nEXPLAIN would say:  Seq Scan on cats  →  Index Scan using cats_email_idx');
console.log('same idea at DB scale: milliseconds vs full-table disk reads');

      

      
the ratio is the lesson — and the build cost is the honest tax

      

    

    

      
// quiz — first pick is the one that counts

      
There's an index on created_at, but WHERE DATE(created_at) = '2026-08-01' still seq-scans. Why, and the fix?

      

        
        
        
        
      

      
Why: the B-tree is sorted by created_at — not by DATE(created_at); the planner can't use an ordering it doesn't have, so any function/cast/concatenation on the indexed column ("non-sargable" predicates) forces a scan. The range rewrite is the everyday fix; expression indexes exist for the cases you can't rewrite. Spotting function-wrapped columns in slow queries is a genuinely bankable production skill.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Composite index order rule: equality columns first, then the range/sort column — (status, created_at) serves "open orders, newest first" perfectly.
    • 
        
  • Covering indexes (INCLUDE) let index-only scans skip the table entirely; partial indexes (WHERE status = 'active') index just the hot slice — two power tools, one line each.
    • 
        
  • "Estimates way off from actuals in EXPLAIN → run ANALYZE (stale statistics)" — the DBA one-liner that sounds like ops experience because it is.

    05
    

      
Transactions — all of it or none of it

      
advanced → ACID, isolation levels, and the race you've already shipped

    

  

  

    
A transaction wraps several statements into one atomic unit: BEGIN … COMMIT, and if anything fails, ROLLBACK — the fee is charged AND the adoption recorded, or neither. That's the A in ACID (with Consistency = constraints hold, Isolation = concurrent transactions don't trample, Durability = committed means on-disk).

    
Isolation is where interviews go: two transactions run at once — what can each see? Read Committed (Postgres default): you see only committed data, but two reads in one transaction can see different worlds (another commit landed between). Repeatable Read: your transaction sees one frozen snapshot. Serializable: as if transactions ran one at a time — Postgres aborts one on conflict, and your code retries it. The practical classic though is the lost update: two requests read balance 100, both add 10, both write 110 — one update vanished. Fixes: atomic writes (SET balance = balance + 10 — let the DB do the math), SELECT … FOR UPDATE row locks, or optimistic version columns.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe treat jar holds 100. Two volunteers both peek (100), both compute "plus ten is 110", both write 110 on the label. Twenty treats went in; the label says ten did. Nobody was careless — the read-think-write shape itself is the bug. Fix one: don't peek — tell the jar "add ten yourself" (atomic update). Fix two: hold the jar while you work (row lock). Fix three: write "…if the label still says 100" (optimistic version check) and redo if not.

    

    

      

        
lost-update.js — run it

        
// simulate the race: read-modify-write vs atomic
const sleep = (ms) => new Promise(r => setTimeout(r, ms));

async function raceWith(strategy) {
  let balance = 100;                      // the treat jar
  const addTen = async () => {
    if (strategy === 'read-think-write') {
      const seen = balance;               // both volunteers peek…
      await sleep(50);                    // …think…
      balance = seen + 10;                // …write. one update dies
    } else {
      await sleep(50);
      balance = balance + 10;             // atomic at write time:
    }                                     // read+add as ONE step (no stale copy)
  };
  await Promise.all([addTen(), addTen()]);
  return balance;
}
console.log('read-think-write:', await raceWith('read-think-write'),
            '← twenty went in, label says ten');
console.log('atomic update:   ', await raceWith('atomic'),
            '← SET balance = balance + 10');

// the SQL, for your hands:
// UPDATE jars SET treats = treats + 10 WHERE id = 1;        -- atomic
// SELECT * FROM jars WHERE id = 1 FOR UPDATE;               -- pessimistic
// UPDATE jars SET treats = 110, version = 2
//   WHERE id = 1 AND version = 1;                          -- optimistic

// quiz — first pick is the one that counts

      
Adopting the LAST adoptable cat: two requests arrive together, both must not succeed. Which fix is wrong?

      

        
        
        
        
      

      
Why: option 3 is the read-think-write shape with extra steps — both requests read 'adoptable' before either writes; the JS check changes nothing (same bug as the JS uniqueness pre-check in node-backend §07). The conditional UPDATE (option 2) is the elegant lock-free answer — the WHERE clause makes check-and-set one atomic statement, and the rowcount tells you who won. All three DB-side options work; the app-side guard alone never does. "The database is the only referee" — twice now, and it'll come up again.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Postgres is MVCC: readers don't block writers (each sees a snapshot) — that's WHY Read Committed behaves as it does, and why long transactions bloat tables (old versions can't be vacuumed).
    • 
        
  • Keep transactions short and never hold one across a network call to a third party — the deadlock/latency multiplier hiding in "just wrap it all".
    • 
        
  • Deadlocks: two transactions locking rows in opposite orders; Postgres detects and kills one — the fix is consistent lock ordering. One sentence, big credit.

Isolation levels — the four anomalies, staged on purpose

      
intermediate → what READ COMMITTED actually promises (and doesn't)

    

  

  

    
Section 05 raced two writers; isolation levels govern what concurrent transactions see. The anomalies, mildest first: dirty read (seeing uncommitted data — Postgres never allows this, even at its floor), non-repeatable read (re-read a row mid-transaction, it changed), phantom read (re-run a query, new rows appeared), serialization anomaly (each transaction consistent alone, nonsense together — two vets each checking "is another vet on duty?" then both leaving). The levels are just which anomalies you accept: READ COMMITTED (Postgres default — each statement sees a fresh snapshot), REPEATABLE READ (whole transaction shares one snapshot), SERIALIZABLE (as if run one at a time — at the price of retry-able serialization failures).

    

      

        
anomaly-theatre.js — run it (two transactions, interleaved)

        
// a tiny versioned table + snapshot machinery (MVCC preview!)
let committed = { mochiWeight: 4.2 };            // the committed truth
const snapshotOf = () => ({ ...committed });

// NON-REPEATABLE READ at READ COMMITTED — each statement re-snapshots
console.log('— READ COMMITTED —');
let stmtSnap = snapshotOf();
console.log('T1 reads weight:', stmtSnap.mochiWeight);
committed = { mochiWeight: 5.0 };                // T2 commits an update between reads
stmtSnap = snapshotOf();                          // T1's NEXT statement: fresh snapshot
console.log('T1 re-reads:    ', stmtSnap.mochiWeight, ' ← changed mid-transaction (allowed here)');

// REPEATABLE READ — one snapshot for the whole transaction
console.log('\n— REPEATABLE READ —');
committed = { mochiWeight: 4.2 };
const txSnap = snapshotOf();                      // taken ONCE at first read
console.log('T1 reads weight:', txSnap.mochiWeight);
committed = { mochiWeight: 5.0 };                 // T2 commits again
console.log('T1 re-reads:    ', txSnap.mochiWeight, ' ← stable — same snapshot');

// SERIALIZATION ANOMALY — consistent alone, nonsense together
console.log('\n— the on-duty vets (needs SERIALIZABLE to prevent) —');
const duty = { vetA: true, vetB: true };
const aSees = { ...duty }, bSees = { ...duty };   // both read the same start state
if (aSees.vetB) duty.vetA = false;                // A: "B is here, I can leave"
if (bSees.vetA) duty.vetB = false;                // B: "A is here, I can leave"
console.log('vets on duty after both "safe" departures:', duty,
  '← both gone. SERIALIZABLE would abort one with a retry error.');

      

      
three isolation behaviors from one snapshot mechanic — MVCC is next

      

    

    

      
// quiz — first pick is the one that counts

      
A monthly report transaction reads the orders table many times over 3 minutes and the numbers must be mutually consistent. Minimum isolation level?

      

        
        
        
        
      

      
Why: at READ COMMITTED, page 1's totals and page 9's details can describe different moments (orders committed in between) — the report disagrees with itself. REPEATABLE READ freezes the world without locking it (MVCC magic, next section). SERIALIZABLE adds write-conflict machinery a read-only report doesn't need — though a read-only transaction at RR is so cheap the "over-provision" is forgivable; saying that nuance wins the point.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Postgres's READ COMMITTED already prevents dirty reads — its four levels are really three behaviors; "the floor is higher than the SQL standard's" is a nice precision flex.
    • 
        
  • SERIALIZABLE means your code must retry — error 40001 is a feature; a retry loop with backoff is part of adopting it, not an afterthought.
    • 
        
  • The §05 lost-update race is not fixed by RR alone — a concurrent write to the same row at RR throws a serialization failure instead of losing the update. Different failure, still needs handling. Connecting the two sections is the depth.
    • 
        
  • "Which level do you actually run?" — READ COMMITTED + explicit locking/atomic updates where it matters is the industry default answer; name it as a choice, not an accident.

    07
    

      
MVCC & VACUUM — why readers never block writers

      
intermediate → row versions, dead tuples & the bloat story

    

  

  

    
The trick behind those snapshots: Postgres never updates a row in place. An UPDATE writes a new row version and marks the old one as expired (each version carries xmin/xmax — the transaction ids that created and expired it). A snapshot is just a rule for which versions are visible to me. That's MVCC — multi-version concurrency control — and it's why readers never block writers: your report reads yesterday's versions while updates happily write new ones alongside.

    
The bill: expired versions (dead tuples) pile up. VACUUM reclaims them — and autovacuum must keep pace, because bloated tables mean slower scans and, in the worst neglect, transaction-id wraparound (the outage that gets blog posts written). This is also why long-running transactions hurt: VACUUM can't reclaim any version some old snapshot might still need — one forgotten idle-in-transaction connection holds back cleanup for the whole database.

    

      

        
row-versions.js — run it (a table with xmin/xmax, visible)

        
// every UPDATE = new version; nothing is overwritten
let xid = 100;
const versions = [];
const insert = (data) => versions.push({ ...data, xmin: ++xid, xmax: null });
const update = (name, patch) => {
  const live = versions.find(v => v.name === name && v.xmax === null);
  live.xmax = ++xid;                                   // expire the old version
  versions.push({ ...live, ...patch, xmin: xid, xmax: null });
};
const visibleAt = (snapshotXid) =>
  versions.filter(v => v.xmin <= snapshotXid && (v.xmax === null || v.xmax > snapshotXid));

insert({ name: 'Mochi', weight: 4.2 });
const reportSnapshot = xid;                            // report starts HERE
update('Mochi', { weight: 4.5 });
update('Mochi', { weight: 5.0 });

console.log('all stored versions:');
versions.forEach(v => console.log(`  xmin ${v.xmin} xmax ${v.xmax ?? '—'}  ${v.name} ${v.weight}kg`));
console.log('\nreport (old snapshot) sees:', JSON.stringify(visibleAt(reportSnapshot).map(v => v.weight)));
console.log('new transaction sees:      ', JSON.stringify(visibleAt(xid).map(v => v.weight)));

const dead = versions.filter(v => v.xmax !== null && v.xmax <= reportSnapshot).length;
const reclaimable = versions.filter(v => v.xmax !== null).length;
console.log(`\ndead tuples: ${reclaimable} — but VACUUM can only reclaim ${dead} while the report snapshot lives`);
console.log('close the report transaction and all', reclaimable, 'become reclaimable. Idle-in-transaction = bloat.');

      

      
two readers, two answers, zero locks — and the vacuum debt on display

A table gets 100% of its rows UPDATEd hourly. Disk usage triples in a week and scans slow down. The mechanism?

The N+1 story — death by a thousand tiny queries

      
intermediate → the bug every ORM manufactures by default

    

  

  

    
The shape: fetch 50 cats (1 query), then loop rendering each cat's adopter — and the ORM lazily fires one query per cat (N more). 51 round trips where 1–2 would do; page latency = N × (query time + network hop). It hides because each query is fast and the code reads innocently — cat.adopter.name looks like a property, costs a network call.

    
Fixes, in the order to say them: JOIN it in one query when shapes align; batch with WHERE id IN (…) then stitch in memory (two queries total — how DataLoader and every ORM's eager-loading work); and in your ORM, the explicit include/populate/eager syntax that turns lazy N+1 into batched loading. Detection: query logging in dev ("one page = 51 queries" jumps out), APM per-endpoint query counts in prod.

    

      

        
fifty-one-queries.js — run it

        
// a fake DB where every query costs a 5ms round trip
let queryCount = 0;
const db = {
  async cats() { queryCount++; await new Promise(r => setTimeout(r, 5));
    return Array.from({ length: 50 }, (_, i) => ({ id: i, adopterId: i % 7 })); },
  async adopterById(id) { queryCount++; await new Promise(r => setTimeout(r, 5));
    return { id, name: 'adopter-' + id }; },
  async adoptersByIds(ids) { queryCount++; await new Promise(r => setTimeout(r, 5));
    return ids.map(id => ({ id, name: 'adopter-' + id })); },
};

// the N+1 — innocent-looking loop
queryCount = 0;
let t0 = performance.now();
const cats = await db.cats();
for (const cat of cats) {
  cat.adopter = await db.adopterById(cat.adopterId);   // ← one per cat!
}
console.log(`lazy loop:  ${queryCount} queries, ${(performance.now() - t0).toFixed(0)}ms`);

// the batch fix — two queries, stitch in memory
queryCount = 0;
t0 = performance.now();
const cats2 = await db.cats();
const ids = [...new Set(cats2.map(c => c.adopterId))];
const adopters = await db.adoptersByIds(ids);           // WHERE id IN (…)
const byId = new Map(adopters.map(a => [a.id, a]));     // the cubby wall!
cats2.forEach(c => c.adopter = byId.get(c.adopterId));
console.log(`batched:    ${queryCount} queries, ${(performance.now() - t0).toFixed(0)}ms`);

      

      
51 queries vs 2 — and the Map stitch is DSA Foundations again

      

    

    

      
// quiz — first pick is the one that counts

      
When is the JOIN fix WORSE than the two-query batch fix?

      

        
        
        
        
      

      
Why: join output = rows multiplied (§03's warning): 50 cats × 20 visits each with the cat's full row repeated 20 times = a megabyte of redundancy for kilobytes of facts. ORMs often choose two queries for exactly this reason. "Fewest round trips, least redundant data — those trade off and I'd measure" is the complete answer. Also worth one breath: sometimes the TRUE fix is neither — the page didn't need adopters at all (fetch what you render).

Window functions — aggregates that keep the rows

      
intermediate → rank, running totals & top-N-per-group

    

  

  

    
GROUP BY collapses rows into summaries; a window function computes the summary while keeping every row — each row gains a column calculated over its "window" of peers. The grammar: fn() OVER (PARTITION BY … ORDER BY … ) — partition = which rows are peers, order = how the frame walks. The greatest hits: ROW_NUMBER / RANK / DENSE_RANK (positions — differing only in tie-handling), SUM(...) OVER (ORDER BY d) (running totals), LAG / LEAD (the previous/next row's value — month-over-month deltas without self-joins).

    
And the interview classic they unlock: top-N-per-group ("each cat's 2 biggest meals") — rank within partitions in a subquery, filter rn <= 2 outside. The pre-window alternative was a correlated-subquery monstrosity; this is the modern answer, expected on sight.

    

      

        
window-engine.js — run it (OVER, implemented)

        
const meals = [
  { cat: 'Mochi',   day: 1, grams: 40 }, { cat: 'Mochi',   day: 2, grams: 60 },
  { cat: 'Mochi',   day: 3, grams: 50 }, { cat: 'Biscuit', day: 1, grams: 80 },
  { cat: 'Biscuit', day: 2, grams: 30 }, { cat: 'Biscuit', day: 3, grams: 80 },
];

// OVER (PARTITION BY cat ORDER BY grams DESC): rank within each cat
function withWindow(rows, partitionBy, orderBy, fns) {
  const parts = new Map();
  rows.forEach(r => (parts.get(r[partitionBy]) ?? parts.set(r[partitionBy], []).get(r[partitionBy])).push(r));
  const out = [];
  for (const peers of parts.values()) {
    const sorted = [...peers].sort(orderBy);
    let running = 0;
    sorted.forEach((r, i) => {
      running += r.grams;
      out.push({ ...r, ...fns({ row: r, i, sorted, running }) });
    });
  }
  return out;
}

const ranked = withWindow(meals, 'cat', (a, b) => b.grams - a.grams, ({ i, sorted, row }) => ({
  row_number: i + 1,
  rank: 1 + sorted.findIndex(s => s.grams === row.grams),          // ties share rank
}));
console.log('ranked within each cat (by grams desc):');
ranked.forEach(r => console.log(`  ${r.cat.padEnd(8)} day${r.day} ${r.grams}g  row_number ${r.row_number}  rank ${r.rank}`));

console.log('\ntop-2 meals per cat (WHERE row_number <= 2):');
ranked.filter(r => r.row_number <= 2).forEach(r =>
  console.log(`  ${r.cat} day${r.day} ${r.grams}g`));

const runningTotals = withWindow(meals, 'cat', (a, b) => a.day - b.day, ({ running }) => ({ running }));
console.log('\nrunning grams by day (SUM OVER ORDER BY day):');
runningTotals.forEach(r => console.log(`  ${r.cat.padEnd(8)} day${r.day}: ${r.running}g so far`));
console.log('\nnote Biscuit\'s day-1 and day-3 both rank 1 — RANK ties; ROW_NUMBER breaks them arbitrarily.');

CTEs & recursion — named steps, and walking trees in SQL

      
intermediate → WITH as pipeline, WITH RECURSIVE as iteration

    

  

  

    
A CTE (WITH name AS (…)) names a query step so the next step can read it — turning nested-subquery pyramids into a readable top-to-bottom pipeline. Since Postgres 12 they're inlined by the planner (the old "optimization fence" folklore is stale — MATERIALIZED is now an explicit choice when you want the fence).

    
WITH RECURSIVE is the headline: SQL that iterates. Shape: a base case UNION ALL a step that reads the CTE itself, repeating until the step returns no rows — dsa's BFS, wearing SQL. It's THE answer for hierarchies in relational tables: org charts, category trees, "all prerequisites of this course", "everyone Mochi has ever influenced".

    

      

        
recursive-cte.js — run it (the fixpoint loop, visible)

        
// cats and their mentors (an adjacency table — parent_id style)
const mentors = [                       // [student, mentor]
  ['Biscuit', 'Mochi'], ['Beans', 'Mochi'],
  ['Clawdia', 'Biscuit'], ['Tuna', 'Biscuit'], ['Salem', 'Clawdia'],
];

// WITH RECURSIVE lineage AS (
//   SELECT 'Mochi' AS cat, 0 AS depth              -- base case
//   UNION ALL
//   SELECT m.student, l.depth + 1                  -- the step: reads lineage
//   FROM mentors m JOIN lineage l ON m.mentor = l.cat
// ) SELECT * FROM lineage;
function recursiveCTE(root) {
  let result = [{ cat: root, depth: 0 }];           // base case
  let frontier = result;
  let round = 1;
  while (frontier.length) {                          // until the step adds nothing
    const next = [];
    for (const { cat, depth } of frontier)
      for (const [student, mentor] of mentors)
        if (mentor === cat) next.push({ cat: student, depth: depth + 1 });
    if (next.length)
      console.log(`round ${round++}: +${next.map(n => n.cat).join(', ')}`);
    result = result.concat(next);
    frontier = next;                                 // next round reads THIS round
  }
  return result;
}
const lineage = recursiveCTE('Mochi');
console.log('\nfull lineage of Mochi:');
lineage.forEach(l => console.log(`  ${'  '.repeat(l.depth)}${l.cat} (depth ${l.depth})`));
console.log('\n— this is BFS: each UNION ALL round is one ring of the flood.');

      

      
round by round until empty — the dsa BFS flood, running inside "SQL"

Why: the loop only terminates when a round adds nothing — cycles feed it forever. The guards mirror graph-walking guards from dsa: a visited set (SQL: accumulate a path array, filter NOT cat = ANY(path)) or a depth limit. Fun fact worth saying: plain UNION (dedupe) also breaks the cycle — the "for speed" framing is wrong but the mechanism is real; explaining that distinction precisely is a strong moment.

JSONB — documents inside the relational world

      
intermediate → operators, GIN, and when to normalize instead

    

  

  

    
JSONB stores parsed, binary JSON in a column — real document storage with real indexing, which is why "Postgres or MongoDB?" is mostly settled by "Postgres has both shapes". The operator set: -> (get as json) vs ->> (get as text — the one you compare on), @> (containment: does this document include this shape?), ? (key exists), and jsonpath for the ambitious. The power move is a GIN index on the column: containment queries over millions of documents stop being sequential scans — an inverted index (the search-engine structure) over every key and value.

    
The judgment half: JSONB is for genuinely variable shapes — per-integration payloads, user-defined attributes, event envelopes. It is NOT a way to skip schema design: fields you filter on daily, join on, or enforce constraints over belong in columns (constraints, statistics, foreign keys — everything §02 taught — don't reach inside a blob).

    

      

        
containment.js — run it (@> and the inverted index, simulated)

        
const cats = [
  { id: 1, doc: { name: 'Mochi', traits: { vocal: true, lap: true }, tags: ['tabby'] } },
  { id: 2, doc: { name: 'Biscuit', traits: { vocal: false, lap: true }, tags: ['orange','chonk'] } },
  { id: 3, doc: { name: 'Beans', traits: { vocal: true, lap: false }, tags: ['void'] } },
];

// @> containment: does doc include this sub-shape?
function contains(doc, shape) {
  if (Array.isArray(shape)) return shape.every(s => (doc ?? []).some(d => contains(d, s)));
  if (typeof shape === 'object' && shape !== null)
    return typeof doc === 'object' && doc !== null &&
      Object.entries(shape).every(([k, v]) => contains(doc[k], v));
  return doc === shape;
}
const q = { traits: { vocal: true, lap: true } };
console.log(`WHERE doc @> '${JSON.stringify(q)}':`);
cats.filter(c => contains(c.doc, q)).forEach(c => console.log('  hit:', c.doc.name));

// why GIN: invert the documents → (path,value) → row ids
const gin = new Map();
cats.forEach(({ id, doc }) => {
  (function walk(v, path) {
    if (typeof v === 'object' && v !== null && !Array.isArray(v))
      return Object.entries(v).forEach(([k, x]) => walk(x, path + '.' + k));
    const vals = Array.isArray(v) ? v : [v];
    vals.forEach(x => {
      const key = `${path}=${x}`;
      (gin.get(key) ?? gin.set(key, []).get(key)).push(id);
    });
  })(doc, '$');
});
console.log('\nthe GIN index (inverted: value → rows):');
[...gin].slice(0, 6).forEach(([k, ids]) => console.log(`  ${k} → rows [${ids}]`));
console.log('  …');
console.log('\nquery via index: $.traits.vocal=true ∩ $.traits.lap=true =',
  gin.get('$.traits.vocal=true').filter(id => gin.get('$.traits.lap=true').includes(id)),
  '— set intersection, zero documents opened');

Reading EXPLAIN fluently — scans, joins & lying estimates

      
advanced → the plan is a tree; read it bottom-up, argue with its rows=

    

  

  

    
Section 04 ran EXPLAIN; this section makes you fluent. A plan is a tree read bottom-up: leaves fetch (Seq Scan, Index Scan, Index Only Scan — never touches the table, Bitmap Scan — collect matching pages first, then read them in order), inner nodes combine — Nested Loop (for each outer row, probe inner: wants an index, wins for few rows), Hash Join (build a hash of one side: wins for big unsorted sets — dsa's hash maps at work), Merge Join (both sides sorted). The planner picks by cost model: essentially "how many pages will I touch", steered by table statistics.

    
The debugging skill is comparing estimated vs actual: rows=3 estimated, rows=30000 actual means the statistics are stale or the predicate defeats them — and every join above that node inherited a catastrophically wrong strategy (a nested loop probing 30k times). ANALYZE the table, rewrite the un-estimatable predicate, or raise the stats target. Plans aren't read for style points; they're read to find the one node where reality diverged.

    

      

        
cost-crossover.js — run it (why the planner switches scans)

        
// the planner's core arithmetic: pages touched per strategy
const table = { rows: 1_000_000, rowsPerPage: 100 };   // 10,000 pages on disk
const pages = table.rows / table.rowsPerPage;

function seqScanCost() { return pages; }                // read everything, in order
function indexScanCost(selectivity) {
  const matches = table.rows * selectivity;
  const indexPages = Math.ceil(Math.log2(table.rows));  // walk the B-tree
  // each match may live on a DIFFERENT page → random I/O, costed ~4x sequential
  return indexPages + matches * 4;
}

console.log('1M rows, 10k pages — cost in page-reads by % of rows matched:');
console.log('  match%      index-scan      seq-scan     planner picks');
for (const sel of [0.0001, 0.001, 0.01, 0.05, 0.2, 0.5]) {
  const idx = Math.round(indexScanCost(sel));
  const seq = seqScanCost();
  console.log(`  ${(sel * 100).toFixed(2).padStart(6)}%   ${String(idx).padStart(9)}   ${String(seq).padStart(9)}     ${idx < seq ? 'Index Scan' : 'Seq Scan  ← yes, on purpose'}`);
}
console.log('\nthe crossover is why "it ignored my index!" is usually the planner being right:');
console.log('past a few % selectivity, hopping randomly via the index costs MORE than reading it all.');
console.log('(Bitmap scans blur the middle: gather page ids from the index, then read sequentially.)');

      

      
the crossover table explains 80% of "why is Postgres ignoring my index"

The exotic indexes — partial, covering, expression, GIN & BRIN

      
advanced → five specialists beyond the default B-tree

    

  

  

    
Section 04's B-tree answers equality and ranges; the specialists each shrink a specific cost. Partial: index only the rows a predicate keeps (WHERE status = 'pending') — if queries always filter the same slice, why index the 99% you never search? Tiny index, hot cache. Covering (INCLUDE): pack the queried columns into the index so the plan becomes an Index Only Scan — the table itself never opens. Expression: index lower(email) — because §04 taught that functions blind an index; this one is born matching the function. GIN: inverted, for "contains" questions (jsonb §11, arrays, full-text). BRIN: block-range summaries — for huge append-only tables where physical order tracks the column (timestamps), a min/max per block-range is thousands of times smaller than a B-tree and nearly as good.

Zero-downtime migrations — expand, migrate, contract

      
advanced → schema changes while the app keeps serving

    

  

  

    
Two facts make naive migrations outages. One: during a deploy, old and new code run simultaneously — so every schema version must serve both. Two: some DDL takes locks that queue behind (and ahead of) all traffic — an ALTER TABLE waiting on a long transaction blocks every subsequent query on that table: a ten-second lock queue IS an outage. The discipline is expand → migrate → contract: add the new thing (nullable column, new table) while old code ignores it; backfill in batches (one giant UPDATE = lock pressure + MVCC bloat from §07); switch code to write-both-then-read-new; only when nothing reads the old shape, drop it — in a later release.

    
Postgres-specific traps worth naming: adding a column with a volatile default used to rewrite the table (constant defaults are metadata-only since v11); NOT NULL on a big table validates with a full scan (add as CHECK … NOT VALID, then VALIDATE separately — brief lock, long scan without one); and CREATE INDEX CONCURRENTLY — slower, can't run in a transaction, but doesn't block writes: the only acceptable way to index a hot table.

    

      

        
expand-contract.js — run it (the deploy matrix, checked)

        
// renaming users.name → full_name, the zero-downtime way.
// at every step, BOTH code versions must work against the CURRENT schema.
const steps = [
  { schema: 'name',                 codeOld: 'r/w name',        codeNew: 'r/w name' },
  { schema: 'name + full_name',     codeOld: 'r/w name',        codeNew: 'w both, read full_name ?? name' },
  { schema: 'name + full_name (backfilled in batches)', codeOld: 'r/w name', codeNew: 'w both, read full_name' },
  { schema: 'name + full_name',     codeOld: '(retired)',       codeNew: 'r/w full_name only' },
  { schema: 'full_name',            codeOld: '—',               codeNew: 'r/w full_name' },
];
steps.forEach((s, i) => {

// quiz — first pick is the one that counts

      
Why does CREATE INDEX (without CONCURRENTLY) on a busy table cause an incident even though reads "aren't blocked"?

      

        
        
        
        
      

      
Why: the failure cascades: writes queue on the lock → pool exhausts → the app's every request waits for a connection → total outage from a "read-safe" operation. CONCURRENTLY trades build time and a caveat (failed builds leave an INVALID index to drop) for no write lock. The cascade story — lock → pool → everything — is what "senior" sounds like in a migration question, and it's the same resource-exhaustion shape as §11's rate-limiter reasoning.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Always set lock_timeout (~2s) in migrations — better to fail and retry at 3am than to queue the world behind a lock you can't get.
    • 
        
  • Migrations are code: reviewed, versioned, ordered, with a tested down path — and irreversible ones (dropping data) split from reversible ones.
    • 
        
  • The deploy-matrix test generalizes: "old code × new schema, new code × old schema — both must pass" is the one-line spec for any zero-downtime change (APIs included).
    • 
        
  • Big-table column drops are also two-phase: stop reading it, THEN drop later — the column that's "unused since March" is the safe kind of boring.

Scaling Postgres — the ladder before the exotic

      
advanced → pooling, replicas, partitions, and honest limits

    

  

  

    
Postgres scales further than the internet's mythology suggests — but in a specific order. Rung 1 — connection pooling: each Postgres connection is a process; hundreds of serverless functions opening their own = collapse. A pool (app-side, or PgBouncer in front) multiplexes; this is the first thing that breaks in modern deployments and the first thing to say. Rung 2 — query work: indexes, EXPLAIN, killing N+1 (you now own all three). Rung 3 — caching reads that tolerate staleness (Redis, the systems course's cache-aside). Rung 4 — read replicas: writes to the primary, reads fan out over async copies — with replication lag as the price: read-your-own-writes needs the primary (or you show a user their post "missing" right after posting).

    
Rung 5 — partitioning: one logical table split by time/tenant into physical chunks — queries touching one partition fly, old partitions drop instantly (the events-table answer). Rung 6 — sharding: different rows on different servers — real horizontal write scaling, real pain (cross-shard joins and transactions stop being free). The honest close interviews love: "most products never need rung 6; and workloads that do often also want a different tool for that slice — analytics to a warehouse, ephemeral state to Redis — while Postgres stays the system of record."

    

      
// quiz — first pick is the one that counts

      
After adding read replicas, users report: "I updated my profile and the page still shows the old name." Diagnosis and fix?

      

        
        
        
        
      

      
Why: async replication means replicas trail by milliseconds-to-seconds — usually invisible, EXCEPT in the write-then-immediately-read-it-back flow, which is exactly what "save profile → show profile" is. The pattern has a name (read-your-writes consistency) and standard fixes: primary reads for the writing user for N seconds, sticky sessions, or returning the written data in the write response so no read happens at all. This is the #1 replica gotcha in both interviews and production.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Pool sizing sanity: connections ≈ cores × small-multiple, not thousands — "more connections" past saturation makes Postgres slower, not faster.
    • 
        
  • Migrations at scale: expand-and-contract (add nullable → backfill in batches → switch reads → drop later), never a table-locking ALTER at noon. The fullstack course drills the recital version.
    • 
        
  • The "when NOT Postgres" list, calibrated: genuine document-scale-out, cache/ephemeral (Redis), search ranking (Elastic), billions-of-rows analytics (columnar) — "Postgres by default, exceptions by evidence".

§the ideathe sentence to remember

    
      
01SQLRead in execution order — FROM → WHERE → GROUP → HAVING → SELECT → ORDER → LIMIT; WHERE filters rows, HAVING filters groups.

      
02modelingEvery living fact once, referenced by key; snapshot facts (order price) are deliberately copied.

      
03joinsINNER keeps matches, LEFT keeps everyone (NULLs for loners); COUNT the right side's column after a LEFT join.

      
04indexesA B-tree per query pattern: reads fly, writes pay; functions on the column blind the index; EXPLAIN ends the guessing.

      
05transactionsAll or nothing; read-think-write is the race — atomic updates, FOR UPDATE, or version checks. The DB is the only referee.

      
06isolationREAD COMMITTED re-snapshots per statement; REPEATABLE READ freezes the world; SERIALIZABLE makes you retry.

      
07MVCCUPDATE is INSERT + expire; VACUUM is the GC — and one idle transaction holds back the cleanup.

      
08N+11 + one-per-row queries; JOIN or batch + Map-stitch; watch the query count, not the query speed.

      
09windowsAggregates that keep their rows; rank in a subquery, filter rn — top-N-per-group, solved.

      
10CTEsWITH names the steps; WITH RECURSIVE is BFS — base ∪ step until nothing new (guard the cycles).

      
11JSONBColumns for what you filter/join/constrain; JSONB for what genuinely varies; GIN for @>.

      
12EXPLAINRead bottom-up; find the node where actual ≫ estimated — everything above it is collateral.

      
13indexes+Partial, covering, expression, GIN, BRIN — each deletes one named cost; audit the unused.

      
14migrationsExpand → backfill in batches → contract; both code versions serve every schema; CONCURRENTLY or outage.

      
15scalePool → tune → cache → replicas (mind read-your-writes) → partition → shard last, if ever.
