Values & types — what a variable actually holds

beginner → the reference model most bugs come from

JavaScript has exactly eight types. Seven are primitives — string, number, boolean, undefined, null, bigint, symbol — and everything else is an object (including arrays and functions; they're objects with extra talents).

The single most important idea in this whole module: primitives are copied by value, objects are copied by reference. A variable never "contains" an object — it holds a pointer to one, the way a cat's adoption certificate isn't the cat, just a way to find her.

PROFESSOR WHISKERS EXPLAINSIf two people both hold a copy of Mochi's adoption paper, and one of them takes Mochi to the groomer, both papers now point at a groomed cat. But if two people each write down her weight on their own paper, changing one paper changes nothing else. Objects are the cat; primitives are the number on the paper.

one-cat-two-papers.js — run it
// primitives copy the VALUE
let weight = 4.2;
let weightCopy = weight;
weightCopy = 5.0;
console.log(weight);          // still 4.2 — separate papers

// objects copy the REFERENCE
const mochi = { name: 'Mochi', groomed: false };
const sameCat = mochi;        // not a clone — the same cat!
sameCat.groomed = true;
console.log(mochi.groomed);   // true — one cat, two papers

// "const" freezes the PAPER, not the cat
mochi.name = 'Mochi II';      // fine — mutating the object
console.log(mochi.name);
// mochi = {} would throw — THAT reassigns the binding
runs right here — edit nothing, just watch the two behaviors

    

    
This is why a function can mutate an object you pass it (you handed over the real cat), and why {...mochi} — a shallow copy — only copies one level: nested objects inside are still shared references. A true clone of everything is structuredClone(mochi).

    

      
// quiz — first pick is the one that counts

      
function feed(cat) { cat.fed = true; cat = { fed: false }; } — after feed(mochi), what is mochi.fed?

      

        
        
        
        
      

      
Why: the parameter received a copy of the reference. Line one follows that reference to the shared object — visible outside. Line two points the local copy somewhere new — invisible outside. This is "pass-by-value where the value is a reference" in one function, and it's a genuine screen question.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • "JS is always pass-by-value — but for objects, the value being passed is the reference." That sentence, verbatim, settles a famously confused question.
    • 
        
  • typeof null === 'object' is a 30-year-old bug kept for compatibility. Check null with x === null.
    • 
        
  • Numbers are IEEE-754 doubles: 0.1 + 0.2 !== 0.3. Money lives in integer paise/cents, never floats.
    • 
        
  • Object.freeze(obj) makes an object shallowly immutable — and is the start of the "how would you make this deeply immutable?" follow-up.

Coercion & equality — the rules behind the "wat"

      
beginner → why == behaves and when to allow it

    

  

  

    
JavaScript converts types for you — helpfully in template strings, chaotically in comparisons. The chaos is rule-based, though, and there are only three rules you actually need.

    
Rule 1: === compares type and value, converting nothing. Rule 2: == first converts both sides to a common type (usually numbers) — that's how '5' == 5 is true. Rule 3: when JS needs a boolean (an if, a !), exactly eight values are falsy — false, 0, -0, 0n, '', null, undefined, NaN — and everything else is truthy, including [], {}, and 'false'.

    

      
      
PROFESSOR WHISKERS EXPLAINSThink of == as a cat translator with strong opinions: before comparing a cat's meow to a dog's bark, it translates both into "animal sounds" and then compares. Usually fine, occasionally you learn that an empty carrier [] translates to silence '', which translates to 0. The translator isn't random — it's just very literal.

    

    

      

        
the-translator.js — predict each line, then run

        
// Say each answer OUT LOUD before running. Grade yourself.
console.log('5' == 5);        // ?
console.log('5' === 5);       // ?
console.log([] == false);     // ?  ([] → '' → 0, false → 0)
console.log([] == ![]);       // ?  (![] is false! so: [] == false)
console.log(null == undefined);   // ?  (special rule: only each other)
console.log(null == 0);       // ?  (null only == undefined, nothing else)
console.log(NaN === NaN);     // ?  (NaN equals NOTHING)
console.log(Number.isNaN(NaN));   // the correct NaN check

// the ONE respectable use of == :
const x = undefined;
console.log(x == null);       // true for null AND undefined — handy guard

      

      
score yourself honestly — this is a real screen question

      

    

    

      
// quiz — first pick is the one that counts

      
Mochi's shop sells treats: if (cart.items.length) { checkout() }. When does checkout NOT run?

      

        
        
        
        
      

      
Why: length is a number; the only falsy numbers are 0, -0 and NaN. An array with items has truthy length; empty array → 0 → falsy → no checkout. (And {} is truthy — objects always are.)

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The calibrated rule: "always ===, except x == null as a deliberate null-or-undefined guard."
    • 
        
  • ?? (nullish coalescing) beats || for defaults: count || 10 wrongly replaces 0; count ?? 10 only replaces null/undefined.
    • 
        
  • +'42' is a number, '' + 42 is a string, 1 + '2' is '12' but 1 - '2' is -1 — + is the only operator that prefers strings.

    03
    

      
Scope, hoisting & the TDZ — where variables live

      
beginner → the machinery closures are built on

    

  

  

    
Scope answers one question: which variables can this line of code see? Modern JS has three kinds — global (everywhere), function (inside the enclosing function), and block (inside the nearest { }). let and const are block-scoped; var ignores blocks entirely and attaches to the whole function, which is the root of most of its crimes.

    
Hoisting is the part everyone half-knows: before running your code, the engine walks it and registers every declaration first. Function declarations are hoisted with their body — you can call them above where they're written. var is hoisted but initialized to undefined. let/const are hoisted too — but left uninitialized, and touching them before their declaration line throws. That forbidden stretch has a name interviewers love: the temporal dead zone (TDZ).

    

      
      
PROFESSOR WHISKERS EXPLAINSBefore adoption day opens, the shelter pins up name tags for every cat that will attend. A function-declaration cat arrives early and sits under her tag — visit any time. A var cat has a tag but the cage is empty (undefined) until she's carried in. A let cat's tag says "DO NOT APPROACH until formally introduced" — walk up early and security throws you out. That roped-off waiting period is the temporal dead zone.

    

    

      

        
name-tags.js — predict, then run

        
// 1 · function declarations: hoisted WITH their body
console.log(greet('Mochi'));      // works — called above its definition
function greet(cat) { return `hello, ${cat}`; }

// 2 · var: hoisted, initialized to undefined
console.log(bowl);                // undefined — tag up, cage empty
var bowl = 'tuna';

// 3 · let: hoisted but UNINITIALIZED — the TDZ
try {
  console.log(treats);            // BOOM
} catch (e) { console.log('TDZ says:', e.constructor.name); }
let treats = 3;

// 4 · var ignores blocks; let respects them
if (true) { var leaked = 'var escapes blocks'; let contained = 'let does not'; }
console.log(leaked);              // visible — function-scoped
try { console.log(contained); } catch (e) { console.log('contained is gone:', e.constructor.name); }

// 5 · shadowing: inner declaration hides the outer one
let cat = 'Mochi';
{ let cat = 'Biscuit'; console.log('inner:', cat); }
console.log('outer:', cat);       // untouched

      

      
five behaviors, one scoreboard — say each answer out loud first

      

    

    
Why this matters beyond trivia: block scoping is what makes the classic for (let i…) loop create a fresh i per iteration (the fix you'll meet in the closures section), and the TDZ is why const can guarantee "declared before used". Hoisting explains the difference between a function declaration and a function expression: const f = () => {} hoists the variable into the TDZ, not the function — call it early and you get a TDZ throw, not undefined is not a function.

    

      
// quiz — first pick is the one that counts

      
What does this log? console.log(x); let x = 5;

      

        
        
        
        
      

      
Why: let IS hoisted — the binding exists at the top of the block — but it's uninitialized until its declaration line runs. Reading an uninitialized binding is a runtime ReferenceError, not a parse-time SyntaxError. Swap let for var and you'd get undefined. That three-way distinction is the whole question.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The precise sentence: "let and const are hoisted but not initialized — the gap is the TDZ." Saying "let isn't hoisted" is the common half-truth interviewers probe.
    • 
        
  • typeof undeclared is safely 'undefined', but typeof x inside x's TDZ throws — the TDZ even breaks typeof's famous safety.
    • 
        
  • Un-declared assignment (bowl = 'tuna' with no keyword) creates a global in sloppy mode and throws in strict mode — one of the best one-line arguments for 'use strict' and modules (which are strict by default).
    • 
        
  • Old code wrapped everything in IIFEs — (function () { … })() — purely to fake block scope before let existed. Recognize the pattern; don't write it new.

Closures — functions that remember

      
the #1 interview topic in all of JavaScript

    

  

  

    
Scope is "which variables can this line see?" — and in modern JS it follows the braces: a let or const lives inside the nearest { } and nowhere else. (var ignores braces and belongs to the whole function — one of several reasons we've retired it.)

    
A closure is what happens when a function is created inside another function: the inner function keeps a live link to the outer function's variables — even after the outer function has finished and returned. Not a snapshot. A live link.

    

      
      
PROFESSOR WHISKERS EXPLAINSAn automatic treat dispenser is built (the outer function runs once) with a jar of treats sealed inside (its local variable). The dispenser's button (the inner function you kept) still reaches that jar every time it's pressed — long after the factory that built it closed. Two dispensers? Two separate jars. That's a closure: the button carries its jar with it.

    

    

      

        
treat-dispenser.js — run it

        
function makeDispenser(cat) {
  let treats = 3;                  // the sealed jar
  return function dispense() {     // the button — closes over `treats`
    if (treats === 0) return `${cat}: jar empty 😾`;
    treats--;                      // a LIVE link — it mutates the jar
    return `${cat} gets a treat (${treats} left)`;
  };
}

const forMochi = makeDispenser('Mochi');
const forBiscuit = makeDispenser('Biscuit');  // separate jar!

console.log(forMochi());     // 2 left
console.log(forMochi());     // 1 left
console.log(forBiscuit());   // 2 left — Biscuit's own jar
console.log(forMochi());     // 0 left
console.log(forMochi());     // jar empty 😾

// makeDispenser finished running long ago —
// yet `treats` lived on, privately, per dispenser.

      

      
two dispensers, two jars — the whole concept in one run

      

    

    
The interview classic: the loop that logs 3, 3, 3

    
Because closures link to variables (not values), three callbacks closing over one shared var i all see its final value. let fixes it by creating a fresh i per loop iteration — three callbacks, three variables. Run it:

    

      

        
the-loop-question.js — run it

        
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var says:', i));   // one shared i
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log('let says:', j));   // fresh j each loop
}
// prediction time: what prints, in what order?

      

      
the timers fire after the loops finish — watch both behaviors

Naming debounce ("the timer variable lives in a closure") makes the answer concrete.

    •

    05
    

      
this, tamed — four rules, zero mystery

      
intermediate → the bug class you'll never write again

    

  

  

    
this feels haunted because it's decided at the wrong moment compared to everything else in JS. Variables are resolved where a function is written (lexical). this is resolved where a function is called — every single call, fresh.

    
Four rules, checked in order, answer every this question: (1) called with new? → the brand-new object. (2) called via .call/.apply/.bind? → whatever you passed. (3) called as a method, obj.fn()? → the thing before the dot. (4) called bare, fn()? → undefined in modules/strict mode. And the special case that fixes everything: arrow functions have no this at all — they see the enclosing scope's, like any other variable.

    

      
      
PROFESSOR WHISKERS EXPLAINSthis is "whose lap is the function sitting on when it's called?" — not whose house it was born in. mochi.meow(): sitting on Mochi's lap, this is Mochi. Hand the same meow to someone else and call it bare — it's on nobody's lap, and this is undefined. Arrow functions are kittens who refuse to change laps: they stay on the lap they were born on, forever.

    

    

      

        
whose-lap.js — run it

        
const mochi = {
  name: 'Mochi',
  meow() { return `${this?.name ?? 'nobody'} says meow`; },
};

console.log(mochi.meow());        // rule 3: lap = mochi

const detached = mochi.meow;      // took the function off the lap
console.log(detached());          // rule 4: nobody's lap

console.log(detached.call(mochi));       // rule 2: lap supplied
const glued = detached.bind(mochi);      // permanently re-lapped
console.log(glued());

// arrows don't have their own `this` — they inherit
const biscuit = {
  name: 'Biscuit',
  friends: ['Mochi', 'Clawdia'],
  listFriends() {
    // this arrow sees listFriends' `this` — biscuit. no .bind needed
    return this.friends.map(f => `${this.name} ♥ ${f}`);
  },
};
console.log(biscuit.listFriends());

      

      
the four rules, live — narrate each line like an interview trace

      

    

    

      
// quiz — first pick is the one that counts

      
setTimeout(mochi.meow, 100) logs "nobody says meow". Why?

      

        
        
        
        
      

      
Why: only the function value travels into setTimeout — the mochi. lap is gone. The timer invokes it as a plain call. Fixes, all equivalent: () => mochi.meow() (call it ON the lap), mochi.meow.bind(mochi), or make meow an arrow that closes over what it needs. This exact bug is why React class components needed .bind(this) — and why hooks + arrows made it extinct.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Arrows can't be constructors, have no arguments, and ignore .call/.bind's this — the cost of lap-loyalty. Don't use them as object methods when you WANT the calling object.
    • 
        
  • class fields like handleClick = () => {} are per-instance arrows — the modern auto-bind. Know the memory tradeoff: one function per instance instead of one shared prototype method.
    • 
        
  • In event handlers, DOM sets this to the element for regular functions — one more reason arrows + explicit variables read clearer.
    •

    06
    

      
Prototypes & classes — inheritance without the theater

      
intermediate → what `class` actually compiles down to

    

  

  

    
JavaScript has no "real" classes under the hood — it has objects linked to objects. Every object carries a hidden link to a prototype object; when you read a property the object doesn't have, JS follows the link and looks there, then follows that object's link, until it finds the property or hits null. That walk is the prototype chain, and it's the entire inheritance system.

    
The class keyword is lovely, modern syntax for wiring exactly those links: methods go on ClassName.prototype (one shared copy, not one per instance), and extends points one prototype at another.

    

      
      
PROFESSOR WHISKERS EXPLAINSAsk Mochi to fetchStick(). She checks her own tricks — nothing. She checks what she learned from Cat School (her prototype) — nothing. Cat School checks Animal Academy (its prototype) — found! Every cat shares the school's single trick book instead of carrying a photocopy — that's why methods live on the prototype: one book, many cats.

    

    

      

        
cat-school.js — run it

        
class Animal {
  constructor(name) { this.name = name; }        // own property per animal
  eat() { return `${this.name} eats`; }          // shared, on the prototype
}
class Cat extends Animal {
  meow() { return `${this.name} says meow`; }
  eat() { return super.eat() + ' (elegantly)'; } // override + call up-chain
}

const mochi = new Cat('Mochi');
console.log(mochi.meow());                  // found on Cat.prototype
console.log(mochi.eat());                   // Cat's version, using super

// proof it's all just linked objects:
console.log(Object.getPrototypeOf(mochi) === Cat.prototype);           // true
console.log(Object.getPrototypeOf(Cat.prototype) === Animal.prototype);// true
console.log('meow' in mochi, mochi.hasOwnProperty('meow'));  // true, false!
// `in` walks the chain; hasOwnProperty checks only the cat herself

// the chain ends at null:
console.log(Object.getPrototypeOf(Object.prototype));        // null

      

      
watch `in` vs hasOwnProperty split — that's the chain, visible

      

    

    

      
// quiz — first pick is the one that counts

      
Why do methods live on the prototype instead of being created in the constructor?

      

        
        
        
        
      

      
Why: 10,000 cats with a constructor-created meow = function(){} = 10,000 function objects; on the prototype = exactly one, found via the chain. (It's also why catA.meow === catB.meow is true — handy for memo/equality reasoning.) Arrow-function class fields make the opposite tradeoff for lap-loyalty — see section 04.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • "Prototypal inheritance in two sentences": every object links to a prototype; failed lookups walk the chain until found or null. class is syntax over those links.
    • 
        
  • Composition over inheritance is the design answer: deep extends chains are brittle; mixing in capabilities (functions, hooks) scales better. React chose composition — that's a great supporting example.
    • 
        
  • #private fields are real privacy (not convention), static lives on the constructor itself, and instanceof just walks the chain looking for Ctor.prototype.
    • 
        
  • Object.create(proto) makes an object with any prototype you like — the primitive underneath the whole system, and occasionally the cleanest way to make a lookup object with no prototype at all: Object.create(null).

    07
    

      
Classes, for real — fields, #private, static & super

      
intermediate → what the syntax actually creates

    

  

  

    
The previous section showed that class is syntax over prototypes. This one covers the parts of the syntax that are genuinely new — because "class is just sugar" stopped being fully true a few years ago. Field declarations, #private fields, and static blocks have no prototype-era equivalent.

    
The one distinction that explains almost every class question: methods live once on the prototype; fields are copied onto every instance. Write meow() {} and a thousand cats share one function. Write meow = () => {} as a field and a thousand cats carry a thousand private copies — each one closing over its own this, which is exactly why the arrow-field trick fixes callback this (and what it costs).

    

      
      
PROFESSOR WHISKERS EXPLAINSThe shelter's rulebook (the prototype) is written once and every cat consults it — that's a method. Each cat's collar tag is stamped fresh per cat — that's a field. And a #microchip is under the skin: the vet who implanted it (the class's own code) can read it; nobody outside can, not even by shaving the cat (JSON.stringify, Object.keys — nothing reveals it).

    

    

      

        
microchips.js — run it

        
class Cat {
  static #population = 0;              // private AND shared by the class
  static get population() { return Cat.#population; }

  #chipId;                             // instance-private
  name;                                // public field — per instance
  constructor(name) {
    this.name = name;
    this.#chipId = 'CHIP-' + (++Cat.#population);
  }
  identify() { return `${this.name} → ${this.#chipId}`; }   // shared method
  static isCat(x) { return #chipId in x; }  // brand check — the modern instanceof
}

class Kitten extends Cat {
  constructor(name) {
    super(name);                       // MUST run before touching `this`
    this.zoomies = true;
  }
  identify() { return super.identify() + ' (kitten)'; }
}

const mochi = new Cat('Mochi');
const beans = new Kitten('Beans');
console.log(mochi.identify());
console.log(beans.identify());
console.log('population:', Cat.population);

console.log('chip visible from outside?', Object.keys(beans));
console.log('JSON sees:', JSON.stringify(beans));
console.log('real cat?', Cat.isCat(beans), '· imposter?', Cat.isCat({ name: 'Dog' }));

// methods are SHARED; fields are PER-INSTANCE:
console.log(mochi.identify === beans.__proto__.__proto__.identify);  // hmm — walk the chain!

      

      
private fields, static state, super, and a brand check in 30 lines

      

    

    
Rules worth knowing cold: a subclass constructor must call super() before using this (the parent literally creates the object). #private is enforced by the language, not convention — accessing beans.#chipId outside the class is a syntax error, a stronger guarantee than TypeScript's private (which compiles away) or the _underscore handshake. Getters/setters (get/set) make computed properties read like plain ones — the same mechanism frameworks lean on for reactive state.

    

      
// quiz — first pick is the one that counts

      
class Timer { start = () => this.tick() } vs class Timer { start() { this.tick() } } — why might the arrow-field version be chosen?

      

        
        
        
        
      

      
Why: a method extracted from its object is just a function — called bare, its this is undefined (section on this). An arrow field is created per-instance during construction and closes over that instance's this forever. The cost: one function object per instance instead of one shared on the prototype — fine for a handful, worth knowing for ten thousand.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • "Methods go on the prototype; fields are own properties, initialized per instance in declaration order, before the constructor body." That sentence separates syntax users from people who know the object model.
    • 
        
  • #x in obj is the modern brand check — it can't be faked the way instanceof can (prototypes are swappable at runtime).
    • 
        
  • static members live on the constructor function itself — Cat.population, not mochi.population. Static blocks (static { … }) run once at class definition for multi-step setup.
    • 
        
  • The senior answer to "should this be a class?": classes earn their keep for stateful things with identity (a connection, a game entity); for data + transforms, plain objects and functions compose better. "Composition over inheritance" — one level of extends, rarely two.
    •

    08
    

      
Modules — how code finds other code

      
intermediate → live bindings, cycles, and the CJS/ESM split

    

  

  

    
A module is a file with its own private scope — nothing leaks out unless you export it, nothing comes in unless you import it. Before modules, every script shared one global namespace, and library authors lived in fear of each other's variable names.

    
Two systems coexist: ESM (import/export — the standard, statically analyzable, what browsers and modern Node speak) and CommonJS (require/module.exports — Node's original, dynamic, still everywhere in npm). The differences that matter: ESM imports are live read-only bindings (not copies), they're resolved before code runs (so bundlers can tree-shake), and top-level await only works in ESM.

    

      
      
PROFESSOR WHISKERS EXPLAINSA module is a cat café with a service window. The kitchens (file internals) are private; only what's placed in the window (export) can be seen. And ESM's window is glass, not a photo: if the kitchen swaps the pastry, everyone looking through the window sees the new pastry instantly — a live binding, not a copy handed over once.

    

    

      
cafe-modules.js — the patterns to recognize

      
// named exports — the default choice (refactor-safe, tree-shakeable)
export const OPEN_HOURS = '9–17';
export function orderTreat(cat) { /* … */ }

// one default per module — for the module's "main thing"
export default class Cafe { /* … */ }

// importing
import Cafe, { orderTreat, OPEN_HOURS as hours } from './cafe.js';
import * as cafe from './cafe.js';       // namespace object
const { heavy } = await import('./reports.js');  // dynamic — code splitting!

// module-private state + closure = the classic singleton
let visits = 0;                          // nobody outside can touch this
export function checkIn() { return ++visits; }

// CommonJS, for when you meet it in Node:
const { orderTreat: order } = require('./cafe');  // runs the file, copies exports
module.exports = { order };

    

    

      
// quiz — first pick is the one that counts

      
Why can bundlers tree-shake import { debounce } from 'lodash-es' but not const _ = require('lodash')?

      

        
        
        
        
      

      
Why: ESM's imports/exports are fixed at parse time — the bundler sees the full dependency graph and provably-unused exports without executing anything. require('lo' + 'dash') is legal CommonJS; nothing is provable, so everything ships. Arrays, objects & iteration — the daily toolkit, sharpened

Errors done right — throw, catch, cause & custom types

      
intermediate → the difference between failing and failing usefully

    

  

  

    
Error handling has a small surface — throw, try/catch/finally, the Error family — and a large skill gap. The gap is knowing what to throw, where to catch, and what to do there. The mechanics first: throw can hurl any value, but you always throw Error objects (or subclasses), because only they carry a stack trace and a message. finally runs on every exit path — return, throw, or fall-through — which makes it the home for cleanup.

    
The modern upgrade most engineers haven't met: cause. Since ES2022, new Error('save failed', { cause: originalError }) lets you wrap a low-level error in a high-level one without losing the original — a chain of custody instead of a cover-up.

    

      
      
PROFESSOR WHISKERS EXPLAINSWhen a cat knocks a vase off the shelf, a bad shelter files the report as "vase broken" — cause unknown, cat unfindable. A good shelter files "vase broken (report attached: Mochi, 3:07 pm, zoomies)". Wrapping an error with cause is stapling the original incident report to the new one. And finally is the staff member who locks the supply room on the way out whatever happened during the shift.

    

    

      

        
incident-reports.js — run it

        
class CatNotFoundError extends Error {
  constructor(name) {
    super(`no cat named ${name}`);
    this.name = 'CatNotFoundError';   // otherwise it reports as "Error"
    this.catName = name;              // structured data for handlers
  }
}

const shelter = { Mochi: { hungry: true } };

function findCat(name) {
  const cat = shelter[name];
  if (!cat) throw new CatNotFoundError(name);
  return cat;
}

function feed(name) {
  try {
    findCat(name).hungry = false;
    return `${name} fed`;
  } catch (err) {
    if (err instanceof CatNotFoundError) {
      return `skipped: ${err.message}`;        // expected — handle it
    }
    throw new Error(`feed(${name}) blew up`, { cause: err });  // unexpected — wrap & rethrow
  } finally {
    console.log(`· log: feed(${name}) attempted`);  // runs on BOTH paths
  }
}

console.log(feed('Mochi'));
console.log(feed('Biscuit'));

// the cause chain in action:
try {
  try { JSON.parse('{oops'); }
  catch (low) { throw new Error('settings unreadable', { cause: low }); }
} catch (high) {
  console.log(high.message, '<-caused by-', high.cause.constructor.name);
}

      

      
expected errors handled, unexpected ones wrapped — the whole discipline

      

    

    
The design rule underneath: catch only what you can handle, exactly where you can handle it. A catch block that logs and continues turns a loud failure into a silent lie — the most expensive bug class in production. If you can't recover, don't catch; let it propagate to a boundary (Express error middleware, a React error boundary) that turns it into a 500 or a fallback UI once, in one place.

    

      
// quiz — first pick is the one that counts

      
What does this return? function f() { try { return 'try'; } finally { console.log('cleanup'); } }

      

        
        
        
        
      

      
Why: finally intercepts every exit — return, throw, break. The return value is computed, then finally runs, then the value leaves. (And try/finally with no catch is legal — it means "I don't handle errors, but I do clean up.") The trap for extra credit: a return inside finally overrides the original — never do that.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Never throw strings. throw 'oops' has no stack, no type to check, and instanceof can't route it. Errors are data — subclass and attach fields.
    • 
        
  • Name the built-ins and what they signal: TypeError (wrong kind of value), RangeError (right kind, bad magnitude), ReferenceError (unknown binding), SyntaxError (unparseable code).
    • 
        
  • "Errors for the exceptional, values for the expected" — a lookup that often finds nothing should return null/undefined, not throw. Throwing on every miss makes control flow out of exceptions.
    • 
        
  • Async changes the plumbing, not the philosophy — rejected promises are throws in transit. The js-async module's rejections section picks up exactly here.

Copying & immutability — shallow, deep, frozen

      
intermediate → the bug class React made everyone confront

    

  

  

    
Section 01 established that objects copy by reference. This section is about actually copying them — and the three-way choice every "copy" hides: share it, copy one level, or copy everything. Spread ({...cat}) and Object.assign copy one level — every nested object inside is still the original, shared. That's a shallow copy, and forgetting it is the classic "my state changed by itself" bug.

    
For a true deep copy, the platform finally has a real answer: structuredClone(value) — handles nesting, Date, Map, Set, cycles. The old folk remedy, JSON.parse(JSON.stringify(x)), silently mangles data: drops undefined and functions, turns Dates into strings, and explodes on cycles. Know it to recognize it, and know exactly what it breaks.

    

      
      
PROFESSOR WHISKERS EXPLAINSPhotocopying a cat's adoption folder copies the cover page — but the vet-history booklet inside is the same physical booklet, slipped into both folders. Scribble in one, the other has the scribble. That's spread. structuredClone is the intern who re-photocopies every page of every booklet, all the way down. And Object.freeze laminates the cover page only — the booklets inside are still very writable.

const mochi = {

When state nests deep enough that the spines get painful, that's the signal to flatten the state shape — or reach for a library like Immer that writes the spines for you.

Regular expressions — read them, write them, know when not to

      
intermediate → from line noise to a tool you reach for calmly

    

  

  

    
A regex is a pattern for text: literals match themselves, and a small set of operators mean "kinds of characters" (\d digit, \w word char, \s whitespace, . almost anything), "how many" (* 0+, + 1+, ? 0-1, {2,4} a range), and "where" (^ start, $ end, \b word boundary). Wrap part of a pattern in ( ) and you've made a group you can extract — name it with (?<name>…) and the match comes back labeled.

    
The one behavior that separates people who read regexes from people who squint: quantifiers are greedy — they grab as much as possible, then give back only if the rest can't match. Add ? to make one lazy (grab as little as possible). <.+> against <a><b> matches the whole thing; <.+?> matches just <a>.

    

      
      
PROFESSOR WHISKERS EXPLAINSA greedy cat at the buffet piles everything onto the plate, then puts items back one by one only if the kitchen complains. A lazy cat takes one bite, and returns for more only if forced. Both end up "full" (a valid match) — but what's on the plate differs completely. When your regex captures way more than intended, you've sent the greedy cat.

    

    

      

        
pattern-practice.js — run it

        
// named groups: extraction that reads like code
const chip = 'CHIP-2026-00412 (Mochi)';
const m = chip.match(/CHIP-(?<year>\d{4})-(?<serial>\d+) \((?<cat>\w+)\)/);
console.log(m.groups);                        // { year, serial, cat }

// greedy vs lazy — same string, wildly different plates
const tags = '<name>Mochi</name><age>2</age>';
console.log(tags.match(/<.+>/)[0]);           // greedy: the WHOLE string
console.log(tags.match(/<.+?>/)[0]);          // lazy: just <name>

// replace with a callback — regex as a transformer
const snake = 'cat_name_first';
console.log(snake.replace(/_(\w)/g, (_, c) => c.toUpperCase()));  // camelCase

// matchAll: every match, with groups, lazily
const log = 'fed Mochi 3x, fed Biscuit 1x, fed Beans 2x';
for (const f of log.matchAll(/fed (\w+) (\d+)x/g)) {
  console.log(`${f[1]} ate ${f[2]} times`);
}

// boundaries beat contains: /\bcat\b/ won't match "category"
console.log(/\bcat\b/.test('my cat sleeps'), /\bcat\b/.test('category'));

      

      
named groups, laziness, replace-with-function — the working set

      

    

    
Flags you'll actually use: g (all matches, required for matchAll/global replace), i (case-insensitive), m (^$ per line), s (. also matches newlines), u (real Unicode handling — always safe to add). And the honest boundary: regexes are for regular text — tokens, IDs, log lines. For nested structures (HTML, JSON, code), reach for a parser; the famous Stack Overflow answer about parsing HTML with regex is famous because it's right.

    

      
// quiz — first pick is the one that counts

      
Against 'aaa', what does /a+?/ match?

      

        
        
        
        
      

      
Why: + requires at least one a; the ? suffix makes it stop there unless the rest of the pattern forces more. There is no rest, so one a wins. Greedy and lazy find the same set of valid matches — they differ in which one they settle on first.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Catastrophic backtracking is a real outage class: nested quantifiers like (a+)+$ against a non-matching string go exponential — a crafted input pins a CPU (ReDoS). Linear-time guarantee: avoid nested quantifiers, or use the v/RE2-style engines where available.
    • 
        
  • .test() for yes/no, .match()/.matchAll() for extraction, .replace() with a function for transformation — naming the right tool is half the answer.
    • 
        
  • A g-flagged regex object is stateful (lastIndex advances between .test() calls) — the classic "why does my regex match every other time" bug. Recreate the regex or use matchAll.
    • 
        
  • Email validation: the pragmatic answer is /^\S+@\S+\.\S+$/ plus a confirmation email — not the 6,000-character RFC monster. Knowing when to stop is the senior signal.

Generators & the iterator protocol — functions that pause

      
advanced → lazy sequences, and the machinery under for…of

    

  

  

    
Section 09 used iterables; this section builds them. The iterator protocol is just a handshake: an object is an iterator if it has next() returning { value, done }; it's an iterable if it has a [Symbol.iterator]() method that returns an iterator. Everything that "just works" in a for…of, a spread, or destructuring is speaking this protocol.

    
Writing next() by hand is bookkeeping, so the language gives you generators: function* plus yield. Call one and nothing runs — you get back an iterator. Each next() runs the body to the next yield and pauses there, stack frame intact, locals alive. It's the only place in synchronous JS where a function can stop mid-body and resume later — the same trick await is built on.

    

      
      
PROFESSOR WHISKERS EXPLAINSA normal function is a cat that eats the whole bowl in one sitting. A generator is a cat that takes one bite, walks away mid-chew, and — this is the strange part — resumes from the exact same bite when it returns, even hours later. The bowl (local variables) waits, untouched. Nobody refills it; nobody resets it. The nap is the feature.

    

    

      

        
one-bite-at-a-time.js — run it

        
// an INFINITE sequence — fine, because it's lazy
function* catNames() {
  const bases = ['Mochi', 'Biscuit', 'Beans'];
  let n = 1;
  while (true) {
    for (const b of bases) yield `${b} ${'I'.repeat(n)}`;
    n++;
  }
}

// take(k): consume only what you need
function* take(k, iterable) {
  for (const v of iterable) { if (k-- <= 0) return; yield v; }
}
console.log([...take(5, catNames())]);

// two-way: next(value) SENDS data to the paused yield
function* feeder() {
  const first = yield 'who is hungry?';
  const second = yield `${first} fed. who else?`;
  return `${second} fed. kitchen closed.`;
}
const f = feeder();
console.log(f.next().value);          // runs to the first yield
console.log(f.next('Mochi').value);   // 'Mochi' becomes `first`
console.log(f.next('Beans').value);   // return value, done: true

// yield* delegates to another iterable
function* all() { yield* ['a', 'b']; yield* catNames(); }
console.log([...take(4, all())]);

// any object can join for…of — implement the protocol
const clowder = {
  cats: ['Mochi', 'Biscuit'],
  *[Symbol.iterator]() { yield* this.cats; },
};
console.log([...clowder]);

      

      
infinite-but-lazy, two-way yield, delegation, and a custom iterable

      

    

    
When do you actually reach for one? Lazy pipelines (process a million-line file one line at a time, not one array at a time), custom iteration order for your own data structures (walk a tree in-order with five lines), and resumable processes (pagination cursors, state machines that advance one step per call). If you've used Redux-Saga, or for await in the async module — those are this protocol wearing different jackets.

    

      
// quiz — first pick is the one that counts

      
function* g() { yield 1; yield 2; } — what does g() return?

      

        
        
        
        
      

      
Why: calling a generator function executes zero lines of its body — it returns a generator object (an iterator that's also iterable). Execution is entirely demand-driven: each next() buys you one segment, up to the next yield. That "call runs nothing" behavior is the #1 surprise interviewers test.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The crisp definition: "iterable has Symbol.iterator; iterator has next() → {value, done}; generators are both."
    • 
        
  • Generators are not threads and not async — they're cooperative pauses in synchronous code. (Async generators + for await add promises on top; see js-async.)
    • 
        
  • yield is an expression — next(v)'s argument becomes the value the paused yield evaluates to. Two-way flow is what made generator-based coroutine libraries (co, redux-saga) possible before async/await shipped.
    • 
        
  • Spread, destructuring, Array.from, for…of, new Map(pairs) — all consume the same protocol. Implement Symbol.iterator once and every one of those works on your type for free.

Symbols — the language's hidden hooks

      
advanced → the seventh primitive, and why libraries adore it

    

  

  

    
A symbol is a primitive whose only job is to be unique: Symbol('id') !== Symbol('id'), always — the string is just a debugging label. Use one as a property key and it can never collide with anyone else's key, which makes symbols the language's mechanism for metadata that stays out of the way: symbol-keyed properties are skipped by for…in, Object.keys, and JSON.stringify.

    
The deeper story is the well-known symbols — slots the language itself checks on your objects. You met Symbol.iterator in the generators section; its siblings customize other built-in behavior: Symbol.toPrimitive (how your object coerces), Symbol.toStringTag (what Object.prototype.toString reports), Symbol.hasInstance (what instanceof means for your class). They're the official override points for machinery that used to be magic.

    

      
      
PROFESSOR WHISKERS EXPLAINSEvery shelter uses name tags, and two cats named Mochi collide constantly. A symbol is a tamper-proof microchip number issued once in the universe — even chips labeled "Mochi" are different chips. Regular visitors (Object.keys, JSON) don't even have the scanner: they walk past chipped data without seeing it. Only someone holding that exact chip (the symbol reference) can read what's stored under it.

    

    

      

        
hidden-hooks.js — run it

        
// uniqueness — the entire point
console.log(Symbol('id') === Symbol('id'));           // false, always

// symbol keys hide from normal enumeration
const SECRET = Symbol('vetNotes');
const mochi = { name: 'Mochi', [SECRET]: 'scared of vacuum' };
console.log(Object.keys(mochi));                      // ['name'] only
console.log(JSON.stringify(mochi));                   // {"name":"Mochi"}
console.log(mochi[SECRET]);                           // holders of the symbol read it
console.log(Object.getOwnPropertySymbols(mochi).map(String));  // …but not truly secret

// Symbol.toPrimitive — YOU write the coercion rules from section 02
const weight = {
  kg: 4.2,
  [Symbol.toPrimitive](hint) {
    return hint === 'number' ? this.kg : `${this.kg} kg`;
  },
};
console.log(weight * 2);        // number hint → 8.4
console.log(`Mochi: ${weight}`); // string hint → "4.2 kg"

// Symbol.for — the global registry (same key → SAME symbol)
console.log(Symbol.for('app.cache') === Symbol.for('app.cache'));  // true

// Symbol.toStringTag — rebrand the default [object Object]
class Clowder { get [Symbol.toStringTag]() { return 'Clowder'; } }
console.log(Object.prototype.toString.call(new Clowder()));

      

      
unique keys, invisible metadata, and custom coercion — all symbol tricks

      

    

    
Where you've already touched this without knowing: React elements carry $$typeof: Symbol.for('react.element') so a JSON payload from a compromised API can't smuggle in a fake element (JSON can't produce symbols — that's the security property doing real work). Node marks objects for custom console output with a symbol; polyfills detect each other through Symbol.for registry keys. It's the standard way libraries write on your objects without ever colliding with your data.

    

      
// quiz — first pick is the one that counts

      
Why does React tag elements with $$typeof: Symbol.for('react.element') instead of a string like "react.element"?

      

        
        
        
        
      

      
Why: if the tag were a string, a malicious API response {"$$typeof":"react.element", …} would pass the "is this a React element" check and could inject markup. JSON.parse can produce strings, numbers, booleans, nulls, arrays, objects — never symbols — so the check can only pass for objects created in your own JS runtime. A primitive's absence from JSON as a security boundary: peak JavaScript.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Symbol-keyed ≠ private: Object.getOwnPropertySymbols reveals them. For enforcement, that's what #private fields (section 07) are for — symbols are about collision-free, not secret.
    • 
        
  • Symbol() is unique per call; Symbol.for(key) is the global registry — same key, same symbol, even across module copies. That's why cross-package protocols use Symbol.for.
    • 
        
  • Well-known symbols worth naming: iterator, asyncIterator, toPrimitive, toStringTag, hasInstance. Just listing them signals you know where the language's extension sockets are.
    • 
        
  • The seven primitives, complete: string, number, boolean, undefined, null, bigint, symbol — interviewers still ask, and symbol is the one people forget.

Memory & garbage collection — why leaks happen in a GC'd language

      
advanced → reachability, the four classic leaks, and the Weak family

    

  

  

    
JavaScript frees memory for you, so how do JS apps leak? Because the garbage collector's rule is not "free what you're done with" — it's "free what can no longer be reached." Anything findable by walking references from the roots (globals, the current stack, active closures, live timers, DOM event listeners) stays alive. A leak is simply memory that is reachable but useless — the GC can't read your intentions, only your references.

    
The four classics, responsible for nearly every real leak: 1) forgotten timers/subscriptions (the callback's closure pins everything it captured), 2) ever-growing caches (a Map you add to and never evict), 3) detached DOM (a removed node still referenced from JS keeps its whole subtree), 4) accidental globals (sloppy-mode assignment, module-level accumulators).

    

      
      
PROFESSOR WHISKERS EXPLAINSThe shelter only rehomes a cat when no one holds its leash. It doesn't matter that you finished playing with Mochi an hour ago — if the leash is still looped around your wrist (a reference), she stays. A leak is a wall of leashes hooked to cats nobody visits. A WeakMap leash is different: it's enchanted — the moment every other leash is gone, it unclips itself, and the cat goes home.

    

    

      

        
leashes.js — run it

        
// LEAK SHAPE 1 · the immortal cache
const chipCache = new Map();
function register(cat) { chipCache.set(cat, 'CHIP-' + chipCache.size); }
let visitor = { name: 'Mochi', photos: '(imagine 50 MB)' };
register(visitor);
visitor = null;   // we're done with her…
console.log('Map still holds:', chipCache.size, 'entry — 50 MB pinned');

// THE FIX · WeakMap holds keys weakly — no leash of its own
const weakCache = new WeakMap();
let guest = { name: 'Biscuit' };
weakCache.set(guest, 'CHIP-W1');
console.log('readable while alive:', weakCache.get(guest));
guest = null;     // last real leash gone → entry is NOW collectible
// (we can't PRINT the collection happening — GC runs on its own schedule,
//  and that's the point: WeakMap has no .size and no iteration.)

// LEAK SHAPE 2 · the forgotten timer — the closure pins `bigLog`
function watchBowl() {
  const bigLog = new Array(1000).fill('meal record');
  const id = setInterval(() => { bigLog.length; }, 60_000);
  return () => clearInterval(id);   // the unsubscribe — KEEP and CALL this
}
const stop = watchBowl();
stop();
console.log('timer cleared — bigLog is unreachable, collectible');

// LEAK SHAPE 4 · the accidental global (strict mode saves you)
try { orphan = 'no keyword, no home'; }
catch (e) { console.log('strict mode blocks it:', e.constructor.name); }

      

      
two leaks, two fixes — and why WeakMap can't show you its size

      

    

    
The Weak family in one line each: WeakMap/WeakSet associate data with objects without extending their lifetime (keys must be objects — a weakly-held number makes no sense); WeakRef is a leash that might be empty when you check (.deref()); FinalizationRegistry asks for a callback after collection. The last two are for caches and resource bookkeeping — the docs themselves say "avoid if you can", and interviewers respect you for quoting that.

// warm-up 1 of 3 — coercion: trace two operators

      
What does console.log(1 + '2' - 3) print?

      

        
        
        
        
      

      
Why: two operators, two different translators (§02). + is the only operator that prefers strings, so 1 + '2' is '12'; - only knows numbers, so '12' - 3 is 12 - 3 = 9. The 0 pick assumes coercion "just does math" everywhere; NaN assumes numeric strings don't convert (they do — '12' is a clean conversion); '123' assumes string-ness is contagious to every operator, but only + caught it.

    

    

      
// warm-up 2 of 3 — equality is identity, not contents

      
Two identical vet records: console.log({ chip: 7 } === { chip: 7 }). What prints?

      

        
        
        
        
      

      
Why: §01's rule — a variable holds the paper, not the cat. Each { chip: 7 } literal creates a fresh object, so the two references point at two different cats, and === on objects asks only "same cat?" The structural-equality pick imports intuition from other languages (and from === on primitives, where it does compare values); the JSON pick invents a conversion that never happens; Object.is exists but is nearly identical to === — nothing throws. This one fact is why React's dependency arrays re-fire on inline objects.

    

    

      
// warm-up 3 of 3 — walk the chain to null

      
const bare = Object.create(null); bare.toString(); — what happens?

      

        
        
        
        
      

      
Why: chain-walk it (§06). bare has no own toString, and its prototype link is null — the walk ends before it starts, so the property read yields undefined, and calling undefined is a runtime TypeError. The '[object Object]' pick assumes toString is baked into every object — it actually lives on Object.prototype, which bare deliberately skipped. The undefined pick confuses reading a missing property (safe) with calling it (throws). Nothing here is a parse error, so SyntaxError is out.

    

    

      
// apply 1 of 3 — closures capture variables, not values

      
Trace it: for (var i = 0; i < 3; i++) { setTimeout(() => console.log(i * 10)); } — what prints?

      

        
        
        
        
      

      
Why: three steps (§03 + §04). var ignores blocks, so all three arrows close over one variable; the timers fire only after the loop finishes; and the loop exits when the test fails, i.e. when i is 3, not 2 — so each logs 3 * 10. The 0 10 20 pick is what let would do (fresh binding per iteration); 0 0 0 treats closures as snapshots — they're live links; 20 20 20 is the off-by-one that forgets the exit condition runs one extra time.

    

    

      
// apply 2 of 3 — this: read the call site

      
const a = { name: 'Mochi', who() { return this.name; } }; const b = { name: 'Biscuit', who: a.who }; console.log(b.who()); — what prints?

      

        
        
        
        
      

      
Why: §05's whose-lap question, asked at the only moment that matters — the call. b.who() is rule 3: method call, this = the thing before the dot, so 'Biscuit'. The 'Mochi' pick binds this at definition time — that's how variables resolve (lexically), never this. The undefined pick half-remembers the detached-method trap, but here the function was re-attached and called on a lap, not bare. And functions are values (§01) — one function can sit in ten objects without complaint.

    

    

      
// apply 3 of 3 — reads climb, writes don't

      
const proto = { treats: 1 }; const cat = Object.create(proto); cat.treats++; console.log(cat.treats, proto.treats); — what prints?

      

        
        
        
        
      

      
Why: cat.treats++ is a read then a write. The read walks the chain (§06) and finds 1 on proto; the write cat.treats = 2 creates a fresh own property on cat that shadows the inherited one. Prototype untouched. The 2 2 pick assumes writes climb like reads — the asymmetry is the whole lesson, and it's why one instance mutating "shared" state doesn't infect its siblings. Nothing throws and nothing is ignored: shadowing is normal, silent behavior.

    

    

      
// stretch 1 of 3 — spot the false claim

      
Three of these claims are true. Which one is FALSE?

      

        
        
        
        
      

      
Why: only declarations hoist with their body (§03). const greet = function () {} hoists the const binding into the TDZ — call it early and you get a ReferenceError, not a working function (with var you'd get "undefined is not a function" instead; either way, no early call). The claim tempts because "functions are hoisted" is true of one form and gets over-generalized to both. The other three are real: shared var in loops (§03 + §04), arrows treating this as just another outer variable (§04 + §05), and module strict mode making bare calls see undefined (§05 + §08).

    

    

      
// stretch 2 of 3 — back-of-envelope leak math

      
A dashboard caches per-row data in a Map keyed by DOM row elements. Rows are removed from the page over time — about 1,000/day, each pinning ~1 MB of subtree and data — but the Map is never cleaned. After 5 days of uptime, roughly how much reachable-but-useless memory, and what's the fix?

      

        
        
        
        
      

      
Why: arithmetic first — 1,000 rows/day × ~1 MB × 5 days ≈ 5 GB — then the reasoning: the Map is reachable from a root, its keys are reachable from it, so every removed row and its 1 MB stays pinned (§15's leak shapes 2-and-3 in one object). The ~5 MB pick confuses the size of a reference with the size of what it retains — the leash is cheap, the cat is not. The "zero" pick is the detached-DOM misconception: leaving the page doesn't free a node something still points at. And GC never "evicts" — it frees the unreachable only (§15); an LRU is something you build, not something you get. WeakMap keys don't count as leashes, so removed rows become collectible (§09's Map-vs-object choice, with §15's twist).

    

    

      
// stretch 3 of 3 — deep vs shallow identity

      
const a = { tags: ['sleepy'] }; const b = structuredClone(a); const c = { ...a }; console.log(b.tags === a.tags, c.tags === a.tags); — what prints?

      

        
        
        
        
      

      
Why: two sections in one line. structuredClone copies every level (§11), so b.tags is a brand-new array — different reference, === false even though the contents match (§01). Spread copies one level, so c.tags is the same array as a.tags — true. The true true pick is warm-up 2's structural-equality trap resurfacing under pressure; false false believes spread is deep; true false has the right split with the two tools swapped. In React terms: c would dodge a re-render check on tags, b would trigger it — same data, opposite behavior.
