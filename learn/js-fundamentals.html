JavaScript, actually understood.

You can ship JS all day and still feel like parts of it are folklore — why this betrays you, why [] == false, what a closure really is. This module rebuilds the language from first principles, in plain English, with code you can run right on this page.

Every section ramps beginner → advanced: skim what you know, slow down where it gets new. Examples feature a recurring cast of cats, because everything is easier to remember when a cat named Mochi is involved. 🐈

01

Values & types — what a variable actually holds

beginner → the reference model most bugs come from

JavaScript has exactly eight types. Seven are primitives — string, number, boolean, undefined, null, bigint, symbol — and everything else is an object (including arrays and functions; they're objects with extra talents).

The single most important idea in this whole module: primitives are copied by value, objects are copied by reference. A variable never "contains" an object — it holds a pointer to one, the way a cat's adoption certificate isn't the cat, just a way to find her.

PROFESSOR WHISKERS EXPLAINSIf two people both hold a copy of Mochi's adoption paper, and one of them takes Mochi to the groomer, both papers now point at a groomed cat. But if two people each write down her weight on their own paper, changing one paper changes nothing else. Objects are the cat; primitives are the number on the paper.

one-cat-two-papers.js — run it
// primitives copy the VALUE
let weight = 4.2;
let weightCopy = weight;
weightCopy = 5.0;
console.log(weight);          // still 4.2 — separate papers

// objects copy the REFERENCE
const mochi = { name: 'Mochi', groomed: false };
const sameCat = mochi;        // not a clone — the same cat!
sameCat.groomed = true;
console.log(mochi.groomed);   // true — one cat, two papers

// "const" freezes the PAPER, not the cat
mochi.name = 'Mochi II';      // fine — mutating the object
console.log(mochi.name);
// mochi = {} would throw — THAT reassigns the binding
runs right here — edit nothing, just watch the two behaviors

    

    
This is why a function can mutate an object you pass it (you handed over the real cat), and why {...mochi} — a shallow copy — only copies one level: nested objects inside are still shared references. A true clone of everything is structuredClone(mochi).

    

      
// quiz — first pick is the one that counts

      
function feed(cat) { cat.fed = true; cat = { fed: false }; } — after feed(mochi), what is mochi.fed?

      

        
        
        
        
      

      
Why: the parameter received a copy of the reference. Line one follows that reference to the shared object — visible outside. Line two points the local copy somewhere new — invisible outside. This is "pass-by-value where the value is a reference" in one function, and it's a genuine screen question.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • "JS is always pass-by-value — but for objects, the value being passed is the reference." That sentence, verbatim, settles a famously confused question.
    • 
        
  • typeof null === 'object' is a 30-year-old bug kept for compatibility. Check null with x === null.
    • 
        
  • Numbers are IEEE-754 doubles: 0.1 + 0.2 !== 0.3. Money lives in integer paise/cents, never floats.
    • 
        
  • Object.freeze(obj) makes an object shallowly immutable — and is the start of the "how would you make this deeply immutable?" follow-up.

    02
    

      
Coercion & equality — the rules behind the "wat"

      
beginner → why == behaves and when to allow it

    

  

  

    
JavaScript converts types for you — helpfully in template strings, chaotically in comparisons. The chaos is rule-based, though, and there are only three rules you actually need.

    
Rule 1: === compares type and value, converting nothing. Rule 2: == first converts both sides to a common type (usually numbers) — that's how '5' == 5 is true. Rule 3: when JS needs a boolean (an if, a !), exactly eight values are falsy — false, 0, -0, 0n, '', null, undefined, NaN — and everything else is truthy, including [], {}, and 'false'.

    

      
      
PROFESSOR WHISKERS EXPLAINSThink of == as a cat translator with strong opinions: before comparing a cat's meow to a dog's bark, it translates both into "animal sounds" and then compares. Usually fine, occasionally you learn that an empty carrier [] translates to silence '', which translates to 0. The translator isn't random — it's just very literal.

    

    

      

        
the-translator.js — predict each line, then run

        
// Say each answer OUT LOUD before running. Grade yourself.
console.log('5' == 5);        // ?
console.log('5' === 5);       // ?
console.log([] == false);     // ?  ([] → '' → 0, false → 0)
console.log([] == ![]);       // ?  (![] is false! so: [] == false)
console.log(null == undefined);   // ?  (special rule: only each other)
console.log(null == 0);       // ?  (null only == undefined, nothing else)
console.log(NaN === NaN);     // ?  (NaN equals NOTHING)
console.log(Number.isNaN(NaN));   // the correct NaN check

// the ONE respectable use of == :
const x = undefined;
console.log(x == null);       // true for null AND undefined — handy guard

      

      
score yourself honestly — this is a real screen question

      

    

    

      
// quiz — first pick is the one that counts

      
Mochi's shop sells treats: if (cart.items.length) { checkout() }. When does checkout NOT run?

      

        
        
        
        
      

      
Why: length is a number; the only falsy numbers are 0, -0 and NaN. An array with items has truthy length; empty array → 0 → falsy → no checkout. (And {} is truthy — objects always are.)

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The calibrated rule: "always ===, except x == null as a deliberate null-or-undefined guard."
    • 
        
  • ?? (nullish coalescing) beats || for defaults: count || 10 wrongly replaces 0; count ?? 10 only replaces null/undefined.
    • 
        
  • +'42' is a number, '' + 42 is a string, 1 + '2' is '12' but 1 - '2' is -1 — + is the only operator that prefers strings.

    03
    

      
Scope & closures — functions that remember

      
the #1 interview topic in all of JavaScript

    

  

  

    
Scope is "which variables can this line see?" — and in modern JS it follows the braces: a let or const lives inside the nearest { } and nowhere else. (var ignores braces and belongs to the whole function — one of several reasons we've retired it.)

    
A closure is what happens when a function is created inside another function: the inner function keeps a live link to the outer function's variables — even after the outer function has finished and returned. Not a snapshot. A live link.

    

      
      
PROFESSOR WHISKERS EXPLAINSAn automatic treat dispenser is built (the outer function runs once) with a jar of treats sealed inside (its local variable). The dispenser's button (the inner function you kept) still reaches that jar every time it's pressed — long after the factory that built it closed. Two dispensers? Two separate jars. That's a closure: the button carries its jar with it.

    

    

      

        
treat-dispenser.js — run it

        
function makeDispenser(cat) {
  let treats = 3;                  // the sealed jar
  return function dispense() {     // the button — closes over `treats`
    if (treats === 0) return `${cat}: jar empty 😾`;
    treats--;                      // a LIVE link — it mutates the jar
    return `${cat} gets a treat (${treats} left)`;
  };
}

const forMochi = makeDispenser('Mochi');
const forBiscuit = makeDispenser('Biscuit');  // separate jar!

console.log(forMochi());     // 2 left
console.log(forMochi());     // 1 left
console.log(forBiscuit());   // 2 left — Biscuit's own jar
console.log(forMochi());     // 0 left
console.log(forMochi());     // jar empty 😾

// makeDispenser finished running long ago —
// yet `treats` lived on, privately, per dispenser.

      

      
two dispensers, two jars — the whole concept in one run

      

    

    
The interview classic: the loop that logs 3, 3, 3

    
Because closures link to variables (not values), three callbacks closing over one shared var i all see its final value. let fixes it by creating a fresh i per loop iteration — three callbacks, three variables. Run it:

    

      

        
the-loop-question.js — run it

        
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var says:', i));   // one shared i
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log('let says:', j));   // fresh j each loop
}
// prediction time: what prints, in what order?

      

      
the timers fire after the loops finish — watch both behaviors

      

    

    

      
// quiz — first pick is the one that counts

      
Where do you use closures in a normal React week — pick the answer an interviewer loves?

      

        
        
        
        
      

      
Why: every onClick arrow that mentions a prop or state variable is a closure over the render's scope — which is also exactly why stale-closure bugs exist in effects: the callback captured an old render's variables. Naming debounce ("the timer variable lives in a closure") makes the answer concrete.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Stale closures in React: an interval set up once captures that render's count forever. Fixes: functional updates (setCount(c => c + 1)), correct dep arrays, or a ref.
    • 
        
  • Closures are the memory-leak shape in JS: a long-lived callback (listener, cache, timer) holding a huge object it no longer needs. The leak is the reference, not the closure itself.
    • 
        
  • Hoisting, precisely: var hoists as undefined; let/const hoist but are unusable until their line — the temporal dead zone. Saying "TDZ" earns the point.
    • 
        
  • Module-private state, debounce/throttle, once-functions, memoize — all closures. One implementation from memory (debounce) covers the practical follow-up.
    •

    04
    

      
this, tamed — four rules, zero mystery

      
intermediate → the bug class you'll never write again

    

  

  

    
this feels haunted because it's decided at the wrong moment compared to everything else in JS. Variables are resolved where a function is written (lexical). this is resolved where a function is called — every single call, fresh.

    
Four rules, checked in order, answer every this question: (1) called with new? → the brand-new object. (2) called via .call/.apply/.bind? → whatever you passed. (3) called as a method, obj.fn()? → the thing before the dot. (4) called bare, fn()? → undefined in modules/strict mode. And the special case that fixes everything: arrow functions have no this at all — they see the enclosing scope's, like any other variable.

    

      
      
PROFESSOR WHISKERS EXPLAINSthis is "whose lap is the function sitting on when it's called?" — not whose house it was born in. mochi.meow(): sitting on Mochi's lap, this is Mochi. Hand the same meow to someone else and call it bare — it's on nobody's lap, and this is undefined. Arrow functions are kittens who refuse to change laps: they stay on the lap they were born on, forever.

    

    

      

        
whose-lap.js — run it

        
const mochi = {
  name: 'Mochi',
  meow() { return `${this?.name ?? 'nobody'} says meow`; },
};

console.log(mochi.meow());        // rule 3: lap = mochi

const detached = mochi.meow;      // took the function off the lap
console.log(detached());          // rule 4: nobody's lap

console.log(detached.call(mochi));       // rule 2: lap supplied
const glued = detached.bind(mochi);      // permanently re-lapped
console.log(glued());

// arrows don't have their own `this` — they inherit
const biscuit = {
  name: 'Biscuit',
  friends: ['Mochi', 'Clawdia'],
  listFriends() {
    // this arrow sees listFriends' `this` — biscuit. no .bind needed
    return this.friends.map(f => `${this.name} ♥ ${f}`);
  },
};
console.log(biscuit.listFriends());

      

      
the four rules, live — narrate each line like an interview trace

      

    

    

      
// quiz — first pick is the one that counts

      
setTimeout(mochi.meow, 100) logs "nobody says meow". Why?

      

        
        
        
        
      

      
Why: only the function value travels into setTimeout — the mochi. lap is gone. The timer invokes it as a plain call. Fixes, all equivalent: () => mochi.meow() (call it ON the lap), mochi.meow.bind(mochi), or make meow an arrow that closes over what it needs. This exact bug is why React class components needed .bind(this) — and why hooks + arrows made it extinct.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Arrows can't be constructors, have no arguments, and ignore .call/.bind's this — the cost of lap-loyalty. Don't use them as object methods when you WANT the calling object.
    • 
        
  • class fields like handleClick = () => {} are per-instance arrows — the modern auto-bind. Know the memory tradeoff: one function per instance instead of one shared prototype method.
    • 
        
  • In event handlers, DOM sets this to the element for regular functions — one more reason arrows + explicit variables read clearer.
    •

    05
    

      
Prototypes & classes — inheritance without the theater

      
intermediate → what `class` actually compiles down to

    

  

  

    
JavaScript has no "real" classes under the hood — it has objects linked to objects. Every object carries a hidden link to a prototype object; when you read a property the object doesn't have, JS follows the link and looks there, then follows that object's link, until it finds the property or hits null. That walk is the prototype chain, and it's the entire inheritance system.

    
The class keyword is lovely, modern syntax for wiring exactly those links: methods go on ClassName.prototype (one shared copy, not one per instance), and extends points one prototype at another.

    

      
      
PROFESSOR WHISKERS EXPLAINSAsk Mochi to fetchStick(). She checks her own tricks — nothing. She checks what she learned from Cat School (her prototype) — nothing. Cat School checks Animal Academy (its prototype) — found! Every cat shares the school's single trick book instead of carrying a photocopy — that's why methods live on the prototype: one book, many cats.

    

    

      

        
cat-school.js — run it

        
class Animal {
  constructor(name) { this.name = name; }        // own property per animal
  eat() { return `${this.name} eats`; }          // shared, on the prototype
}
class Cat extends Animal {
  meow() { return `${this.name} says meow`; }
  eat() { return super.eat() + ' (elegantly)'; } // override + call up-chain
}

const mochi = new Cat('Mochi');
console.log(mochi.meow());                  // found on Cat.prototype
console.log(mochi.eat());                   // Cat's version, using super

// proof it's all just linked objects:
console.log(Object.getPrototypeOf(mochi) === Cat.prototype);           // true
console.log(Object.getPrototypeOf(Cat.prototype) === Animal.prototype);// true
console.log('meow' in mochi, mochi.hasOwnProperty('meow'));  // true, false!
// `in` walks the chain; hasOwnProperty checks only the cat herself

// the chain ends at null:
console.log(Object.getPrototypeOf(Object.prototype));        // null

      

      
watch `in` vs hasOwnProperty split — that's the chain, visible

      

    

    

      
// quiz — first pick is the one that counts

      
Why do methods live on the prototype instead of being created in the constructor?

      

        
        
        
        
      

      
Why: 10,000 cats with a constructor-created meow = function(){} = 10,000 function objects; on the prototype = exactly one, found via the chain. (It's also why catA.meow === catB.meow is true — handy for memo/equality reasoning.) Arrow-function class fields make the opposite tradeoff for lap-loyalty — see section 04.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • "Prototypal inheritance in two sentences": every object links to a prototype; failed lookups walk the chain until found or null. class is syntax over those links.
    • 
        
  • Composition over inheritance is the design answer: deep extends chains are brittle; mixing in capabilities (functions, hooks) scales better. React chose composition — that's a great supporting example.
    • 
        
  • #private fields are real privacy (not convention), static lives on the constructor itself, and instanceof just walks the chain looking for Ctor.prototype.
    • 
        
  • Object.create(proto) makes an object with any prototype you like — the primitive underneath the whole system, and occasionally the cleanest way to make a lookup object with no prototype at all: Object.create(null).
    •

    06
    

      
Modules — how code finds other code

      
intermediate → live bindings, cycles, and the CJS/ESM split

    

  

  

    
A module is a file with its own private scope — nothing leaks out unless you export it, nothing comes in unless you import it. Before modules, every script shared one global namespace, and library authors lived in fear of each other's variable names.

    
Two systems coexist: ESM (import/export — the standard, statically analyzable, what browsers and modern Node speak) and CommonJS (require/module.exports — Node's original, dynamic, still everywhere in npm). The differences that matter: ESM imports are live read-only bindings (not copies), they're resolved before code runs (so bundlers can tree-shake), and top-level await only works in ESM.

    

      
      
PROFESSOR WHISKERS EXPLAINSA module is a cat café with a service window. The kitchens (file internals) are private; only what's placed in the window (export) can be seen. And ESM's window is glass, not a photo: if the kitchen swaps the pastry, everyone looking through the window sees the new pastry instantly — a live binding, not a copy handed over once.

    

    

      
cafe-modules.js — the patterns to recognize

      
// named exports — the default choice (refactor-safe, tree-shakeable)
export const OPEN_HOURS = '9–17';
export function orderTreat(cat) { /* … */ }

// one default per module — for the module's "main thing"
export default class Cafe { /* … */ }

// importing
import Cafe, { orderTreat, OPEN_HOURS as hours } from './cafe.js';
import * as cafe from './cafe.js';       // namespace object
const { heavy } = await import('./reports.js');  // dynamic — code splitting!

// module-private state + closure = the classic singleton
let visits = 0;                          // nobody outside can touch this
export function checkIn() { return ++visits; }

// CommonJS, for when you meet it in Node:
const { orderTreat: order } = require('./cafe');  // runs the file, copies exports
module.exports = { order };

    

    

      
// quiz — first pick is the one that counts

      
Why can bundlers tree-shake import { debounce } from 'lodash-es' but not const _ = require('lodash')?

      

        
        
        
        
      

      
Why: ESM's imports/exports are fixed at parse time — the bundler sees the full dependency graph and provably-unused exports without executing anything. require('lo' + 'dash') is legal CommonJS; nothing is provable, so everything ships. This one sentence is the whole "why ESM" story — and why import() (dynamic) is the deliberate escape hatch for code splitting.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Modules are singletons: evaluated once, cached; every importer shares the same instance. That's the standard way to share a DB pool or config — and the reason "just import it twice for a fresh copy" doesn't work.
    • 
        
  • Circular imports don't crash ESM — one side temporarily sees an un-initialized binding. If you've hit "cannot access before initialization" across files, that's the cycle; fix by extracting the shared bit.
    • 
        
  • ES modules are strict mode automatically, deferred automatically in browsers (type="module"), and scoped per-file — three "free" behaviors worth naming.
    • 
        
  • Barrel files (index.js re-exporting everything) are convenient but can drag the whole folder into a bundle and slow builds — a current-era nuance that lands well.
    •

    07
    

      
Arrays, objects & iteration — the daily toolkit, sharpened

      
beginner → the fluency layer: destructuring, spread, the big five

    

  

  

    
Ninety percent of day-to-day JS is reshaping data: pull things out (destructuring), copy-with-changes (spread), and transform lists (map / filter / reduce / find / some). Fluency here is what makes your code — and your interview answers — read like a native speaker's.

    
The mental model for the big five: map = same length, transformed. filter = same items, fewer. reduce = anything → one value. find = first match or undefined. some/every = boolean questions. None of them mutate — they hand you a new array, which is exactly what React's state model wants.

    

      
      
PROFESSOR WHISKERS EXPLAINSAn adoption day with a line of cats: map puts a bow on every cat (same cats, dressed up). filter lets only the vaccinated ones into the hall (fewer cats, unchanged). reduce weighs them all and reports one number. find walks the line and stops at the first tabby. Nobody rearranges the original line — every operation forms a new line.

    

    

      

        
adoption-day.js — run it

        
const cats = [
  { name: 'Mochi',   age: 2, weightKg: 4.2, vaccinated: true  },
  { name: 'Biscuit', age: 5, weightKg: 6.1, vaccinated: true  },
  { name: 'Clawdia', age: 1, weightKg: 3.0, vaccinated: false },
];

// destructuring + defaults + rename — read data like prose
const [first, ...rest] = cats;
const { name, weightKg: kg = 0 } = first;
console.log(name, kg, 'and', rest.length, 'more');

// the big five, chained like a sentence
const adoptable = cats
  .filter(c => c.vaccinated)
  .map(c => `${c.name} (${c.age}y)`);
console.log(adoptable);

const totalWeight = cats.reduce((sum, c) => sum + c.weightKg, 0);
console.log('total:', totalWeight.toFixed(1), 'kg');

console.log(cats.find(c => c.age < 2)?.name);   // first kitten
console.log(cats.some(c => !c.vaccinated));      // any unvaccinated?

// copy-with-changes — the React state idiom (never mutate!)
const vaccinatedClawdia = cats.map(c =>
  c.name === 'Clawdia' ? { ...c, vaccinated: true } : c
);
console.log(vaccinatedClawdia[2], '— original untouched:', cats[2].vaccinated);

// group by age bracket — reduce's favorite interview trick
const byAge = cats.reduce((groups, c) => {
  const key = c.age < 2 ? 'kitten' : 'adult';
  (groups[key] ??= []).push(c.name);
  return groups;
}, {});
console.log(byAge);

      

      
this file is 80% of practical day-job JavaScript

      

    

    

      
// quiz — first pick is the one that counts

      
Why does React state code use { ...cat, vaccinated: true } instead of cat.vaccinated = true?

      

        
        
        
        
      

      
Why: React compares old and new state with Object.is — mutate in place and old === new, so React sees "no change". A new object (spread) has a new reference. Bonus honesty: spread is a shallow copy — nested objects are still shared, which is why deeply-nested state updates get verbose (and why state shape is kept flat).

    

    

      
// quiz — first pick is the one that counts

      
When do you reach for Map over a plain object {}?

      

        
        
        
        
      

      
Why: Map takes any key type (objects included), has .size, cheap iteration, and no prototype baggage (a plain object "empty" dictionary still has toString up the chain!). Objects win for fixed, known shapes — records. Set is the same trade for uniqueness: [...new Set(arr)] is the one-line dedupe every interviewer has seen and still likes.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Know what mutates: push/pop/splice/sort/reverse mutate; map/filter/slice/concat, and the new-era toSorted/toReversed/toSpliced, don't. "sort mutates — I use toSorted" is a current-JS flex.
    • 
        
  • Optional chaining ?. + nullish ?? replaced a decade of x && x.y && x.y.z guards — write them naturally.
    • 
        
  • for…of iterates values of anything iterable (arrays, strings, Map, Set); for…in iterates object keys (including inherited ones) — mixing them up is a classic screen trap.
    • 
        
  • Every chained .map().filter() allocates an intermediate array — fine at app scale, worth one reduce/loop in a hot path. Saying "I'd measure first" completes the answer.
    •
