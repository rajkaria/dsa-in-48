Testing, without the guilt or the dogma.

You know you "should test more". This module replaces the guilt with judgment: what tests actually buy, which kinds pay rent at which layer, how to mock without mocking away the truth — and the parts nobody teaches: databases, flakes, and what coverage numbers really mean.

01

Why test — and what to test first

beginner → tests as insurance, priced per layer

Tests buy exactly three things: confidence to change code (the big one — a refactor with tests is an edit; without, a prayer), executable documentation (the test says what the code promises, and unlike the README it can't go stale silently), and design pressure (hard-to-test code is usually badly-shaped code — the test is the first consumer telling you the API is awkward). What tests do NOT buy: proof of correctness (they check the cases you thought of) or a substitute for types (TypeScript §09 catches shape errors for free; tests earn their keep on behavior).

The classic pyramid (many unit, some integration, few e2e — priced by speed and stability) vs the trophy (bulk in integration — where mocks are few and behavior is real). The pragmatic resolution isn't tribal: test where the risk lives. Pure logic (money math, date handling, the dsa-style algorithms) → unit. Wiring (routes + DB + auth) → integration. The three flows the business dies without → e2e. UI cosmetics → mostly nothing, and that's a choice, not a failure.

// quiz — first pick is the one that counts

A pricing function full of discount edge cases, and a settings page of toggles. Same test budget. Where does it go?

Why: test ROI = (chance of bug × cost of bug) ÷ cost of test. Pricing: combinatorial branches, real money, pure function — maximal on all three. Toggles: the framework renders them, the type system checks the wiring, and a bug is visible and cheap. Budgeting tests by risk instead of by module is the judgment interviewers actually probe with this question.

LEVEL UP — what interviewers listen for
  • The regression rule: every bug that reaches production becomes a test before the fix — the suite grows exactly where reality proved it thin.
  • "What's your testing strategy?" wants layers + reasons, not a coverage number: "unit for logic, integration for wiring, e2e for the checkout path, and types doing the shape-checking."
  • Tests as documentation implies naming discipline: it('rejects expired coupons at the second application') reads as spec; it('works') reads as noise.
  • The anti-signal to avoid: testing implementation details (asserting a private was called) — §06 makes it concrete.

Anatomy of a test — arrange, act, assert (and a framework in 20 lines)

beginner → the whole machinery, demystified by building it

Every test everywhere is three moves: Arrange (build the world: inputs, fixtures, doubles), Act (call the one thing under test — one), Assert (compare reality to expectation). A test framework is barely more: a registry of named functions, an expect that throws on mismatch, and a reporter that counts. Watch — the runner below IS a working test framework, and every Jest concept you'll meet is this plus ergonomics.

microtest.js — run it (a real test framework, 20 lines)
// ---- the entire framework ----
const tests = [];
const it = (name, fn) => tests.push({ name, fn });
const expect = (got) => ({
  toBe: (want) => { if (!Object.is(got, want)) throw new Error(`expected ${JSON.stringify(want)}, got ${JSON.stringify(got)}`); },
  toEqual: (want) => { const g = JSON.stringify(got), w = JSON.stringify(want);
    if (g !== w) throw new Error(`expected ${w}, got ${g}`); },
  toThrow: () => { try { got(); } catch { return; } throw new Error('expected it to throw'); },
});

// ---- code under test: shelter pricing ----
const adoptionFee = (cat) => {
  if (cat.age < 0) throw new Error('time-traveling cat');
  const base = cat.age < 1 ? 5000 : 2000;            // kittens cost more
  return cat.bonded ? base * 2 * 0.8 : base;          // bonded pairs: 20% off the pair
};

// ---- the tests: arrange / act / assert ----
it('prices an adult cat at base rate', () => {
  const fee = adoptionFee({ age: 3, bonded: false });   // arrange + act
  expect(fee).toBe(2000);                                // assert
});
it('charges kitten premium', () => expect(adoptionFee({ age: 0.5, bonded: false })).toBe(5000));
it('discounts bonded pairs 20%', () => expect(adoptionFee({ age: 2, bonded: true })).toBe(3200));
it('rejects impossible ages', () => expect(() => adoptionFee({ age: -1 })).toThrow());
it('THIS ONE FAILS on purpose — read the report', () => expect(adoptionFee({ age: 3, bonded: false })).toBe(9999));

// ---- the reporter ----
let pass = 0;
for (const t of tests) {
  try { t.fn(); pass++; console.log('  ✓', t.name); }
  catch (e) { console.log('  ✗', t.name, '\n      →', e.message); }
}
console.log(`\n${pass}/${tests.length} passed — and that is genuinely all a test runner is.`);
real assertions, real failure output — the framework fits in your head now

A teammate's test: act, assert, then MORE acting and asserting, five rounds deep in one it(). What's actually lost?

      

        
        
        
        
      

      
Why: a test's job on failure is to point at the crime scene — "✗ discounts bonded pairs" beats "✗ pricing works (assertion 3 of 11)". Multiple asserts on ONE act are fine (checking several fields of one result); multiple acts are separate behaviors wearing one name. The refactor is mechanical: the arrange block becomes a helper, each act+assert becomes an it. This is the most common review comment in test code — knowing the WHY behind it is the point.

    • 
        
  • Test names as specs: the "it + verb phrase" convention exists so a failing run reads as a broken requirement list.
    • 
        
  • beforeEach exists to reset the world — shared mutable fixtures across tests is the #1 cause of order-dependent flakes (§13's opening suspect).
    • 
        
  • "Write me a test framework" is a real interview prompt — you just read the answer; being able to sketch it from memory is a disproportionate flex.

    03
    

      
Jest, oriented — matchers, lifecycle & snapshots appraised

      
beginner → the 20% of the API that is 95% of usage

    

  

  

    
Jest (and Vitest — same API, faster engine, the modern default for Vite-shaped projects) is §02's microtest plus: matchers beyond toBe/toEqual — toMatchObject (subset — assert what matters, ignore noise), toContain, toBeCloseTo (floats! js-fundamentals' 0.1+0.2), rejects/resolves for promises; lifecycle — describe blocks scoping beforeEach resets; discovery — *.test.ts colocated next to the code it tests (imports stay honest, orphaned tests visible).

    
Snapshots, appraised honestly: the first run records the output, later runs diff against it. Cheap regression nets for stable, reviewable output (an error message, a config object) — and a trap for volatile trees (every UI tweak "fails" the snapshot, everyone reflexively presses update, the net now catches nothing). The tell that a snapshot went bad: nobody reads the diff before updating. Inline snapshots (small, in-file, code-reviewed) age far better than 400-line .snap files.

    

      
pricing.test.ts — read it (terminal-flavored, the shape to copy)

      
import { describe, it, expect, beforeEach } from 'vitest';
import { adoptionFee, Cart } from './pricing';

describe('adoptionFee', () => {
  it('prices adult cats at base rate', () => {
    expect(adoptionFee({ age: 3, bonded: false })).toBe(2000);
  });
  it('rejects impossible ages', () => {
    expect(() => adoptionFee({ age: -1, bonded: false })).toThrow(/time-traveling/);
  });
});

describe('Cart', () => {
  let cart: Cart;
  beforeEach(() => { cart = new Cart(); });        // fresh world per test

  it('totals fees with the bonded discount applied once', () => {
    cart.add({ age: 2, bonded: true });
    expect(cart.summary()).toMatchObject({          // subset assert — resilient
      total: 3200, discounts: ['bonded-pair'],
    });                                             // (createdAt etc: not asserted)
  });
});

    

    

      
// quiz — first pick is the one that counts

      
A test asserts the ENTIRE api response with toEqual, including timestamps and ids. It fails randomly. The durable fix?

      

        
        
        
        
      

      
Why: the failure isn't randomness — it's an assertion claiming more than the test cares about. toMatchObject + expect.any/expect.stringMatching encode "these fields matter, those exist" — the test now fails only for reasons its name describes. (C isn't wrong — fake timers have their place, §05 — but as a fix for over-assertion it's treating the symptom with infrastructure. D is how flake cultures start, §13.)

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • test.each tables for the pricing-matrix genre — one behavior, N cases, no copy-paste; reads like the spec's own table.
    • 
        
  • Watch mode is the actual dev loop (run-on-save, filtered to changed files) — "tests I run once a day" and "tests that drive my editing" are different tools psychologically.
    • 
        
  • Vitest vs Jest in a sentence: same assertions, native ESM/TS, shares Vite config — "Jest for legacy, Vitest for new" is the 2026 default answer.
    • 
        
  • The snapshot rule worth quoting: "a snapshot you wouldn't read in review is a snapshot that shouldn't exist."

    04
    

      
Mocks, spies & fakes — doubles without self-deception

      
intermediate → replace the world carefully; it's easy to test a fantasy

    

  

  

    
The vocabulary, precisely: a spy wraps a real function and records calls (behavior unchanged — you're observing); a stub returns canned answers ("the API says 404 today"); a mock is a stub with expectations about how it's called; a fake is a working lightweight implementation (in-memory repository — the star of §09). The discipline that keeps doubles honest: mock at the boundary you don't own (network, clock, randomness, third-party SDKs) and keep YOUR code real — every internal module you mock is a place the test stops testing your actual wiring.

    

      

        
spies-from-scratch.js — run it (what jest.fn() actually is)

        
// jest.fn(), hand-rolled: a callable that remembers
function fn(impl = () => undefined) {
  const f = (...args) => { f.calls.push(args); return f.impl(...args); };
  f.calls = [];
  f.impl = impl;
  f.mockReturnValue = (v) => { f.impl = () => v; return f; };
  return f;
}

// code under test: notify adopters, politely rate-limited
async function notifyAdopters(adopters, send, clock) {
  const sent = [];
  for (const a of adopters) {
    if (clock.hour() < 8) { sent.push([a, 'queued-for-morning']); continue; }
    await send(a, 'your cat misses you (allegedly)');
    sent.push([a, 'sent']);
  }
  return sent;
}

// the test: SPY on send, STUB the clock — network + time are boundaries
const send = fn(async () => {});                 // spy (records) + stub (resolves)
const nightClock = { hour: fn().mockReturnValue(3) };
const result = await notifyAdopters(['raj', 'prachi'], send, nightClock);
console.log('at 3am →', JSON.stringify(result));
console.log('send called', send.calls.length, 'times (correct: 0 — nobody texts at 3am)');

const dayClock = { hour: fn().mockReturnValue(14) };
await notifyAdopters(['raj', 'prachi'], send, dayClock);
console.log('at 2pm → send called', send.calls.length, 'times, first args:', JSON.stringify(send.calls[0]));
console.log('\nthe spy answered "did we text at night?" WITHOUT sending a single real text.');

      

      
jest.fn in 8 lines — calls recorded, behavior injected, boundaries controlled

      

    

    

      
// quiz — first pick is the one that counts

      
To test OrderService, a teammate mocks its internal PricingCalculator, DiscountEngine AND TaxHelper. All tests pass. What do the passing tests prove?

      

        
        
        
        
      

      
Why: mocking internals welds the test to the implementation structure: rename a method, tests fail (false alarm); break the discount math inside the real DiscountEngine, tests pass (false confidence) — the worst of both. These three classes are YOUR code with no awkward boundary — test OrderService with real collaborators and mock only what's slow/external. "Mock the boundary, not the org chart" — the single most valuable sentence in this module.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Module-mocking (vi.mock('./mailer')) hoists above imports — the confusing magic is the bundler rewriting your imports; DI (passing send in, like the runner) needs no magic at all. Testability IS the design pressure from §01.
    • 
        
  • Clock and randomness are boundaries too: fake timers (§05) and injected/seeded RNG — any test that reads the real clock is a future flake (§13).
    • 
        
  • For HTTP, prefer network-level interception (msw-style: your real fetch code runs, the wire is fake) over mocking your own api module — one layer more honest.
    • 
        
  • The smell heuristic: if the mock setup is longer than the assertions, the unit under test is probably cut at the wrong joint.

    05
    

      
Testing async — awaited asserts & the fake clock

      
intermediate → deterministic tests for time-dependent code

    

  

  

    
Rule one: the test must await what it asserts — an un-awaited async assertion passes vacuously (the test ends before the expect runs; js-async §05's floating promise, now silently green). Frameworks help: return/await the promise, use await expect(p).rejects.toThrow() for failure paths — asserting rejections is where "the sad path is a requirement" (fesd) meets machinery. Rule two: never test time with real time — a test that setTimeouts 3 seconds is slow forever and flaky under load; fake timers swap the clock for a lever you crank: install, run the code, advanceTimersByTime(3000), assert — three simulated seconds in zero real ones.

    

      

        
fake-clock.js — run it (fake timers, hand-rolled + a debounce tested)

        
// a controllable clock — what jest.useFakeTimers() installs
function makeClock() {
  let now = 0; const queue = [];
  return {
    setTimeout: (fn, ms) => queue.push({ at: now + ms, fn }),
    advance: (ms) => {
      now += ms;
      queue.sort((a, b) => a.at - b.at);
      while (queue.length && queue[0].at <= now) queue.shift().fn();
    },
  };
}

// code under test: debounce (js-async §08's), clock injected
function debounce(fn, ms, clock) {
  let timer = null;
  return (...args) => {
    timer = { cancelled: timer ? (timer.cancelled = true, false) : false };
    const mine = timer;
    clock.setTimeout(() => { if (!mine.cancelled) fn(...args); }, ms);
  };
}

// the test — three simulated seconds, zero real ones
const clock = makeClock();
const calls = [];
const search = debounce((q) => calls.push(q), 200, clock);

search('m'); clock.advance(100);       // typing…
search('mo'); clock.advance(100);      // still typing…
search('mochi');
console.log('before quiet period: calls =', JSON.stringify(calls), '(correct: none yet)');
clock.advance(200);                    // the quiet period elapses
console.log('after 200ms quiet:   calls =', JSON.stringify(calls), '(exactly one, the last)');
console.log('\ndeterministic, instant, and it tested TIMING LOGIC — no sleeps, no flakes.');

      

      
the clock is a parameter — advance() replaces waiting; this is all fake timers are

      

    

    

      
// quiz — first pick is the one that counts

      
it('rejects bad cats', () => { expect(validateCat(badCat)).rejects.toThrow() }) — this passes even when validateCat resolves happily. Why?

      

        
        
        
        
      

      
Why: expect(p).rejects.toThrow() evaluates to a promise; unawaited, its verdict arrives after the test already reported success — the floating-promise bug (js-async §05) in its most expensive habitat, because a vacuously-green failure-path test is worse than none (you believe the sad path is covered). Lint saves you here: expect(expect)-style rules and TS's no-floating-promises flag both catch it — say the lint names.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Fake timers + promises interleave (the js-async §10 zoo in test form): after advancing, microtasks still need a tick — await advanceTimersByTimeAsync exists because of exactly this.
    • 
        
  • Retry/backoff logic (js-async §14) is THE fake-timer showcase: assert attempt counts at t=1s, 3s, 7s without waiting seven seconds.
    • 
        
  • Waiting on conditions beats waiting on time: "advance until the queue drains" (or RTL's findBy, §06) — asserting after a fixed sleep is the flake template (§13).
    • 
        
  • AbortController paths are testable async too: abort mid-flight, assert the cleanup — the cancellation section's promises, kept under test.

    06
    

      
Testing React — queries, user-event & what not to assert

      
intermediate → test what the user sees, not what the component hides

    

  

  

    
React Testing Library's whole philosophy is one sentence: "the more your tests resemble the way your software is used, the more confidence they give" — so you find things the way a user (or screen reader) would. The query priority IS the API: getByRole('button', {name: /adopt/i}) first (roles + accessible names — your a11y and your tests share one contract; fesd's mechanisms argument, enforced), then getByLabelText (forms), getByText, and getByTestId as the documented last resort. Interactions go through user-event (await user.click(...) — real event sequences: pointer, focus, keyboard), not fireEvent (a bare dispatch).

    
The async side: findByText = getBy + waiting (for the post-fetch UI), waitFor for arbitrary conditions — never a sleep (§05). And the discipline of NOT asserting: no reaching into state, no counting renders, no snapshot of the whole tree (§03) — if the user can't perceive it, the test doesn't claim it. That's what keeps tests green through refactors that don't change behavior — the exact property §04's over-mocked tests lost.

    

      
AdoptButton.test.tsx — read it (the canonical shape)

      
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('adopts a cat and disables further clicks', async () => {
  const user = userEvent.setup();
  const onAdopt = vi.fn().mockResolvedValue(undefined);
  render(<AdoptButton cat="Mochi" onAdopt={onAdopt} />);

  await user.click(screen.getByRole('button', { name: /adopt mochi/i }));

  expect(onAdopt).toHaveBeenCalledWith('Mochi');            // the contract out
  expect(await screen.findByText(/adopted!/i)).toBeInTheDocument();  // the UI in
  expect(screen.getByRole('button', { name: /adopted/i })).toBeDisabled();
});

// note what is NOT here: no component internals, no state peeking,
// no "expect(setLoading).toHaveBeenCalled" — a rewrite from useState to
// useReducer to a store changes NOTHING above. That's the durability.

    

    

      
// quiz — first pick is the one that counts

      
getByRole('button') throws "unable to find role" but the clickable thing is right there — it's a <div onClick>. What did the test just catch?

      

        
        
        
        
      

      
Why: role queries fail for clickable divs because assistive tech fails for clickable divs — the test simulated your least-served user and reported honestly. Escaping to testId (C) ships the a11y bug with a green checkmark. This is the deepest version of "tests resemble usage": the query priority is an accessibility audit running on every commit. The fesd resilience section made the argument; RTL is its enforcement arm.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Wrap providers once: a custom render with theme/router/query providers — test files stay about behavior, not plumbing.
    • 
        
  • getBy throws now, queryBy for asserting absence, findBy awaits appearance — the trio maps to present/absent/eventually; misusing them is the most common RTL review comment.
    • 
        
  • Mock the network (msw), not the component's fetch logic — loading → success → error states all testable through the UI they produce (§04's boundary rule, React edition).
    • 
        
  • What about the RSC/server components? Rendering runs server-side (react §14) — component tests cover client islands; server components get integration/e2e coverage. Current, honest, rarely said.

    07
    

      
Hooks & context under test — renderHook and friends

      
intermediate → custom hooks are units; test them as such (usually via UI)

    

  

  

    
The default remains: test hooks through a component that uses them — that's the real contract. renderHook earns its place when a hook is a reusable library (your useDebounce, useCart, usePagination — consumed by many components, deserving direct coverage of its edge cases): it renders an invisible host component and hands you result.current. The rules that follow from React's model: state updates inside tests wrap in act() (flush the render — RTL's user-event does this for you, which is why renderHook tests see act() more), and rerenders with new props via rerender(...) test the hook's response to changing inputs — the dependency-array behaviors (react §05) made assertable.

    
Context under test is a wrapper concern: renderHook(() => useCart(), { wrapper: CartProvider }) — and testing "throws a helpful error outside its provider" is a real test (the DX your teammates will actually hit). For context-heavy apps, the §06 custom-render-with-providers pattern covers components; renderHook's wrapper option covers the hooks.

    

      
// quiz — first pick is the one that counts

      
Testing useCounter: result.current.increment(); expect(result.current.count).toBe(1) fails — count is 0. The React-model explanation?

      

        
        
        
        
      

      
Why: hooks don't mutate variables — they schedule renders (the react module's core model, resurfacing in test form). act() is "run this, then flush everything React queued", after which result.current is the fresh snapshot. The reason you rarely write act() in component tests: user-event and findBy wrap it internally. Seeing an act() warning = something updated outside those wrappers — it's a smell detector, not a formality.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Fake timers + renderHook test useDebounce completely: change input, advance clock, assert the settle — §05's machinery composed with this section's.
    • 
        
  • Testing an external-store hook (react §13): assert that two hosts see one update — the selector/subscription logic is exactly what unit tests catch early.
    • 
        
  • "Should I export the hook's internals to test them?" — no: test through the public surface; wanting internals is §04's boundary smell again.
    • 
        
  • Custom hooks returning cleanup behavior (subscriptions): unmount() in the test + assert the unsubscribe spy — the leak-prevention lessons, verified.
    •

    08
    

      
API integration tests — the request-in, response-out contract

      
intermediate → supertest-style: real routes, real middleware, controlled edges

    

  

  

    
Unit tests can't catch a route wired to the wrong middleware order (node §06's lesson) — integration tests exercise the HTTP surface: boot the app (not the network listener — supertest drives the handler directly), send a request, assert status + body shape + side effects. The sweet spot per endpoint: the happy path, each interesting failure (401 unauthenticated, 403 wrong-owner, 400 validation with a helpful message, 404), and the business-rule edge — five-ish tests that pin the CONTRACT while implementation stays free underneath (the same durability argument as §06, one layer down).

    

      
adoptions.test.ts — read it (the five-test contract)

      
import request from 'supertest';
import { makeApp } from '../app';                 // app factory: DI for the win (§04)

const app = makeApp({ db: testDb, clock: fixedClock });

describe('POST /adoptions', () => {
  it('creates an adoption for an available cat', async () => {
    const res = await request(app)
      .post('/adoptions').set(auth('raj')).send({ catId: 'mochi' });
    expect(res.status).toBe(201);
    expect(res.body).toMatchObject({ catId: 'mochi', status: 'pending' });
    expect(await testDb.adoptions.count()).toBe(1);          // the side effect
  });
  it('401s without a session', async () => {
    expect((await request(app).post('/adoptions').send({ catId: 'mochi' })).status).toBe(401);
  });
  it('400s with a NAMED field error on bad input', async () => {
    const res = await request(app).post('/adoptions').set(auth('raj')).send({});
    expect(res.status).toBe(400);
    expect(res.body.errors[0].field).toBe('catId');           // error SHAPE is contract
  });
  it('409s when the cat is already adopted', async () => { /* the business edge */ });
  it('does not leak stack traces in errors', async () => { /* node §10's promise, pinned */ });
});

    09
    

      
Tests & the database — real Postgres, isolated fast

      
intermediate → the fake-vs-real decision, and transaction rollback

    

  

  

    
The eternal question: fake the DB or use a real one? The modern answer leans real — a throwaway Postgres in Docker/testcontainers — because the things worth testing (constraints firing, transactions, the actual SQL your query builder emits, pg §06's isolation behaviors) only exist in the real engine; an in-memory fake repository (§04) stays useful for pure-logic units that just need "a thing that stores". SQLite-as-test-double is the tempting middle that lies: different types, different constraint behavior, no RETURNING quirks — passing tests against an engine you don't deploy.

    
Isolation strategies, priced: (1) transaction-per-test — BEGIN in beforeEach, ROLLBACK in afterEach: fastest, perfect isolation, but code under test that manages its own transactions collides; (2) truncate between tests — slower, honest with transactional code; (3) schema/db-per-worker for parallel runners (Jest's default parallelism will otherwise interleave two tests' rows — the mystery-flake factory). Seed with factories (makeCat({overrides})) instead of shared fixture dumps — each test states what it needs, and the "why does test 41 depend on fixture row 7?" archaeology never starts.

    

      
// quiz — first pick is the one that counts

      
The unique-email constraint test passes locally, flakes in CI. Tests run in parallel; the suite truncates tables in beforeEach. The mechanism?

      

        
        
        
        
      

      
Why: "passes alone, flakes together" is the signature of shared mutable state between parallel workers — and the DB is the biggest shared state there is. Per-worker schemas (cheap in Postgres: CREATE SCHEMA worker_3) restore isolation without giving up parallelism. The general law, third appearance (§02 fixtures, node §12 replicas, now this): parallel things sharing mutable state will eventually interleave — in tests, "eventually" means the Friday deploy.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Run migrations in test setup — testing against a hand-built schema drifts from production's; the migration files (pg §14) are the single truth.
    • 
        
  • Factories with realistic defaults + explicit overrides read as arrange-blocks: makeCat({ adopted: true }) — the test names exactly its relevant state.
    • 
        
  • Test the pg module's races on purpose: two concurrent updates in a test proving your FOR UPDATE actually serializes — the lost-update lesson, pinned forever.
    • 
        
  • Data-layer tests are where N+1 regressions get caught cheaply: assert query COUNT with a counting pool wrapper — "this endpoint makes 3 queries, not 51".

End-to-end — Playwright's model, and when e2e earns its cost

      
advanced → few, critical, trusted: the top of the pyramid, kept honest

    

  

  

    
E2E drives a real browser against your real (or realistically-staged) stack — maximum truth, maximum cost: slowest to run, most machinery to break, most sensitive to timing. The modern tooling (Playwright) removed the classic pain: locators auto-wait (page.click retries until actionable — the sleep-riddled Selenium era is over), web-first assertions retry until timeout (await expect(page.getByText('Adopted!')).toBeVisible()), and the trace viewer records DOM+network+console per step, so a CI failure replays like a film instead of a screenshot and a shrug.

    
The discipline is portfolio-sizing (§01's risk budget at its most expensive tier): the flows the business dies without — signup, login, checkout/adopt, the money path — a dozen-ish journeys, not a re-implementation of the unit suite through a browser. Auth via a shared setup project (log in once, reuse storage state) keeps runs fast; test data via API seeding (not UI clicking through setup — the slowest possible arrange block); and selectors via roles/labels (§06's priority — e2e and component tests share the same "find it like a user" contract).

    

      
// quiz — first pick is the one that counts

      
A team has 400 e2e tests, 40 minutes, ~5 random failures per run that pass on retry. Everyone auto-retries and merges. What has the suite become, and the fix?

      

        
        
        
        
      

      
Why: a test suite's entire value is that red means broken — 5 expected-random failures means red means "shrug", and the day checkout actually breaks, it ships inside the noise. 400 browser tests usually re-test what integration tests prove in seconds; the e2e tier should be small enough that flakes are INCIDENTS. "I'd rather have 15 e2e tests everyone trusts than 400 everyone retries" is the sentence that ends the question.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Playwright vs Cypress in one line: multi-browser + parallel + trace viewer vs the nicer interactive dev UX — both fine; the portfolio discipline matters more than the logo.
    • 
        
  • Run e2e against preview deploys (per-PR environments) — testing the real build artifact catches the "works in dev server" class nothing else can.
    • 
        
  • Visual regression (screenshot diffing) is a separate, deliberately-small suite — pixel-noise management (fonts, antialiasing) is its whole job; know it exists, don't bolt it onto every journey.
    • 
        
  • The staging-data problem is the real e2e boss fight: tests that create their own data via API and clean up after are the only ones that survive shared environments.

Coverage, honestly — what the number measures and misses

      
advanced → line vs branch, and why 100% proves nothing

    

  

  

    
Coverage counts which code executed during tests — nothing about whether anything was asserted. The tiers: line coverage (weakest — the line ran), branch (each if/else arm — the one worth watching: 100% lines can hide an untested else), function, and the ceiling truth: a test suite of it('runs', () => { doEverything() }) with zero expects can score 90%+. Coverage answers exactly one question well — "what did we definitely NOT test?" — and that reading (hunting the red files that matter) is genuinely useful; the inverse reading ("87% = quality") is the cargo cult.

    

      

        
coverage-lies.js — run it (100% covered, 0% tested)

        
// instrument a function the way coverage tools do — count branch hits
const hits = { adult: 0, kitten: 0, bonded: 0, single: 0 };
function fee(cat) {
  let base;
  if (cat.age < 1) { hits.kitten++; base = 5000; }
  else { hits.adult++; base = 2000; }
  if (cat.bonded) { hits.bonded++; return base * 2 * 0.8; }
  else { hits.single++; return base; }
}

// "test suite" A: hits every branch, asserts NOTHING
fee({ age: 0.5, bonded: true });
fee({ age: 3, bonded: false });
const covered = Object.values(hits).filter(h => h > 0).length;
console.log(`suite A: ${covered}/4 branches covered — 100% branch coverage, ZERO assertions`);
console.log('  fee could return -Infinity and this "suite" stays green.\n');

// suite B: 50% coverage, but the covered half is PROVEN
Object.keys(hits).forEach(k => hits[k] = 0);
const expectEq = (got, want, name) =>
  console.log(`  ${Object.is(got, want) ? '✓' : '✗'} ${name} (got ${got})`);
expectEq(fee({ age: 3, bonded: false }), 2000, 'adult single = base');
expectEq(fee({ age: 3, bonded: true }), 3200, 'bonded pair discounts correctly');
console.log(`suite B: ${Object.values(hits).filter(h => h > 0).length}/4 branches — lower number, real knowledge`);
console.log('\ncoverage measures EXECUTION. only assertions measure CORRECTNESS.');
console.log('(mutation testing closes the gap: mutate the code, expect tests to notice.)');

      

      
suite A's 100% vs suite B's 50% — which codebase would you deploy?

      

    

    

      
// quiz — first pick is the one that counts

      
Leadership mandates 90% coverage, gated in CI. Predict the second-order effects, honestly.

      

        
        
        
        
      

      
Why: when a measure becomes a target it stops measuring (Goodhart) — and coverage is maximally gameable because execution ≠ verification (the runner you just ran). The usable versions: per-PR diff coverage ("new code arrives tested" — a ratchet, like the TS migration), coverage as a map for review attention, and mutation testing where correctness truly matters. Saying "coverage is a flashlight, not a scoreboard" earns the nod.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Mutation testing (Stryker) in one line: "it breaks your code on purpose and checks a test notices — the only tool that measures assertion quality." Slow; aim it at the money modules.
    • 
        
  • Exclude the right things (generated code, config) so the number describes decisions, not boilerplate — a 60% honest number beats an 85% padded one.
    • 
        
  • Branch coverage on error paths is where real gaps hide — the catch blocks and 4xx arms (§08's sad-path tests) are the classic red zones.
    • 
        
  • The interview framing: "what's your coverage?" → answer with the strategy (§01) first, the number second, and the diff-ratchet as how you keep it real.

TDD, demystified — red, green, refactor on a real kata

      
advanced → a design technique that emits tests, used when it fits

    

  

  

    
TDD's loop: red (write one failing test — smallest next behavior), green (dumbest code that passes — resist generality), refactor (clean up under the safety net you just built). The part evangelists undersell: the red step is a design act — you write the CALL before the implementation, so awkward APIs get caught while they're one line old (§01's design pressure, systematized). The part skeptics miss: "dumbest thing that passes" isn't stupidity — it's forcing the NEXT test to justify every generalization, which is how you avoid speculative complexity.

    
The honest applicability map: TDD shines on specifiable logic — parsers, pricing, validation, algorithm-shaped problems (every dsa drill is secretly a TDD kata: examples first, code second). It fights you on exploratory UI and unclear requirements — spiking first, then testing what survived, is not a failure of virtue. "I TDD the core, test-after the edges, and always regression-test bugs (§01)" is a real practice, defensible in any interview.

    

      

        
tdd-kata.js — run it (three loops of red-green, narrated)

        
// kata: parse "3 tuna, 2 salmon" into meal counts. Watch the API get designed.
const expectEq = (got, want, name) => {
  const g = JSON.stringify(got), w = JSON.stringify(want);
  console.log(`  ${g === w ? '✓ GREEN' : '✗ RED  '} ${name}${g === w ? '' : `  (got ${g}, want ${w})`}`);
};

console.log('LOOP 1 · red: simplest behavior — empty order');
let parseOrder = undefined;                        // no code yet: the test comes first
try { parseOrder(''); } catch { console.log('  ✗ RED   parseOrder is not even a function'); }
console.log('        green: dumbest passing code');
parseOrder = () => ({});
expectEq(parseOrder(''), {}, 'empty order → empty counts');

console.log('LOOP 2 · red: one item — the dumb version must fail');
expectEq(parseOrder('3 tuna'), { tuna: 3 }, 'single item parses');
console.log('        green: generalize JUST enough');
parseOrder = (s) => {
  if (!s.trim()) return {};
  const [n, food] = s.trim().split(' ');
  return { [food]: Number(n) };
};
expectEq(parseOrder('3 tuna'), { tuna: 3 }, 'single item parses');

console.log('LOOP 3 · red: multiple items force the real shape');
expectEq(parseOrder('3 tuna, 2 salmon'), { tuna: 3, salmon: 2 }, 'multiple items');
console.log('        green + refactor: the loop earns its generality');
parseOrder = (s) => Object.fromEntries(
  s.split(',').map(p => p.trim()).filter(Boolean)
   .map(p => { const [n, food] = p.split(' '); return [food, Number(n)]; }));
expectEq(parseOrder('3 tuna, 2 salmon'), { tuna: 3, salmon: 2 }, 'multiple items');
expectEq(parseOrder(''), {}, 'empty STILL works — the net held during refactor');
console.log('\nthree behaviors, three tests, zero speculative code — that is the whole method.');

      

      
watch each red demand exactly one generalization — no more

      

    

    

      
// quiz — first pick is the one that counts

      
In loop 1, writing parseOrder = () => ({}) — obviously "wrong" — instead of the full parser. What's the actual argument for it?

      

        
        
        
        
      

      
Why: "fake it till the tests force you" inverts the usual failure mode (code that does more than anyone verified). If () => ({}) survives your suite, the suite is silent about everything — a fact better learned in loop 1 than in production. It's the same ratchet logic as coverage-on-diff and TS migration: progress only by evidence. That through-line — evidence-driven increments — is this whole module wearing three costumes.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • In live-coding interviews, lightweight TDD is a visible superpower: state the examples first (that's the red), code to them, run often — the interviewer watches your process, and this IS a process.
    • 
        
  • "Transformation priority" in one line: constants → variables → conditionals → loops — the green steps escalate in tiny, principled jumps.
    • 
        
  • Test-after is fine when honest — the sin isn't sequence, it's tests written to pass the code instead of specify it (they assert what IS, not what SHOULD be).
    • 
        
  • TDD's real product is the safety net at refactor time — the react/node modules' "refactor with confidence" claims all cash out here.

Flakes & CI — keeping red meaningful at team scale

      
advanced → the sociology of test suites, engineered

    

  

  

    
A flake is a test whose verdict varies without code changes, and every flake has a real cause: shared state (parallel workers, module-level mutables — §09's DB, §02's fixtures), real time (sleeps, today's date, timezone — §05's clock), unawaited async (the §05 vacuous pass, or its cousin: asserting before settlement), order dependence (test B needs A's leftovers — run with random order to flush these on purpose), and external services (§08's sandbox). "Flaky" is a diagnosis-pending label, not a category of weather — every one is a bug in test OR code (a race your test found first is a GIFT, node §12 would remind you).

    
The CI machinery that keeps trust: quarantine (a failing-flaky test moves to a non-blocking lane with an owner and a deadline — never deleted silently, never retried into invisibility), ordered stages (lint+types → unit → integration → e2e: cheapest verdicts first, fail fast), parallelism with isolation (per-worker DBs; §09), and the cultural rule that outranks all tooling: a red main is everyone's now-problem — the broken-windows dynamics of a suite are faster than any migration: two weeks of "ignore the red one" and the suite is decoration.

    

      
// quiz — first pick is the one that counts

      
A test fails every day around 05:30 UTC and passes on rerun. Rank the hypotheses.

      

        
        
        
        
      

      
Why: flakes that correlate with WHEN are time bugs; with PARALLELISM, shared state; with ORDER, leftovers — the correlation is the diagnostic (the observability module's whole method, aimed at your own suite). 05:30 UTC screams date-boundary: some assertion about "orders from today" straddling a day flip. Fix = fake the clock (§05) and add the boundary as an explicit case — the flake becomes the suite's best regression test. Permanent quarantine (D) is where test suites go to die.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Flake RATE is a trackable metric (reruns-to-green per week) — teams that chart it fix it; teams that don't, normalize it.
    • 
        
  • Random test order locally, fixed seed on failure for reproduction — flushing order-dependence continuously beats discovering it during an incident freeze.
    • 
        
  • "Retries: 1, with logged shame" is defensible for e2e ONLY — retried unit tests are always hiding a real bug; the tier changes the policy.
    • 
        
  • The closing sentence for any testing interview: "my goal is a suite where green means ship and red means stop — everything in this module is in service of keeping those two words true."
