01

How Node runs your code — one loop, all the users

beginner → why blocking is a server-wide event

Node = V8 (Chrome's JS engine) + libuv (a C library doing async I/O and a small thread pool) + APIs binding them. Your JS still runs on one thread with an event loop — the same machine from Async JS — but now that loop serves every connected user. A request arrives → your handler runs → it awaits the DB → the loop serves other requests → the DB answers → your handler resumes.

The consequence that defines Node backend engineering: one CPU-heavy handler freezes everyone. A 2-second synchronous loop in one route = every other request waits 2 seconds. I/O concurrency is nearly free; CPU work is the thing you architect around (worker threads, job queues, or chunking).

PROFESSOR WHISKERS EXPLAINSThe cat café's delivery kitchen has one chef (the loop) and many appliances (libuv: ovens, fryers — the I/O). Orders fly because the chef never watches an oven — set it, move on, plate when it dings. But if one order requires the chef to hand-whisk for two minutes (CPU work), every order in the kitchen stalls — not just the whisky one. The fix is never "whisk faster": hire a whisking assistant (worker thread) or send it to the prep kitchen (job queue).

one-chef.js — run it
// a tiny server simulation: 4 requests arrive together
const t0 = Date.now();
const at = () => String(Date.now() - t0).padStart(4) + 'ms';
const io = (ms) => new Promise(r => setTimeout(r, ms));   // oven work

async function goodHandler(id) {
  await io(300);                       // DB query — chef moves on
  console.log(at(), `req ${id} done (I/O path)`);
}

function badHandler(id) {
  const end = Date.now() + 300;        // hand-whisking: CPU on the loop
  while (Date.now() < end) {}
  console.log(at(), `req ${id} done (CPU path)`);
}

console.log('--- 4 concurrent I/O requests (300ms each) ---');
await Promise.all([1, 2, 3, 4].map(goodHandler));
console.log(at(), '→ all four finished together: ~300ms total');

console.log('--- 4 "concurrent" CPU requests (300ms each) ---');
const t1 = Date.now();
[5, 6, 7, 8].forEach(badHandler);
console.log(at(), `→ serialized: ~${Date.now() - t1}ms — everyone waited`);
300ms vs 1200ms — the entire Node performance model in two numbers

    02
    

      
The event loop's phases — libuv's actual schedule

      
beginner → timers, poll, check: where callbacks really queue

    

  

  

    
Section 01 gave you the one-chef model; here's the chef's actual rota. Node's loop (provided by libuv) cycles through phases, each with its own queue: timers (expired setTimeout/setInterval) → poll (I/O callbacks: sockets, files — and where the loop waits when idle) → check (setImmediate callbacks) → close callbacks, then around again. Two queues jump ALL of it: process.nextTick and then promise microtasks drain completely after every single callback, whatever the phase.

    
Why care? Three production behaviors fall out. setImmediate vs setTimeout(0) ordering is guaranteed only inside an I/O callback (you're in poll; check comes next — setImmediate wins). A recursive process.nextTick starves the entire loop (I/O included — worse than the browser's microtask loop). And "the loop is blocked" has a number: event-loop lag, the delay between a timer's due time and its firing — the first metric any Node dashboard should chart.

    

      
phase-order.js — read it, run it in a terminal (Node-only APIs)

      
// inside an I/O callback, the order is deterministic — narrate why:
const fs = require('fs');
fs.readFile(__filename, () => {          // ← we're in the POLL phase
  setTimeout(() => console.log('4 · timeout'), 0);     // waits for next TIMERS phase
  setImmediate(() => console.log('3 · immediate'));    // CHECK phase — right after poll!
  process.nextTick(() => console.log('1 · nextTick')); // jumps everything
  Promise.resolve().then(() => console.log('2 · promise'));
});
// prints 1, 2, 3, 4 — nextTick → microtasks → check → (wrap around) → timers

// off I/O (top level), setTimeout-vs-setImmediate order is a COIN FLIP —
// the loop may or may not reach timers before 1ms elapses. Famous trivia.

    

    

      

        
loop-lag.js — run it (the metric, simulated here in the browser)

        
// event-loop lag: schedule a 10ms timer, measure when it ACTUALLY fires
async function measureLag(blockMs) {
  const due = performance.now() + 10;
  const fired = await new Promise(r => {
    setTimeout(() => r(performance.now()), 10);
    const t0 = performance.now();               // meanwhile: block the loop
    while (performance.now() - t0 < blockMs) {} // (sync spin = CPU work on the loop)
  });
  return Math.max(0, fired - due).toFixed(1);
}
console.log('lag with  0ms of blocking work:', await measureLag(0), 'ms');
console.log('lag with 60ms of blocking work:', await measureLag(60), 'ms');
console.log('lag with 150ms of blocking work:', await measureLag(150), 'ms');
console.log('\nthe timer was "due" — the loop was busy. In Node, EVERY user request');
console.log('queued behind that spin. Chart this number; alert on it.');

      

      
lag ≈ the blocking work — the one Node metric that predicts outages

      

    

    

      
// quiz — first pick is the one that counts

      
A teammate "yields to the event loop" inside a heavy job with recursive process.nextTick. What actually happens?

      

        
        
        
        
      

      
Why: nextTick's contract is "before anything else, always" — recursing on it means "before anything else, forever". setImmediate queues in the check phase, so each iteration lets poll (your users' requests) run between chunks.     • 
        
  • Monitor lag with perf_hooks.monitorEventLoopDelay() — name the API and the alert threshold instinct (p99 > ~100ms = users feel it).
    • 
        
  • Chunk CPU work with awaited setImmediate between slices — or skip to the honest fix: worker threads (§12), because chunking shares the chef, it doesn't hire one.

    03
    

      
Streams & backpressure — process the river, don't drink it

      
intermediate → the memory model that saves your RAM

    

  

  

    
Reading a 2GB CSV with readFile puts 2GB in RAM before you touch byte one. A stream hands you the file in chunks (~64KB) as they arrive — memory stays flat regardless of file size, and the first chunk is processed before the last is even read. Files, HTTP bodies, DB cursors, S3 uploads — all the big data paths in Node are streams; .pipe() (or pipeline()) snaps them together.

    
Backpressure is the flow control that makes piping safe: when a slow consumer (client on 3G) can't keep up with a fast producer (SSD read), the pipe signals the producer to pause until the consumer drains. Without it, chunks pile up in memory and you've reinvented readFile with extra steps. pipeline() handles it — and error propagation — automatically, which is why it's the modern answer over bare .pipe.

    

      

        
the-river.js — run it

        
// simulate: 12-chunk file, slow consumer, buffer watched live
async function withBackpressure() {
  let buffered = 0, peak = 0;
  for (let chunk = 1; chunk <= 12; chunk++) {
    buffered++;                                   // producer reads a chunk
    peak = Math.max(peak, buffered);
    await new Promise(r => setTimeout(r, 40));    // consumer drains it
    buffered--;                                   // …before the next read
  }
  return peak;
}
async function withoutBackpressure() {
  let buffered = 0, peak = 0;
  const drains = [];
  for (let chunk = 1; chunk <= 12; chunk++) {
    buffered++;                                   // producer sprints ahead
    peak = Math.max(peak, buffered);
    drains.push(new Promise(r => setTimeout(() => { buffered--; r(); }, 40 * chunk)));
  }
  await Promise.all(drains);
  return peak;
}
console.log('peak buffer WITH backpressure:   ', await withBackpressure(), 'chunk');
console.log('peak buffer WITHOUT backpressure:', await withoutBackpressure(), 'chunks');
console.log('now imagine chunks are 64KB and the file is 2GB…');

// the real-world shape (Node):
// await pipeline(
//   fs.createReadStream('big.csv'),
//   csvParser(),                    // transform stream
//   uploadTo(s3),                   // writable
// );  ← backpressure + error handling, handled

      

      
1 chunk vs 12 chunks in memory — backpressure is the difference

      

    

    

      
// quiz — first pick is the one that counts

      
The "export all orders as CSV" endpoint OOMs the server on big accounts. The streaming fix, end to end?

      

        
        
        
        
      

      
Why: the OOM chain is "SELECT * into an array → stringify → res.send" — three full copies in RAM. Cursor + transform + response streams process a few hundred rows at a time; a slow downloader slows the DB read down (backpressure reaching all the way back), which is exactly what you want. The temp file dodges RAM but doubles latency and adds disk churn — mention it as the fallback, not the answer.

    

    

      
LEVEL UP — what interviewers listen for

    • 
        
  • pipeline() over .pipe(): propagates errors and cleans up on failure — bare pipe chains leak file descriptors when a middle stream errors. This detail reads as production scar tissue.
    • 
        
  • Web Streams (the WHATWG kind) are converging with Node streams — Readable.toWeb() bridges them; fetch bodies and RSC streaming use the web flavor.

    04
    

      
Backpressure, measured — highWaterMark & the pause signal

      
intermediate → what §03 promised, with the queue levels visible

    

  

  

    
Section 03 said "backpressure pauses the producer"; this section shows the machinery. Every stream stage owns a small buffer with a highWaterMark (default 64KB for bytes, 16 objects in object mode). Writing returns a boolean: writable.write(chunk) says false when the buffer crossed the mark — "I'll take it, but stop sending". A disciplined producer pauses and resumes on the 'drain' event. pipe()/pipeline() wire that pause/resume automatically, which is why hand-rolled .on('data', write) loops (which ignore the boolean) are the classic memory-blowup.

    

      

        
water-levels.js — run it (Web Streams, same physics as Node's)

        
// producer: instant. consumer: 25ms per bowl. queue: capacity 3.
// watch desiredSize — positive = "send more", ≤0 = backpressure engaged
const results = [];
const sink = new WritableStream(
  { async write(chunk) {
      await new Promise(r => setTimeout(r, 25));      // slow eater
      results.push(chunk);
    } },
  new CountQueuingStrategy({ highWaterMark: 3 })       // the water mark
);

const writer = sink.getWriter();
for (let i = 1; i <= 8; i++) {
  console.log(`offer meal ${i} — desiredSize ${writer.desiredSize}` +
              (writer.desiredSize <= 0 ? '  ← full: producer must WAIT' : ''));
  await writer.ready;                                  // ← the pause, honored
  writer.write(`meal-${i}`);
}
await writer.close();
console.log(`\nall ${results.length} meals eaten; queue never exceeded 3.`);
console.log('writer.ready is the polite producer; ignoring it is the RAM spike.');

      

      
desiredSize hits 0 and the producer waits — backpressure, observed live

      

    

    

      
// quiz — first pick is the one that counts

      
A Node service reads a fast socket and writes to a slow disk with src.on('data', c => dst.write(c)). Under load, memory climbs until the process dies. The mechanism?

      

        
        
        
        
      

      
Why: write() never rejects work — it buffers and signals. Ignore the signal and the writable's internal queue becomes an unbounded array of Buffers (reachable, so GC is helpless — js-fundamentals' leak definition, server edition). pipe/pipeline exist because the protocol is easy to describe and tedious to honor by hand; pipeline also propagates errors and cleanup, which raw pipe famously doesn't.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • highWaterMark is a hint, not a cap — write() above it still buffers; the mark only flips the boolean. "Soft limit + honor system" is the accurate description.
    • 
        
  • Async iteration (for await (const c of src)) gets backpressure free — the pull model can't outrun the consumer (js-async §11's point, now on the server).
    • 
        
  • Tuning: bigger marks = throughput (fewer pauses), smaller = memory ceiling × concurrent streams. The multiplication by concurrency is the part juniors miss.
    • 
        
  • The interview sentence: "backpressure is flow control — TCP has it, streams have it, and any queue without it is an outage postponed" (system-design's queues section says the same about SQS).
    •

    05
    

      
Buffers & encodings — bytes, honestly

      
intermediate → what a Buffer is, and the multibyte traps

    

  

  

    
Everything on the wire is bytes; a Buffer is Node's fixed-length byte array (a Uint8Array subclass — the browser code below uses the parent and everything transfers). An encoding is the contract for turning text into bytes: UTF-8 spends 1 byte on ASCII, 2–4 on everything else. The traps all come from forgetting which side you're on: string length ≠ byte length ("🐈".length is 2 JS code units, 4 UTF-8 bytes — Content-Length bugs live here), and chunk boundaries don't respect characters — a multibyte cat can be sliced mid-byte by the network, so decoding chunk-by-chunk corrupts; stream decoders hold partial characters until complete.

    

      

        
bytes-honestly.js — run it (TextEncoder = Buffer.from's browser twin)

        
const enc = new TextEncoder(), dec = new TextDecoder();

// 1 · string length vs BYTE length — the Content-Length bug
for (const s of ['cat', 'café', '🐈']) {
  console.log(`"${s}" — .length ${s.length}, UTF-8 bytes ${enc.encode(s).length}`);
}

// 2 · bytes are just numbers — read the cat
const bytes = enc.encode('🐈');
console.log('the cat, as bytes:', [...bytes].map(b => b.toString(16)).join(' '));

// 3 · THE SPLIT-CHARACTER TRAP: a chunk boundary lands mid-cat
const chunk1 = bytes.slice(0, 2), chunk2 = bytes.slice(2);
console.log('naive per-chunk decode:',
  JSON.stringify(dec.decode(chunk1) + dec.decode(chunk2)), '← corrupted');

// the fix: a STREAMING decoder holds incomplete sequences
const sdec = new TextDecoder();
const out = sdec.decode(chunk1, { stream: true })    // "" — waiting for the rest
          + sdec.decode(chunk2);                     // completes the cat
console.log('streaming decode:  ', JSON.stringify(out), '← intact');
console.log('\nNode twin: string_decoder / TextDecoder — same reason, same fix.');

// 4 · base64: bytes dressed for text-only channels (+33% size)
console.log('cat in base64:', btoa(String.fromCharCode(...bytes)),
  '— JWTs, data URLs, email attachments all pay this tax');

      

      
the corrupted cat in part 3 is a real production bug class — chunked JSON logs

      

    

    

      
// quiz — first pick is the one that counts

      
An API sets Content-Length: body.length (JS string length) and clients report truncated responses — but only for some users. Who, and why?

      

        
        
        
        
      

      
Why: ASCII-only bodies have length == bytes, so the bug hides until Renée or 🐈 shows up — the worst kind of intermittent. Buffer.byteLength(body) (or letting the framework set the header) is the fix. The pattern to name: "works in dev, breaks on real names" is almost always an encoding assumption — same family as the é-vs-é normalization traps.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Buffer.allocUnsafe hands you recycled memory — fast, but unwritten regions can leak other requests' old data. Naming that risk is a real security signal (it's a CVE pattern).
    • 
        
  • Binary protocol work is DataView/readUInt32BE territory — endianness gets one sentence: "network order is big-endian".
    • 
        
  • String concatenation of chunks (body += chunk) both corrupts multibyte AND is the O(n²) trap — collect Buffers, Buffer.concat once, decode once.
    • 
        
  • JWTs are base64url, not base64 — the +/→-_ swap; decoding one by hand in an interview (auth §08's tamper demo) is a two-minute flex.
    •

    06
    

      
Express, from scratch — the middleware machine

      
intermediate → app.use, demystified in 20 lines

    

  

  

    
Express is a small idea executed well: a request flows through a chain of functions — each gets (req, res, next), does its bit (parse, log, authenticate, authorize), and either passes control on with next(), or ends the chain by responding. Routes are just middleware with a path filter. That's the entire framework — and building it in 20 lines makes every Express behavior obvious forever.

    
Two behaviors people learn by pain instead: order matters (auth before routes, error handler last — the chain runs top to bottom), and forgetting next() hangs the request (nobody ends the chain, the client waits forever).

    

      

        
express-in-20-lines.js — run it

        
// a faithful miniature of Express's core
function createApp() {
  const chain = [];
  return {
    use(fn) { chain.push(fn); },
    async handle(req) {
      const res = { sent: null,
        send(body) { this.sent = body; return this; } };
      let i = 0;
      const next = async (err) => {
        if (err) { res.send({ status: 500, error: err.message }); return; }
        const fn = chain[i++];
        if (fn) await fn(req, res, next);
      };
      await next();
      return res.sent ?? { status: 404, error: 'no one answered' };
    },
  };
}

const app = createApp();
app.use(async (req, res, next) => {           // logger
  console.log('→', req.method, req.path);
  await next();
});
app.use(async (req, res, next) => {           // auth gate
  if (!req.headers.token) return res.send({ status: 401, error: 'who are you?' });
  req.user = 'mochi';                          // enrich req, pass on
  await next();
});
app.use(async (req, res, next) => {           // the route
  if (req.path !== '/treats') return next();   // not mine — pass
  res.send({ status: 200, treats: ['tuna'], for: req.user });
});

console.log(await app.handle({ method: 'GET', path: '/treats', headers: {} }));
console.log(await app.handle({ method: 'GET', path: '/treats', headers: { token: 'meow' } }));
console.log(await app.handle({ method: 'GET', path: '/naps', headers: { token: 'meow' } }));

      

      
401 without a token, 200 with, 404 for unclaimed paths — the chain at work

      

    

    

      
// quiz — first pick is the one that counts

      
In Express 4, an async route handler throws. What happens, and what's the discipline?

      

        
        
        
        
      

      
Why: Express 4 predates promises — it only catches synchronous throws; an async throw is just a rejected promise it never awaits. The pattern: const wrap = fn => (req, res, next) => fn(req, res, next).catch(next) around every async handler (Express 5 finally does this natively). Knowing WHICH major version fixed it is exactly the kind of precision screens fish for.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The error middleware's four-argument signature (err, req, res, next) is how Express recognizes it — and it goes LAST. One centralized error handler > try/catch confetti.
    • 
        
  • Layered structure to say out loud: routes (HTTP concerns) → services (business logic, framework-free) → data access. Testable without HTTP, swappable without rewrites.
    • 
        
  • Fastify/Hono/NestJS in one line each: faster serialization / edge-portable / enterprise DI structure — "Express's model transfers to all of them" is the calming close.

    07
    

      
REST API design — a contract, not a vibe

      
intermediate → resources, verbs, and the decisions that age well

    

  

  

    
REST's discipline in one line: URLs name things (nouns), methods act on them (verbs), status codes report honestly. GET /cats/42 reads, POST /cats creates (201 + Location), PATCH /cats/42 partially updates, DELETE deletes (204). Collections are plural; nesting expresses ownership one level deep (/cats/42/vaccinations) and then stops — deep nesting handcuffs you later.

    
The parts that separate a professional API: consistent error envelope (code + message + details, same shape everywhere), cursor pagination (you know why from DSA — offsets shift under writes), idempotency (GET/PUT/DELETE naturally; POST via idempotency keys — the double-click double-charge killer), and versioning you can live with (/v1 path pragmatism; additive changes don't need a bump, removals do).

    

      
the-contract.txt

      
the adoption-center API, designed out loud:

GET    /v1/cats?status=adoptable&cursor=eyJpZCI6OTh9&limit=20
       → 200 { items: [...], nextCursor: "…" }        (stable under writes)
POST   /v1/cats            → 201 + Location: /v1/cats/43
       Idempotency-Key: 7f3a…                          (retry-safe create)
GET    /v1/cats/43         → 200 | 404
PATCH  /v1/cats/43         → 200 { …updated cat }      (partial update)
DELETE /v1/cats/43         → 204                       (repeatable: still 204/404)
POST   /v1/cats/43/adoptions → the "verb as sub-resource" trick
                               for actions that aren't CRUD

errors, ONE shape everywhere:
  422 { error: { code: "VALIDATION", message: "name is required",
                 details: [{ field: "name", rule: "required" }],
                 requestId: "r-8823" } }

status honesty cheat-line:
  200 ok · 201 created · 204 no-body · 400 malformed · 401 who?
  403 no. · 404 nothing here · 409 conflict · 422 invalid · 429 slow down
  500 our bug · 503 overloaded

    

    

      
// quiz — first pick is the one that counts

      
"Adopt a cat" doesn't fit CRUD — it changes cat status, creates a record, notifies staff. How do you model it RESTfully?

      

        
        
        
        
      

      
Why: "model the action as the noun it produces" keeps REST's benefits (a GET-able adoption record, clean auditing) for real workflows. GET mutating is the cardinal sin (crawlers adopt cats). Bare PATCH loses the event's identity — who adopted, when, the paperwork. And full RPC is premature surrender; though naming that some APIs do use :verb suffixes (Google style) shows range. This question is beloved because it tests design taste, not memorized verbs.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • PUT vs PATCH precisely: PUT replaces the whole resource (idempotent by definition); PATCH applies a partial change. Saying "PUT is what makes retries trivially safe" links it to resilience.
    • 
        
  • Rate limiting headers (429 + Retry-After), request ids in every error (support can trace), and sunset headers for deprecation — three small marks of an API run by adults.
    • 
        
  • The REST-vs-GraphQL calibration lives in Full-Stack in 48 · API design — one sentence here: REST for service-to-service and cacheability; GraphQL when many client shapes query many services.

    08
    

      
Auth, decided — sessions, JWTs, and the hybrid everyone ships

      
the interview classic, resolved properly

    

  

  

    
Sessions: login → server stores a session record (Redis) → browser holds an opaque id in an httpOnly cookie → every request looks the session up. Revocation is trivial (delete the record); the cost is that lookup on every request and shared session storage across servers. JWTs: login → server signs a token containing the claims → client sends it back → server verifies the signature, no lookup. Stateless and cheap to check — but you can't un-sign a token: revocation before expiry needs a denylist… which is state again.

    
The judgment, stated like a senior: short-lived access token (5–15 min) + rotating refresh token, both in httpOnly SameSite cookies for browsers. The access token gives you stateless verification on every request; the refresh flow gives you a revocation point (refresh tokens live server-side, can be killed); the cookies keep XSS's hands off everything. Passwords, when you store them: bcrypt/argon2, never anything reversible — that part is settled law.

    

      

        
sign-verify.js — run it (a real HMAC-JWT, minus the base64url pedantry)

        
// JWTs aren't magic: header.payload.signature, signed not encrypted
const SECRET = 'cafe-secret-keep-in-env';

async function hmac(data) {
  const key = await crypto.subtle.importKey('raw',
    new TextEncoder().encode(SECRET),
    { name: 'HMAC', hash: 'SHA-256' }, false, ['sign']);
  const sig = await crypto.subtle.sign('HMAC', key,
    new TextEncoder().encode(data));
  return btoa(String.fromCharCode(...new Uint8Array(sig))).slice(0, 16) + '…';
}

async function sign(payload) {
  const body = btoa(JSON.stringify(payload));
  return body + '.' + await hmac(body);
}
async function verify(token) {
  const [body, sig] = token.split('.');
  if (await hmac(body) !== sig) return { valid: false, reason: 'TAMPERED' };
  const claims = JSON.parse(atob(body));
  if (claims.exp < Date.now()) return { valid: false, reason: 'EXPIRED' };
  return { valid: true, claims };
}

const evil = btoa(JSON.stringify({ ...JSON.parse(atob(body)), role: 'admin' }));
console.log('tampered:', await verify(evil + '.' + token.split('.')[1]));
// payload is READABLE by anyone (it's just base64!) — never put
// secrets in a JWT. the signature only proves nobody CHANGED it.

OAuth & token lifecycles — the flows, finally drawn

      
intermediate → "Login with Google" step by step, plus rotation done right

    

  

  

    
Section 08 decided sessions-vs-JWT for your users; this section covers borrowing someone else's login. OAuth 2 + OIDC, the authorization-code flow: (1) you redirect to Google with your client_id, requested scopes, and a redirect_uri; (2) the user consents on Google's page — their password never touches you; (3) Google redirects back with a one-time code; (4) your server exchanges code + client_secret for tokens — an ID token (a JWT proving who they are — that's the OIDC part) and an access token (permission to call Google's APIs). The code hop exists so tokens never transit the browser URL; PKCE (a hashed one-time secret) protects the exchange for apps that can't hold a client_secret — and is now recommended for everyone.

    
The other half is refresh rotation: every refresh issues a new refresh token and retires the old one. The payoff is reuse detection — if a retired token ever comes back, someone was cloned (the user has the new one, so who's replaying the old?): revoke the whole family, force re-login.

    

      

        
rotation-tripwire.js — run it (reuse detection, simulated)

        
// a token family: each refresh rotates; reuse of a RETIRED token = alarm
function makeFamily(user) {
  let current = 1, revoked = false;
  const issued = () => `${user}.rt${current}`;
  return {
    refresh(presented) {
      if (revoked) return '⛔ family revoked — login required';
      if (presented === issued()) {
        current++;                                   // rotate: old one retires
        return `✓ new pair issued (access + ${issued()})`;
      }
      if (presented.startsWith(user + '.rt')) {      // an OLD token replayed!
        revoked = true;
        return `🚨 RETIRED token replayed → thief or victim has it — revoking the ENTIRE family`;
      }
      return '⛔ unknown token';
    },
  };
}

const mochi = makeFamily('mochi');
console.log('legit refresh:   ', mochi.refresh('mochi.rt1'));
console.log('legit refresh:   ', mochi.refresh('mochi.rt2'));
// meanwhile an attacker exfiltrated rt2 earlier and replays it:
console.log('attacker replays:', mochi.refresh('mochi.rt2'));
console.log('victim tries rt3:', mochi.refresh('mochi.rt3'));
console.log('\nboth locked out → one re-login for the victim, nothing for the thief.');
console.log('without rotation, the stolen refresh token worked for 30 silent days.');

      

      
the replay trips the wire — rotation turns theft into a detectable event

Errors & validation — the boundary is the law

      
intermediate → trust nothing that crossed the network

    

  

  

    
Rule one of backend: validate at the boundary, everything, always. The frontend's validation is UX; yours is security — anyone with curl skips their form. Schema validators (zod/joi) turn "trust nothing" into declarative code: parse the input against a schema, get typed clean data or a structured 422. Validate params, query, body — and outputs to third parties if you're thorough.

    
Rule two: errors are part of the API. Operational errors (bad input, not-found, conflict) get precise statuses and safe messages; programmer errors (undefined is not a function) get a generic 500 — never the stack trace (it leaks internals) — plus a full log entry with a request id linking user report ↔ log line. One error middleware enforces all of it; every route just throws typed errors.

    

      

        
the-boundary.js — run it

        
// a zod-flavored schema validator in 25 lines
const schema = {
  name:  { type: 'string', min: 1, max: 40 },
  age:   { type: 'number', min: 0, max: 38 },     // oldest known cat
  email: { type: 'string', pattern: /^[^@\s]+@[^@\s]+\.[^@\s]+$/ },
};
function validate(input) {
  const errors = [], clean = {};
  for (const [field, rule] of Object.entries(schema)) {
    const v = input[field];
    if (v === undefined) { errors.push({ field, rule: 'required' }); continue; }
    if (typeof v !== rule.type) { errors.push({ field, rule: 'type:' + rule.type }); continue; }
    if (rule.min !== undefined && (v.length ?? v) < rule.min) errors.push({ field, rule: 'min' });
    if (rule.max !== undefined && (v.length ?? v) > rule.max) errors.push({ field, rule: 'max' });
    if (rule.pattern && !rule.pattern.test(v)) errors.push({ field, rule: 'format' });
    clean[field] = v;
  }
  return errors.length ? { ok: false, status: 422, errors } : { ok: true, data: clean };
}

console.log(validate({ name: '', age: '4', email: 'not-an-email' }));
console.log(validate({ name: 'Chonk', age: 900, email: 'c@cafe.cat', role: 'admin' }));
// note the last one: age rejected AND the sneaky extra `role`
// field silently dropped — allowlisting beats blocklisting.

Hardening Express — headers, rate limits & the OWASP hits

      
intermediate → the defense checklist, with a working limiter

    

  

  

    
Section 10 validated inputs; this section defends the perimeter. The checklist that covers most audits: security headers (what helmet sets: Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options: nosniff, frame denial) · rate limiting (below) · injection discipline — parameterized queries only (the postgres module's hill to die on), never string-built shell commands · secrets hygiene — env/secret manager, never the repo, and different keys per environment · dependency posture — lockfiles, npm audit in CI, and knowing that most Node breaches arrive via a compromised package, not your code.

    
The token bucket is the rate limiter worth knowing cold: each client owns a bucket of N tokens; requests spend one; tokens refill at R/sec. Bursts up to N pass instantly (good UX), sustained abuse drains to a trickle (R/sec) — which is exactly the shape you want and why it beats fixed windows (burst-at-the-boundary problem) in one sentence.

    

      

        
token-bucket.js — run it (the limiter, complete)

        
function makeBucket(capacity, refillPerSec) {
  let tokens = capacity, last = 0;                 // simulated clock (ms)
  return (now) => {
    tokens = Math.min(capacity, tokens + (now - last) / 1000 * refillPerSec);
    last = now;
    if (tokens >= 1) { tokens--; return { ok: true,  left: tokens.toFixed(1) }; }
    return { ok: false, retryAfter: ((1 - tokens) / refillPerSec).toFixed(1) };
  };
}

const limit = makeBucket(5, 1);                    // burst 5, refill 1/sec
console.log('burst of 7 at t=0 (capacity 5):');
for (let i = 1; i <= 7; i++) {
  const r = limit(0);
  console.log(`  req ${i}: ${r.ok ? '200 (tokens left ' + r.left + ')' : '429 — Retry-After ' + r.retryAfter + 's'}`);
}
console.log('patient client returns at t=2500ms:');
console.log('  req 8:', JSON.stringify(limit(2500)));
console.log('\nper-key buckets (ip / user / api-key) live in Redis in production —');
console.log('in-memory buckets reset per instance and per deploy: fine for one box, a lie behind a load balancer.');

Clustering & worker threads — more chefs, chosen correctly

      
advanced → processes for traffic, threads for math

    

  

  

    
One Node process uses one core; your box has eight. Two multipliers, often confused. cluster (or PM2/container replicas — same idea, better ops): fork N processes, share the listening port, each with its own event loop and memory — this scales request throughput and adds crash isolation. worker_threads: extra threads inside one process, sharing memory via transfer/SharedArrayBuffer — this rescues the event loop from CPU work (the js-async workers section, server-side). The decision is the §01 diagnosis reapplied: many concurrent requests → processes; one heavy computation → threads.

    
The trap that gets everyone: with replicas, in-process state becomes a lie. In-memory sessions "randomly" log users out (each replica has its own Map); the §11 rate limiter counts per-replica; a global cache multiplies. The rule: replicate the compute, externalize the state (Redis, DB) — which is also why stateless services (system-design module) scale by photocopier.

    

      

        
more-chefs.js — run it (throughput vs blocking, simulated)

        
// 12 requests: eleven quick (10ms) + one CPU-heavy (200ms), round-robin dispatch
function simulate(workers) {
  const done = [];                     // [finishTime, label]
  const free = new Array(workers).fill(0);          // when each worker frees up
  const jobs = Array.from({ length: 12 }, (_, i) =>
    i === 2 ? ['report-gen', 200] : [`req-${i}`, 10]);   // the heavy one arrives 3rd
  jobs.forEach(([label, cost], i) => {
    const arrival = i * 5;
    const w = i % workers;                           // round-robin (like SO_REUSEPORT)
    const start = Math.max(arrival, free[w]);
    free[w] = start + cost;
    done.push([free[w], label, w]);
  });
  const p95 = done.map(d => d[0]).sort((a, b) => a - b)[Math.floor(done.length * .95) - 1];
  return { p95, worst: Math.max(...done.map(d => d[0])) };
}
console.log('1 process: ', JSON.stringify(simulate(1)), ' ← everyone queues behind report-gen');
console.log('4 replicas:', JSON.stringify(simulate(4)), ' ← only worker 2\'s lane suffers');
console.log('\nreplicas contain the blast radius; a worker THREAD for report-gen');
console.log('removes it entirely — different tools, and the interview wants both named.');

WebSockets server-side — lifecycles, heartbeats & fan-out

      
advanced → long-lived connections change every assumption

    

  

  

    
HTTP handlers borrow the server for milliseconds; a WebSocket occupies it — one open TCP connection per user, for hours. Three server-side consequences. Liveness is your problem: TCP won't tell you about a vanished phone; you ping every ~30s and terminate silent connections (the heartbeat), or half-dead sockets accumulate forever. Memory is per-connection: 50k idle users = 50k sockets + their buffers — capacity planning shifts from req/sec to concurrent connections. Fan-out crosses replicas: user A on replica 1 messages user B on replica 3 — replicas must gossip through a broker (Redis pub/sub is the standard answer), the same externalize-the-state law as §12, now for connections.

    

      

        
heartbeat-ledger.js — run it (dead-connection reaping, simulated)

        
// server pings every 30s; a client missing 2 pongs is presumed dead
const clients = new Map();     // name → last pong time
['mochi-phone', 'biscuit-laptop', 'beans-tablet'].forEach(c => clients.set(c, 0));

function sweep(now) {
  console.log(`t=${now}s — ping all (${clients.size} connections)`);
  for (const [name, lastPong] of clients) {
    if (now - lastPong > 60) {
      clients.delete(name);
      console.log(`  ⚰️  ${name}: no pong for ${now - lastPong}s → terminate, free buffers`);
    }
  }
}
// beans' tablet goes through a tunnel at t=10 (no clean close — just silence)
const pong = (name, t) => clients.set(name, t);
for (const t of [30, 60, 90]) {
  pong('mochi-phone', t); pong('biscuit-laptop', t);      // healthy pongs
  if (t <= 0) pong('beans-tablet', t);                     // beans went silent
  sweep(t);
}
console.log('\nsurvivors:', [...clients.keys()].join(', '));
console.log('without the reaper, beans\' socket lives forever — RAM leak shaped like a user.');

// reconnect etiquette (client side, for symmetry): backoff + jitter
let delay = 1;
const backoff = [];
for (let i = 0; i < 5; i++) { backoff.push(delay); delay = Math.min(delay * 2, 30); }
console.log('client reconnect schedule (s):', backoff.join(' → '), '+ jitter — never a synchronized stampede');

Observability — logs, metrics & traces that answer questions

      
advanced → structured events, the four golden signals, one request's story

    

  

  

    
Three instruments, three questions. Logs answer "what happened?" — but only if they're structured: one JSON object per event, machine-queryable (level=error AND route=/checkout AND userId=…), instead of prose you grep and pray over. Metrics answer "how are we doing?" — cheap aggregates over time; the four golden signals (latency, traffic, errors, saturation) plus Node's own vitals: event-loop lag (§02's number), heap used, open handles. Traces answer "where did this request spend its time?" — a request id minted at the edge and carried through every log line and downstream call, so one slow checkout becomes a waterfall you can read instead of four services' logs you can't correlate.

Testing & shipping — confidence, then repetition

      
intermediate → the pyramid that fits APIs, and the deploy shape

    

  

  

    
The API testing pyramid, practical edition: unit tests for services and pure logic (fast, no HTTP, no DB — the layered structure from §03 pays off here); integration tests hitting real routes with supertest against a test database (the workhorse layer — auth flows, validation, the error envelope); a few end-to-end smoke tests against a deployed environment. Mock at the edges you don't own (Stripe, S3, email) — never mock your own database in integration tests, or you're testing your mocks.

    
The deploy shape, in one breath: Docker image built once in CI (npm ci, not install), promoted through staging to prod; N Node processes (cluster/PM2 or one-per-container with an orchestrator); health checks split into liveness ("process up") and readiness ("DB reachable"); logs as structured JSON to stdout; SIGTERM handled for zero-dropped-request deploys. Where each of those runs on AWS is the aws-cloud module's whole story.

The reasoning gym — nine questions, three tiers

      
all levels → transfer, not recall: every question is an inference

    

  

  

    
Fifteen sections of engine room; now the transfer test. Warm-up isolates one idea each — every wrong option is a real misconception with a name. Apply hands you code and makes you run it in your head. Stretch chains two or more sections under constraints, which is what a backend interview actually is. First pick is the recorded one, and the "why" under each answer is the actual lesson — read it even when you're right. Professor Whiskers wrote several distractors from personal experience. 🐈

    

      
// warm-up 1 of 3 — who stalls during loop blocking

      
A route handler runs a synchronous 200ms JSON.parse on a huge payload. At that moment, three other users' DB queries are already in flight. What's true while the parse runs?

      

        
        
        
        
      

      
Why: the distinction is progress vs delivery: the database server and the kernel are other machines and threads, so the queries keep completing — but completion arrives as a JS callback, and every callback queues behind the parse (§01's one chef, §02's phases). "Everything pauses" over-rotates: blocking the loop doesn't stop the outside world, only your ability to respond to it. The thread-per-request option imports another runtime's model into Node. And libuv only offloads its own C-level work (fs, dns, crypto) — it never lifts your JS off the loop.

    

    

      
// warm-up 2 of 3 — where thrown errors travel

      
A teammate registers the four-argument error middleware FIRST — "so it's ready before anything can fail" — then the routes. A route throws synchronously. Who answers the request?

      

        
        
        
        
      

      
Why: the chain is a one-way street (§06): a sync throw becomes next(err), which jumps forward past normal middleware to the NEXT four-argument handler — and there isn't one after the routes, so the built-in default responds (in dev, with a stack trace: §10's "never leak internals" rule violated for free). The scan-anywhere option assumes position doesn't matter, but position is the entire mechanism — it's also why four-arg handlers are skipped during normal, error-free dispatch. The hang belongs to §06's async-throw story, a different failure. Retrying doesn't exist in Express.

    

    

      
// warm-up 3 of 3 — signed is not secret

      
Login works, so a teammate adds the user's apiKey and card fingerprint to the JWT payload — "it's signed, so it's safe". Where does the reasoning break?

      

        
        
        
        
      

      
Why: signing gives integrity, not confidentiality — §08's demo decoded a payload with plain atob, no secret required. "Signed = encrypted" is the single most common JWT misconception, and the HTTPS option is its cousin: TLS protects the pipe, not the token at rest in storage, logs, or headers. Option three inverts the model — tampering is exactly what verification does catch; reading is what nothing prevents. The rule that falls out: identifiers in tokens, secrets in the database.

    

    

      
// apply 1 of 3 — trace the loop's guarantees

      
Top level of a Node script: setTimeout(() => log('A'), 0); setImmediate(() => log('B')); Promise.resolve().then(() => log('C')); process.nextTick(() => log('D')); log('E'); — what is guaranteed about the output?

      

        
        
        
        
      

      
Why: sync code first (E); then the between-everything queues drain — nextTick before promise microtasks (D, then C), Node's one deviation from browser intuition, which is exactly what the last option imports. The A/B tail is §02's famous coin flip: whether the loop's first timers pass sees the 0ms timer depends on whether a millisecond has elapsed by then, so both "always" options mistake a sometimes for an always. §02's snippet only got a deterministic order by scheduling from inside an I/O callback — you're in poll, check is next, immediate wins. In an interview, naming the nondeterminism IS the correct answer.

    

    

      
// apply 2 of 3 — middleware chain, traced top-down

      
Registered in order: app.use(logger) → app.get('/health', ok) → app.use(requireAuth) (401s without a token) → app.get('/stats', stats) → app.use((req, res) => res.status(404).end()). An unauthenticated GET /no-such-path returns?

      

        
        
        
        
      

      
Why: run it down the list: logger (logs, calls next) → /health (path mismatch, skipped) → requireAuth (pathless, matches everything, no token → 401, chain over). The 404-first option imagines routing as a lookup table resolved before dispatch — Express is §06's flat top-down chain, and "no route matched" just means "nobody has answered yet". This trace is why the 404 handler goes last yet still sits BEHIND auth — and why an app's favicon request can mysteriously 401. Hanging only happens when nobody ends the chain (§06's forgotten-next bug), and requireAuth ends it.

    

    

      
// apply 3 of 3 — backpressure at real rates

      
pipeline(fs.createReadStream('video.mp4'), res) serves a 1GB file to a client draining at 1MB/s. The disk reads at 500MB/s. Which is true?

      

        
        
        
        
      

      
Why: back-of-envelope first — 1GB at 1MB/s ≈ 1,000 seconds ≈ 17 minutes. That's the transfer time, and with backpressure it's also the READ time: §04's pause protocol (write() returns false → pause → resume on drain) reaches all the way to the source, so the disk's 500MB/s only matters for keeping the small buffer topped up. Option one is precisely the world WITHOUT backpressure — §03's "readFile with extra steps". No temp-file spill exists; that's a strategy you'd have to build yourself. And raising highWaterMark trades MORE memory for fewer pauses — the last option holds the dial backwards.

    

    

      
// stretch 1 of 3 — spot the false security claim

      
Four claims about the §08/§09 auth design. Which one is FALSE?

      

        
        
        
        
      

      
Why: httpOnly blunts XSS — scripts can't READ the cookie — but CSRF never needed to read it: the browser auto-attaches cookies to cross-site requests, and that auto-attach IS the attack. The defenses are SameSite and CSRF tokens, which is why §08's cookie spell recites both flags — each answers a different attack, and swapping them is the classic §08×§11 stumble. The other three claims are the load-bearing truths of the design: statelessness has no kill switch (§08), rotation is the tripwire (§09), and secret rotation is the nuclear logout.

    

    

      
// stretch 2 of 3 — the loop's throughput ceiling

      
Profiling shows each request costs ~2ms of CPU on the loop (parse, validate, serialize); p50 latency is 40ms, almost all of it awaiting the DB. Rough throughput ceiling for ONE replica?

      

        
        
        
        
      

      
Why: the loop is §01's one chef — only the CPU slice is serial, so one core saturates near 1000/2 = 500 req/s, and §02's event-loop lag starts climbing well before the errors do (§14's alert). Dividing by the 40ms latency is the classic latency/throughput confusion: while one request awaits the DB, dozens of others are mid-flight — Little's law puts ~20 in the air at the ceiling. Benchmark folklore measures hello-world, not YOUR 2ms per request; "unbounded" forgets the CPU exists at all. Need 2,000 req/s? That's §12's answer: four replicas, not a faster database.

    

    

      
// stretch 3 of 3 — slow is not dead

      
A live dashboard broadcasts 50 messages/s to every WebSocket. One client's connection degrades to ~1 message/s of real delivery — but it's alive and answers every ping. What happens server-side, and the defense?

      

        
        
        
        
      

      
Why: chain §04's law with §13's economics: send() is a write() that never says no out loud — it buffers, and a producer outrunning a consumer by 49 messages/s grows that buffer without bound, a RAM leak shaped like one slow user. The heartbeat option is the subtle trap: heartbeats detect DEAD (no pong), and this client pongs happily — slow and dead are different failure modes needing different tripwires. A blocking send would at least be backpressure, but that's not the API's behavior — and nothing drops frames for you; the coalesce/drop/disconnect policy is application code you have to write.

Each wrong option was a named misconception, not noise.
    • 
        
  • Apply misses → adopt the tracing ritual: before picking, write the queues (sync → nextTick → microtasks → phases) or the middleware list top-to-bottom, then walk the request through with a pencil. The exercise is holding state in your head, not remembering facts.
    • 
        
  • Stretch misses → name the pairings and reread the weaker half: §08×§11 (which cookie flag answers which attack), §01×§12×§14 (loop CPU × replicas × the lag metric), §04×§13 (backpressure, now per connection). Combining sections IS the skill being tested.

Recap table

§the ideathe sentence to remember

    
      
01runtimeOne chef, many ovens: I/O concurrency is free, CPU on the loop stalls EVERYONE — offload it.

      
02phasesTimers, poll, check — nextTick between everything; event-loop lag is the metric that predicts outages.

      
03streamsProcess the river in chunks; backpressure pauses the producer so slow consumers can't flood RAM.

      
04backpressurewrite() returning false is a plea — honor writer.ready or buffer RAM until it dies; pipeline honors it for you.

      
05buffersString length ≠ byte length; chunk edges slice characters — streaming decoders hold the fragment.

      
06expressA chain of (req, res, next) functions; order matters; async errors need forwarding (until Express 5).

      
07RESTNouns in URLs, verbs in methods, honest statuses, cursor pages, one error envelope, actions as created resources.

      
08authShort-lived access + rotating refresh, both httpOnly — stateless checks with a revocation point.

      
09oauthThe code hop keeps tokens out of URLs; PKCE guards the exchange; rotation turns theft into detection.

      
10robustnessValidate at the boundary (allowlist the shape); typed errors → one middleware; stack traces never leave.

      
11securityHelmet headers, parameterize everything, token buckets keyed twice — by IP and by username.

      
12clusteringProcesses for traffic, threads for math — replicated compute means externalized state.

      
13websocketsHeartbeat the silent, budget per-connection memory, fan out through a broker.

      
14observabilityStructured events + golden signals + one request id through everything; p99 is a user, not noise.

      
15shippingReal-DB integration tests, mock only unowned edges; build once, promote; liveness ≠ readiness.

      
16the gymNine inferences, zero recall — who stalls, where errors land, what buffers cost; argue with your first instinct.

  • "Explain the event loop in Node" — tell it server-side: one loop per process serving all users, CPU work is the enemy, and name event-loop lag as the metric. Drill pairs: Full-Stack in 48 · Node internals.

  • The advanced band is the on-call interview: "users randomly logged out after scaling" (12), "chat broke on three replicas" (13), "p50 fine, p99 four seconds" (14) — each is a war story with a named fix now.
