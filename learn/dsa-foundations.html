01

Big-O, from scratch — how work grows

beginner → the growth explorer makes it visceral

Big-O answers one question: if the input gets 10× bigger, how much more work does the code do? Not "how fast is it in milliseconds" — machines vary — but how the work scales. O(n) = work grows in step with input. O(n²) = 10× input, 100× work. O(log n) = 10× input, barely any extra work. O(1) = input size is irrelevant.

Two simplifications make it usable: drop constants (O(2n) is O(n) — doubling speed doesn't change the shape of growth) and keep only the biggest term (O(n² + n) is O(n²) — at scale the square dwarfs everything). Read code by its loops: a loop over n is O(n); a loop inside a loop is O(n²); halving the search space each step is O(log n).

PROFESSOR WHISKERS EXPLAINSA shelter with n cats. O(1): "fetch the cat in cage 7" — same effort whether there are 10 cats or 10,000. O(log n): find Mochi in an alphabetized registry — open the middle, go left or right, repeat; 10,000 cats ≈ 14 peeks. O(n): weigh every cat. O(n²): introduce every cat to every other cat — 100 cats is 4,950 introductions, 10,000 cats is ruinous. The shape of the chore, not the speed of the volunteer.

// quiz — first pick is the one that counts

Nested loops: for each cat, scan all n cats for a name clash — but you added break on first match. What's the worst-case complexity?

Why: a break helps lucky inputs; Big-O is the guarantee for unlucky ones. When no duplicates exist, every inner scan completes: n × n. (And O(2n) isn't a thing — constants drop.) Bonus vocabulary: best case, average case, and amortized — the occasional expensive operation averaged over many cheap ones, like array push.

LEVEL UP — what interviewers listen for
  • Space complexity gets the same treatment: extra memory as a function of n. The follow-up "can you do it in O(1) space?" is asking you to trade the helper array for pointers.
  • Two sequential loops = O(n + n) = O(n). A loop over n with an inner loop over m (different input!) = O(n·m) — don't collapse different variables.
  • The five shapes worth recognizing on sight: O(1), O(log n) (halving), O(n), O(n log n) (sort), O(n²) (all pairs). Interview answers rarely need more.
  • "n is small, so n² is fine" is a legitimate engineering sentence — Big-O guides choices at scale; it doesn't forbid nested loops over 20 items.

Arrays & strings — the costs you're already paying

beginner → what's O(1), what's secretly O(n)

An array is a numbered row of boxes. Index access (cats[7]) is O(1) — the position is computed, not searched. The end of the array is cheap real estate: push/pop are O(1). The front is expensive: shift/unshift move every remaining element — O(n). Same for splice in the middle. And the innocuous-looking ones that touch everything — includes, indexOf, slice, spread, filter, map — are all O(n).

Strings in JS are immutable arrays of characters: every "modification" builds a new string. Building a string with += in a loop re-copies the whole thing each time — the classic accidental O(n²); collect parts in an array and join once.

costs-measured.js — run it
// feel the front-vs-back difference on a real array
const N = 60_000;
const cats = Array.from({ length: N }, (_, i) => 'cat' + i);

let t0 = performance.now();
const a = [...cats];
for (let i = 0; i < 5_000; i++) a.pop();          // O(1) each
console.log('5k pops:   ', (performance.now() - t0).toFixed(1), 'ms');

t0 = performance.now();
const b = [...cats];
for (let i = 0; i < 5_000; i++) b.shift();        // O(n) each!
console.log('5k shifts: ', (performance.now() - t0).toFixed(1), 'ms');

// string building: += vs join
t0 = performance.now();
let s = '';
for (let i = 0; i < 20_000; i++) s += 'meow';     // re-copies s each time
console.log('+= loop:   ', (performance.now() - t0).toFixed(1), 'ms');

t0 = performance.now();
const parts = [];
for (let i = 0; i < 20_000; i++) parts.push('meow');
const joined = parts.join('');                     // one pass
console.log('join once: ', (performance.now() - t0).toFixed(1), 'ms',
            '(same result:', s === joined, ')');
numbers vary by machine — the RATIO is the lesson

Processing a queue of jobs with while (jobs.length) { const job = jobs.shift(); … } over 100k jobs is mysteriously slow. Why, and the O(1) fix?

    •

    • 
        
  • JS arrays are dynamic (push is amortized O(1) — occasional internal regrow) and can be sparse; engines optimize dense same-type arrays. One sentence of that = strong JS-specific signal.

Hash maps & sets — trading memory for speed

      
the single most useful tool in interviews, period

    

  

  

    
A hash map buys O(1) lookup by spending memory: a hash function turns any key into a bucket number, and the value goes in that bucket. Ask for the key later — same function, same bucket, no searching. A Set is the same machine storing only "have I seen this?"

    
The interview superpower: hash maps convert "search for it" (O(n)) into "remember it" (O(1)). Whole problem categories collapse: duplicates (Set), frequency counting (Map of counts), grouping (Map of key → list), and the legendary two-sum move — store what you've seen, look up what you need.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe shelter's cubby wall: each cat's name decides its cubby number (the hash). Where's Mochi's vet record? Compute her cubby — walk straight to it. No cubby wall means rifling through a drawer of n folders every time. Two cats hash to one cubby (a collision)? The cubby holds a short list — fine until the wall is overcrowded, which real implementations fix by adding cubbies (resizing). One-time filing cost, instant lookups forever.

    

    

      

        
two-sum-both-ways.js — run it

        
// THE interview problem: which two cats' weights sum to the target?
// values ≤ 4000, so no accidental pair can reach 10,000…
const weights = Array.from({ length: 4_000 }, () => Math.ceil(Math.random() * 4000));
weights[1500] = 4001; weights[3800] = 5999;        // …except the planted one

// brute force: every pair — O(n²)
function twoSumBrute(nums, target) {
  for (let i = 0; i < nums.length; i++)
    for (let j = i + 1; j < nums.length; j++)
      if (nums[i] + nums[j] === target) return [i, j];
}
// hash map: remember what you've seen — O(n)
function twoSumMap(nums, target) {
  const seen = new Map();                       // value → index
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i);
  }
}

let t0 = performance.now();
console.log('brute:', twoSumBrute(weights, 10_000),
            (performance.now() - t0).toFixed(2) + 'ms');
t0 = performance.now();
console.log('map:  ', twoSumMap(weights, 10_000),
            (performance.now() - t0).toFixed(2) + 'ms');

// frequency counting — the pattern behind anagrams, top-k, and more
const adopters = ['amy', 'raj', 'amy', 'lin', 'raj', 'amy'];
const counts = new Map();
for (const name of adopters)
  counts.set(name, (counts.get(name) ?? 0) + 1);
console.log('visit counts:', Object.fromEntries(counts));

    04
    

      
Two pointers — meeting in the middle

      
intermediate → turning O(n²) pair-scans into one pass

    

  

  

    
When a problem asks about pairs or ranges in a sorted (or sortable) array, checking every pair is O(n²). Two pointers replaces that with one smart pass: start a pointer at each end, look at what they point to, and — this is the whole trick — the comparison tells you which pointer can safely move. Every step eliminates a whole batch of pairs you now know can't win. n² candidates, n steps.

    
The reasoning template to say out loud: "if the sum is too small, only moving the left pointer up can help (right is already the biggest); too big, only moving right down helps." The pattern's power is that discard argument — find it and the problem is done.

    

      
      
PROFESSOR WHISKERS EXPLAINSCats lined up by weight, and you need two whose weights sum to exactly 10kg. Check the lightest and heaviest: 2kg + 9kg = 11 — too heavy, and pairing the 9kg cat with anyone even lighter only gets heavier-than-needed… wait, lighter. The point: the 9kg cat is done — no partner to its left can fix "too big" better than trying the next-heaviest. Dismiss her, step inward. Each comparison retires one cat and all her un-tried pairings at once. That wholesale dismissal is why it's O(n).

    

    

      

        
converging-pointers.js — run it

        
// pair-sum in a SORTED array — the canonical converging pattern
function pairWithSum(sorted, target) {
  let left = 0, right = sorted.length - 1, steps = 0;
  while (left < right) {
    steps++;
    const sum = sorted[left] + sorted[right];
    if (sum === target) return { pair: [sorted[left], sorted[right]], steps };
    if (sum < target) left++;      // smallest is hopeless — retire it
    else right--;                  // biggest is hopeless — retire it
  }
  return { pair: null, steps };
}
const weights = [1, 2, 3, 5, 6, 7, 8, 8, 9, 11, 12, 14];
console.log('target 20 →', pairWithSum(weights, 20));
console.log('checked', weights.length * (weights.length - 1) / 2,
            'possible pairs — visited far fewer');

// same skeleton, different clothes: is it a palindrome?
function isPalindrome(s) {
  const t = s.toLowerCase().replace(/[^a-z0-9]/g, '');
  let i = 0, j = t.length - 1;
  while (i < j) {
    if (t[i] !== t[j]) return false;
    i++; j--;
  }
  return true;
}
console.log('taco cat →', isPalindrome('Taco cat!'));
console.log('tuna cat →', isPalindrome('Tuna cat'));

// quiz — first pick is the one that counts

      
Container With Most Water: bars of heights, pick two that trap the most area. Pointers at both ends — which one moves, and why is it safe?

      

        
        
        
        
      

      
Why: area = min(heights) × width. Move the taller bar inward and min can't rise (still capped by the short one) while width definitely shrinks — provably never better. Move the shorter and you might find taller. That "provably can't win → discard" argument IS the two-pointer pattern; interviews grade the argument, not the loop.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The second flavor — slow/fast on the same side — powers Move Zeroes (writer chases reader) and cycle detection (next module). Converging = pairs; chasing = in-place rewrites.
    • 
        
  • 3Sum = sort + fix one element + two-pointer the rest: O(n²) instead of O(n³), plus the duplicate-skipping discipline. It's THE "medium that's really a pattern check".
    • 
        
  • If the array isn't sorted and can't be: that's usually the hash-map version of the problem (Two Sum) — sorting costs O(n log n) and destroys indices. Saying which tool and why = the senior move.
    •

Sliding window — a caterpillar over the array

      
intermediate → "longest/shortest substring/subarray with…"

    

  

  

    
Trigger phrase: "longest / shortest / best contiguous run that satisfies a condition." Checking every start-end range is O(n²). The window is two same-side pointers forming a caterpillar: the right end stretches forward growing the window; when the window breaks the rule, the left end contracts until it's legal again. Each pointer only ever moves forward → O(n) total.

    
The bookkeeping between the moves is the problem-specific part: a Set of what's in the window, a count map, a running sum — whatever answers "is this window still valid?" in O(1).

    

      

        
caterpillar.js — run it

        
// longest stretch of distinct treats (LC 3, cat edition)
function longestDistinctRun(treats) {
  const inWindow = new Set();
  let left = 0, best = 0, bestAt = 0;
  for (let right = 0; right < treats.length; right++) {
    while (inWindow.has(treats[right])) {   // rule broken → contract
      inWindow.delete(treats[left]);
      left++;
    }
    inWindow.add(treats[right]);            // stretch
    if (right - left + 1 > best) { best = right - left + 1; bestAt = left; }
  }
  return { best, run: treats.slice(bestAt, bestAt + best) };
}
const bowl = ['tuna','salmon','tuna','chicken','salmon','beef','tuna','duck'];
console.log(longestDistinctRun(bowl));

// fixed-size window: best 3-day treat total — subtract the tail, add the head
function bestWindowSum(nums, k) {
  let sum = 0;
  for (let i = 0; i < k; i++) sum += nums[i];
  let best = sum;
  for (let i = k; i < nums.length; i++) {
    sum += nums[i] - nums[i - k];           // O(1) per slide — no re-add!
    best = Math.max(best, sum);
  }
  return best;
}
console.log('best 3-day haul:', bestWindowSum([3,1,4,1,5,9,2,6], 3));

      

      
left never backtracks — that's the O(n) guarantee

      

    

    

      
// quiz — first pick is the one that counts

      
Why is the distinct-run function O(n) when it contains a while-loop inside a for-loop?

      

        
        
        
        
      

      
Why: count total pointer movement, not loop nesting: right advances n times ever, left advances at most n times ever — ≤2n steps however they interleave. "Nested ≠ quadratic when the inner loop consumes a shared budget" is a genuinely impressive sentence to say out loud, and it's the same argument behind monotonic stacks in the next module.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Variable window + count map + a "how many chars still missing" counter = Minimum Window Substring (hard, but it's this exact skeleton with heavier bookkeeping).
    • 
        
  • "At most K distinct/replacements" problems: the window stays valid via a budget you spend and reclaim — Longest Repeating Character Replacement is the archetype.
    • 
        
  • Negative numbers break the "shrink to fix the sum" logic — that's when subarray-sum problems switch to prefix sums (next section). Knowing the boundary between the patterns is the real skill.
    • 
        
  • practice (verified): 3 · Longest Substring w/o Repeats · 121 · Best Time to Buy/Sell · 424 · Char Replacement · 76 · Min Window (hard)

Prefix sums — pre-compute once, answer forever

      
intermediate → range queries and the elegant map trick

    

  

  

    
Precompute a running total: prefix[i] = sum of everything up to i. Now any range sum is one subtraction — sum(i..j) = prefix[j] − prefix[i−1]. O(n) once, O(1) per question, forever. It's the same instinct as a cache: pay upfront, answer instantly.

    
The advanced form marries it to a hash map: walking the array, ask "have I seen a prefix equal to currentPrefix − k?" If yes, a subarray summing to exactly k just ended here. That combo — running value + map of seen values — cracks Subarray Sum Equals K and an entire family of "count the ranges" problems, negatives included (where sliding windows give up).

    

      

        
running-totals.js — run it

        
// daily treats dispensed this week
const daily = [3, 1, 4, 1, 5, 9, 2];

// build once: prefix[i] = total through day i (with a 0 sentinel)
const prefix = [0];
for (const d of daily) prefix.push(prefix[prefix.length - 1] + d);
console.log('prefix:', prefix);

const rangeSum = (i, j) => prefix[j + 1] - prefix[i];   // O(1) forever
console.log('days 2–4:', rangeSum(2, 4));               // 4+1+5
console.log('days 0–6:', rangeSum(0, 6));

// the map trick: COUNT subarrays summing to exactly k (negatives welcome)
function countSubarrays(nums, k) {
  const seen = new Map([[0, 1]]);          // prefix 0 seen once (empty start)
  let running = 0, count = 0;
  for (const x of nums) {
    running += x;
    count += seen.get(running - k) ?? 0;   // ranges ending here
    seen.set(running, (seen.get(running) ?? 0) + 1);
  }
  return count;
}
console.log('subarrays summing to 6:', countSubarrays([3, 1, 4, 1, 5, -4, 6], 6));

      

      
the Map([[0,1]]) seed is the detail everyone forgets

A dashboard hits you with 10,000 queries like "total adoptions between day i and day j" over a fixed year of data. Architecture instinct?

      

        
        
        
        
      

      
Why: many queries over static data = precompute. Memoizing per-(i,j) only helps repeated identical queries; prefix sums make every possible range O(1) with n numbers of storage. This is also a systems instinct wearing DSA clothes — materialized views and CDN caches are prefix sums' grown-up cousins, and saying so connects your two worlds.

The practice ladder — how to actually get good

      
method → the 20-minute rule and pattern-first drilling

    

  

  

    
The method matters more than the volume. Grinding 300 random problems builds anxiety; drilling patterns builds recognition. The routine that works: pick ONE pattern, read its template until you can write it blind, then solve 3–4 of its problems in a row. Your brain starts seeing the pattern's shape in the wording — which is the actual skill interviews test.

    
The 20-minute rule: stuck for 20 minutes → read the solution completely, close it, and re-implement from memory. Then — non-negotiable — re-solve it from scratch two days later. Struggling forever teaches frustration; the read-rebuild-revisit loop teaches patterns. Track your re-solves; they're the real progress metric.

    

      
      
PROFESSOR WHISKERS EXPLAINSCats don't learn to hunt by staring at a mouse for three hours. They watch one good demonstration, try, fail, nap, and try again tomorrow — and the nap is load-bearing. Spaced repetition isn't a productivity hack; it's how pattern memory consolidates. Be like cat: short intense sessions, shameless imitation, sacred naps.
