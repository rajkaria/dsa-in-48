System design, from zero to whiteboard.

System design is learnable because it's six building blocks and one loop, recombined forever: spread the traffic, cache the heat, scale the data, queue the slow, estimate honestly, and walk the loop out loud. // beginner — the loop & the envelope
01

The design loop — requirements, envelope, skeleton, deep-dive

beginner → the 4 phases that structure every answer

Every design interview (and every real design doc) walks the same loop. Phase 1 — requirements (5 min): functional ("shorten URLs, redirect fast") and the numbers that shape everything: how many users, what read/write ratio, how fresh must data be, what can we lose? Scope out loud. Phase 2 — the envelope (5 min): back-of-envelope math (next section) that tells you whether you're designing for one Postgres box or a fleet — the single highest-leverage five minutes, because the numbers pick the architecture.

Phase 3 — the skeleton (10 min): the stage-2 shape from the AWS module — client → LB → stateless app tier → cache → database, with S3/CDN for files. Draw it fast and say why each box exists. Phase 4 — deep-dives (20 min): the interviewer (or the workload) picks the hard parts: the data model, the cache policy, the queue, the sharding story, the failure modes. The rest of this module is those deep-dives, one per section.

// quiz — first pick is the one that counts

The single most common way candidates fail system design rounds?

Why: the round tests whether your design follows from requirements — a beautiful unjustified diagram proves the opposite. 100 rps fits comfortably on stage-1/stage-2 infrastructure; saying so, THEN describing what changes at 100× scale, demonstrates the actual skill: matching architecture to numbers. "Let me do the envelope first, because it decides how much machinery we need" is the strongest possible opening sentence.

LEVEL UP — what interviewers listen for
  • Read/write ratio is the first number to extract — a 100:1 read-heavy system (most consumer apps) designs completely differently from write-heavy telemetry ingest.
  • CAP in one honest breath: during a network partition you choose availability or consistency — banks pick C (reject writes), feeds pick A (serve stale). Nobody needs the theorem's proof; everybody needs the instinct.
  • The timed drill version of this loop is System Design in 48's whole day 1 — this module is the depth behind it.

02

Estimation — the envelope, with a calculator

the five minutes that pick your architecture

Four numbers carry every estimate. 1 — requests: daily active users × actions/day ÷ 86,400 ≈ average RPS (~10⁵ seconds/day makes mental division easy); peak ≈ 3–10× average. 2 — storage: items/day × bytes/item × days retained. 3 — bandwidth: RPS × payload size. 4 — memory for cache: the hot fraction (80/20 rule: ~20% of data serves ~80% of reads). Round brutally — powers of ten, not decimals; the goal is picking between "one box", "a few boxes", and "a fleet", not accounting.

Calibration anchors worth memorizing: one Postgres box handles thousands of simple queries/sec (not millions); one app server handles hundreds to low thousands of RPS; Redis does 100k+ ops/sec; a disk seek ~10ms, same-region network hop ~1ms, memory read ~100ns. With those five anchors, the calculator below is just multiplication.

THE ENVELOPE CALCULATOR — numbers → architecture

Pick a scenario (or reason along). Watch which architecture the numbers demand.

// quiz — first pick is the one that counts

1M DAU, each reading 30 items and writing 1 (2KB each). Which claim does the envelope support?

Why: 1M × 30 ÷ 86,400 ≈ 347 read RPS; 1M × 1 ÷ 86,400 ≈ 12 write RPS; 1M × 2KB ≈ 2GB/day. Even at 10× peak, reads are cache-and-replica territory and writes barely register — the envelope just deleted the sharding conversation and the Kafka conversation. That deletion IS the skill: five multiplications that keep the design honest. (Anchors: one PG box = thousands of QPS.)

LEVEL UP — what interviewers listen for
  • State your anchors before using them ("assuming a Postgres box comfortably does a few thousand simple QPS…") — auditable math beats confident magic.
  • p50 vs p99: averages hide tail pain; SLOs are set on percentiles. One sentence, big signal.
  • The 80/20 cache estimate: hot 20% of 100GB = a 20GB Redis — suddenly "will it fit in cache?" is answerable arithmetic.

03

Spreading traffic — LBs, statelessness, and failure as routine

intermediate → horizontal scaling's actual mechanics

Vertical scaling (bigger box) is correct until it isn't: no code changes, but a hard ceiling and still one failure point. Horizontal scaling (more boxes) is unbounded but demands the discipline you built across two modules: stateless app servers (sessions in Redis, files in S3) so any box can serve any request, behind a load balancer doing three jobs — spreading load (round-robin/least-connections), health-checking (a failing box is quietly removed: failure becomes routine, not incident), and TLS termination.

The part that separates rehearsed answers from understood ones: what the LB enables. Deploys become rolling (drain one box, replace, next); capacity becomes elastic (auto-scaling adds boxes on signals); and failure recovery becomes automatic — a crashed server is just a failed health check. The load balancer isn't a traffic cop; it's the mechanism that turns servers into cattle.

// quiz — first pick is the one that counts

WebSocket chat servers hold open connections — each socket lives on ONE box. How does horizontal scaling survive this statefulness?

Why: the nuance is distinguishing state kinds: a socket is connection state (re-establishable — the frontend module's reconnect/catch-up dance), not data state (which still lives in Redis/PG). The pub/sub bridge (socket.io's Redis adapter is exactly this) lets any box deliver to any user. "Sockets in Redis" is a category error — sockets are OS resources, not data. This question is THE chat-design filter, from both sides of the stack.

LEVEL UP — what interviewers listen for
  • L4 vs L7 in one line: L4 balances TCP (fast, blind), L7 reads HTTP (routes by path/host, terminates TLS) — ALB is L7; that's why it can send /api and /ws to different services.
  • DNS + anycast + CDN is the load balancing ABOVE your LB — how traffic picks a region before it picks a server.
  • "Cattle, not pets" + health checks + statelessness is a three-legged stool — remove one leg and the other two stop working. Saying WHY (state pins, no checks means routing to corpses) beats reciting the slogan.

04

Caching — the fastest request is a skipped one

intermediate → layers, policies, and the two classic failures

Caching happens at every layer, and interviews want you to see the whole stack: browser cache → CDN (whole responses at the edge) → app-level Redis (query results, computed objects) → the database's own buffer pool. Each layer answers the same three questions: what's cached (key design), when does it die (TTL / explicit invalidation on write / LRU eviction under memory pressure — the structure you built in dsa-structures!), and what happens on a miss.

The default pattern is cache-aside: read → try cache → miss → read DB → write cache with TTL. Its two classic failures are interview gold: stale reads after writes (fix: bust or update the key on write, accept a staleness window, and say WHICH the product tolerates) and the stampede — a hot key expires and ten thousand concurrent misses hit the DB at once (fixes: jittered TTLs so keys don't expire in sync, a per-key lock so ONE request rebuilds while others wait or serve stale). Naming the stampede unprompted is a seniority marker in both this round and real Redis postmortems.

// quiz — first pick is the one that counts

Your product page cache (60s TTL) causes this bug report: "I updated the price and the site showed the old one for a minute." Product says unacceptable. Options, best first?

Why: write-triggered invalidation gets both properties because the write path is the one place that KNOWS the data changed — TTL alone is a freshness lottery. 1s TTLs mostly delete the cache's value (and stampede hourly); removing it entirely trades a solved problem for a capacity one. The pro-level addendum: invalidation fans out in multi-layer setups (Redis + CDN both need the purge) — which is why "how many layers hold this value?" is the first debugging question for staleness bugs.

LEVEL UP — what interviewers listen for
  • Write-through (write cache+DB together) and write-behind (cache first, flush async — fast and scary) complete the pattern family — one line each, cache-aside as your stated default.
  • "What's your hit rate?" — the cache metric that matters; below ~80% on a hot path, revisit key design or TTLs.
  • Negative caching (cache the 404s) stops misses-for-things-that-don't-exist from hammering the DB — tiny trick, real systems, rarely said.

05

Scaling the data — replicas, partitions, shards, and honesty

advanced → the postgres module's ladder, at whiteboard altitude

You built this ladder in the postgres module; the design round wants it at altitude. Read replicas multiply read capacity and carry replication lag — the read-your-own-writes wrinkle is now a design consideration you volunteer, not a bug you hit. Partitioning splits one table by time/tenant inside one server. Sharding splits data ACROSS servers by a shard key — the real answer to write scale, at the real price: cross-shard queries and transactions stop being free, and resharding is surgery.

The design-round questions that matter: what's the shard key? (user_id spreads load but scatters a user's social graph; a bad key creates hot shards — the celebrity problem); how do you route? (hash the key → shard, with consistent hashing so adding shards moves 1/n of data, not all of it); what breaks? (global uniqueness needs id services or UUIDs; cross-shard joins become fan-out + merge in the app — the DSA merge you know). And the honest alternative worth saying: at feed-scale reads, a denormalized NoSQL store (Dynamo-style, partition key = the access pattern) is sometimes the cleaner tool — "Postgres as system of record, purpose-built stores for the extreme paths".

// quiz — first pick is the one that counts

Sharding chat messages: shard by conversation_id or by sender's user_id?

Why: the shard key rule is "co-locate what you query together" — pick the key that makes the hot query single-shard. message_id distributes beautifully and ruins every read (the distribution-vs-locality trap); time-sharding makes NOW a hot shard. Follow-up to volunteer: a mega-group-chat is still a hot conversation — cap group sizes or sub-partition. The reasoning pattern transfers to every "what's your partition key?" question, SQL or NoSQL.

LEVEL UP — what interviewers listen for
  • Consistent hashing in one sentence: keys and nodes live on a ring; a node's arrival claims only its arc — 1/n of keys move instead of nearly all (naive modulo). That sentence is the whole interview requirement.
  • Fan-out cost honesty: a cross-shard query is min(shards touched) round trips + an app-side merge — "I'd design the schema so the 99% query never fans out".
  • "Shard when a beefy primary + replicas + partitioning can't hold writes — which for most products is never" — the calibrated close, again.

06

Queues & async — decouple the slow from the now

advanced → the buffer that absorbs spikes and survives crashes

A queue between "accept the request" and "do the slow work" buys four properties at once: latency (respond in 50ms, render the PDF later), spike absorption (a 10× burst becomes queue depth, not dropped requests — workers drain at their own pace), failure isolation (email provider down = queue grows, site unaffected), and retry-ability (a crashed worker's message reappears after the visibility timeout). The price, which you must say in the same breath: eventual consistency (the user gets 202-accepted, the effect lands later — the UI shows "processing", the frontend module's optimistic/pending patterns) and at-least-once delivery, which makes idempotent consumers non-negotiable (the idempotency-key discipline from node-backend, now mandatory).

Queue vs pub/sub vs event log, in one line each: a queue (SQS) is a to-do list — one consumer group, message deleted when done. Pub/sub (SNS) is an announcement — every subscriber gets a copy, fire-and-forget. An event log (Kafka-style) is an append-only history consumers replay at their own cursor — fan-out AND replay AND ordering per partition, at real operational cost. "SQS until proven otherwise" is the calibrated default for product work.

// quiz — first pick is the one that counts

Order placement does: charge card, then queue [send email, update analytics, notify warehouse]. The email worker crashes mid-send and the message redelivers. What MUST be true?

Why: "exactly-once delivery" is the famous impossible promise (the message may have been processed right before the crash-ack was lost) — real systems do at-least-once + idempotent processing, which composes to effectively-once. The dedupe key can live in Redis/DB ("processed set") or the provider's idempotency header. Bonus depth: poison messages (fail forever) go to a dead-letter queue after N attempts — the DLQ mention completes the answer.

LEVEL UP — what interviewers listen for
  • Queue health = oldest-message age, not length (the AWS module's ops lesson) — and workers auto-scale on it.
  • Ordering: queues don't promise it globally; when order matters, partition by key (per-user FIFO lanes) — same co-location logic as sharding.
  • The outbox pattern in one line: write "email pending" in the SAME DB transaction as the order, a relay publishes it — closes the "charged but never queued" gap. Rarely named, heavily rewarded.

07

Consistency models — what "reading your own write" costs

intermediate → linearizable to eventual, and PACELC over CAP

Once data lives in two places (replicas, caches, regions), "what does a read return?" needs a contract. The ladder, strongest first: linearizable — every read sees the latest committed write, as if one copy existed (pay in latency and availability); read-your-writes — you see your own updates, others may lag (the one users actually notice — post a comment, refresh, it's gone = this violated); monotonic reads — time never runs backwards for one client; eventual — replicas converge, eventually, promises nothing meanwhile. Most products need linearizability for a few things (payments, inventory decrement, usernames) and get away with eventual + read-your-writes everywhere else — choosing per-operation, not per-system, is the design skill.

CAP's honest successor is PACELC: under Partition, choose Availability or Consistency — Else (normal operation!) choose Latency or Consistency. The "else" is the daily trade: a linearizable read crosses to the leader (slow, correct); a local replica read is fast and slightly stale. Partitions are rare; the latency choice is every request.

// quiz — first pick is the one that counts

A user updates their profile photo, and the app reads from replicas. Which is the cheapest fix for "my photo didn't change"?

Why: the violation only matters to the writer — nobody else knows the photo changed. Pinning the writer to the primary for ~replication-lag seconds (a cookie/timestamp trick), or echoing the write back from the client/cache, buys the experience without taxing every read (option A) or every write (option C). "Scope the consistency to who needs it" is the senior sentence — and it's the postgres module's read-replica caveat, promoted to a design principle.

LEVEL UP — what interviewers listen for
  • Say "stale-read window ≈ replication lag" with a number (ms to seconds) — quantifying the staleness turns hand-waving into engineering.
  • The interview trap: "we need strong consistency" — reply "for which operations?" Inventory decrements yes; product-page view counts no. Per-operation budgets impress.
  • Causal consistency is the honorable middle: "replies never appear before their parent comment" — name it for social/threaded features.
  • Tie-in: caching (§04) is deliberately-stale replication — TTL is your consistency contract written in seconds.

08

Idempotency, end to end — the retry-safe request path

intermediate → from double-click to double-charge, closed at every layer

Queues (§06) needed idempotent consumers; this section closes the whole path, because retries happen at every layer — double-clicks, timeout-and-retry HTTP clients (did the first request land? unknowable!), queue redeliveries, replayed webhooks. The standard machinery: the client generates an idempotency key (UUID per logical operation, not per attempt); the server, in one atomic step, records the key and does the work; a repeat key returns the stored original response — not an error, the same 200, so retrying clients can't tell (and don't need to). The atomic step matters: check-then-do without atomicity is the §pg lost-update race — implement as a unique-constraint insert on the key, the DB as referee again.

The complementary discipline is knowing what's naturally idempotent: setting absolute state (status = 'shipped', seats = 4) retries harmlessly; relative mutations (seats = seats − 1, "append line") do not — so prefer absolute writes where the domain allows, and guard the truly relative ones with keys. HTTP's contract encodes this: PUT/DELETE are idempotent by spec, POST is not — which is why "retry-able POST" is precisely what idempotency keys exist to build.

// quiz — first pick is the one that counts

A payment request times out client-side. The client retries with the SAME idempotency key and gets a 200 with a charge id. What actually happened at the server, in both possible worlds?

Why: a timeout means "outcome unknown" — the request may have died en route OR completed with the response lost. Idempotency keys make both worlds converge on one charge and one canonical response, which is why Stripe et al. mandate them. Option D is the dangerous myth: timeouts abort the wait, never the work. Saying "timeouts create ambiguity; keys collapse it" is the whole interview answer in eight words.

LEVEL UP — what interviewers listen for
  • Key scope: one key per user intent ("this checkout"), minted client-side, stored with TTL (24h covers retry storms without unbounded growth).
  • Concurrent duplicates: the second request arriving mid-flight blocks on (or is rejected by) the key row — the unique constraint serializes them; mention the "in-progress" state.
  • Webhooks are inbound retries: process-exactly-once = dedupe on the event id — same machinery, direction reversed.
  • Cross-service sagas: each step idempotent + compensations for rollback — one sentence of it signals you know where this scales to.

09

Design a rate limiter — the classic, assembled

intermediate → algorithm, storage, distribution & the 429 contract

"Design a rate limiter" is beloved because it's every trade-off in one small box. Algorithm: token bucket (bursts up to N, refill R/sec — the node-backend implementation) vs sliding-window counter (smooth, Redis-friendly: weight two adjacent window counts) — fixed windows lose to the boundary-burst (2× limit straddling the reset). Storage: in-process is a lie behind a load balancer (each replica its own count — the nb clustering lesson); centralize in Redis — INCR + EXPIRE, atomic via Lua/pipelines, ~sub-ms. Placement: at the gateway (protects everything behind it) with per-route budgets; auth'd requests key by user/API-key, anonymous by IP (both, for login — the credential-stuffing lesson). The contract: 429 + Retry-After + rate-limit headers — a limiter without honest headers turns polite clients into accidental attackers.

The distributed wrinkle worth volunteering: Redis round-trips per request add latency and a SPOF — production gateways use local buckets synced asynchronously (slightly loose global limit, zero hot-path dependency) or Redis cell-style sharding by key. "Exactly enforced, globally, cheaply — pick two" is the honest framing.

// quiz — first pick is the one that counts

Your limiter allows 100 req/min with fixed 1-minute windows. An attacker sends 100 requests at 11:59:58 and 100 more at 12:00:01. Result, and the fix?

Why: the fixed window resets at 12:00:00 sharp — both bursts are "legal", delivering 2× the intended rate exactly when someone tries. The sliding-window counter approximates the trailing window from two adjacent counts (weighted by overlap) — one extra Redis field, boundary closed. This precise failure narrative is what separates "I'd use Redis" from "I've thought about limiters".

LEVEL UP — what interviewers listen for
  • State the tiers unprompted: per-user, per-IP, per-route, global (load-shedding) — different budgets, different keys, one mechanism.
  • Degradation policy: if Redis is down, fail OPEN with local fallback limits (availability) or fail CLOSED (protection) — say which and why for THIS product; the choice is the answer.
  • Cost of a limiter miss ≠ uniform: login and password-reset get tight budgets; GET /catalog gets loose ones — budgets follow abuse value.
  • The aws messaging tie-in: queues are rate limiting for writes you can defer — throttle what must be sync, buffer what needn't be.

10

Quorums & leader election — agreement without a boss (briefly, with one)

advanced → why odd numbers, what Raft settles, and split-brain

Replicated systems keep needing one fact agreed on — who's the leader, what's the next log entry — while nodes crash and networks tear. The workhorse idea is the quorum: any decision needs a majority (⌈(n+1)/2⌉ of n). Why majorities: any two majorities overlap — so two conflicting decisions can't both pass, even during a partition; the minority side simply can't decide. That's also why clusters are odd-sized: 4 nodes tolerate one failure (majority 3), same as 3 nodes — the fourth buys nothing but cost; and why a 6/6 split network halts both halves (no majority anywhere) — a halt being the correct behavior, because the alternative is split-brain: two leaders both accepting writes, divergence you get to reconcile by hand at 3am.

Raft (the consensus algorithm you name) packages this: nodes elect a leader by majority vote (with terms — epoch numbers — so a stale leader returning from a partition discovers it's been deposed), the leader sequences all writes, and a write is committed once a majority acknowledges. You will likely never implement it; you operate it constantly — etcd, the control planes of Kafka/Kubernetes, Postgres HA tooling. The interview asks for the shape: majorities overlap, terms fence the stale, minorities halt.

// quiz — first pick is the one that counts

A 5-node cluster partitions 3/2. The old leader is in the 2-side. What happens, and why is it correct?

Why: the old leader can still accept requests but can never commit them (needs 3 acks, has 2 nodes) — its writes are stuck proposals, not divergent truth. The overlap argument does the work: any majority (3) intersects any other, so a second concurrent leader is arithmetically impossible. Options A and D are split-brain descriptions; option C over-halts (the majority side is fine). Walking this scenario cleanly is the entire consensus interview.

LEVEL UP — what interviewers listen for
  • Fencing tokens: the deposed leader's in-flight side effects (a write to storage!) are blocked by attaching the term/token to every operation — storage rejects stale terms. Name it for the "zombie leader" follow-up.
  • Leases = leadership with an expiry heartbeat — cheaper than full consensus for locks; clock-skew is their known sin.
  • Dynamo-style quorums (R + W > N) are replication quorums — tunable consistency per read/write, related math, different machinery than leader consensus; keeping them distinct is a depth marker.
  • The calibration sentence: "I don't build consensus; I rent it (etcd/managed) and design so few things need it — most data tolerates §07's weaker contracts."

11

Search systems — the inverted index & the sync problem

advanced → why LIKE dies, how relevance ranks, keeping two truths aligned

WHERE title LIKE '%wireless%' scans every row and can't rank — search needs the inverted index: tokenize documents (lowercase, strip stems — "charging" → "charg"), then map term → posting list of document ids. A query intersects posting lists (dsa's hash-set intersection at planetary scale) and ranks the survivors: TF-IDF/BM25 — a document scores higher when the term is frequent in it but rare overall ("wireless" beats "the"). That's Elasticsearch/OpenSearch's core; Postgres's built-in full-text (tsvector + GIN — the pg module's index!) is the right first stop for modest scale, and saying so before reaching for a search cluster is judgment interviewers reward.

The system-design half is two sources of truth: the DB owns the data, the index owns the searchable copy, and they will drift. Sync options, in ascending robustness: dual-write from the app (races and partial failures — the known-bad), async via the outbox/CDC (change-data-capture tailing the DB log — the standard), and periodic full reindex as the self-healing backstop. Search being eventually consistent with the DB is accepted and stated: a new listing appearing in search seconds later is fine; say the window.

// quiz — first pick is the one that counts

Products are updated in Postgres and dual-written to Elasticsearch in the same request handler. What failure will support eventually report, and the fix?

Why: two independent writes = the partial-failure zoo (DB yes + ES no; or interleaved updates applying in different orders to each store). The DB's WAL already serializes the truth — CDC replays that, giving ordering and at-least-once retries for free; the reindex backstop bounds any residual drift. "Never dual-write two sources of truth; derive one from the other's log" generalizes to caches, analytics, and every read-model — it's a whole architecture lesson wearing a search costume.

LEVEL UP — what interviewers listen for
  • Autocomplete ≠ search: prefix queries want edge-ngrams or a trie-shaped index (dsa's tries, deployed) with tiny latency budgets — name it as its own system.
  • Faceted search (counts per brand/size) is aggregations over the same inverted index — one sentence connects the UI feature to the structure.
  • Relevance is a product decision: boosting (title > description), recency decay, personalization — "BM25 is the floor, the ranking function is the product".
  • Semantic/vector search is the modern sibling (embeddings + ANN index) — one honest sentence: "different index, same sync problem".

12

Multi-region — failover, active-active & the write problem

advanced → RTO/RPO, and why "just run it in two regions" is a data question

Two reasons to leave one region: latency (Sydney users, Virginia servers, 200ms floor — physics) and survival (regions do fail). The vocabulary that structures every answer: RTO (how long until service returns) and RPO (how much data you may lose), because they price the strategies. Backup-restore: hours RTO, backup-age RPO, nearly free. Active-passive (warm standby + replication): minutes RTO, seconds RPO, double-ish infra. Active-active: zero-ish RTO... and now writes conflict — two regions accepting updates to the same row is the §10 split-brain, invited on purpose.

Resolving active-active writes is a menu of costs: home-region routing (each user's writes go to their region — co-location again; cross-region only for the rare shared object), CRDTs/last-write-wins for data that merges (counters, presence — and LWW silently drops updates: say so), or global consensus databases (Spanner-class: correct, expensive, latency-taxed). Reads are the easy 90%: serve locally everywhere (CDN + replicas), and most "multi-region" asks dissolve into "global reads, home-region writes, regional failover" — the calibrated shape to draw.

// quiz — first pick is the one that counts

Leadership wants "zero downtime even if a region dies" for a payments system. The RPO conversation to have first?

Why: replication lag IS the RPO under async — failover loses the in-flight tail, and for payments "we lost 4 seconds of charges" is a reconciliation project. Sync replication buys RPO≈0 by putting a cross-region round-trip inside every commit — the PACELC latency choice (§07) at its starkest. There's no trick answer; the skill is surfacing the trade before the outage: latency every day, or data-loss risk on the bad day. Executives can choose; engineers must ask.

LEVEL UP — what interviewers listen for
  • Failover is a practiced procedure, not a config: DNS/anycast shift, replica promotion, and the drill cadence — "we game-day it quarterly" is worth more than any diagram.
  • Data residency (EU data stays in EU) is multi-region for legal reasons — partitioning by law, not latency; one sentence shows awareness.
  • The failback trap: after the region returns, who reconciles writes the standby took? Rejoining is harder than leaving — mention it and watch the interviewer nod.
  • Cost honesty: active-active ≈ 2× infra + engineering forever; "most businesses buy active-passive and spend the difference on preventing incidents" is a defensible close.

Five worked designs — the blocks, recombined

the payoff: watch the same six blocks solve everything

1 · URL shortener (the classic opener). Envelope: write-light, read-heavy, tiny rows. Design: POST → generate a short code (base62 of a counter, or random + collision check) → one Postgres table; GET → cache-aside Redis (hot links are VERY hot) → 301. The twist interviewers add: analytics — answer with a queue (fire a click event, count async) so redirects stay fast. Every block, smallest possible dose.

2 · Rate limiter. Token bucket per user in Redis (atomic INCR + TTL — the postgres lost-update lesson says why atomicity matters); at the edge for blunt abuse, in-app for fairness; return 429 + Retry-After. Distributed subtlety: per-node buckets drift — a shared Redis makes the limit global.

3 · News feed (the big one — full walkthrough). Envelope at 10M cats posting + following: reads dwarf writes ~100:1. The core decision: fan-out on write (push each new post into followers' precomputed feed lists — reads are O(1) list fetches; a celebrity with 5M followers makes one post = 5M writes) vs fan-out on read (compute the feed at request time — cheap writes, expensive every read). The answer that wins: hybrid — push for normal accounts, pull-and-merge for celebrity follows (the DSA merge-k-lists, in production). Feed lists in Redis, posts in Postgres/S3, media on CDN, everything downstream of a queue.

4 · Chat. The frontend module owns the client half (sockets, reconnect, optimistic sends); this side: socket servers with a Redis pub/sub bridge (§03's quiz), messages sharded by conversation_id (§05's quiz), delivery states (sent/delivered/read) as receipts flowing back through the same pipes, offline users caught up from the message store on reconnect — the sequence-number catch-up from the frontend course, served from this side.

5 · "Design Google Docs" (the humility test). The expected answer is mostly shape: operational transforms or CRDTs for concurrent edits (name, don't derive), a socket fan-out layer like chat's, snapshots + operation logs for history, and presence as ephemeral pub/sub. Knowing what you'd NOT build (the OT engine — you'd use Yjs) is the senior move, one last time.

// quiz — first pick is the one that counts

In the hybrid feed, WHY do celebrity posts use fan-out-on-read instead of write?

Why: fan-out-on-write's cost scales with follower count — fine at 200 followers, catastrophic at 5M (write amplification: 1 action → 5M operations). The hybrid puts each account on the side of the trade its numbers favor, and the reader merges "my precomputed list + posts from the 3 celebrities I follow" — a k-way merge over tiny k. This one question contains the module: envelope → identify the amplification → split the strategy → reuse a DSA primitive. If you can narrate it cold, you're ready.

LEVEL UP — what interviewers listen for
  • Every design ends with the same 60-second closer: failure modes (what breaks, what users see), the monitoring that catches it (symptoms!), and what you'd build first vs defer. Rehearse it as a ritual.
  • The five designs above map to System Design in 48's drills — do them timed there after learning them here.
  • And the frontend halves of feed/chat/docs live in Frontend SD in 48 + the deep-dive module — you now hold both sides of every full-stack design question. That's rare. Use it.

Three more worked designs — geo, contention & rankings

advanced → the blocks again, plus this module's new machinery

6 · Proximity — "find cat cafés near me" (the geo question). Envelope: read-heavy, location updates modest, staleness tolerable (a café doesn't move). The core problem: SQL can't index "within 2km" with a B-tree — lat/lon are two dimensions. The answer is geo-bucketing: geohash/S2 cells turn coordinates into string prefixes where nearby places share prefixes — suddenly it's a prefix query (the trie idea, on the planet). Design: places in Postgres (+ PostGIS or a geohash column), hot cells cached, query = "my cell + 8 neighbors" (edge cases at cell boundaries — the detail that shows you've thought), rank by distance + rating. Moving objects (drivers, not cafés) flip the envelope: write-heavy location pings → in-memory grid sharded by cell, TTL'd — nobody needs last hour's position.

7 · Ticketmaster — selling exactly N seats (the contention question). Envelope: reads dwarf writes until on-sale moment, then 100k people want seat 14B simultaneously — the lost-update race as a business model. The layers: a virtual waiting room (queue admission tokens — §06 absorbing the spike before it touches inventory), seat holds with TTL (SELECT … FOR UPDATE or Redis SETNX + expiry: hold, pay within 8 minutes, release on timeout — §08's idempotency keys on the payment), and the final decrement atomic in Postgres (the single-row referee; sharding by event id keeps each on-sale's contention on one shard — co-location). The honest sentence: "the database is the bottleneck on purpose — correctness for seats beats throughput, and the waiting room makes the queue explicit instead of a thundering herd."

8 · Leaderboard — live game rankings (the sorted-data question). Envelope: heavy score writes, heavy rank reads ("my rank among 10M"). Naive SQL (ORDER BY score + COUNT for rank) recomputes the world per query. The purpose-built structure: Redis sorted sets — O(log n) score updates, O(log n) rank lookups, top-100 pages for free (a skip list underneath — the dss balance section's cousin, in production). Design: ZADD on game events (via a queue — spikes again), ZREVRANK for "my rank", periodic snapshot to Postgres for durability (Redis is the fast copy, not the truth — §11's derive-don't-dual-write). Windowed boards (daily/weekly) = one sorted set per window with TTLs; "rank among friends" = intersect with the friend set, small n, compute live.

// quiz — first pick is the one that counts

At on-sale, 100k concurrent buyers hit "reserve seat". Why does the design put a waiting room + holds IN FRONT of an atomic decrement, instead of just trusting the atomic decrement?

Why: the atomic decrement keeps you correct; it does nothing for the experience of 100k people retrying against locked rows (connection-pool exhaustion → the whole site down — the nb migration lesson's cascade). Layering is the answer: shed load early (waiting room), convert contention into held state with expiry (holds), and let only serialized, admitted traffic reach the referee. "Correctness at the core, flow control at the edges" is the pattern this whole design exists to teach.

LEVEL UP — what interviewers listen for
  • Geo edge case to volunteer: a search point near a cell border misses neighbors in adjacent cells — always query the 3×3 block; the follow-up ("what about the poles/meridian?") is why libraries, not hand-rolled geohashing.
  • Ticketing's idempotency: the payment retry with the same key (§08) is what makes "I clicked pay twice during the timeout" harmless — connect the sections aloud.
  • Leaderboard ties: "top-K" is the dss heap question; "rank among 10M" is why sorted sets (skip lists) beat heaps here — heaps answer top, not arbitrary rank. Choosing between your OWN tools is the final exam.
  • All three designs end the same way: name the block (bucketing / admission control / purpose-built structure), the consistency contract, and the failure story. The ritual from §13 applies verbatim.

In the interview

The design round rewards structure, numbers, and named tradeoffs — all three are rehearsable.

  • Open with the loop, audibly: "requirements and numbers first, then a skeleton, then let's go deep where it's interesting." The interviewer relaxes; you've taken the wheel.
  • Do the envelope even if unasked — it's the five minutes that makes everything after defensible, and skipping it is the #1 failure mode.
  • Volunteer a failure story per component: "if Redis dies, we degrade to DB reads with a latency hit; if the queue backs up, the age alarm fires and workers scale." That closing ritual is worth a level.
  • The advanced band is the L5/L6 gate: per-operation consistency budgets (07), the timeout-ambiguity story (08), a rate limiter you can whiteboard from memory (09), the majority-overlap argument (10), derive-don't-dual-write (11), and the RPO conversation (12). Each is three rehearsed minutes.
  • Timed drills: System Design in 48 (the whole course is this module at sprint pace). The interview-kit module (next!) adds the mock-loop run sheets to practice it under a clock.

Run the calculator on every app you use this week. Estimation is a habit, not a talent — and it's the habit that makes design rounds feel like home turf.
