Trees & graphs, walked, not memorized.

Trees and graphs carry a reputation they don't deserve. A tree is a linked list that branches. A graph is things-connected-to-things — you debug one every time you look at node_modules. What interviews test is walking them: BFS (a queue, in waves) and DFS (a stack, deep first), plus two famous patterns built on those walks. All of it is watchable on this page, including BFS flooding a grid live.

Prerequisites: recursion instincts help but aren't assumed; the queue/stack duo from Linear Structures is the engine here. The cats have climbed into a family tree. Naturally. 🐈

Trees & traversals — three orders, one shape

beginner → recursion that finally feels natural

A tree: nodes with children, no cycles, one root. You navigate one daily — the DOM — and render another — your component tree. The recursive insight that unlocks everything: every subtree is itself a tree. So tree code has one shape: do something with this node, recurse into the children. Height, size, search, invert — all four lines each.

The three DFS orders differ only in when the node acts relative to its children: pre-order (act, then children — copying/serializing), in-order (left, act, right — sorted output from BSTs), post-order (children first — deleting, computing sizes bottom-up). Level-order is the odd one out: it's BFS with a queue, floor by floor.

PROFESSOR WHISKERS EXPLAINSA cat family tree: Grandma Whiskers, her two kids, their kittens. "How many descendants do you have?" — Grandma doesn't count the whole clan herself; she asks each kid the same question, they ask theirs, and answers bubble up: my descendants = my kids + everything they report. That delegation IS tree recursion — nobody counts more than their own doorstep. And a family photo taken floor-by-floor (grandma row, parents row, kittens row)? Level-order — the dinner-line queue from last module, reused.

family-tree.js — run it
const node = (name, left = null, right = null) => ({ name, left, right });
//            grandma
//            /     \
//        momo       tuft
//        /  \          \
//    mochi  biscuit    clawdia
const root = node('grandma',
  node('momo', node('mochi'), node('biscuit')),
  node('tuft', null, node('clawdia')));

// every tree function is this 4-line shape:
const count = (n) => !n ? 0 : 1 + count(n.left) + count(n.right);
const height = (n) => !n ? 0 : 1 + Math.max(height(n.left), height(n.right));
console.log('clan size:', count(root), '· generations:', height(root));

// the three DFS orders — same walk, different MOMENT of action
const pre = (n, out = []) => { if (n) { out.push(n.name); pre(n.left, out); pre(n.right, out); } return out; };
const inod = (n, out = []) => { if (n) { inod(n.left, out); out.push(n.name); inod(n.right, out); } return out; };
const post = (n, out = []) => { if (n) { post(n.left, out); post(n.right, out); out.push(n.name); } return out; };
console.log('pre :', pre(root).join(' '));
console.log('in  :', inod(root).join(' '));
console.log('post:', post(root).join(' '));

// level-order = BFS = the queue from last module
function levels(rootNode) {
  const q = [rootNode], out = [];
  let head = 0;
  while (head < q.length) {
    const floor = [];
    for (let size = q.length - head; size > 0; size--) {
      const n = q[head++];
      floor.push(n.name);
      if (n.left) q.push(n.left);
      if (n.right) q.push(n.right);
    }
    out.push(floor.join(' + '));
  }
  return out;
}
console.log('floors:', levels(root));

"Invert a binary tree" (the meme question). The four-line answer's shape?

      

        
        
        
        
      

      
Why: mirror the whole tree = swap children at every node — and "every node" is what recursion gives you for free: if (!n) return; [n.left, n.right] = [n.right, n.left]; invert both. If a tree problem feels hard, ask "what's the one-node version of this job?" — the recursion writes itself. That reframe is the section's whole superpower.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Complexity: every traversal visits each node once — O(n) time; space is the height (recursion stack): O(log n) balanced, O(n) for a degenerate chain. Saying "space is height, not n… unless it's a stick" is precise and charming.
    • 
        
  • Diameter, "is balanced", max path sum — all post-order: children report up, parent combines. Recognizing "answers flow bottom-up → post-order" solves a whole family.
    • 
        
  • Right-side view = level-order keeping each floor's last; zigzag = level-order flipping alternate floors. BFS variants are mostly bookkeeping.

Binary search trees — the ordered family

      
intermediate → the invariant, its powers, and its betrayal

    

  

  

    
Add one rule to a binary tree and it becomes a search machine: everything in the left subtree is smaller than me; everything right is bigger. Now "find 7" is the cat-registry trick from Foundations — go left or right, halving the search world each step: O(height) ≈ O(log n) when balanced. Bonus superpower: in-order traversal emits everything in sorted order, free.

    
The betrayal: insert already-sorted data and the "tree" grows as a stick — height n, powers gone. Real systems use self-balancing variants (red-black trees under language maps, B-trees under your Postgres indexes — yes, this section is why your WHERE indexed_col = ? is fast). Interviews don't ask you to implement balancing; they ask you to know the failure and name the fix.

    

      

        
ordered-registry.js — run it

        
const node = (v, left = null, right = null) => ({ v, left, right });
function insert(n, v) {
  if (!n) return node(v);
  if (v < n.v) n.left = insert(n.left, v); else n.right = insert(n.right, v);
  return n;
}
// cat weights arrive in scrambled order → bushy, healthy tree
let bst = null;
for (const w of [5.5, 3.2, 7.1, 2.8, 4.9, 6.3, 8.4]) bst = insert(bst, w);

const height = (n) => !n ? 0 : 1 + Math.max(height(n.left), height(n.right));
const sorted = (n, out = []) => { if (n) { sorted(n.left, out); out.push(n.v); sorted(n.right, out); } return out; };
console.log('scrambled insert → height', height(bst), 'for 7 cats (log₂7 ≈ 2.8 ✓)');
console.log('in-order = sorted, free:', sorted(bst).join(', '));

function find(n, v, hops = 0) {
  if (!n) return { found: false, hops };
  if (v === n.v) return { found: true, hops };
  return find(v < n.v ? n.left : n.right, v, hops + 1);
}
console.log('find 6.3:', find(bst, 6.3));

// the betrayal: SORTED inserts → a stick
let stick = null;
for (const w of [1, 2, 3, 4, 5, 6, 7]) stick = insert(stick, w);
console.log('sorted insert → height', height(stick), '— a linked list in disguise');

Validate a BST: why does "check each node's children are on the right side of it" miss invalid trees, and what's the fix?

      

        
        
        
        
      

      
Why: the invariant is about entire subtrees, not parent-child pairs: a 6 in the right-left position under root 5 passes the local check ("6 > 5's right child's parent…") but sits in territory that must ALL be >5 and <its parent. Shrinking (min, max) windows carry the full constraint down. This is the canonical "local reasoning fails, thread the invariant" lesson — it reappears in distributed systems arguments, which is a fun thing to say out loud.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Kth smallest in a BST = in-order walk, stop at k. LCA in a BST = walk from root, first node where the two targets split sides — both one-liners once the invariant is instinct.
    • 
        
  • The systems bridge: B-trees are BSTs widened for disk pages (hundreds of keys per node, tiny height) — "my Postgres index is this section at warehouse scale" connects your two interview tracks beautifully.
    • 
        
  • BST vs hash map: map wins pure lookup O(1); BST wins ordered ops — range queries, nearest-neighbor, sorted iteration. "Do I ever need neighbors or ranges?" picks the structure.
    • 
        
  • practice (verified): 98 · Validate BST · 230 · Kth Smallest · 235 · LCA of BST

Tries — the autocomplete tree

      
intermediate → one letter per hop, shared prefixes shared once

    

  

  

    
A trie stores words by spelling them down a tree: one letter per edge, shared prefixes sharing a path. "mochi" and "momo" split only after "mo". Lookup and insert cost O(word length) — independent of how many thousands of words are stored — and every word passing through a node is a completion of that node's prefix. That's why it IS autocomplete: walk down the typed prefix, then everything below is a suggestion.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe shelter files cat names as a choose-your-own-adventure of letters: from the lobby, the M door, then O — and here "mochi" and "momo" part ways at their third letter. Ten thousand names, but finding one never takes more steps than its spelling. And standing at "mo-" and shouting "who's downstairs?" — that's autocomplete returning mochi, momo, and moose the confused dog.

    

    

      

        
name-registry.js — run it

        
class Trie {
  constructor() { this.root = {}; }
  insert(word) {
    let n = this.root;
    for (const ch of word) n = (n[ch] ??= {});
    n.$ = true;                                // end-of-word marker
  }
  has(word) {
    let n = this.root;
    for (const ch of word) if (!(n = n[ch])) return false;
    return !!n.$;
  }
  suggest(prefix) {
    let n = this.root;
    for (const ch of prefix) if (!(n = n[ch])) return [];
    const out = [];
    (function walk(node, path) {
      if (node.$) out.push(prefix + path);
      for (const ch of Object.keys(node))
        if (ch !== '$') walk(node[ch], path + ch);
    })(n, '');
    return out;
  }
}
const registry = new Trie();
['mochi', 'momo', 'moose', 'biscuit', 'bisque', 'clawdia']
  .forEach(w => registry.insert(w));
console.log('has mochi:', registry.has('mochi'), '· has mo:', registry.has('mo'));
console.log('mo… →', registry.suggest('mo').join(', '));
console.log('bis… →', registry.suggest('bis').join(', '));

      

      
a working autocomplete in 25 lines — the $ marker is the subtle bit

      

    

    

      
// quiz — first pick is the one that counts

      
Why does the trie need the end-of-word marker ($) — what breaks without it?

      

        
        
        
        
      

      
Why: every stored word's path exists — but so does every prefix of it. has('mo') reaches a real node either way; only $ says whether someone actually filed a cat named Mo. This is LC 208's core test case, and forgetting it is the #1 trie bug. (Real engines add frequency counts at nodes to rank suggestions — say that for the systems flourish.)

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Trie vs hash set: the set answers "is this exact word here?" — the trie also answers prefix questions (autocomplete, spell-check candidates, longest-common-prefix) which sets simply cannot.
    • 
        
  • Space is the trade: one node per distinct prefix. Compressed tries (radix trees) merge single-child chains — that's what routers and IP tables use; one sentence suffices.
    • 
        
  • Word Search II (find dictionary words in a letter grid) = trie + DFS pruning: walking the grid and the trie together, abandoning paths no word starts with. It's the flagship "combine two tools" hard.
    •

Graphs — BFS & DFS, watched live

      
the centerpiece: two walks, one flood animation

    

  

  

    
A graph is nodes + edges, no rules about shape. You operate several before lunch: node_modules (directed), your social graph (undirected), microservice call maps, city roads. Interviews represent them one of two ways: an adjacency list (Map: node → [neighbors] — the default) or an implicit grid where each cell's neighbors are up/down/left/right.

    
Everything reduces to the two walks. BFS (queue): explore in rings — 1 hop, then 2, then 3 — which is why it finds shortest paths in unweighted graphs; the wave hits everything at distance d before anything at d+1. DFS (stack/recursion): commit to a direction, go deep, backtrack — the tool for "explore/count/fill whole regions" and cycle detection. One non-negotiable for both: mark nodes visited when you enqueue them, or cycles trap you forever.

    

      
WATCH BFS FLOOD A GRID — shortest path by rings

      
Mochi (M) wants the tuna (T). Walls are dark. BFS floods outward one ring per step — the number on each cell is its discovered distance. When the wave reaches T, that number IS the shortest path.

      

        
        
        
        press step — the queue does the walking
      

      

    

    

      

        
the-two-walks.js — run it

        
// the café's cat friendship graph, as an adjacency list
const friends = new Map([
  ['mochi',   ['biscuit', 'clawdia']],
  ['biscuit', ['mochi', 'tuft']],
  ['clawdia', ['mochi', 'tuft']],
  ['tuft',    ['biscuit', 'clawdia', 'ziggy']],
  ['ziggy',   ['tuft']],
  ['loner',   []],                          // separate component!
]);

// BFS: fewest introductions from mochi to anyone
function hops(from) {
  const dist = new Map([[from, 0]]);
  const q = [from]; let head = 0;
  while (head < q.length) {
    const cat = q[head++];
    for (const f of friends.get(cat))
      if (!dist.has(f)) {                    // visited check ON enqueue
        dist.set(f, dist.get(cat) + 1);
        q.push(f);
      }
  }
  return dist;
}
console.log('intro-distance from mochi:',
  Object.fromEntries(hops('mochi')));

// DFS: count friendship circles (connected components)
function circles() {
  const seen = new Set();
  let count = 0;
  const dive = (cat) => {
    seen.add(cat);
    for (const f of friends.get(cat)) if (!seen.has(f)) dive(f);
  };
  for (const cat of friends.keys())
    if (!seen.has(cat)) { count++; dive(cat); }
  return count;
}
console.log('friendship circles:', circles(), '(the loner counts as one)');

      

      
BFS gives distances; DFS counts islands — the eternal division of labor

Topological sort — dependency order, formalized

      
advanced-sounding, genuinely easy → Kahn's algorithm

    

  

  

    
Given tasks with dependencies (course prerequisites, build steps, package.json install order), a topological order is any sequence where everything comes after its prerequisites. It exists exactly when the dependency graph has no cycle — a cycle means "A needs B needs A", i.e. deadlock.

    
Kahn's algorithm is the intuitive one: count incoming edges (in-degree) per node → queue everything with in-degree 0 (no prerequisites — startable now) → repeatedly take a task, "complete" it, decrement its dependents' counts, enqueueing any that hit zero. If you complete all n tasks, that order is your answer; if the queue dries up early, the leftovers form a cycle — and that's how Course Schedule detects impossibility.

    

      
      
PROFESSOR WHISKERS EXPLAINSKitten school: Pouncing requires Stalking, Stalking requires Sitting Still. Each class posts how many prerequisites it's waiting on. Anything at zero runs today. When a class graduates its kittens, every course waiting on it ticks its counter down — hit zero, join tomorrow's schedule. If one day nothing is at zero but courses remain… someone wrote "Advanced Napping requires Advanced Napping II, which requires Advanced Napping". The curriculum is broken, and the counter proves it.

    

    

      

        
kitten-school.js — run it

        
function schedule(courses, prereqs) {           // prereqs: [needs, first]
  const next = new Map(courses.map(c => [c, []]));
  const indeg = new Map(courses.map(c => [c, 0]));
  for (const [course, first] of prereqs) {
    next.get(first).push(course);
    indeg.set(course, indeg.get(course) + 1);
  }
  const q = courses.filter(c => indeg.get(c) === 0);
  let head = 0;
  const order = [];
  while (head < q.length) {
    const c = q[head++];
    order.push(c);
    for (const dep of next.get(c)) {
      indeg.set(dep, indeg.get(dep) - 1);
      if (indeg.get(dep) === 0) q.push(dep);
    }
  }
  return order.length === courses.length
    ? { possible: true, order }
    : { possible: false, stuck: courses.filter(c => indeg.get(c) > 0) };
}

const courses = ['sitting', 'stalking', 'pouncing', 'napping', 'advanced-napping'];
console.log(schedule(courses, [
  ['stalking', 'sitting'], ['pouncing', 'stalking'], ['advanced-napping', 'napping'],
]));

// now break the curriculum with a cycle:
console.log(schedule(courses, [
  ['stalking', 'sitting'], ['pouncing', 'stalking'],
  ['napping', 'advanced-napping'], ['advanced-napping', 'napping'],  // 💥
]));

Union-find — "same group?" at machine speed

      
advanced → 15 lines that answer connectivity instantly

    

  

  

    
When items merge into groups over time and you keep asking "are these two in the same group?", re-running DFS per question is wasteful. Union-find (a.k.a. disjoint set union) maintains group membership directly: every element points toward a representative ("the boss cat"); find(x) follows pointers to the boss, union(a, b) makes one boss report to the other. Two optimizations — path compression (everyone you pass repoints straight at the boss) and union by size — make operations effectively O(1).

    
Trigger phrases: "accounts belonging to the same person", "provinces/friend circles", "does adding this edge create a cycle" (both endpoints already share a boss = cycle — that's Redundant Connection, and it's how Kruskal's MST works).

    

      

        
boss-cats.js — run it

        
class UnionFind {
  constructor(n) { this.boss = Array.from({ length: n }, (_, i) => i); }
  find(x) {
    if (this.boss[x] !== x)
      this.boss[x] = this.find(this.boss[x]);   // path compression
    return this.boss[x];
  }
  union(a, b) {
    const ra = this.find(a), rb = this.find(b);
    if (ra === rb) return false;                // already same clique
    this.boss[rb] = ra;
    return true;
  }
  same(a, b) { return this.find(a) === this.find(b); }
}

// six cats: 0..5. friendships merge cliques
const cats = ['mochi', 'biscuit', 'clawdia', 'tuft', 'ziggy', 'loner'];
const uf = new UnionFind(6);
uf.union(0, 1);            // mochi ~ biscuit
uf.union(2, 3);            // clawdia ~ tuft
console.log('mochi ~ clawdia?', uf.same(0, 2));      // separate cliques
uf.union(1, 3);            // biscuit ~ tuft — cliques MERGE
console.log('mochi ~ clawdia now?', uf.same(0, 2));  // one big clique
console.log('anyone ~ loner?', uf.same(0, 5));

// cycle detection: an edge inside an existing clique is redundant
console.log('add mochi–tuft edge:',
  uf.union(0, 3) ? 'merged something new' : 'CYCLE — already connected');

      

      
union returning false IS the cycle detector

Union-find vs DFS for connectivity — when does union-find actually win?

      

        
        
        
        
      

      
Why: it's static-vs-dynamic: one connectivity question over a finished graph → DFS is simpler. A stream of "friend A and B just connected — same circle as C?" → union-find amortizes beautifully. And note what it can't do: paths (it forgets structure, keeping only membership) — that's option 4's trap. "Right tool by access pattern" framing = senior signal.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Accounts Merge is the flagship: union accounts sharing an email, then group by boss. Real dedupe systems (contacts, identity resolution) genuinely do this.
    • 
        
  • Say "inverse Ackermann — effectively constant" once, with a smile, and move on. Deriving it is nobody's interview.

  • Hear "shortest / fewest / minimum steps" in an unweighted world → BFS, say "rings" out loud. "Count regions / can it reach / explore all" → DFS flood. "Prerequisites / build order / deadlock" → topo sort. "Same group, merging over time" → union-find.
    •

    • 
      
  • Trees: pick the traversal by where answers flow — down (pre), sorted (in), up (post) — and always mention stack space.
