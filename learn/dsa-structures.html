Linked lists — cats holding tails

beginner → the reversal, stepped through slowly

A linked list is nodes scattered anywhere in memory, each holding a value and a pointer to the next node. No indexes — to reach item 500 you walk 500 hops (O(n)). So why bother? Because splicing is O(1): insert or remove anywhere by rewiring two pointers, no mass shuffling of neighbors like an array.

Interview reality: you'll rarely choose a linked list at work (arrays are cache-friendly and usually win), but interviews use them constantly because they test whether you can manipulate references without losing your grip — which is a real skill you use every day in object graphs.

PROFESSOR WHISKERS EXPLAINSA conga line of cats, each holding the tail of the next cat. You only know where the front cat is. Finding the 5th cat = walking down the line. But slipping a new cat into the middle? The cat in front lets go of one tail, grabs the newcomer's — two grip changes, nobody else moves. Try that with theater seats (an array) and twenty cats shuffle over. The danger: let go of a tail before grabbing the rest of the line, and everyone behind that point wanders off forever. That's the bug the stepper below is about.

POINTER SURGERY — reverse a list without dropping it

Three variables walk the list: prev (reversed so far), curr (working on), next (the safety grip). Watch the arrows flip one at a time.

// the reversal — the exact loop from the stepper above
function reverse(h) {
  let prev = null, curr = h;
  while (curr) {
    const next = curr.next;   // 1. grip the rest BEFORE letting go
    curr.next = prev;         // 2. flip this cat's arrow
    prev = curr;              // 3. reversed section grows
    curr = next;              // 4. step forward along the grip
  }
  return prev;                // prev is the new front
}
head = reverse(head);
show(head, 'after: ');

// fast & slow — find the middle in ONE pass
function middle(h) {
  let slow = h, fast = h;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
  return slow.name;
}
console.log('middle:', middle(head));

Stacks — last in, first out, everywhere

      
beginner → matching, undo, and the monotonic upgrade

    

  

  

    
A stack is a pile: add on top (push), take from the top (pop), both O(1) — a plain JS array IS one. The pattern trigger: "most recent unfinished thing". Matching brackets (most recent unclosed opener), undo history (most recent action), the call stack itself (most recent unfinished function), DFS (most recent unexplored branch).

    
The interview upgrade is the monotonic stack: keep the stack sorted-by-construction by popping everything your new element beats. Each pop permanently resolves a waiting item ("found the next warmer day!") — n pushes, n pops max, so the scary-looking nested loop is O(n) by the same amortized budget as the sliding window.

    

      

        
piles-of-cats.js — run it

        
// valid parentheses — the stack "hello world" (LC 20)
function validBrackets(s) {
  const pair = { ')': '(', ']': '[', '}': '{' };
  const stack = [];
  for (const ch of s) {
    if ('([{'.includes(ch)) stack.push(ch);
    else if (stack.pop() !== pair[ch]) return false;  // wrong/missing opener
  }
  return stack.length === 0;                          // nothing left open
}
console.log('([{}]) →', validBrackets('([{}])'));
console.log('([)]   →', validBrackets('([)]'));

// monotonic stack: days until a warmer day (LC 739, cat-nap edition)
// temps of the sunbeam spot; a cat naps until it's warmer than today
function daysUntilWarmer(temps) {
  const wait = new Array(temps.length).fill(0);
  const stack = [];                        // indexes of unresolved days
  for (let i = 0; i < temps.length; i++) {
    while (stack.length && temps[i] > temps[stack[stack.length - 1]]) {
      const day = stack.pop();             // resolved forever — that's the O(n)
      wait[day] = i - day;
    }
    stack.push(i);
  }
  return wait;
}
console.log(daysUntilWarmer([23, 24, 21, 19, 22, 26, 23]));
// each index pushed once, popped at most once → 2n operations total

Queues & deques — fair lines and clever windows

      
beginner → BFS's engine, plus the deque party trick

    

  

  

    
A queue is a fair line: in at the back, out at the front, FIFO. It's the engine of breadth-first search (process things in discovery order → shortest paths), task schedulers, buffers, and rate limiters. The JS gotcha you already know from Foundations: shift() is O(n), so real queues use an index pointer, a linked list, or a ring buffer.

    
A deque (double-ended queue) opens both ends. Its star turn is the monotonic deque behind Sliding Window Maximum: keep candidates in decreasing order — new arrivals evict everyone smaller from the back (they can never be a max while a bigger, newer value lives), and the front retires when it slides out of the window. Every element enters and leaves once: O(n) window maximums.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe dinner line is FIFO — cats who queue first eat first, and BFS is just "serve dinner in waves: everyone 1 hop away, then everyone 2 hops away". The deque trick is the judging panel at a cat show with a 3-cat viewing window: when a clearly-more-magnificent cat struts in, every less magnificent cat still waiting at the back leaves immediately — they can never win while the new cat is around and newer. The front of the panel is always the current champion.

    

    

      

        
dinner-lines.js — run it

        
// an O(1) queue: index pointer instead of shift()
class Queue {
  constructor() { this.items = []; this.head = 0; }
  push(x) { this.items.push(x); }
  shift() { return this.items[this.head++]; }         // "remove" = move marker
  get length() { return this.items.length - this.head; }
}
const dinner = new Queue();
['mochi', 'biscuit', 'clawdia'].forEach(c => dinner.push(c));
while (dinner.length) console.log('now eating:', dinner.shift());

// monotonic deque: max of each sliding window of 3 (LC 239)
function windowMax(nums, k) {
  const dq = [];                            // indexes, values decreasing
  const out = [];
  for (let i = 0; i < nums.length; i++) {
    while (dq.length && nums[i] >= nums[dq[dq.length - 1]]) dq.pop();
    dq.push(i);                             // evict the outclassed, join
    if (dq[0] <= i - k) dq.shift();         // champion aged out of window
    if (i >= k - 1) out.push(nums[dq[0]]);  // front = current champion
  }
  return out;
}
console.log('maxes:', windowMax([1, 3, -1, -3, 5, 3, 6, 7], 3));

      

      
the champion logic: evict the outclassed, retire the aged-out

    04
    

      
Heaps — always know the winner

      
intermediate → a real MinHeap in 30 lines, then top-k judgment

    

  

  

    
A heap answers one question, constantly and cheaply: "who's currently first?" Peek the min (or max) in O(1); insert or remove-the-top in O(log n). It does this by maintaining a weak promise — not full sorted order, just "every parent beats its children" — and weak promises are cheap to repair.

    
The elegant bit: the "tree" is just an array. Node i's children live at 2i+1 and 2i+2; its parent at ⌊(i−1)/2⌋. Insert = append + bubble up while beating your parent. Remove-top = move the last element to the root + sift down toward the better child. The tree is complete, so the height is log n — that's the whole complexity story.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe vet's waiting room doesn't keep cats fully sorted by urgency — that would mean re-sorting the whole room every arrival. Instead: a tournament bracket where every cat only promises to be less urgent than the cat above it. New arrival? She challenges her way up a single column — log n hisses, not a room-wide reshuffle. "Who's next?" is always the cat at the top. Weak ordering, strong answer, tiny maintenance.

    

    

      

        
vet-triage.js — run it

        
class MinHeap {
  constructor() { this.a = []; }
  get size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(x) {
    this.a.push(x);
    let i = this.a.length - 1;                  // bubble up
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.a[p] <= this.a[i]) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }
  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;                                 // sift down
      while (true) {
        const l = 2 * i + 1, r = l + 1;
        let best = i;
        if (l < this.a.length && this.a[l] < this.a[best]) best = l;
        if (r < this.a.length && this.a[r] < this.a[best]) best = r;
        if (best === i) break;
        [this.a[best], this.a[i]] = [this.a[i], this.a[best]];
        i = best;
      }
    }
    return top;
  }
}

// top-3 heaviest cats from a stream — keep a SMALL min-heap of winners
const weights = [4.2, 6.1, 3.0, 5.5, 7.3, 2.8, 6.8, 4.9, 5.1];
const h = new MinHeap();
for (const w of weights) {
  h.push(w);
  if (h.size > 3) h.pop();      // evict the lightest of the champions
}
const top3 = [];
while (h.size) top3.push(h.pop());
console.log('top-3 heaviest:', top3);
// n items through a k-sized heap: O(n log k) — and the stream
// never needed to fit in memory. THAT's the heap's real pitch.

    05
    

      
Intervals — sort, then sweep

      
intermediate → the overlap test and the one pattern that rules them

    

  

  

    
Interval problems (meetings, bookings, nap schedules) all rest on two moves. Move 1 — the overlap test: two ranges overlap iff a.start ≤ b.end && b.start ≤ a.end — memorize it as "neither starts after the other ends." Move 2 — sort by start, then sweep once: after sorting, any overlap must involve your immediate neighbor, so one linear pass with a "current merged block" handles everything. O(n log n) for the sort, O(n) for the sweep.

    

      
      
PROFESSOR WHISKERS EXPLAINSFive cats book the sunbeam. Sort the bookings by start time, then walk them holding one "current sunbeam session": next booking starts before the current session ends? Same pile of cats — extend the session to the later end. Starts after? Close the session, start fresh. One walk down the list and every overlapping pile is found — because after sorting, an overlap can't skip over your neighbor to reach you.

    

    

      

        
sunbeam-schedule.js — run it

        
// merge overlapping sunbeam bookings (LC 56)
function mergeBookings(intervals) {
  const sorted = [...intervals].sort((a, b) => a[0] - b[0]);
  const merged = [sorted[0].slice()];
  for (const [start, end] of sorted.slice(1)) {
    const current = merged[merged.length - 1];
    if (start <= current[1]) current[1] = Math.max(current[1], end); // extend
    else merged.push([start, end]);                                  // new block
  }
  return merged;
}
const bookings = [[13, 15], [1, 3], [2, 6], [8, 10], [15, 18]];
console.log('merged:', JSON.stringify(mergeBookings(bookings)));

// min removals so no two bookings overlap (LC 435) — greedy by END time
function minRemovals(intervals) {
  const byEnd = [...intervals].sort((a, b) => a[1] - b[1]);
  let keptEnd = -Infinity, removed = 0;
  for (const [start, end] of byEnd) {
    if (start >= keptEnd) keptEnd = end;   // compatible — keep it
    else removed++;                        // overlaps a kept one — drop it
  }
  return removed;
}
console.log('remove', minRemovals([[1,2],[2,3],[3,4],[1,3]]), 'booking(s)');
// why sort by END? keeping the earliest-ending booking leaves the
// most room for everyone after — the exchange argument in one line.

      

      
merge sorts by START; the greedy scheduler sorts by END — know why

      

    

    

      
// quiz — first pick is the one that counts

The +1/−1 sweep (or a min-heap of end times) reads concurrency directly off the timeline. This "events on a timeline with a running counter" idea is also how load graphs and connection-pool sizing work — another DSA-to-systems bridge worth saying.

    06
    

      
Monotonic stacks — resolve each element exactly once

      
intermediate → "next greater / until warmer / visible from here"

    

  

  

    
Section 02 name-dropped this; now build it. A monotonic stack keeps its contents sorted by construction: before pushing, pop everything your new element beats. The magic is what popping means — for each popped element, the newcomer is the answer to its question ("who's the next one bigger than me?"). Every element pushes once and pops at most once → O(n) for a problem that reads like O(n²).

    
The recipe has one decision: which comparison pops. Looking for the next greater? Pop while the newcomer is bigger (the stack stays decreasing). Next smaller? Pop while it's smaller. Say the invariant out loud before coding — "my stack holds the unresolved, in decreasing order" — and the code writes itself.

    

      
      
PROFESSOR WHISKERS EXPLAINSCats queue at the window ledge, each waiting for a taller cat to see over. When a tall cat arrives, every shorter cat waiting in line goes "ah, found mine", gets its answer, and leaves — all at once. The line only ever holds cats still-waiting, tallest first. Nobody re-queues, nobody re-asks: one arrival can resolve five waiters, and that's why the whole day is O(n).

    

    

      

        
window-ledge.js — run it

        
// Daily Temperatures (LC 739): days until a warmer day
function daysUntilWarmer(temps) {
  const answer = new Array(temps.length).fill(0);
  const waiting = [];                       // indexes, temps decreasing
  for (let i = 0; i < temps.length; i++) {
    while (waiting.length && temps[i] > temps[waiting.at(-1)]) {
      const resolved = waiting.pop();       // today answers their question
      answer[resolved] = i - resolved;
      console.log(`  day ${resolved} (${temps[resolved]}°) resolved by day ${i} (${temps[i]}°)`);
    }
    waiting.push(i);
  }
  return answer;                            // still waiting → 0 (never warmer)
}
const temps = [73, 74, 75, 71, 69, 72, 76, 73];
console.log('temps: ', temps.join(' '));
console.log('answer:', daysUntilWarmer(temps).join(' '));

// same machine, "previous smaller" flavor — one comparison flipped
function prevSmaller(nums) {
  const out = [], stack = [];               // values, increasing
  for (const x of nums) {
    while (stack.length && stack.at(-1) >= x) stack.pop();
    out.push(stack.length ? stack.at(-1) : -1);
    stack.push(x);
  }
  return out;
}
console.log('prev smaller of [4,7,2,9,3]:', prevSmaller([4,7,2,9,3]).join(' '));

      

      
watch one warm day resolve three waiters at once — that's the O(n) proof

      

    

    

      
// quiz — first pick is the one that counts

      
The while-pop sits inside the for-loop. Why is the total still O(n)?

      

        
        
        
        
      

      
Why: the same amortized budget argument as the sliding window and the set-walk: charge each pop to the element being popped, and no element can be popped twice. Loop nesting describes the shape of code, not its cost — the cost lives in how many total operations the input can fund. Three patterns, one argument: say it once per interview and mean it.

    07
    

      
Deques & the sliding-window maximum

      
intermediate → the champion's line, implemented for real

    

  

  

    
A deque (double-ended queue) pushes and pops at both ends. Its one famous trick — teased in section 03 — is Sliding Window Maximum: the maximum of every k-wide window, in O(n) total. The deque holds indexes of "still-relevant champions", front = current max, values decreasing. Two maintenance moves per step: evict the front if it slid out of the window; pop the back while the newcomer beats it (a smaller element behind a bigger, younger one can never be a future max — it's dominated, gone forever).

    
It's the monotonic stack's cousin with an expiry date: monotonicity handles "beaten by a newcomer", the front-eviction handles "too old". Between them, every index enters once and leaves once.

    

      

        
champions-line.js — run it

        
// Sliding Window Maximum (LC 239) — the full machine
function windowMax(nums, k) {
  const out = [], dq = [];                  // dq: indexes, values decreasing
  for (let i = 0; i < nums.length; i++) {
    if (dq[0] <= i - k) dq.shift();         // front too old → expire
    while (dq.length && nums[dq.at(-1)] < nums[i]) dq.pop();  // dominated → out
    dq.push(i);
    if (i >= k - 1) out.push(nums[dq[0]]);  // front IS the window max
  }
  return out;
}
const nums = [1, 3, -1, -3, 5, 3, 6, 7];
console.log('nums:      ', nums.join(' '));
console.log('max per 3: ', windowMax(nums, 3).join(' '));

// why "dominated → gone forever" is safe: trace one step
// window [3, -1, -3], then 5 arrives:
//   -3 < 5 → popped. -1 < 5 → popped. 3 < 5 → popped. deque = [5]
// none of the popped could EVER beat 5 while 5 remains in any window.

// honesty about JS: Array.shift() is O(n). For interviews it's accepted;
// the "real" deque uses a head index (or a ring buffer):
function windowMaxIndexed(nums, k) {
  const out = [], dq = []; let head = 0;    // dq[head..] is the live deque
  for (let i = 0; i < nums.length; i++) {
    if (head < dq.length && dq[head] <= i - k) head++;
    while (dq.length > head && nums[dq.at(-1)] < nums[i]) dq.pop();
    dq.push(i);
    if (i >= k - 1) out.push(nums[dq[head]]);
  }
  return out;
}
console.log('same, O(1) front:', windowMaxIndexed(nums, 3).join(' '));

      

      
the traced step is the whole proof — dominated means never-again

      

    

    

      
// quiz — first pick is the one that counts

      
Why does the deque pop smaller elements from the back when a bigger one arrives, instead of keeping everything in the window?

      

        
        
        
        
      

      
Why: the newcomer is bigger AND will outlive them (it entered later, so it expires later). Dominated on both axes → provably irrelevant → discard permanently. This "dominated candidates can be discarded" reasoning is the same logic behind monotonic stacks and half of greedy proofs — it's an argument template, not a deque fact.

Linked lists, advanced — cycles, clones & k-group surgery

      
intermediate → fast/slow pointers and the interleave trick

    

  

  

    
Three upgrades to section 01's pointer grip. Floyd's tortoise & hare: a slow pointer (1 step) and fast pointer (2 steps) — if there's a cycle they must meet inside it, in O(1) space. The encore that wins interviews: after meeting, reset one pointer to the head and walk both at speed 1 — they meet exactly at the cycle's entrance (the head-to-entrance distance provably equals meeting-point-to-entrance, going around).

    
Copy List with Random Pointer: each node has a random pointing anywhere. The Map solution is easy (old→new, two passes). The O(1)-space showpiece is the interleave trick: weave each clone in right after its original (A→A'→B→B'…), so every clone's random is just original.random.next — then unzip. And k-group reversal is section 01's three-finger reversal applied per block with a dummy head stitching blocks together — pure composure testing.

    

      

        
tortoise-and-hare.js — run it

        
const node = (v) => ({ v, next: null, random: null });
const chain = (...vs) => {
  const nodes = vs.map(node);
  nodes.forEach((n, i) => n.next = nodes[i + 1] ?? null);
  return nodes;
};

// 1 · FLOYD — detect the cycle, then FIND ITS ENTRANCE in O(1) space
const cats = chain('Mochi','Biscuit','Beans','Clawdia','Tuna','Salem');
cats[5].next = cats[2];                     // Salem sneaks back to Beans → cycle!
function cycleEntrance(head) {
  let slow = head, fast = head;
  while (fast?.next) {
    slow = slow.next; fast = fast.next.next;
    if (slow === fast) {                    // met inside the cycle
      let probe = head;                     // the famous reset
      while (probe !== slow) { probe = probe.next; slow = slow.next; }
      return probe.v;
    }
  }
  return null;
}
console.log('cycle starts at:', cycleEntrance(cats[0]));

// 2 · CLONE with random pointers — the O(1)-space interleave
const [a, b, c] = chain('A', 'B', 'C');
a.random = c; b.random = a; c.random = b;
function cloneList(head) {
  for (let n = head; n; n = n.next.next)          // weave: A→A'→B→B'…
    n.next = Object.assign(node(n.v + "'"), { next: n.next });
  for (let n = head; n; n = n.next.next)          // clone randoms via the weave
    if (n.random) n.next.random = n.random.next;
  const clone = head.next;                         // unzip
  for (let n = head; n; n = n.next) {
    const twin = n.next;
    n.next = twin.next;
    twin.next = twin.next ? twin.next.next : null;
  }
  return clone;
}
const cloned = cloneList(a);
console.log('clone:', cloned.v, cloned.next.v, cloned.next.next.v);
console.log("clone randoms:", cloned.random.v, cloned.next.random.v, '— point at CLONES, not originals');

LRU cache — the structures capstone

      
advanced → two structures composed, O(1) everything

    

  

  

    
The interview section promised this capstone; here it is. An LRU (least-recently-used) cache holds N items and evicts the one untouched longest. The requirement that makes it a composition problem: get AND put must both be O(1) — including the eviction and the "this item just became freshest" bump. A map alone can't order by recency; a list alone can't look up by key. The textbook answer: hash map (key → list node) + doubly-linked list in recency order — the map teleports you to the node, the DLL unlinks and re-heads it in O(1), evictions pop the tail.

    
JS has a shortcut worth knowing and worth being honest about: Map preserves insertion order, so delete + re-set moves a key to "most recent", and map.keys().next().value is the oldest. Ten lines, genuinely O(1) — but say "the Map is my ordered list; in a language without ordered maps I'd build map + DLL" so the interviewer hears the real structure, not a dodge.

    

      

        
nap-spot-cache.js — run it

        
// LRU via JS Map's insertion order — every op O(1)
class LRU {
  constructor(cap) { this.cap = cap; this.m = new Map(); }
  get(k) {
    if (!this.m.has(k)) return -1;
    const v = this.m.get(k);
    this.m.delete(k); this.m.set(k, v);       // bump to freshest
    return v;
  }
  put(k, v) {
    if (this.m.has(k)) this.m.delete(k);       // re-insert = refresh position
    else if (this.m.size === this.cap) {
      const oldest = this.m.keys().next().value;
      this.m.delete(oldest);
      console.log(`  · evicted ${oldest} (least recently used)`);
    }
    this.m.set(k, v);
  }
  peek() { return [...this.m.keys()].join(' < '); }   // oldest < … < freshest
}

const napSpots = new LRU(3);
napSpots.put('windowsill', '☀️'); napSpots.put('laptop', '🔥'); napSpots.put('boxNo3', '📦');

napSpots.put('radiator', '♨️');              // full → someone's spot is gone
console.log('after put(radiator):', napSpots.peek());
console.log('get(laptop):', napSpots.get('laptop'), ' ← evicted, correctly');

Two heaps — the streaming median & friends

      
advanced → balance a max-heap and a min-heap at the split point

    

  

  

    
Section 04 built one heap. The famous composition uses two, facing each other: a max-heap holding the smaller half of the numbers and a min-heap holding the larger half. The median lives at the boundary — the top of one heap (odd count) or the average of both tops (even). Each arrival: push into the correct half, then rebalance so sizes differ by at most one (move one top across). Every operation O(log n), median reads O(1) — on a stream where re-sorting would be O(n log n) per query.

    
The pattern generalizes: any time you need live access to a boundary between two dynamic groups — median, "k-th largest so far", scheduling against a budget — the answer is heaps facing each other across the cut.

    

      
      
PROFESSOR WHISKERS EXPLAINSWeigh-in day. Cats split into two rooms: lighter cats in one, heavier cats in the other. Each room only needs to know its cat nearest the doorway (heaviest of the light room, lightest of the heavy room) — the median stands in the doorway between them. A new cat walks into whichever room fits, and if one room gets two cats fuller, the doorway cat switches rooms. Nobody ever lines up all the cats in order — just the doorway, maintained.

    

    

      

        
doorway-median.js — run it

        
// compact binary heap (comparator decides min vs max)
class Heap {
  constructor(cmp) { this.a = []; this.cmp = cmp; }
  get size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(x) {
    this.a.push(x);
    for (let i = this.a.length - 1; i > 0;) {
      const p = (i - 1) >> 1;
      if (this.cmp(this.a[i], this.a[p]) >= 0) break;
      [this.a[i], this.a[p]] = [this.a[p], this.a[i]]; i = p;
    }
  }
  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.size) {
      this.a[0] = last;
      for (let i = 0;;) {
        let best = i;
        for (const c of [2*i+1, 2*i+2])
          if (c < this.size && this.cmp(this.a[c], this.a[best]) < 0) best = c;
        if (best === i) break;
        [this.a[i], this.a[best]] = [this.a[best], this.a[i]]; i = best;
      }
    }
    return top;
  }
}

const light = new Heap((x, y) => y - x);   // max-heap: smaller half
const heavy = new Heap((x, y) => x - y);   // min-heap: larger half
function addWeight(kg) {
  (light.size === 0 || kg <= light.peek()) ? light.push(kg) : heavy.push(kg);
  if (light.size > heavy.size + 1) heavy.push(light.pop());   // rebalance
  if (heavy.size > light.size) light.push(heavy.pop());
  const median = light.size === heavy.size
    ? (light.peek() + heavy.peek()) / 2 : light.peek();
  console.log(`+${kg}kg → median ${median}  (light:${light.size} heavy:${heavy.size})`);
}
[4.2, 6.1, 3.0, 5.5, 4.8, 7.2, 2.9].forEach(addWeight);

Rolling hashes — string search without re-reading

      
advanced → Rabin-Karp, and hashing windows in O(1)

    

  

  

    
Searching a length-m pattern in a length-n text naively compares up to m characters at each of n positions — O(n·m). Rabin-Karp's move: treat each m-wide window as a number in base B (each char a digit), and roll it — slide one position by subtracting the departing char's contribution, multiplying by B, adding the newcomer. One O(1) update per slide, like the sliding-window sum from dsa-foundations, but encoding order, not just contents.

    
Hashes collide, so a hash match is a candidate, not a verdict — verify with a real comparison. Expected cost stays O(n + m) because verifications are rare with a decent base and modulus; the honest sentence is "O(n+m) expected, O(n·m) adversarial worst case".

    

      

        
rolling-window.js — run it

        
// Rabin-Karp with comparison counting — vs naive
const B = 31n, M = 1_000_000_007n;
const code = (ch) => BigInt(ch.charCodeAt(0));

function rabinKarp(text, pat) {
  const n = text.length, m = pat.length;
  let compares = 0, hits = [];
  let hp = 0n, hw = 0n, pow = 1n;
  for (let i = 0; i < m; i++) {
    hp = (hp * B + code(pat[i])) % M;
    hw = (hw * B + code(text[i])) % M;
    if (i < m - 1) pow = (pow * B) % M;
  }
  for (let i = 0; ; i++) {
    if (hp === hw) {                          // candidate — VERIFY
      compares += m;
      if (text.slice(i, i + m) === pat) hits.push(i);
    }
    if (i + m >= n) break;
    hw = ((hw - code(text[i]) * pow % M + M * B) % M * B + code(text[i + m])) % M;
  }
  return { hits, compares };
}

function naive(text, pat) {
  let compares = 0, hits = [];
  for (let i = 0; i + pat.length <= text.length; i++) {
    let j = 0;
    while (j < pat.length) { compares++; if (text[i + j] !== pat[j]) break; j++; }
    if (j === pat.length) hits.push(i);
  }
  return { hits, compares };
}

const text = 'mochi naps, biscuit naps, everyone naps in the nap room'.repeat(4);
const pat = 'naps';
const rk = rabinKarp(text, pat), nv = naive(text, pat);
console.log(`text length ${text.length}, pattern "${pat}"`);
console.log('rabin-karp: found', rk.hits.length, 'matches —', rk.compares, 'char compares');
console.log('naive:      found', nv.hits.length, 'matches —', nv.compares, 'char compares');
console.log('same answers, fraction of the reads — the hash pre-screens candidates');

// quiz — first pick is the one that counts

Why: the hash is a many-to-one compression — equality of hashes is necessary, never sufficient. The asymmetry is the useful part: unequal hashes REJECT with certainty, so the expensive verify runs only on the rare candidates. That "cheap filter + exact confirm" shape is everywhere in systems too (Bloom filters in front of databases) — connecting the two is a senior-sounding sentence you should absolutely say.

Balanced trees — why they exist, when to name them

      
advanced → the O(log n) promise, and the honest interview scope

    

  

  

    
A binary search tree promises O(log n) lookups — if it stays bushy. Feed one sorted input and it degenerates into a linked list: every "left or right?" answer is "right", depth n, promise void. Self-balancing trees (AVL, red-black) defend the promise with rotations — local pointer surgeries that lift a heavy subtree's middle node up one level, shortening the tall side without breaking the sort order. Each insert does O(1) rotations after the normal walk; depth stays O(log n) forever.

    
The honest interview scope, stated plainly: nobody expects you to implement AVL or red-black live. You're expected to (1) explain why balance matters (the degeneration story), (2) know a rotation preserves in-order order, and (3) name who uses what: red-black inside most standard-library ordered maps (C++ std::map, Java TreeMap), B-trees in databases (dsa-trees-graphs and postgres-databases both pick that up), and skip lists — the probabilistic cousin — inside Redis sorted sets.

The line is mochi → biscuit → clawdia → tuna, head at mochi. Run: const p = head.next; head.next = p.next; p.next = head; head = p; — what does the list look like from head?

      

        
        
        
        
      

      
Why: trace it like §01's stepper: p grips biscuit (so she is never lost — option 1 dies on line one), mochi's arrow jumps to clawdia, biscuit's arrow turns back to mochi, and head enters at biscuit — the first-pair swap that opens LC 24. Option 2's cycle is what you get if you flip lines 2 and 3: rewire biscuit first and head.next = p.next then reads the already-rewired pointer, leaving mochi pointing at herself — order of surgery is everything. Option 3 confuses copying a reference with copying a node: p holds the same biscuit, so p.next = mutates the real list.

    

    

      
// apply 2 of 3 — run the monotonic stack by hand

      
In your head, run §06's daysUntilWarmer([70, 71, 68, 72]). What comes back?

      

        
        
        
        
      

      
Why: day 0 (70°) is resolved immediately by day 1 (71°) — distance 1. Day 1 then waits past the dip: 68° pushes on top of it, and both are popped by day 3's 72° — distances 2 and 1. Day 3 never sees warmer, and unresolved means 0, not "days to the end" (option 4). Option 2 is the "the answer is always tomorrow" instinct — it forgets 71 sits unresolved while 68 stacks above it; option 3 makes everyone wait for the maximum, but each day's question is "next warmer than me", and 71 answers 70 perfectly well. Bonus check: the stack ends holding just index 3 — the still-unresolved.

    

    

      
// apply 3 of 3 — recency, not insertion order

      
An LRU cache with capacity 2 (§09): put(1); put(2); get(1); put(3); — the cache is full when 3 arrives. Who gets evicted?

      

        
        
        
        
      

      
Why: LRU evicts the least recently used, and a read is a use — that's the entire point of the delete-and-re-set bump in §09's runner (and of move-to-front in the classic map + DLL version). Option 1 describes FIFO eviction, a different and worse-hit-rate policy: insertion order stops mattering the moment anything is re-touched. Option 4 is a real design fork in some cache variants, but the LRU contract (and LC 146's) counts gets. Option 3 inverts what a cache is for — eviction is the feature, not a failure.

    

    

      
// stretch 1 of 3 — spot the false complexity claim

      
Three of these claims survive scrutiny. Which one is FALSE?

      

        
        
        
        
      

      
Why: "parent ≤ children" points every path away from the minimum but says nothing about which child leads toward the maximum — greedy larger-child descent walks right past it. Try it on the valid min-heap [1, 2, 3, 10, 11, 4, 5]: the walk goes 1 → 3 → 5 and reports 5, while the true max, 11, hides down the "smaller" side. The maximum lives somewhere among the ~n/2 leaves and finding it costs O(n) — the weak promise (§04) buys cheap repair precisely by promising nothing sideways. The two true amortized claims are one argument wearing two costumes: charge the work to the element, not to the loop shape.

    

    

      
// stretch 2 of 3 — structure for the operation mix

      
A leaderboard ingests millions of scores per day, every write must ack fast, and the only read query is "current top 100". Best fit for that operation mix?

      

        
        
        
        
      

      
Why: the stated mix IS the question — reads only ever touch the top 100, so everything below 100th place is dead weight you'd be paying to keep ordered. The BST (option 4) is the tempting "senior" answer because it does everything in O(log n)… including maintaining order among millions of scores nobody will ever read; the size-k heap keeps exactly the 100 that matter, with log₂ 100 ≈ 7 as its worst step. Option 1 hides an O(n) shift of millions of elements inside a "binary search" headline (the same trap as the next question), and option 2 makes writes cheap by setting every read on fire. Choosing by operation mix, not by general-purpose power, is the judgment this module keeps circling.

    

    

      
// stretch 3 of 3 — estimate the hidden O(n)

      
You enqueue 1,000,000 jobs, then drain them one by one with Array.prototype.shift(). Back-of-envelope: total element moves, versus §03's index-pointer queue?

      

        
        
        
        
      

      
Why: the first shift moves 999,999 elements, the next 999,998, and the sum is ≈ n²/2 = 5 × 10¹¹ — a quadratic hiding inside a one-line method call, which is exactly why §03's queue "removes" by moving a head index instead. Option 3 holds a grain of truth (engines memmove efficiently and fast-path small arrays), but on a million-element array each shift still slides O(n) elements — a fast constant times 10¹¹ loses to 10⁶ every time. Option 4 names a real trade-off — the index queue does hold its array until drained — but that's memory, not time, and §07's ring buffer fixes it with two wrapping indexes. This order-of-magnitude arithmetic is how you catch accidental quadratics in code review before production catches them for you.

    

    

      
LEVEL UP — how to read your score

      
    
        
  • Warm-up misses → reread the reference model in §01 (a variable is a grip on a node, not the node — "reassignment deletes things" was the trap), the LIFO trace in §02 (counting brackets isn't matching them), and §04's weak promise (a heap is not a sorted array — parent-child edges are the only promises made).
    • 
        
  • Apply misses → adopt the tracing ritual: paper, boxes and arrows, and after every line write the complete state — head, each .next, the stack's contents — before reading the next line. The bug always lives between two lines, never inside one; §01's stepper is this ritual, animated.
    • 
        
  • Stretch misses → name the combinations: §04×§06 (invariants are what fund complexity claims), §04×§12 (the operation mix picks the structure, not general-purpose power), §03×§07 (the hidden O(n) inside a one-liner). Combining sections is the skill — interviews never ask one section at a time.
    • 
        
  • Transferable habit: argue against your first answer before committing. Every distractor above was built from somebody's first instinct — if you can't articulate why the runner-up option is wrong, you pattern-matched instead of reasoned, and the follow-up question will find you out.
