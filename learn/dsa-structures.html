Linked lists — cats holding tails

beginner → the reversal, stepped through slowly

A linked list is nodes scattered anywhere in memory, each holding a value and a pointer to the next node. No indexes — to reach item 500 you walk 500 hops (O(n)). So why bother? Because splicing is O(1): insert or remove anywhere by rewiring two pointers, no mass shuffling of neighbors like an array.

Interview reality: you'll rarely choose a linked list at work (arrays are cache-friendly and usually win), but interviews use them constantly because they test whether you can manipulate references without losing your grip — which is a real skill you use every day in object graphs.

PROFESSOR WHISKERS EXPLAINSA conga line of cats, each holding the tail of the next cat. You only know where the front cat is. Finding the 5th cat = walking down the line. But slipping a new cat into the middle? The cat in front lets go of one tail, grabs the newcomer's — two grip changes, nobody else moves. Try that with theater seats (an array) and twenty cats shuffle over. The danger: let go of a tail before grabbing the rest of the line, and everyone behind that point wanders off forever. That's the bug the stepper below is about.

POINTER SURGERY — reverse a list without dropping it

Three variables walk the list: prev (reversed so far), curr (working on), next (the safety grip). Watch the arrows flip one at a time.

// build: mochi → biscuit → clawdia → null
const node = (name, next = null) => ({ name, next });
let head = node('mochi', node('biscuit', node('clawdia')));

const show = (h, label) => {
  const parts = [];
  for (let n = h; n; n = n.next) parts.push(n.name);
  console.log(label, parts.join(' → ') + ' → null');
};
show(head, 'before:');

// the reversal — the exact loop from the stepper above
function reverse(h) {
  let prev = null, curr = h;
  while (curr) {
    const next = curr.next;   // 1. grip the rest BEFORE letting go
    curr.next = prev;         // 2. flip this cat's arrow
    prev = curr;              // 3. reversed section grows
    curr = next;              // 4. step forward along the grip
  }
  return prev;                // prev is the new front
}
head = reverse(head);
show(head, 'after: ');

// fast & slow — find the middle in ONE pass
function middle(h) {
  let slow = h, fast = h;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
  return slow.name;
}
console.log('middle:', middle(head));
the four lines of the while-loop, in the stepper's order

    

    

      
// quiz — first pick is the one that counts

      
Why does the fast/slow pointer trick detect a cycle (Floyd's algorithm)?

      

        
        
        
        
      

      
Why: relative speed is +1 node per step, so the gap closes by exactly one each time — no jumping over. The Set answer also works but costs O(n) memory; Floyd is the O(1)-space flex, and "fast laps slow like runners on a track" is the sentence to say. Same duo finds the middle (fast at end → slow at mid) — one tool, three problems.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The dummy head: a fake node before the real head makes "delete the first node" and "insert at front" stop being special cases — dummy.next is the answer at the end. Interviewers smile when it appears unprompted.
    • 
        
  • Merge Two Sorted Lists = the zipper: dummy + tail pointer, always attach the smaller head. It's the building block of mergesort's merge.
    • 
        
  • Remove-Nth-from-end = two pointers with an n-node head start — one pass, no length count. Doubly-linked lists trade an extra pointer per node for O(1) removal given the node — which is exactly what LRU cache needs (map → node + doubly-linked recency list).

Stacks — last in, first out, everywhere

      
beginner → matching, undo, and the monotonic upgrade

    

  

  

    
A stack is a pile: add on top (push), take from the top (pop), both O(1) — a plain JS array IS one. The pattern trigger: "most recent unfinished thing". Matching brackets (most recent unclosed opener), undo history (most recent action), the call stack itself (most recent unfinished function), DFS (most recent unexplored branch).

    
The interview upgrade is the monotonic stack: keep the stack sorted-by-construction by popping everything your new element beats. Each pop permanently resolves a waiting item ("found the next warmer day!") — n pushes, n pops max, so the scary-looking nested loop is O(n) by the same amortized budget as the sliding window.

    

      

        
piles-of-cats.js — run it

        
// valid parentheses — the stack "hello world" (LC 20)
function validBrackets(s) {
  const pair = { ')': '(', ']': '[', '}': '{' };
  const stack = [];
  for (const ch of s) {
    if ('([{'.includes(ch)) stack.push(ch);
    else if (stack.pop() !== pair[ch]) return false;  // wrong/missing opener
  }
  return stack.length === 0;                          // nothing left open
}
console.log('([{}]) →', validBrackets('([{}])'));
console.log('([)]   →', validBrackets('([)]'));

// monotonic stack: days until a warmer day (LC 739, cat-nap edition)
// temps of the sunbeam spot; a cat naps until it's warmer than today
function daysUntilWarmer(temps) {
  const wait = new Array(temps.length).fill(0);
  const stack = [];                        // indexes of unresolved days
  for (let i = 0; i < temps.length; i++) {
    while (stack.length && temps[i] > temps[stack[stack.length - 1]]) {
      const day = stack.pop();             // resolved forever — that's the O(n)
      wait[day] = i - day;
    }
    stack.push(i);
  }
  return wait;
}
console.log(daysUntilWarmer([23, 24, 21, 19, 22, 26, 23]));
// each index pushed once, popped at most once → 2n operations total

      

      
the while-inside-for that's still O(n) — same budget argument as the window

Why: the hard part is that popping the minimum must reveal the previous minimum — a single variable loses history (option 3 degrades pops to O(n)). Queues & deques — fair lines and clever windows

      
beginner → BFS's engine, plus the deque party trick

    

  

  

    
A queue is a fair line: in at the back, out at the front, FIFO. It's the engine of breadth-first search (process things in discovery order → shortest paths), task schedulers, buffers, and rate limiters. The JS gotcha you already know from Foundations: shift() is O(n), so real queues use an index pointer, a linked list, or a ring buffer.

    
A deque (double-ended queue) opens both ends. Its star turn is the monotonic deque behind Sliding Window Maximum: keep candidates in decreasing order — new arrivals evict everyone smaller from the back (they can never be a max while a bigger, newer value lives), and the front retires when it slides out of the window. Every element enters and leaves once: O(n) window maximums.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe dinner line is FIFO — cats who queue first eat first, and BFS is just "serve dinner in waves: everyone 1 hop away, then everyone 2 hops away". The deque trick is the judging panel at a cat show with a 3-cat viewing window: when a clearly-more-magnificent cat struts in, every less magnificent cat still waiting at the back leaves immediately — they can never win while the new cat is around and newer. The front of the panel is always the current champion.

    

    

      

        
dinner-lines.js — run it

        
// an O(1) queue: index pointer instead of shift()
class Queue {
  constructor() { this.items = []; this.head = 0; }
  push(x) { this.items.push(x); }
  shift() { return this.items[this.head++]; }         // "remove" = move marker
  get length() { return this.items.length - this.head; }
}
const dinner = new Queue();
['mochi', 'biscuit', 'clawdia'].forEach(c => dinner.push(c));
while (dinner.length) console.log('now eating:', dinner.shift());

// monotonic deque: max of each sliding window of 3 (LC 239)
function windowMax(nums, k) {
  const dq = [];                            // indexes, values decreasing
  const out = [];
  for (let i = 0; i < nums.length; i++) {
    while (dq.length && nums[i] >= nums[dq[dq.length - 1]]) dq.pop();
    dq.push(i);                             // evict the outclassed, join
    if (dq[0] <= i - k) dq.shift();         // champion aged out of window
    if (i >= k - 1) out.push(nums[dq[0]]);  // front = current champion
  }
  return out;
}
console.log('maxes:', windowMax([1, 3, -1, -3, 5, 3, 6, 7], 3));

      

      
the champion logic: evict the outclassed, retire the aged-out

      

    

    

      
// quiz — first pick is the one that counts

      
Implement a queue using two stacks (LC 232) — how, and what's the cost?

      

        
        
        
        
      

      
Why: two reversals make a FIFO — but the insight graded is the amortized argument: the expensive pour is rare, and per-element lifetime cost is exactly two pushes + two pops. It's the cleanest interview showcase of amortized analysis, and the same "measure per-element lifetime, not per-operation worst case" lens you used on the window and the monotonic stack.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • BFS = queue, DFS = stack — swapping the container literally swaps the traversal. This one-liner carries you into the trees module.
    • 
        
  • Real-world queues you already operate: BullMQ/SQS job queues, Node's event loop task queue, backpressure buffers in streams. Naming them makes the abstract concrete.
    • 
        
  • Ring buffer: fixed array + two wrapping indexes — the allocation-free queue behind audio buffers and high-perf systems. One sentence is plenty.

Heaps — always know the winner

      
intermediate → a real MinHeap in 30 lines, then top-k judgment

    

  

  

    
A heap answers one question, constantly and cheaply: "who's currently first?" Peek the min (or max) in O(1); insert or remove-the-top in O(log n). It does this by maintaining a weak promise — not full sorted order, just "every parent beats its children" — and weak promises are cheap to repair.

    
The elegant bit: the "tree" is just an array. Node i's children live at 2i+1 and 2i+2; its parent at ⌊(i−1)/2⌋. Insert = append + bubble up while beating your parent. Remove-top = move the last element to the root + sift down toward the better child. The tree is complete, so the height is log n — that's the whole complexity story.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe vet's waiting room doesn't keep cats fully sorted by urgency — that would mean re-sorting the whole room every arrival. Instead: a tournament bracket where every cat only promises to be less urgent than the cat above it. New arrival? She challenges her way up a single column — log n hisses, not a room-wide reshuffle. "Who's next?" is always the cat at the top. Weak ordering, strong answer, tiny maintenance.

    

    

      

        
vet-triage.js — run it

        
class MinHeap {
  constructor() { this.a = []; }
  get size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(x) {
    this.a.push(x);
    let i = this.a.length - 1;                  // bubble up
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.a[p] <= this.a[i]) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }
  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;                                 // sift down
      while (true) {
        const l = 2 * i + 1, r = l + 1;
        let best = i;
        if (l < this.a.length && this.a[l] < this.a[best]) best = l;
        if (r < this.a.length && this.a[r] < this.a[best]) best = r;
        if (best === i) break;
        [this.a[best], this.a[i]] = [this.a[i], this.a[best]];
        i = best;
      }
    }
    return top;
  }
}

// top-3 heaviest cats from a stream — keep a SMALL min-heap of winners
const weights = [4.2, 6.1, 3.0, 5.5, 7.3, 2.8, 6.8, 4.9, 5.1];
const h = new MinHeap();
for (const w of weights) {
  h.push(w);
  if (h.size > 3) h.pop();      // evict the lightest of the champions
}
const top3 = [];
while (h.size) top3.push(h.pop());
console.log('top-3 heaviest:', top3);
// n items through a k-sized heap: O(n log k) — and the stream
// never needed to fit in memory. THAT's the heap's real pitch.

      

      
a min-heap of maximums — the inversion that confuses everyone once

      

    

    

      
// quiz — first pick is the one that counts

      
Kth largest element: sort is O(n log n), heap is O(n log k). When is the heap genuinely the better answer, not just flexing?

      

        
        
        
        
      

      
Why: for a one-shot array, sort is simpler and often fine — say so. The heap earns its keep when data streams (top-10 trending from millions of events, "as results arrive") or k is tiny versus n. Quickselect is worth naming as the O(n)-average alternative — knowing all three and picking by context is exactly what "senior" sounds like in this question.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Two-heap trick: a max-heap of the lower half + min-heap of the upper half = O(log n) running median. Named unprompted, it's a strong signal.
    • 
        
  • "Merge k sorted lists" = min-heap of k current heads — every stream/log-merge system does this for real.
    • 
        
  • JS has no built-in heap — in interviews either bring this 30-liner or say "assume a MinHeap class" and keep moving; interviewers accept both. Priority queues in schedulers, Dijkstra, and A* are all this structure.

Intervals — sort, then sweep

      
intermediate → the overlap test and the one pattern that rules them

    

  

  

    
Interval problems (meetings, bookings, nap schedules) all rest on two moves. Move 1 — the overlap test: two ranges overlap iff a.start ≤ b.end && b.start ≤ a.end — memorize it as "neither starts after the other ends." Move 2 — sort by start, then sweep once: after sorting, any overlap must involve your immediate neighbor, so one linear pass with a "current merged block" handles everything. O(n log n) for the sort, O(n) for the sweep.

    

      
      
PROFESSOR WHISKERS EXPLAINSFive cats book the sunbeam. Sort the bookings by start time, then walk them holding one "current sunbeam session": next booking starts before the current session ends? Same pile of cats — extend the session to the later end. Starts after? Close the session, start fresh. One walk down the list and every overlapping pile is found — because after sorting, an overlap can't skip over your neighbor to reach you.

    

    

      

        
sunbeam-schedule.js — run it

        
// merge overlapping sunbeam bookings (LC 56)
function mergeBookings(intervals) {
  const sorted = [...intervals].sort((a, b) => a[0] - b[0]);
  const merged = [sorted[0].slice()];
  for (const [start, end] of sorted.slice(1)) {
    const current = merged[merged.length - 1];
    if (start <= current[1]) current[1] = Math.max(current[1], end); // extend
    else merged.push([start, end]);                                  // new block
  }
  return merged;
}
const bookings = [[13, 15], [1, 3], [2, 6], [8, 10], [15, 18]];
console.log('merged:', JSON.stringify(mergeBookings(bookings)));

// min removals so no two bookings overlap (LC 435) — greedy by END time
function minRemovals(intervals) {
  const byEnd = [...intervals].sort((a, b) => a[1] - b[1]);
  let keptEnd = -Infinity, removed = 0;
  for (const [start, end] of byEnd) {
    if (start >= keptEnd) keptEnd = end;   // compatible — keep it
    else removed++;                        // overlaps a kept one — drop it
  }
  return removed;
}
console.log('remove', minRemovals([[1,2],[2,3],[3,4],[1,3]]), 'booking(s)');
// why sort by END? keeping the earliest-ending booking leaves the
// most room for everyone after — the exchange argument in one line.

      

      
merge sorts by START; the greedy scheduler sorts by END — know why

      

    

    

      
// quiz — first pick is the one that counts

      
"How many meeting rooms do we need?" (classic variant). The cleanest approach?

      

        
        
        
        
      

      
Why: rooms = maximum simultaneous overlap, which merging destroys (a merged block of 3 stacked meetings looks like 1). The +1/−1 sweep (or a min-heap of end times) reads concurrency directly off the timeline. This "events on a timeline with a running counter" idea is also how load graphs and connection-pool sizing work — another DSA-to-systems bridge worth saying.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Insert Interval doesn't need re-sorting: before / overlapping (absorb while start ≤ newEnd) / after — three phases, one pass.
    • 
        
  • Sort-by-end = greedy scheduling ("activity selection"); sort-by-start = merging. Mixing them up is THE classic interval error — say which and why before coding.

The practice ladder — structures edition

      
method → build each one once, then drill its problems

    

  

  

    
Structures reward a different drill than patterns: implement each one from scratch, once, from memory — the 30-line heap, the O(1) queue, reverse-a-list — then never again. The implementation isn't the interview skill; the fluency it leaves behind is. After building a heap once, "min-heap of size k" stops being scary vocabulary and becomes a tool you reach for.

    
Same 20-minute rule as Foundations, same sacred re-solve two days later. And interleave: a list problem, then a stack problem, then heaps — interleaving feels harder and works better; blocked practice feels smooth and evaporates.

LRU Cache asks for O(1) get AND put with eviction of the least-recently-used. Which pair of structures, and why both?

      

        
        
        
        
      

      
Why: the map finds nodes instantly but has no order; the doubly-linked list maintains recency order with O(1) splicing (that's why doubly — you unlink a node given only itself) but can't find things. Together: find via map, reorder via list. The heap fails because bumping recency is O(log n) and JS Maps' insertion order can't re-order on access cheaply… and this is exactly why Redis exists in your systems interviews. One problem, two courses connected.
