01

One thread, no waiting — why async exists

beginner → what "blocking" actually means

JavaScript executes one line at a time, on one thread. While your code runs, nothing else can happen — no clicks handled, no pixels painted. If a function takes 3 seconds, the page is frozen for 3 seconds. That's blocking.

The slow things — network requests, timers, file reads — would block everything if JS waited for them. So it doesn't: it hands the slow job to the environment (browser or Node), leaves a callback like a note that says "when it's ready, run this", and moves on. Async isn't JS being fast; it's JS refusing to wait.

PROFESSOR WHISKERS EXPLAINSThe cat café has one waiter (the thread). A blocking waiter takes your espresso order and then stands at the machine staring at it for two minutes — the queue at the door grows and nobody gets served. The async waiter gives the order to the espresso machine (the browser), keeps serving tables, and comes back when the machine dings. One waiter, zero standing around — that's the entire model.

blocking-vs-not.js — run it
// BLOCKING: the waiter stares at the machine
function busyWaitMs(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) {}   // pure stubbornness
}
console.log('order taken…');
busyWaitMs(800);                 // page frozen for 800ms — feel it
console.log('espresso done (the hard way)');

// NON-BLOCKING: hand it to the machine, keep serving
console.log('order taken…');
setTimeout(() => console.log('☕ espresso done (the machine dinged)'), 800);
console.log('serving the next table meanwhile');
// notice the last line prints BEFORE the espresso
the 800ms freeze is real — that's what blocking feels like

    

    

      
// quiz — first pick is the one that counts

      
"JS is single-threaded" — so how does it handle 100 network requests at once?

      

        
        
        
        
      

      
Why: the waiting happens in the environment's machinery (network stack, timers, thread pool). JS's single thread only executes callbacks, sequentially, when the event loop hands them over. "Concurrency without parallelism — the waiting is outsourced" is the interview-grade phrasing.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Long synchronous work is the only thing that freezes a page — a slow network request never does. Distinguishing those two instantly marks you as someone who gets it.
    • 
        
  • Node CAN do real parallel threads (worker_threads) and browsers have Web Workers — but they share nothing and talk by message passing. "One thread per JS realm" is the precise claim.
    • 
        
  • The 3-second .map() over a huge array freezes the UI exactly like busyWaitMs — chunk it, defer it, or move it to a worker.

    02
    

      
The event loop — step through it yourself

      
the centerpiece: stack, queues, and who goes first

    

  

  

    
Three pieces of machinery run the show. The call stack: where code executes right now, one frame per running function. The macrotask queue (or just "task queue"): finished timers, clicks, network responses waiting their turn. The microtask queue: promise callbacks — a VIP line.

    
The loop's rule, and it's the whole exam: run one task to completion → drain the ENTIRE microtask queue → (maybe paint) → take the next task. Microtasks always jump the line: every promise callback that's ready runs before any waiting timer, click, or paint. That single sentence answers every ordering puzzle ever asked.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe waiter finishes a table (one task). Before walking to the regular queue at the door (timers, clicks), house rules say: serve every cat in the VIP lounge first (microtasks) — even VIPs who arrived while serving other VIPs. Only when the lounge is empty does the next regular customer get seated. Timers aren't "in 0ms" — they're "join the regular queue after 0ms". The lounge always wins.

A promise chain keeps scheduling new microtasks forever. What happens to a pending setTimeout and to rendering?

      

        
        
        
        
      

      
Why: "drain the ENTIRE microtask queue" has no fairness clause — microtasks scheduling microtasks extend the drain forever.     • 
        
  • Rendering happens between tasks, never mid-task — which is why one 500ms task drops frames but 50 × 10ms chunks don't. That's the INP story from the frontend course, seen from below.
    • 
        
  • requestAnimationFrame callbacks run just before paint — a third timing bucket, distinct from both queues.

    03
    

      
Callbacks → promises — the upgrade, honestly told

      
beginner → chaining, error highways, and the one-shot rule

    

  

  

    
Callbacks work — Node was built on them — but composing them nests ("callback hell"), error handling duplicates into every level, and nothing stops a bad API from calling you twice.

    
A promise is a container for a future value with strict guarantees: it's pending until it settles into fulfilled (with a value) or rejected (with a reason) — exactly once, then frozen forever. .then returns a new promise, which is what makes flat chains possible; a rejection skips down the chain to the nearest .catch, like an error highway with one exit.

    

      
      
PROFESSOR WHISKERS EXPLAINSA promise is the buzzer the café hands you while your order's in the kitchen. It buzzes exactly once — food ready (fulfilled) or "we're out of tuna" (rejected) — and once it's buzzed, it never changes its mind. Already-buzzed buzzer? Anyone who checks it later still gets the answer — that's why .then on a settled promise still fires (as a microtask, from the VIP lounge, naturally).

    

    

      

        
buzzers.js — run it

        
// kitchen simulator: resolves or rejects after a delay
function order(dish, ms, outOfStock = false) {
  return new Promise((resolve, reject) => {
    setTimeout(() => outOfStock
      ? reject(new Error(`out of ${dish}`))
      : resolve(`${dish} 🍽`), ms);
  });
}

// a flat chain — each .then returns a NEW promise
order('tuna tartare', 300)
  .then(dish => { console.log('served:', dish); return order('milk foam', 200); })
  .then(dish => console.log('served:', dish))
  .catch(err => console.error('kitchen says:', err.message))
  .finally(() => console.log('table cleared'));

// the error highway: rejection SKIPS to the catch
order('salmon', 100, true)
  .then(dish => console.log('never runs:', dish))
  .then(dish => console.log('never runs either'))
  .catch(err => console.error('caught:', err.message));

// settled means settled — late listeners still get the value
const buzzer = Promise.resolve('cream puff');
setTimeout(() => buzzer.then(v => console.log('late but fine:', v)), 400);

      

      
watch the rejection skip two .thens — the highway in action

      

    

    

      
// quiz — first pick is the one that counts

      
What does .then(fn) return, and why is that the entire trick?

      

        
        
        
        
      

      
Why: each link is a fresh promise adopting the callback's result — return a value, the next link gets it; return a promise, the chain waits; throw, the chain rejects. Nesting becomes sequencing. This mechanism is also exactly what await compiles into — next section.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • "Promisification": wrapping a callback API — new Promise((res, rej) => legacy(args, (err, data) => err ? rej(err) : res(data))). Node ships util.promisify. Write it once from memory.
    • 
        
  • An unhandled rejection (no catch anywhere on the chain) crashes modern Node processes — "every chain ends in a catch, and a global handler logs stragglers" is the production answer.
    • 
        
  • .finally passes values through untouched — cleanup only. And .then(fn1, fn2)'s second argument doesn't catch errors thrown inside fn1 — a genuinely sneaky trivia edge.
    • 
        
  • The constructor runs synchronously — only the callbacks are async. new Promise(r => console.log('now!')) logs immediately.

    04
    

      
async / await — promises wearing sync clothing

      
intermediate → what await ACTUALLY pauses (hint: not the thread)

    

  

  

    
Two keywords, two facts. async: the function now always returns a promise — return a value and it's wrapped, throw and it rejects. await: unwrap this promise — pause this function, let everything else run, resume here (as a microtask) when it settles.

    
The crucial precision: await suspends the function, never the thread. The rest of the function is parked as a continuation — literally a closure holding your local variables — and the waiter goes back to serving tables. Error handling collapses into ordinary try/catch, which is 80% of why the syntax won.

    

      
      
PROFESSOR WHISKERS EXPLAINSawait is the waiter bookmarking your table: "espresso pending — I'll be back at this exact chair, with your name and order remembered." The bookmark (closure) holds everything; the waiter serves other tables meanwhile. When the machine dings, the bookmark goes in the VIP lounge and the waiter resumes mid-sentence. The café never stopped.

    

    

      

        
bookmarks.js — run it

        
const wait = (ms) => new Promise(r => setTimeout(r, ms));

async function serveTable(name, ms) {
  console.log(`${name}: order taken`);
  await wait(ms);                     // bookmark — function pauses, thread doesn't
  console.log(`${name}: food served after ${ms}ms`);
  return `${name} happy`;
}

// both start immediately — the awaits interleave!
serveTable('Mochi', 300).then(console.log);
serveTable('Biscuit', 150).then(console.log);
console.log('waiter: still moving, nothing blocked');

// try/catch replaces .catch — errors become ordinary
async function riskyOrder() {
  try {
    await wait(100);
    throw new Error('out of catnip cookies');
  } catch (err) {
    console.error('handled like sync code:', err.message);
    return 'substitute: tuna biscuit';
  }
}
riskyOrder().then(v => console.log('resolved with:', v));

      

      
Biscuit finishes first — proof the functions interleave

      

    

    

      
// quiz — first pick is the one that counts

      
What's wrong with const users = await Promise.all(ids.map(async id => await fetchUser(id))) — trick question?

      

        
        
        
        
      

      
Why: map never awaits anything — it synchronously calls the async callback N times, getting N already-started promises. The await inside each callback pauses that callback, not the loop. Contrast with for…of + await, which IS sequential. Knowing both shapes — and when sequential is actually correct (rate limits, ordering) — is the complete answer.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • return await p vs return p: nearly identical, except inside try/catch — only return await lets the catch see the rejection. A famously subtle line.
    • 
        
  • Forgetting await gives you a promise where you wanted a value — if (user.isAdmin) on a promise is always truthy. Modern TS/eslint (no-floating-promises) exists for exactly this.
    • 
        
  • Top-level await works in ES modules — and delays every importer of that module until it settles. Convenient; occasionally a startup-time footgun.
    • 
        
  • An async function runs synchronously until its first await — that ordering detail decides several puzzle questions in the next section.
    •

    05
    

      
Rejections — where async errors actually go

      
intermediate → the propagation rules, and the forgotten-await trap

    

  

  

    
A rejected promise is a throw in transit: it travels down the chain, skipping every .then handler, until something catches it — a .catch, or the try/catch wrapped around an await. No catcher anywhere? The runtime fires unhandledrejection (browser) or crashes the process by default (modern Node) — async errors don't politely disappear, they detonate later, out of context.

    
The bug family to know by name: the floating promise. Call an async function and don't await or .catch it, and its rejection belongs to nobody. The subtle cousin is return promise vs return await promise inside a try — without the await, the rejection happens after your function already left the try block, and your catch never fires.

    

      
      
PROFESSOR WHISKERS EXPLAINSA complaint letter (the rejection) rides the mail line past every desk labeled "good news only" (.then) until it finds the complaints desk (.catch). Send a cat on an errand and keep no way to hear back — that's a floating promise: when she knocks over a vase across town, the first you hear of it is the city filing a report against the whole shelter (unhandledrejection).

    

    

      

        
complaints-desk.js — run it

        
const errand = (ok) => ok
  ? Promise.resolve('vase delivered')
  : Promise.reject(new Error('vase knocked over'));

// 1 · rejections SKIP then-handlers and find the catch
await errand(false)
  .then(() => console.log('desk 1: never runs'))
  .then(() => console.log('desk 2: never runs'))
  .catch(e => console.log('complaints desk:', e.message));

// 2 · a .catch RECOVERS — the chain continues on the happy path
await errand(false)
  .catch(e => 'replacement vase')       // handled → fulfilled again
  .then(v => console.log('carried on with:', v));

// 3 · try/catch + await is the same machinery in costume
try { await errand(false); }
catch (e) { console.log('caught by try/catch:', e.message); }

// 4 · THE TRAP · return vs return await inside try
async function sneaky() {
  try {
    return errand(false);          // no await — leaves try IMMEDIATELY
  } catch (e) {
    return 'sneaky caught it';     // NEVER runs
  }
}
await sneaky().catch(e => console.log('escaped to the caller:', e.message));

async function honest() {
  try {
    return await errand(false);    // await keeps it inside the try
  } catch (e) {
    return 'honest caught it';
  }
}
console.log(await honest());

      

      
case 4 is the senior-level trap — same code, one keyword, opposite outcome

      

    

    
Placement matters as much as presence: a.catch(...).then(b) and a.then(b).catch(...) are different programs — the first only guards a, the second also guards b. The house style that keeps teams sane: catch at the boundary (the route handler, the effect, the event handler — the place that can actually render an error state or return a 500), and let everything below just throw.

    

      
// quiz — first pick is the one that counts

      
async function f() { try { return fetchData(); } catch (e) { log(e); } } — fetchData rejects. What happens?

      

        
        
        
        
      

      
Why: return fetchData() hands back a pending promise and exits the try block in the same tick. When the rejection arrives later, the try/catch is long gone — stack frames don't wait around. return await fetchData() parks the function inside the try until settlement, so the catch can do its job. This is the one place where "redundant" return await is load-bearing.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • "A rejection is a throw that travels through time" — same propagation rules as exceptions, shifted to settlement time. Saying it this way shows the model, not memorized API.
    • 
        
  • Promise.all rejects with the first error and drops the rest; Promise.any rejects with an AggregateError holding all of them — know where the lost errors go.
    • 
        
  • Node kills the process on unhandled rejections by default (since v15) — "it worked in the browser" is not a defense. Lint rule name-drop: no-floating-promises (TS) catches the whole class at build time.
    • 
        
  • Fire-and-forget is occasionally right (analytics, cache warm) — the honest version is explicit: void track().catch(logQuietly). Intentional, visible, handled.
    •

    06
    

      
Ordering puzzles — the screen question, mechanized

      
the exam itself: trace like a machine, out loud

    

  

  

    
"What does this log?" is answered with an algorithm, not intuition. Pass 1: run all synchronous code top to bottom, noting what each line schedules (timer → macrotask queue, .then/await-continuation → microtask queue when settled). Pass 2: drain microtasks — including new ones they create. Pass 3: one macrotask, then back to pass 2. Repeat.

    
Narrate exactly that in an interview — "sync first… now the microtask queue holds C… drain it… now the timer" — and you score even if you slip on a line, because the method is what's being graded.

    

      

        
the-final-boss.js — predict FIRST, then run

        
// Write your prediction down. Every line. Then run.
console.log('1');

setTimeout(() => console.log('2: timer'), 0);

Promise.resolve()
  .then(() => console.log('3: micro'))
  .then(() => console.log('4: chained micro'));

(async function main() {
  console.log('5: async runs sync until…');
  await null;                        // still schedules a continuation!
  console.log('6: after await');
})();

queueMicrotask(() => console.log('7: queued micro'));

console.log('8: sync done');
// answer: 1, 5, 8 — then microtasks: 3, 6, 7, then 4 — then the timer: 2
// (6 beats 7? both queued during sync pass — 6's await ran before
//  queueMicrotask's line, so it enqueued first. FIFO within the lounge.)

// quiz — first pick is the one that counts

      
Why does await null (or awaiting any already-settled value) still delay the next line?

      

        
        
        
        
      

      
Why: if settled promises resumed synchronously, the same function would behave differently depending on data readiness — a race-condition factory. So await unconditionally yields: "asynchronous even when it doesn't need to be" (same reason .then on a settled promise still fires as a microtask). This one rule explains most "off by one position" mistakes in ordering puzzles.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • setTimeout(fn, 0) means "≥0ms, after sync + all microtasks, in queue order" — and nested timers clamp to ~4ms in browsers. Never say "runs immediately".
    • 
        
  • Two independent chains interleave per-link: a1, b1, a2, b2 — each .then hop is one microtask, and the queue is FIFO. Drawing the queue beats eyeballing.
    • 
        
  • In Node, process.nextTick cuts ahead of promise microtasks — its own mini-queue. One line of that = instant Node cred.
    •

    07
    

      
Running things together — the combinators, with judgment

      
intermediate → all / allSettled / race / any, and the loop trap

    

  

  

    
Four ways to wait on many promises, distinguished by two questions: do you need every result? and what should one failure do? all — everything, fail-fast (one rejection kills it). allSettled — everything, never rejects, per-item status. race — first to settle, win or lose. any — first to fulfill, ignores rejections until all fail.

    
And the performance trap hiding in plain syntax: awaiting inside a loop serializes. Three independent 300ms fetches take 900ms sequentially, ~300ms with Promise.all. The fix is two lines; recognizing it is the interview point.

    

      
      
PROFESSOR WHISKERS EXPLAINSFeeding three cats: all — "dinner is served when every bowl is down; if any bowl breaks, cancel dinner." allSettled — "report per cat: fed, fed, bowl broke." race — "first cat to any outcome decides" (great with a timeout cat). any — "first cat actually eating wins; broken bowls don't count." Feeding them one at a time when they have separate bowls? That's the await-in-a-loop bug — three hungry cats glaring at you.

    

    

      

        
three-bowls.js — run it

        
const feed = (cat, ms, broken = false) =>
  new Promise((res, rej) => setTimeout(
    () => broken ? rej(new Error(`${cat}'s bowl broke`)) : res(`${cat} fed`),
    ms));

// SEQUENTIAL — the accidental slowdown (~600ms total)
let t0 = Date.now();
await feed('Mochi', 200);
await feed('Biscuit', 200);
await feed('Clawdia', 200);
console.log('one-at-a-time took', Date.now() - t0, 'ms');

// PARALLEL — all bowls down at once (~200ms total)
t0 = Date.now();
const results = await Promise.all(
  [feed('Mochi', 200), feed('Biscuit', 200), feed('Clawdia', 200)]);
console.log('together took', Date.now() - t0, 'ms:', results);

// fail-fast vs full-report
try {
  await Promise.all([feed('Mochi', 100), feed('Biscuit', 50, true)]);
} catch (e) { console.error('all is fail-fast:', e.message); }

const report = await Promise.allSettled(
  [feed('Mochi', 100), feed('Biscuit', 50, true)]);
console.log(report.map(r => r.status).join(' / '));

      

      
600ms vs 200ms — the whole argument in two numbers

      

    

    

      
// quiz — first pick is the one that counts

      
Sending 50 password-reset emails: Promise.all or allSettled — and why?

      

        
        
        
        
      

      
Why: all fits all-or-nothing reads (parallel queries composing one page — if one fails the page fails anyway). Independent side-effect jobs want allSettled + retry of the failures. Bonus depth: at 5,000 emails you'd add a concurrency limit (batches or a small pool) — unbounded parallelism is its own outage.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Promise.all's rejection doesn't cancel the other promises — they keep running, results ignored. JS promises aren't cancellable; cancellation is section 07's AbortController.
    • 
        
  • Concurrency limiting from scratch: a worker-pool of N loops pulling from a shared queue — say the shape, name p-limit as the library.
    • 
        
  • for await…of is for async iterables (streams, paginated APIs) — sequential by design; don't confuse it with the await-in-loop bug.
    •

    08
    

      
Timeouts, cancellation & taming the flood

      
advanced → AbortController, debounce/throttle, retries

    

  

  

    
Production async is less about starting work and more about stopping it: the search the user already replaced, the fetch that's taking 30 seconds, the resize handler firing 200 times a second.

    
AbortController is the standard kill switch: create one, pass its signal to fetch (or listen yourself), call .abort() — the fetch rejects with an AbortError and the browser actually cancels the network request. Timeouts are just "abort on a timer" (AbortSignal.timeout(ms) does it in one line). Debounce waits for quiet before firing once; throttle fires at most every N ms during the storm — both are closures around a timer, both from JS Fundamentals' treat jar.

    

      

        
kill-switches.js — run it

        
// a cancellable slow job (respects an abort signal)
function slowJob(name, ms, signal) {
  return new Promise((resolve, reject) => {
    const t = setTimeout(() => resolve(`${name} finished`), ms);
    signal?.addEventListener('abort', () => {
      clearTimeout(t);
      reject(new Error(`${name} aborted`));
    });
  });
}

// cancel a stale search — the autocomplete pattern
const ctrl = new AbortController();
slowJob('search "mo"', 500, ctrl.signal)
  .then(console.log)
  .catch(e => console.error(e.message));
setTimeout(() => {
  console.log('user typed "mochi" — cancelling old search');
  ctrl.abort();
}, 150);

// debounce: quiet-then-fire-once (the search box)
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}
const lookup = debounce(q => console.log('🔎 searching:', q), 200);
['m', 'mo', 'moc', 'mochi'].forEach((q, i) =>
  setTimeout(() => lookup(q), i * 80));   // rapid typing…
// only "mochi" searches — one call instead of four

      

      
one aborted search + four keystrokes collapsing to one call

      

    

    

      
// quiz — first pick is the one that counts

      
Timeout via Promise.race([fetchP, rejectAfter(5000)]) vs fetch(url, {signal: AbortSignal.timeout(5000)}) — the real difference?

      

        
        
        
        
      

      
Why: losing a race doesn't cancel anything — the fetch continues, holding a connection, eventually resolving into the void (and a server somewhere did the work anyway). Real cancellation frees the socket and lets the server stop too. "Race abandons; abort cancels" — five words that close the question.

    

    

      
// quiz — first pick is the one that counts

      
Search box (fire when typing pauses) vs scroll-position tracker (update continuously but cheaply) — which tool for which?

      

        
        
        
        
      

      
Why: debounce = "act once, after the storm ends" — perfect when only the final state matters (search text, resize end, autosave). Throttle = "act every N ms during the storm" — perfect for continuous feedback (scroll progress, drag, analytics sampling). Debouncing scroll means nothing updates until scrolling stops — visibly broken UX.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Retry with exponential backoff + jitter: delay = base × 2^attempt + random — and only retry idempotent operations (the frontend course's network topic tells that story from the product side).
    • 
        
  • One AbortController can cancel many things (fetch + listeners + your own jobs) — it's a broadcast, and AbortSignal.any([a, b]) composes signals (user-cancel OR timeout).
    • 
        
  • React tie-in: the effect cleanup that aborts the in-flight fetch is this exact pattern — return () => ctrl.abort() kills the race condition on fast route changes.
    •

    09
    

      
Building with promises — promisify, deferred & event interop

      
intermediate → wrapping the callback world, by hand

    

  

  

    
You'll spend years consuming promises and then an interview asks you to construct one. The constructor's shape: new Promise((resolve, reject) => { … }) — the executor runs immediately, and whichever of resolve/reject is called first wins; every later call is silently ignored (settling is one-shot, like the buzzer from section 03).

    
Three build patterns cover ~all of real life: promisify (wrap a callback-style API once, use it cleanly forever), event → promise (turn "the next time X happens" into an awaitable), and the deferred (create the promise here, settle it from somewhere else — the escape hatch for APIs where creation and settlement live in different places).

    

      
      
PROFESSOR WHISKERS EXPLAINSThe old shelter phone system: you call, they promise to call you back on whatever number you shouted (a callback). Promisify is hiring a receptionist who takes those callback-calls and rings one proper buzzer instead. A deferred is ordering the buzzer blank — you hand the button to the vet down the hall, and whenever she decides the results are in, she presses it. Same buzzer; the button just lives somewhere else.

    

    

      

        
receptionist.js — run it

        
// a 2005-style callback API (error-first, like old Node)
function fetchCatLegacy(name, cb) {
  setTimeout(() => name === 'Mochi'
    ? cb(null, { name, mood: 'imperious' })
    : cb(new Error('unknown cat')), 80);
}

// 1 · promisify — write the adapter ONCE
const promisify = (fn) => (...args) =>
  new Promise((resolve, reject) =>
    fn(...args, (err, val) => err ? reject(err) : resolve(val)));

const fetchCat = promisify(fetchCatLegacy);
console.log(await fetchCat('Mochi'));
await fetchCat('Rex').catch(e => console.log('adapter rejects:', e.message));

// 2 · event → promise — await "the next meow"
function once(target, event) {
  return new Promise(resolve =>
    target.addEventListener(event, resolve, { once: true }));
}
const door = new EventTarget();
setTimeout(() => door.dispatchEvent(new Event('meow')), 100);
await once(door, 'meow');
console.log('heard the meow — exactly one, listener auto-removed');

// 3 · deferred — settle from OUTSIDE (now standard: Promise.withResolvers)
const { promise, resolve } = Promise.withResolvers
  ? Promise.withResolvers()
  : (() => { let r; const p = new Promise(res => r = res); return { promise: p, resolve: r }; })();
setTimeout(() => resolve('vet pressed the button'), 60);
console.log(await promise);

// 4 · settling is one-shot — later calls are ignored
const oneShot = new Promise(res => { res('first'); res('second'); });
console.log(await oneShot);

      

      
the three adapters that connect promise code to everything else

      

    

    
Two construction rules interviewers watch for. Don't wrap what's already a promise — new Promise((res) => fetch(url).then(res)) is the "explicit construction antipattern"; fetch already returns one. And make errors reject, never throw-async: inside an executor, a synchronous throw becomes a rejection automatically, but a throw inside a setTimeout callback escapes the promise entirely — route it through reject.

    

      
// quiz — first pick is the one that counts

      
When do you genuinely need new Promise(...) (or a deferred) instead of chaining existing promises?

      

        
        
        
        
      

      
Why: the constructor is the boundary tool — it turns not-yet-promise things (a callback API, "next click", "when the worker replies") into promises. Inside promise-land, chaining and async/await compose everything without it. If you're wrapping something that already returns a promise, you're writing the antipattern.

    

    

      
LEVEL UP — what interviewers listen for

    • 
        
  • Node's util.promisify does pattern 1 with edge cases handled; events.once(emitter, 'x') does pattern 2. Write them by hand in interviews, name the built-ins after.
    • 
        
  • Promise.resolve(x) is also a coercer: if x is a thenable it adopts its state — that's how await handles third-party promise libraries seamlessly.
    • 
        
  • The executor runs synchronously — new Promise(() => console.log('now')) logs before the next line. Only the handlers are deferred to microtasks.

The scheduling zoo — timers, microtasks & frames

      
intermediate → every way to say "later", and which later you get

    

  

  

    
Section 02 gave you two queues. The full zoo has more cages, each with a different definition of "later": queueMicrotask (this tick, before anything else — the VIP lounge, explicitly), setTimeout(fn, 0) (next macrotask — but "0" is a polite fiction), requestAnimationFrame (right before the next paint — the only correct "just before the user sees it"), and Node adds setImmediate / process.nextTick with their own phase rules.

    
The polite fictions matter in production: browsers clamp nested timers (after ~5 levels of setTimeout-inside-setTimeout, the minimum delay becomes ~4ms) and throttle background tabs (timers in a hidden tab may fire once per second or less — the reason "my countdown drifts when I switch tabs" is a bug report that always comes back). Timers promise "no sooner than", never "exactly at".

    

      
      
PROFESSOR WHISKERS EXPLAINSFour ways to schedule a cat's snack: "before you do anything else" (microtask — she's already on the counter), "when you next have a free moment" (timer — could be a while, and the kitchen rounds it up), "right before guests arrive" (rAF — tied to the doorbell, not the clock), and the house rule: snacks promised for a hidden room get delivered rarely (background-tab throttling). Same word — "later" — four different contracts.

    

    

      

        
four-laters.js — run it

        
// 1 · the pecking order in one shot
setTimeout(() => console.log('3 · timer (macrotask)'), 0);
queueMicrotask(() => console.log('2 · microtask'));
console.log('1 · sync');
await null;   // let the microtask queue drain before part 2

// 2 · setTimeout(0) is not 0 — measure the real gap
const t0 = performance.now();
await new Promise(r => setTimeout(r, 0));
console.log(`"0ms" timer actually waited ${(performance.now() - t0).toFixed(1)}ms`);

// 3 · nested-timer clamping — watch the floor appear (~4ms after depth 5)
let depth = 0, last = performance.now();
await new Promise(done => {
  function hop() {
    const now = performance.now();
    console.log(`hop ${++depth}: gap ${(now - last).toFixed(1)}ms`);
    last = now;
    depth < 8 ? setTimeout(hop, 0) : done();
  }
  setTimeout(hop, 0);
});
console.log('→ the first hops are fast; the clamp kicks in around hop 5');

// 4 · a microtask LOOP starves everything — 10k microtasks, zero timers ran
let spins = 0;
await new Promise(done => {
  setTimeout(() => { console.log('timer finally ran after', spins, 'microtasks'); done(); }, 0);
  (function spin() { if (++spins < 10000) queueMicrotask(spin); })();
});

      

      
measure the fictions: the fake 0ms, the 4ms clamp, the starving loop

      

    

    
Choosing correctly: DOM measurement/mutation before the user sees it → requestAnimationFrame (never setTimeout — you'll land a frame late and flicker). Yield to let the browser breathe during heavy work → setTimeout(0) chunks or, where supported, scheduler.yield(). "After the current operation completes, guaranteed" → microtask. And clocks/countdowns → never accumulate timer ticks; recompute from Date.now() each fire, so throttling can't drift you.

    

      
// quiz — first pick is the one that counts

      
A 10-minute countdown implemented as setInterval(() => seconds--, 1000) shows 11:23 remaining after the user returns from another tab. Why?

      

        
        
        
        
      

      
Why: hidden tabs get timers once per second at best, often once per minute — the interval fired far fewer than 60 times per minute, and each miss silently added phantom time. The fix is structural, not a tweak: store the end timestamp, and every tick render endTime - Date.now(). Ticks then only affect refresh rate, never correctness.

    • 
        
  • Long-task chunking: slice heavy loops with awaited setTimeout(0) (or scheduler.yield()) so input events can interleave — this is the event-loop answer to "the page freezes during import".

Async iteration — for await, and generators that fetch

      
advanced → consuming sequences that arrive over time

    

  

  

    
Arrays hold values you have; async iterables hold values that are on their way — pages of an API, chunks of a file, messages on a socket. The protocol is the sync one with a promise wrapper: next() returns a promise of { value, done }, the object advertises itself via Symbol.asyncIterator, and for await…of is the loop that awaits each step. An async generator (async function*) can both await and yield — which makes it a machine for turning "fetch page, yield items, repeat" into five readable lines.

    
The killer use case is pagination you can stop early: yield item by item, and the moment the consumer breaks, no further pages are fetched. Pull-based laziness — the consumer's appetite drives the producer's work.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe shelter's adoption files live in boxes in the basement, one box per year. A sync iterator hands you files from a box already on the table. The async version: you ask for the next file, and sometimes the clerk says "moment — fetching the next box" and disappears downstairs (an await between items). Crucially, if you find your file in box two, boxes three through nine never come up the stairs at all. Laziness isn't a performance trick down there — it's the whole basement staying unfetched.

    

    

      

        
basement-boxes.js — run it

        
// a fake paginated API — 3 items per page, 60ms per fetch
async function fetchPage(n) {
  await new Promise(r => setTimeout(r, 60));
  console.log(`  · network: fetched page ${n}`);
  return {
    items: ['Mochi', 'Biscuit', 'Beans'].map(c => `${c}-p${n}`),
    hasMore: n < 4,
  };
}

// the async generator: pagination as a stream of ITEMS
async function* allCats() {
  let page = 1, hasMore = true;
  while (hasMore) {
    const res = await fetchPage(page++);
    yield* res.items;                    // hand out one at a time
    hasMore = res.hasMore;
  }
}

// 1 · consume it like an array that arrives over time
let count = 0;
for await (const cat of allCats()) {
  console.log('got:', cat);
  if (++count === 5) break;   // ← stop early…
}
console.log('→ note: pages 3 and 4 were NEVER fetched');

// 2 · async iterables compose — a reusable filter
async function* only(pattern, source) {
  for await (const v of source) if (v.includes(pattern)) yield v;
}
for await (const m of only('Mochi', allCats())) console.log('filtered:', m);

      

      
watch the network lines — early break means unfetched pages

      

    

    
The sharp edge: for await is sequential by contract — one item settles before the next is requested. That's exactly right for ordered streams and rate-limited APIs, and exactly wrong for "fire these 20 independent requests" (that's Promise.all from section 07). The two-question test: does order matter, or does the next step depend on the last? Sequential. Independent jobs? Combinators.

    

      
// quiz — first pick is the one that counts

      
You need the total size of 200 files from an API that returns them as an async iterable. A colleague writes for await (const f of files) total += await stat(f) and it's slow. What's the honest assessment?

      

        
        
        
        
      

      
Why: each loop turn awaits one stat before requesting the next — 200 × latency, by design. Independent per-item work wants the combinator toolbox (with a pool limit from section 14); for await earns its place when items must arrive in order or the source itself is the bottleneck. Naming which contract you need is the senior move.

    

    

      
LEVEL UP — what interviewers listen for

    • 
        
  • break-ing a for await calls the generator's return() — finally blocks inside the generator run, which is where cleanup (closing the cursor, aborting the fetch) belongs.
    • 
        
  • Real async iterables you already hold: Node streams (for await (const chunk of req)), fetch response bodies, and every paginated SDK worth using.
    • 
        
  • Backpressure preview: pull-based iteration is backpressure — the consumer's pace throttles the producer. The streams section makes that explicit with queues and high-water marks.

Streams — processing data bigger than memory

      
advanced → readable, transform, writable & backpressure

    

  

  

    
Everything so far delivered whole values. Streams deliver chunks: a 2GB file as ten thousand pieces, a fetch body as it downloads, a video as it plays. The Web Streams pipeline has three roles — ReadableStream (the source), TransformStream (a worker in the middle), WritableStream (the sink) — snapped together with .pipeThrough() and .pipeTo().

    
The concept that makes streams streams and not just loops: backpressure. Every stage has a small internal queue with a high-water mark; when a slow consumer's queue fills, the pull signals stop flowing upstream and the fast producer pauses. Speed mismatch is absorbed by design, not by an unbounded buffer eating your memory — which is precisely the bug streams exist to prevent.

    

      
      
PROFESSOR WHISKERS EXPLAINSFeeding wet food from a huge pot: the ladler (readable) fills bowls, the garnish cat (transform) adds a treat to each, the eater (writable) works at eating speed. Between stations sits a counter with room for three bowls — when it's full, the garnish cat stops ladling requests upstream. Nobody stacks four hundred bowls (that's loading the file into memory); nobody yells "slow down" (that's manual pause/resume). The counter's size is the protocol.

    

    

      

        
bowl-pipeline.js — run it

        
// source: a readable that ladles 8 meals
const pot = new ReadableStream({
  start(controller) {
    ['tuna','salmon','chicken','beef','duck','shrimp','liver','egg']
      .forEach(m => controller.enqueue(m));
    controller.close();
  }
});

// middle: a transform that garnishes each chunk
const garnish = new TransformStream({
  transform(meal, controller) {
    controller.enqueue(meal.toUpperCase() + ' + treat');
  }
});

// sink: a writable eater — 40ms per bowl (the slow stage)
const eaten = [];
const eater = new WritableStream({
  async write(bowl) {
    await new Promise(r => setTimeout(r, 40));   // chewing…
    eaten.push(bowl);
    console.log('eaten:', bowl);
  }
});

await pot.pipeThrough(garnish).pipeTo(eater);
console.log(`pipeline done — ${eaten.length} bowls, one at a time, bounded memory`);

// bonus: every ReadableStream is async-iterable (section 11 machinery!)
const numbers = new ReadableStream({
  start(c) { [1, 2, 3].forEach(n => c.enqueue(n)); c.close(); }
});
for await (const n of numbers) console.log('for-await over a stream:', n);

      

      
a three-stage pipeline with a deliberately slow sink — backpressure in action

      

    

    
Where you'll actually meet them: fetch bodies are streams — response.body.pipeThrough(new TextDecoderStream()) is how you show download progress or process a huge NDJSON export without holding it; compression is one stage (CompressionStream('gzip')); and server-sent AI responses (every chat UI that types word by word) are a ReadableStream being read chunk by chunk. Node's streams are the older cousins — same roles, .pipe() instead of .pipeTo(), and stream/promises' pipeline() as the safe composer.

    

      
// quiz — first pick is the one that counts

      
A Node service reads 1GB uploads with chunks.push(chunk) then processes the concatenated buffer, and dies with out-of-memory under load. The streams-native fix?

      

        
        
        
        
      

      
Why: collect-then-process holds every concurrent upload fully in memory — 20 users × 1GB is game over regardless of heap size. A pipeline holds only each stream's small queues (kilobytes), and a slow stage automatically slows the socket read itself. Options A/C/D relocate the problem; the pipeline dissolves it.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The definition to lead with: "backpressure = the consumer's pace propagating upstream through bounded queues" — high-water mark is the queue size, desiredSize is the live reading.
    • 
        
  • A stream is consumed once — response.json() after touching response.body throws. .tee() splits one into two when two consumers genuinely need it.
    • 
        
  • Node trap with manual .pipe(): errors don't propagate across stages (leaked file handles on failure) — pipeline() exists because of that; naming it is the production-experience tell.
    • 
        
  • The judgment line: streams pay off for big, slow, or unbounded data. For a 4KB JSON config, response.json() is correct — streaming it is ceremony.

Workers — actual parallelism, at the price of a postbox

      
advanced → when one thread isn't enough, and what message passing costs

    

  

  

    
Everything in this module so far has been concurrency on one thread — interleaving waits, never computing twice at once. A Web Worker is the real second thread: its own event loop, its own memory, running your heavy computation while the main thread keeps painting at 60fps. The price of that isolation is the API: workers share nothing. You postMessage data over; the browser structured-clones it (the deep copy from JS Fundamentals); results come back the same way. No DOM over there, no shared variables, no races — a postbox, not a shared desk.

    
The decision rule: async/await solves waiting (network, timers, disk) and workers solve working (parsing a 50MB CSV, image processing, crypto, physics). Moving a fetch into a worker buys nothing — the network wasn't blocking your thread. Moving a 2-second parse into one turns a frozen tab into a responsive one.

    

      
      
PROFESSOR WHISKERS EXPLAINSThe front-desk cat greets every visitor (the main thread — she must never be busy long). Shredding two hundred boxes is real work, so it goes to the basement cat — separate room, separate everything. They communicate by photocopies through a mail slot: send the list down (a copy!), shredded confetti summary comes back up. The basement cat can't rearrange the lobby (no DOM), and the front desk never smells cardboard. Slower to coordinate? Slightly. But the lobby never, ever freezes.

    

    

      

        
basement-cat.js — run it

        
// a worker from a Blob URL — same-origin, no separate file needed
const workerCode = `
  self.onmessage = (e) => {
    const { upTo } = e.data;              // arrived as a COPY
    let primes = 0;
    for (let n = 2; n <= upTo; n++) {     // deliberately brute-force
      let isPrime = true;
      for (let d = 2; d * d <= n; d++) if (n % d === 0) { isPrime = false; break; }
      if (isPrime) primes++;
    }
    self.postMessage({ upTo, primes });
  };
`;
const url = URL.createObjectURL(new Blob([workerCode], { type: 'text/javascript' }));
const worker = new Worker(url);

// wrap the postbox in a promise (section 09's pattern, immediately useful)
const compute = (upTo) => new Promise(resolve => {
  worker.onmessage = (e) => resolve(e.data);
  worker.postMessage({ upTo });
});

console.log('main thread: sending the heavy job downstairs…');
const t0 = performance.now();

// main thread stays FREE while the worker grinds — prove it with a heartbeat
const beat = setInterval(() => console.log('  ♥ main thread still responsive'), 50);
const result = await compute(300000);
clearInterval(beat);

console.log(`worker found ${result.primes} primes ≤ ${result.upTo} ` +
            `in ${Math.round(performance.now() - t0)}ms — zero jank`);
worker.terminate();  // basement cat clocks out (always clean up!)
URL.revokeObjectURL(url);

      

      
the heartbeat keeps printing WHILE the primes grind — that's the whole point

      

    

    
The cloning tax has an escape hatch: transferables. postMessage(buffer, [buffer]) hands an ArrayBuffer across in O(1) — the sender's copy goes dead (neutered) instead of duplicated, which is how you move a 100MB image between threads without paying for it twice. And SharedArrayBuffer + Atomics is genuine shared memory for the rare lock-free ambitions — gated behind cross-origin isolation headers precisely because shared mutable memory is as dangerous as it is fast.

    

      
// quiz — first pick is the one that counts

      
Search results render in 4s: profiling shows 3.5s inside a synchronous ranking function over 100k items. Moving which thing where fixes the frozen UI?

      

        
        
        
        
      

      
Why: async doesn't create threads — a CPU-bound function blocks identically inside an async wrapper, and setTimeout just freezes the tab slightly later. Workers are the only true "run JS elsewhere" (short of chunking the algorithm itself). The fetch was never the problem: waiting doesn't block; working does. That distinction is the entire question.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • The rule as one sentence: "async for I/O-bound, workers for CPU-bound" — interviewers ask it exactly that abstractly, and this is the expected shape.
    • 
        
  • Structured clone (not JSON!) crosses the postbox: Maps, Sets, Dates, ArrayBuffers survive; functions and DOM nodes don't. Same algorithm as structuredClone() — one mental model, two features.
    • 
        
  • Node's equivalent is worker_threads (threads, shared memory possible) — distinct from cluster (processes for scaling request handling). Naming which is which is a node-backend module drill.
    • 
        
  • Frameworks ride this too: Comlink turns postMessage into awaitable RPC; the ~50ms round-trip floor means you batch work, not ping-pong per item.

Production patterns — pools, dedupe & polite polling

      
advanced → the four async utilities every real codebase reinvents

    

  

  

    
Every mature codebase contains the same four hand-rolled utilities, and interviews love asking for them because each is ten lines of closures + promises — everything this module built, composed. The concurrency pool: run 500 jobs, but only N in flight (unbounded Promise.all is a self-inflicted DDoS). In-flight dedupe: five components request the same user at once — share one promise instead of five requests. The serial queue: writes to one resource must not interleave. Polling with backoff: ask again politely, at widening intervals, with a give-up point.

    

      
      
PROFESSOR WHISKERS EXPLAINSFour house rules of a well-run shelter: only three volunteers groom at once, however long the queue (the pool). If someone's already fetching Mochi's file, walk with them — don't send a second runner (dedupe). One cat through the medical room door at a time, in arrival order (serial queue). And checking whether the vet called back: once a minute, then every two, then five — not every ten seconds forever (backoff). None of these are exotic; they're what "someone thought about load" looks like.

    

    

      

        
house-rules.js — run it

        
const nap = (ms) => new Promise(r => setTimeout(r, ms));

// 1 · THE POOL — N workers pulling one shared queue (the interview classic)
async function pool(limit, tasks) {
  const results = new Array(tasks.length);
  let next = 0;
  const workers = Array.from({ length: limit }, async () => {
    while (next < tasks.length) {
      const i = next++;                  // single-threaded: no race on this
      results[i] = await tasks[i]();
    }
  });
  await Promise.all(workers);
  return results;
}

const t0 = Date.now();
const jobs = Array.from({ length: 6 }, (_, i) => async () => {
  await nap(100);
  return `job ${i}`;
});
await pool(2, jobs);
console.log(`6 × 100ms jobs, limit 2 → ${Date.now() - t0}ms (≈300, not 100 or 600)`);

// 2 · IN-FLIGHT DEDUPE — five callers, one request
const inflight = new Map();
let hits = 0;
function fetchCat(id) {
  if (inflight.has(id)) return inflight.get(id);      // join the walk
  const p = (async () => {
    hits++; await nap(80); return `cat #${id}`;
  })().finally(() => inflight.delete(id));            // clean up after landing
  inflight.set(id, p);
  return p;
}
const five = await Promise.all([1,1,1,2,1].map(fetchCat));
console.log(`${five.length} callers served by ${hits} actual requests`);

// 3 · SERIAL QUEUE — chain onto a rolling promise tail
let tail = Promise.resolve();
const serialize = (job) => tail = tail.then(job, job);
['first','second','third'].forEach(name =>
  serialize(async () => { await nap(30); console.log('door:', name); }));
await tail;   // arrival order, guaranteed — even though all queued at once

      

      
pool math, dedupe hit-count, and a strict one-at-a-time door

      

    

    
Polling completes the set, and its two rules are judgment, not code: widen the interval (1s → 2s → 4s… capped, plus jitter so a thousand clients don't sync up), and always carry a stop condition — a deadline, an attempt cap, or an AbortSignal from section 08. Then know when to stop polling entirely: past a few requests a minute per client, the answer changes shape — server push via SSE or sockets (the frontend-system-design module's real-time section owns that trade-off).

    

      
// quiz — first pick is the one that counts

      
In the pool above, why is const i = next++ safe with 2 workers "running at once" — no lock, no race?

      

        
        
        
        
      

      
Why: workers only swap at await points — between them, each runs uninterrupted (the event-loop contract from section 02, paying rent). next++ sits in such a gap, so no two workers can read the same value. This is why JS needs so much less locking than Java — and the same reasoning explains where you would get a race: two awaits between a read and its dependent write.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Pool ≠ batching: all in chunks of N waits for each chunk's slowest job (convoy effect); a true pool starts a new job the instant any slot frees. Explaining that difference is the distinguisher.
    • 
        
  • Dedupe's .finally(delete) is the subtle line — forget it and errors poison the cache: every future caller receives the same stale rejection. (SWR and React Query ship this exact machinery, tuned.)
    • 
        
  • The serial queue's .then(job, job) keeps the chain alive through failures — one rejected write mustn't wedge the door shut forever.
    • 
        
  • Library names to offer after the hand-rolled version: p-limit, p-queue, p-retry — "I can write it, and I know not to maintain my own in production."

// warm-up 1 of 3 — queue priority vs registration order

      
setTimeout(() => log('T'), 0); Promise.resolve().then(() => log('P')); log('S'); — the timer was registered first. What logs?

      

        
        
        
        
      

      
Why: registration order only matters within a queue, never between queues — the loop finishes the sync pass ('S'), drains the VIP lounge ('P'), then takes the timer ('T'), per §02's one rule. "S, T, P" is the belief that first-registered runs first across queues; "T, P, S" is the "0ms means now" myth (§10: 0ms means "join the macrotask queue after ≥0ms"); "P, S, T" imagines .then callbacks running synchronously, which §03's buzzer rule forbids. Queue priority beats scheduling order, every time.

    


    

      
// warm-up 2 of 3 — what a chain actually carries

      
Promise.resolve(1).then(v => { v + 1; }).then(v => console.log(v)); — what prints?

      

        
        
        
        
      

      
Why: each link settles with its handler's return value (§03), and { v + 1; } is a block that computes 2 and throws it away, returning undefined. "Logs 2" assumes the result flows on its own — it only flows if you return it. "Logs 1" imagines values tunneling through do-nothing handlers; only .finally has pass-through. And nothing throws: undefined is a perfectly legal fulfillment value — which is exactly why this bug ships quietly.

    


    

      
// warm-up 3 of 3 — settled means settled

      
A fetch fulfilled two seconds ago; only now does your code call the matching controller.abort(). What happens to that fetch's promise and its .then handlers?

      

        
        
        
        
      

      
Why: a promise is the buzzer from §03 — it buzzes exactly once and never changes its mind, so no API can flip fulfilled to rejected after the fact. abort() (§08) fires the signal's abort event, and with the fetch long finished, nobody is listening — it's a no-op, and it never throws at the call site. Handlers can't be "removed" either; attaching them is one-way. If the first option tempted you, you've merged "cancel the future" with "rewrite the past" — abort only does the first.

    


    

      
// apply 1 of 3 — trace the full ordering

      
async function f() { log('a'); await Promise.resolve(); log('b'); } f(); log('c'); setTimeout(() => log('d'), 0); Promise.resolve().then(() => log('e')); — what order?

      

        
        
        
        
      

      
Why: trace it like §06's algorithm. Sync pass: f() runs synchronously to its first await and logs 'a' (§04), the await parks its continuation in the microtask queue, 'c' runs, the timer joins the macrotask queue, and the .then joins the microtask queue behind the continuation. Drain the lounge FIFO — 'b', then 'e' — then the timer: a, c, b, e, d. "a, b, c…" believes awaiting an already-settled promise continues synchronously — §06 showed await always yields; "c, a…" forgets async functions start synchronously; "a, c, e, b…" puts the later-enqueued .then ahead of the earlier-enqueued continuation, but the lounge is strictly first-come, first-served.

    


    

      
// apply 2 of 3 — rejection highway, then recovery

      
Promise.reject(new Error('boom')).then(v => log('A')).catch(e => { log('B'); return 'ok'; }).then(v => log('C', v)).catch(e => log('D')); — what prints?

      

        
        
        
        
      

      
Why: the rejection rides §03's error highway past the good-news desk (skipping 'A') to the .catch, which logs 'B' — and because it returns 'ok', that's a recovery: the new promise it produces is fulfilled, so 'C ok' prints and D has nothing to catch (§05). "B, then D" treats .catch as a logger that leaves the chain rejected — returning from a catch is precisely how you get back on the happy path. "B only" forgets .catch returns a fresh promise that keeps the chain alive. "A…" forgets rejections skip fulfillment handlers entirely.

    


    

      
// apply 3 of 3 — the forEach await trap

      
Inside an async function: [1, 2, 3].forEach(async n => { await save(n); }); log('all saved'); — each save takes ~50ms. What's true?

      

        
        
        
        
      

      
Why: forEach calls its callback and throws the return value away — it has no idea promises exist. Three saves start, each suspends at its await, and the sync pass reaches 'all saved' before any finishes; worse, if one rejects, nobody owns it — a floating promise straight out of §05. "One at a time" describes for…of with await (§07's serializing loop); "waits for them together" describes map + Promise.all (§04's pattern). Three loop shapes, three different contracts — naming which is which is the skill.

    


    

      
// stretch 1 of 3 — spot the false claim

      
Three of these are facts. Which claim is FALSE?

      

        
        
        
        
      

      
Why: .catch never converts anything — it returns a NEW promise carrying the recovery (§03's rule that every link is a fresh promise), while p stays settled-rejected forever, so a later p.then(g) skips g and re-delivers the same rejection (§05). It tempts because chained p.catch(fn).then(g) DOES see the recovery — the fix lives on the returned promise, not the original. The other three are checkable facts: settled .then still queues a microtask (§03), all abandons but can't cancel its losers (§07), and Node ≥15 dies on unhandled rejections (§05).

    


    

      
// stretch 2 of 3 — pool math under constraints

      
600 thumbnails to fetch, ~150ms each. The browser allows 6 concurrent requests to this origin; the API rate-limits at 50 req/s. With a §14-style pool at limit 6, roughly how long — and can unbounded Promise.all beat it?

      

        
        
        
        
      

      
Why: pool math first: 600 ÷ 6 in flight = 100 waves × 150ms ≈ 15s, which is 40 req/s — safely under the 50 req/s cap, so the connection limit binds, not the rate limit. That sinks the ~12s answer: always check which ceiling you hit first before dividing by it. ~90s assumes the pool serializes — a pool runs limit-wide, not one-wide (§14). ~150ms needs 600 truly parallel requests, i.e. the threads §01 says don't exist — and unbounded Promise.all (§07) buys nothing here but a shot at rate-limit errors.

    


    

      
// stretch 3 of 3 — win the autocomplete race

      
An autocomplete fires a fetch per keystroke and writes results to the DOM in .then. The user types "mo", then "moc" — and the "mo" response arrives after the "moc" one. What renders, and which fix is complete?

      

        
        
        
        
      

      
Why: two independent chains settle in network order, not creation order (§06) — the slow "mo" response lands last and its .then overwrites the fresh results. Abort-on-keystroke (§08) is the complete fix: the stale fetch rejects with an AbortError, its handler never touches the DOM, and the socket is freed. await can't help — it orders steps within one chain, never across two independent ones. And debounce (§08) reduces how many requests exist but can't stop a slow response from overlapping the next quiet period — it narrows the race window without closing it.
