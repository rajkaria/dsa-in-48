Algorithms as strategies, not spells.

Sorting, binary search, backtracking, dynamic programming, greedy — five strategies for shrinking a problem, not five incantations. Each section builds the strategy from a decision you'd naturally make, shows it running (the sorts literally race), and names the trigger phrases that tell you which one a problem wants.

DP gets the careful treatment: recursion you already trust → "stop re-answering the same question" (memoization) → the table version. In that order, it's almost anticlimactic — which is the goal. The cats are competing this time. There are brackets. 🐈

Sorting — watch n² lose the race

beginner → why "divide and conquer" earns the log

You'll almost never hand-write a sort at work — .toSorted() exists — but sorting is where algorithm design is easiest to feel. Bubble/insertion sort (compare neighbors, swap, repeat): O(n²), because fixing one item's position takes a pass. Merge sort: split in half, sort each half (recursively — halves of halves…), then merge two sorted lists — the zipper you built in Linear Structures. log n levels of splitting × O(n) merging per level = O(n log n), guaranteed.

Quicksort gets the same average by partitioning around a pivot in place. And the interview nuance that impresses: comparison sorting can't beat n log n — but counting sort does O(n + k) when values live in a small known range, by tallying instead of comparing. "Sort Colors" is secretly that.

Why is merge sort O(n log n) — the actual accounting?

Why: draw the recursion as a triangle: level 0 merges one n-sized pair-set, level 1 two n/2s (still n total), level 2 four n/4s (still n)… log n levels deep because halving n hits 1 in log₂n steps. "Levels × per-level work" is the analysis template for every divide-and-conquer — learn the accounting once, reuse forever. Bonus: merge sort is stable and needs O(n) scratch; quicksort is in-place but O(n²) on adversarial pivots.

LEVEL UP — what interviewers listen for
  • "When would you NOT just call .sort()?" — when a heap (streaming top-k), counting sort (small value range), or bucket-by-property beats comparison sorting; or when stability matters and you must check the runtime's guarantee (JS .sort is stable per spec now).
  • Sorting as preprocessing is its real interview job: sort THEN two-pointer / sweep intervals / binary search. "I'll pay n log n to unlock a linear pattern" is a sentence that wins mediums.
  • practice (verified): 75 · Sort Colors · 88 · Merge Sorted Array · 215 · Kth Largest (vs heap!)

Binary search — beyond finding numbers

intermediate → search any monotonic ANSWER space

The basic move you know: sorted array, check the middle, discard half, O(log n). The version interviews actually test is bigger: binary search works on any question whose answers split into "no no no YES yes yes" — a monotonic boundary. The array is optional; the monotonicity is everything.

"Slowest eating speed that still finishes in time" (Koko), "first bad version", "smallest capacity that ships in D days" — none of these search an array. They search candidate answers: guess a value, test feasibility ("can Koko finish at speed 5?"), and the yes/no pattern tells you which half to discard. Template: lo, hi, shrink toward the boundary, return the first yes.

PROFESSOR WHISKERS EXPLAINSHow high can Mochi jump? You don't test every centimeter. Set the bar at 60cm — clears it. 90 — refuses. 75 — clears. The answer's between 75 and 90, and every test halves the unknown region, because jumping is monotonic: clear 75 ⇒ clear anything lower. Any question with that "clears-below, fails-above" shape is binary-searchable — including "what's the minimum speed / capacity / size that works", where each test is a little simulation instead of a jump.

search-the-answer.js — run it
// classic: find 7.1 in sorted weights — count the peeks
function searchArray(sorted, target) {
  let lo = 0, hi = sorted.length - 1, peeks = 0;
  while (lo <= hi) {
    peeks++;
    const mid = (lo + hi) >> 1;
    if (sorted[mid] === target) return { at: mid, peeks };
    if (sorted[mid] < target) lo = mid + 1; else hi = mid - 1;
  }
  return { at: -1, peeks };
}
const weights = Array.from({ length: 1024 }, (_, i) => i / 10);
console.log('find 71.4 in 1024 items:', searchArray(weights, 71.4));

// the grown-up version: Koko the cat eats treat piles at speed k/hour.
// minimum k to finish all piles within h hours? (LC 875)
function minEatingSpeed(piles, h) {
  const hoursAt = (k) =>
    piles.reduce((sum, p) => sum + Math.ceil(p / k), 0);
  let lo = 1, hi = Math.max(...piles);
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    if (hoursAt(mid) <= h) hi = mid;    // fast enough — try slower
    else lo = mid + 1;                  // too slow — must speed up
  }
  return lo;                            // first speed that works
}
console.log('min speed for piles [30,11,23,4,20] in 6h:',
  minEatingSpeed([30, 11, 23, 4, 20], 6));
// we binary-searched SPEEDS, not an array — feel that shift

Search in a ROTATED sorted array ([6,7,1,2,3,4,5]) — why does binary search still work?

      

        
        
        
        
      

      
Why: a rotation leaves one clean half at any split — nums[lo] ≤ nums[mid] tells you which. If the target's inside that half's range, go there; else the other. Still O(log n), one extra comparison. (Two-pass — find pivot then search — also works and is easier to code correctly; offering both with the tradeoff is a fine answer.) The lesson generalizing: binary search survives structure damage as long as you can still decide which half to discard.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Off-by-one discipline: pick ONE template (lo < hi, hi = mid / lo = mid + 1, returns first-true) and use it everywhere — inventing boundaries per-problem is where infinite loops breed.
    • 
        
  • The trigger phrase for answer-space search: "minimum X such that…" / "maximum X such that…" + a feasibility check you can run. Say "monotonic predicate" once.
    • 
        
  • lo + ((hi - lo) >> 1) dodges overflow in other languages — in JS it just reads as care.
    • 
        
  • practice (verified): 704 · Binary Search · 153 · Min in Rotated · 33 · Search Rotated · 875 · Koko

Recursion & backtracking — explore, undo, repeat

      
intermediate → the choose/explore/unchoose ritual

    

  

  

    
Recursion you've now used across three modules; backtracking is recursion with commitment issues, on purpose: to enumerate all subsets/permutations/combinations, walk a decision tree — choose an option, explore the consequences recursively, then unchoose (restore state exactly) and try the next option. The unchoose step is what lets one shared "current path" array serve the entire exploration.

    
Complexity is honest about the task: 2ⁿ subsets or n! permutations exist, so generating them costs that — the skill isn't avoiding the exponential, it's pruning: abandoning branches the moment they can't succeed ("sum already exceeds target — stop here"), which is also all Sudoku solvers and Word Search do.

    

      
      
PROFESSOR WHISKERS EXPLAINSMochi exploring boxes: climb into box A (choose), thoroughly investigate everything reachable from inside A (explore), then — crucially — climb back out exactly as she entered (unchoose) before trying box B. A cat who doesn't fully exit box A carries bits of box A into her box-B investigation, and her map of the world is ruined. That's the state-restore bug in every broken backtracking solution: the pop() matching every push().

    

    

      

        
all-the-boxes.js — run it

        
// all subsets of treats — the master template (LC 78)
function subsets(items) {
  const out = [], path = [];
  (function explore(start) {
    out.push([...path]);                 // every path is a subset
    for (let i = start; i < items.length; i++) {
      path.push(items[i]);               // CHOOSE
      explore(i + 1);                    // EXPLORE
      path.pop();                        // UNCHOOSE — restore exactly
    }
  })(0);
  return out;
}
console.log(subsets(['tuna', 'catnip', 'yarn']).map(s => s.join('+') || '∅').join('  '));

// combination sum with PRUNING: which treat-price combos hit exactly 7?
function combosTo(prices, target) {
  const out = [], path = [];
  (function explore(start, remaining) {
    if (remaining === 0) { out.push([...path]); return; }
    for (let i = start; i < prices.length; i++) {
      if (prices[i] > remaining) continue;   // PRUNE: hopeless branch
      path.push(prices[i]);
      explore(i, remaining - prices[i]);     // i again: reuse allowed
      path.pop();
    }
  })(0, target);
  return out;
}
console.log('sum to 7 from [2,3,5]:',
  JSON.stringify(combosTo([2, 3, 5], 7)));

// quiz — first pick is the one that counts

      
Word Search (find "CAT" tracing adjacent grid cells, no reuse): what plays the "unchoose" role?

      

        
        
        
        
      

      
Why: a cell blocked for THIS path must stay available for sibling paths — mark on entry (grid[r][c] = '#'), restore on exit. Clearing everything (option 3) breaks the no-reuse rule within a path; full copies (option 4) work but cost O(grid) per step. The mark/restore pair is the choose/unchoose ritual wearing grid clothes — one mental model, every enumeration problem.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • Duplicates in input? Sort first, then skip items[i] === items[i-1] at the same depth — the dedupe line that separates Subsets from Subsets II.
    • 
        
  • Complexity honesty: "output-bounded — O(2ⁿ · n) because that's what exists" is a correct and confident answer; pretending it's polynomial is the red flag.
    • 
        
  • Permutations swap-in-place or track a used[] — know one cold. Letter Combinations (phone pad) is the gentlest on-ramp; N-Queens is the same ritual with a fancy hat.
    •

Dynamic programming — stop re-answering the same question

      
the feared one, taught in the order that works

    

  

  

    
Forget the name (it's meaningless, chosen in the 1950s to impress a funding committee — true story). DP is one observation: some recursions ask the same sub-question over and over — so cache the answers. That's it. The rest is engineering around that idea.

    
Step 1 — write the honest recursion. Climbing stairs (1 or 2 steps at a time): ways(n) = ways(n−1) + ways(n−2). Correct, and exponential — ways(3) gets recomputed absurdly often. Step 2 — memoize: a Map from argument → answer; each sub-question now computed once. O(n). Step 3 (optional) — flip to a table: fill answers bottom-up from the base cases; same math, no recursion, often just two variables. All three are shown running below — with a counter proving the collapse.

    

      
      
PROFESSOR WHISKERS EXPLAINSA tower of cat shelves, hop up 1 or 2 at a time. Ask Mochi "how many routes to shelf 40?" the naive way and she recounts routes to shelf 3 millions of times — each big question splinters into the same small questions. Give her a notepad: first time she works out shelf 3, she writes it down; every later request is a glance. Same brain, a notepad, million-fold speedup. DP is the notepad. (The table version is just filling the notepad in order before anyone asks.)

    

    

      

        
the-notepad.js — run it

        
// 1 · honest recursion — watch the call counter explode
let calls = 0;
function ways(n) {
  calls++;
  if (n <= 1) return 1;
  return ways(n - 1) + ways(n - 2);
}
console.log('ways(28) =', ways(28), '· calls:', calls.toLocaleString());

// 2 · memoized — same recursion + notepad
calls = 0;
const pad = new Map();
function waysMemo(n) {
  calls++;
  if (n <= 1) return 1;
  if (pad.has(n)) return pad.get(n);
  const answer = waysMemo(n - 1) + waysMemo(n - 2);
  pad.set(n, answer);
  return answer;
}
console.log('memo(28)  =', waysMemo(28), '· calls:', calls);

// 3 · bottom-up table — collapses to two variables
function waysTable(n) {
  let prev = 1n, curr = 1n;               // BigInt — the answer outgrows floats
  for (let i = 2; i <= n; i++) [prev, curr] = [curr, prev + curr];
  return curr;
}
console.log('table(90) =', waysTable(90).toString(),
            '(recursion would take past the heat death)');

// the 2D taste: unique paths through a 4×5 grid, right/down only
function uniquePaths(rows, cols) {
  const row = new Array(cols).fill(1);            // top row: one way each
  for (let r = 1; r < rows; r++)
    for (let c = 1; c < cols; c++)
      row[c] += row[c - 1];                       // from-left + from-above
  return row[cols - 1];
}
console.log('4×5 grid paths:', uniquePaths(4, 5));

// quiz — first pick is the one that counts

      
Coin Change (fewest coins to make an amount): why does greedy "always take the biggest coin" fail, and what does DP do instead?

      

        
        
        
        
      

      
Why: US-style coin systems happen to be greedy-safe; [1,3,4] is the standard counterexample — memorize it as your proof-by-counterexample. The DP frame: best[a] = 1 + min(best[a − coin] for each coin), filled from 0 upward — locally exhaustive, globally optimal, O(amount × coins). Recognizing "greedy needs a proof; DP needs a sub-problem" is this module's judgment core.

    

    

      
LEVEL UP — what interviewers listen for

      
    
        
  • How to FIND the sub-problem: ask "if I knew the answer for every smaller version, could I combine them?" State the recurrence in English before code — interviewers grade the recurrence, not the loops.
    • 
        
  • House Robber's recurrence in one line: best(i) = max(best(i−1), loot[i] + best(i−2)) — skip me or take me + best-two-back. LIS, Jump Game, and most "1D array decisions" fit this take-or-skip mold.
    • 
        
  • Space optimization (table → two variables) is a cheap flex worth doing aloud: "I only ever read two previous cells, so O(1) space."
    •

Greedy — the best local move, when it's provably enough

      
advanced → the burden of proof is the whole topic

    

  

  

    
Greedy algorithms make the locally-best choice at each step and never look back. When they're right, they're beautiful — O(n) or O(n log n), a few lines. The catch you now know from Coin Change: greedy is only correct when a proof-shaped argument says no future regret is possible. The interview skill is exactly that judgment: reach for greedy, then defend it — or produce the counterexample and fall back to DP.

    
Two defenses cover most cases. The exchange argument: "any optimal solution can be rewritten, without loss, to start with my greedy choice" — that's why earliest-end wins interval scheduling (Structures §05). The invariant argument: "after each step, greedy is at least as far ahead as any alternative" — that's Jump Game below.

    

      

        
no-regrets.js — run it

        
// Jump Game (LC 55): each cell = max hop length. Can you reach the end?
// greedy invariant: track the FARTHEST reachable frontier — nothing else matters
function canReach(hops) {
  let frontier = 0;
  for (let i = 0; i < hops.length; i++) {
    if (i > frontier) return false;        // gap! this cell is unreachable
    frontier = Math.max(frontier, i + hops[i]);
  }
  return true;
}
console.log('[2,3,1,1,4] →', canReach([2, 3, 1, 1, 4]));
console.log('[3,2,1,0,4] →', canReach([3, 2, 1, 0, 4]));

// Partition Labels (LC 763): cut a string into max pieces where
// no letter spans two pieces. greedy: extend to each letter's LAST home.
function partition(s) {
  const last = {};
  for (let i = 0; i < s.length; i++) last[s[i]] = i;
  const sizes = [];
  let start = 0, end = 0;
  for (let i = 0; i < s.length; i++) {
    end = Math.max(end, last[s[i]]);       // this letter drags the wall out
    if (i === end) { sizes.push(end - start + 1); start = i + 1; }
  }
  return sizes;
}
console.log('ababcbaca|defegde|hijhklij →', partition('ababcbacadefegdehijhklij'));
// why greedy is SAFE here: a piece must contain every occurrence of
// each letter inside it — the earliest legal wall is forced, not chosen.

In an interview you suspect a problem is greedy. What's the professional move?

      

        
        
        
        
      

      
Why: the attack-then-commit ritual reads as rigor, and it's genuinely how you avoid greedy's famous trap (plausible + wrong). The beautiful consolation: a failing counterexample tells you what the sub-problem must remember — [1,3,4]/6 failing "biggest coin" reveals that every amount needs an answer. Choosing the weapon — the decision tree

      
the meta-skill: hear the problem, name the strategy

    

  

  

    
Under pressure, the first 90 seconds decide the interview: mapping the problem's wording to a strategy. This decision tree, walked out loud, is that mapping — and saying it aloud is itself graded ("I'm choosing between X and Y because…").

    

      
// hear this → reach for that

      
    
        
  • "All / every possible…" (subsets, combos, boards) → backtracking; complexity is the output size, prune hard.
    • 
        
  • "Minimum/maximum X such that [testable condition]" → binary search the answer — write the feasibility check first.
    • 
        
  • "Best / count ways / longest…" where choices compound → smell DP: can you phrase "answer for i from answers before i"? Say the recurrence in English first.
    • 
        
  • "Pick repeatedly, no undo needed" (schedules, frontiers, merges) → try greedy, then attack it for sixty seconds before trusting it.
    • 
        
  • "Fewest steps / shortest path" in an unweighted world → BFS (last module). "Contiguous run" → sliding window. "Pairs in sorted" → two pointers. "Fast lookups / counting" → hash map. The foundations never stop paying.
    • 
        
  • And when the wording fits nothing → brute force it honestly, state the complexity, and optimize the bottleneck out loud. Interviews reward visible method over silent magic — a stated O(n²) beats a mumbled maybe-O(n).
    •
