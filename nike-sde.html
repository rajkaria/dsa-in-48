Node & the runtime

The Node question is the loop's handshake: explain the event loop, and everything after gets friendlier. For a serverless team it comes with a twist — they'll ask how the runtime behaves inside a Lambda sandbox.

YOU ALREADY KNOW THIS

Every time you've awaited a fetch, wondered why a console.log printed "later", or watched one blocking loop freeze a whole Express server, you were living in the event loop. This topic just gives the phases names so you can narrate them under pressure.

// the idea

  • One JS thread, many I/O threads: your JavaScript runs on a single thread; libuv hands file, DNS, and crypto work to a small thread pool (4 by default) and the OS handles sockets. That's why Node scales beautifully for I/O-bound APIs and chokes on CPU-bound loops — the exact judgment call interviewers fish for.
  • The loop has phases: timers → pending callbacks → poll (where I/O lands) → check (setImmediate) → close. Between every callback, the microtask queues drain: process.nextTick first, then resolved promises. Being able to order setTimeout(0) vs setImmediate vs await out loud is the whole flex.
  • Backpressure is the senior stream question: pipe/pipeline pause a fast reader when the writer's buffer (highWaterMark) fills. Reading a 2GB file with readFile instead of streams is the classic junior tell — and it maps straight onto S3 streaming in this stack.
  • CPU work has three escape hatches: worker_threads (shared memory, same process), cluster (one process per core behind a shared port — largely irrelevant in Lambda, where concurrency is horizontal), or "don't" — push it to a queue/Step Function and let another compute tier own it.
  • Lambda changes the idioms: anything outside the handler runs once per container and survives warm invokes — so SDK clients and connections go there. Anything you leak (listeners, globals that grow) survives too. The event loop must be empty or awaited before the handler returns, or work silently dies mid-flight.
  • Modules, one sentence each: CommonJS (require) is synchronous and dynamic; ESM (import) is static, async-friendly, tree-shakeable, and the modern default — Node speaks both, with interop friction at the boundary.

// rapid-fire — answer out loud, then reveal

Explain the event loop like a senior, in 45 seconds.

JavaScript runs single-threaded; Node delegates I/O to libuv (thread pool + OS async primitives) and queues completions. The loop cycles phases — timers, poll for I/O, check for setImmediate — and between callbacks drains microtasks: nextTick first, then promises. The payoff sentence: one blocking callback stalls every request in the process, which is why we stream, chunk, or offload CPU work. Stop there; let them pull for phase detail.

setTimeout(fn, 0) vs setImmediate vs process.nextTick — order and use?

nextTick runs before anything else (even promises) right after the current operation — powerful and dangerous, since a recursive nextTick starves I/O. Promise callbacks drain next. setTimeout(0) fires in the timers phase; setImmediate in the check phase — inside an I/O callback, setImmediate reliably beats setTimeout. Practical guidance: promises for sequencing, setImmediate to yield to I/O, nextTick almost never in app code.

When is Node the wrong choice — and what do you do when it happens anyway?

Sustained CPU-bound work: image transforms, big parses, crypto loops — one hot loop blocks every concurrent request. Escapes in order: move it behind a queue to a compute tier built for it (in this stack, a Step Functions state on Fargate or a dedicated Lambda with high memory = more CPU), or worker_threads if it must stay in-process. Saying "Lambda's CPU scales with the memory setting" earns real points here.

How do streams and backpressure actually work?

Readables emit chunks; writables buffer up to highWaterMark and their write() returns false when full; pipe()/pipeline() honor that by pausing the readable until 'drain'. Result: constant memory for any file size. The follow-up trap is error handling — raw pipe() doesn't forward errors, stream.pipeline() does, which is why it exists. Map it to the job: streaming a 2GB 3D asset from S3 without buffering it whole.

cluster vs worker_threads — and does either matter in Lambda?

cluster forks whole processes sharing a port — the classic way to use all cores on a long-running server. worker_threads spawns threads inside one process with message passing/shared buffers — for CPU work without process overhead. In Lambda, cluster is pointless (each sandbox is one invocation; scale is horizontal and managed), and worker_threads only helps if a single invocation is CPU-parallel. Knowing what NOT to bring to serverless is the senior half of the answer.

What causes memory leaks in production Node?

Unbounded module-level caches, event listeners added per request and never removed, closures pinning big buffers, and forgotten timers. In Lambda it's sneakier: module scope survives warm invokes, so a "cache" that grows per invoke inflates until the container dies. Diagnosis story: heap snapshots (or clinic.js) comparing two points in time, then bound the cache (LRU with a max) — always answer with tooling + fix, not just causes.

Why must everything be awaited before a Lambda handler returns?

When the handler's promise settles, the sandbox is frozen — pending callbacks, un-awaited promises, and fire-and-forget writes just stop. They may resume on the next warm invoke (confusing) or never (data loss). So: await everything, or hand off explicitly — drop a message on SQS/EventBridge and let another function own the tail work. This one question separates "used Lambda" from "operated Lambda".

CommonJS vs ESM — what's worth saying in 2026?

ESM is the default for new code: static imports enable tree shaking and top-level await, and it's the standard both browser and Node share. CJS persists in older deps; interop is the friction point (default-export mismatches, dual packages). For Lambda specifically: smaller bundles (esbuild, tree-shaken ESM, AWS SDK v3's modular clients) measurably cut cold-start init time — tie the module system to a metric and the answer lands senior.

How do you handle errors global-scale in a Node service?

Layered: try/catch (or middleware) at request boundaries returning a consistent error envelope; 'unhandledRejection'/'uncaughtException' as last-resort logging then controlled exit (the process is in unknown state — restart, don't limp); structured logs with correlation ids so one request's failure is traceable across services. In Lambda, thrown errors trigger the platform's retry semantics — which is exactly why handlers must be idempotent, and that sentence is a bridge the interviewer will happily follow.

Lambda · Step Functions · S3

Three of the five named services are the event-driven backbone: objects land in S3, Lambdas react, Step Functions keep multi-step work honest. Fluency here is what "depth of native cloud experience" means in the JD.

YOU ALREADY KNOW THIS

Your Express route handler, minus the server: that's a Lambda. Your BullMQ job chain with retries, backoff, and a dead-letter list: that's a Step Function, drawn as a diagram. The uploads bucket you already have: that's S3, now allowed to trigger the other two.

// the idea

  • Lambda's lifecycle is the cold-start story: first invoke on a fresh container pays init (download, runtime boot, your top-of-file code), warm invokes skip straight to the handler. Mitigations in cost order: smaller bundles + lazy imports, more memory (CPU scales with it), provisioned concurrency for latency-critical paths. Internal tooling verdict, said aloud: a few hundred ms of cold start is usually fine — knowing when NOT to spend is senior.
  • The limits that shape designs: 15-minute max runtime, memory 128MB–10GB, ~6MB synchronous payload (256KB async), 4KB env vars, /tmp scratch (512MB default). Each limit implies a pattern: long work → Step Functions; big payloads → S3 + presigned URLs, pass keys not bytes.
  • Three invocation models, three failure semantics: sync (API Gateway — caller gets the error, you retry client-side), async (S3/EventBridge — Lambda retries twice, then a destination/DLQ), and poll-based (SQS event-source mapping — batches, visibility timeout, partial-batch-failure responses). Retries mean at-least-once, so handlers must be idempotent. That word decides this interview.
  • Step Functions = orchestration you can see: states with per-state retry/catch, Map for fan-out, waits and human-approval callbacks (task tokens), direct SDK integrations that skip glue Lambdas entirely. Standard: up to a year, exactly-once orchestration, priced per transition — approval workflows. Express: ≤5 min, at-least-once, priced per duration — high-volume pipelines. Orchestration (explicit flow) vs choreography (events, loose coupling) is the essay question on top.
  • S3 is the source of truth for bytes: 11-nines durability, strong read-after-write consistency, versioning, lifecycle tiers, event notifications. Uploads at this team's scale go browser → S3 directly via presigned URL (bypassing the 6MB Lambda ceiling), then the bucket event kicks off processing. Multipart for big assets (required >5GB), ~3,500 writes/s per prefix — far above an internal tool's needs, and saying so shows you actually size things.
  • The stitched-together picture (also your design-round spine): presigned upload → S3 event → Step Function (validate → transform fan-out → index → notify) → DynamoDB metadata + OpenSearch. Every JD service, one diagram.
idempotent-s3-handler.js
// S3/SQS/EventBridge deliver AT LEAST once → design for replays.
const s3 = new S3Client({});                  // init once, warm reuse
const ddb = new DynamoDBClient({});

export const handler = async (event) => {
  for (const rec of event.Records) {
    const key = decodeURIComponent(rec.s3.object.key);
    const etag = rec.s3.object.eTag;          // same bytes → same etag

    try {
      // conditional write = the idempotency gate: second delivery
      // of the same object version no-ops instead of re-processing
      await ddb.send(new PutItemCommand({
        TableName: 'asset-ingest',
        Item: marshall({ pk: `INGEST#${key}#${etag}`, at: rec.eventTime }),
        ConditionExpression: 'attribute_not_exists(pk)',
      }));
    } catch (e) {
      if (e.name === 'ConditionalCheckFailedException') continue; // replay
      throw e;                                // real error → let Lambda retry
    }
    await startProcessing(key);               // safe: gated above
  }
};

// rapid-fire — answer out loud, then reveal

What actually happens during a cold start, and what would you do about one?

Fresh container: fetch code, boot the runtime, run everything outside the handler (imports, client init) — then the handler. Warm invokes skip all of it. Fixes in order of cost: shrink the init (esbuild bundle, modular SDK v3 clients, lazy-load rarely-used deps), raise memory (more CPU makes init faster too), provisioned concurrency only where p99 latency is a real requirement. For an internal creation tool, "measure first — a 400ms cold start on 2% of invokes may cost nothing" is the senior close.

Why do SDK clients and DB connections live outside the handler?

Module scope executes once per container and survives warm invocations — so clients, connection pools, config fetches, and compiled regexes initialize once instead of per request. Corollary the interviewer wants: that scope is also where leaks and stale config hide, and per-container state is NOT shared across concurrent invokes — each concurrent request gets its own container. Bonus: relational connections from thousands of sandboxes is the classic serverless foot-gun — RDS Proxy or (in this stack) DynamoDB's HTTP API sidesteps it.

Sync vs async vs poll-based invocation — who retries what?

Sync (API Gateway): errors return to the caller; the platform retries nothing — clients own retry with backoff. Async (S3, EventBridge, SNS): Lambda queues the event, retries twice on failure, then dead-letters to a DLQ/failure destination. Poll-based (SQS): the event-source mapping polls in batches; failed messages reappear after the visibility timeout, with maxReceiveCount routing poison messages to a DLQ — report partial batch failures so one bad record doesn't recycle the batch. Every path implies at-least-once → idempotent handlers, always.

A processing job takes 20 minutes. Lambda caps at 15. Go.

First: can it decompose? A Step Functions Map over chunks keeps each state well under the limit and adds per-chunk retry for free — usually the right answer in this stack. If it's genuinely monolithic (one long ffmpeg/3D-conversion pass), run that state on Fargate via Step Functions' ECS integration — same workflow visibility, different compute. The wrong answer is hand-rolling chained Lambdas with self-invocation; you'd be rebuilding Step Functions badly, and naming that trap is worth as much as the fix.

Standard vs Express Step Functions — pick for (a) design-approval workflow, (b) per-upload thumbnail pipeline.

(a) Standard: approvals wait on humans for days (Express caps at 5 minutes), you want exactly-once orchestration and a full execution history for audit; per-transition pricing is irrelevant at approval volumes. (b) Express: thousands of short-lived executions, at-least-once is fine because the pipeline steps are idempotent, and duration pricing is much cheaper at volume. One extra sentence — "Standard for long/critical/auditable, Express for short/hot/idempotent" — turns it into a rule they'll remember you by.

Design the upload path for 500MB 3D asset files.

Never through Lambda — the sync payload ceiling (~6MB) and the cost of proxying bytes both say no. Client asks your API for a presigned URL (that Lambda runs milliseconds), browser uploads straight to S3 — multipart for parallelism and resumability — then the S3 event (or an explicit "complete" call) starts the processing workflow. Add key conventions per project/asset-id, SSE encryption default, and lifecycle rules moving old versions to cheaper tiers. "Pass keys, not bytes" is the sentence that sticks.

How does the same event arriving twice not corrupt your data?

Assume replays: S3 events, SQS, EventBridge, and Step Functions (Express) are all at-least-once. Gate side effects on a natural idempotency key — object key + etag, or the event id — with a DynamoDB conditional write (attribute_not_exists) as the check-and-set; duplicate deliveries hit the condition and no-op. For downstream APIs, pass an idempotency key header so they can dedupe too. This is the single most reliable "operated it for real" signal in the whole loop.

Orchestration vs choreography — where's the line?

Orchestration (Step Functions): one place owns the flow — great when steps are ordered, need per-step retry/compensation, or humans must see where a given asset is stuck. Choreography (EventBridge events, subscribers react): loose coupling — great when teams/services evolve independently and the "flow" is really independent reactions. Honest heuristic: inside one bounded workflow, orchestrate; across team boundaries, publish events. Saying "I'd start with the state machine because debuggability is a feature for internal tools" fits this team's world exactly.

Where do you look when a pipeline "sometimes loses files"?

Method over vibes: CloudWatch metrics first (invocation errors, throttles, DLQ depth, Step Functions failed executions), then structured logs joined by correlation id (asset key) across stages, then X-Ray/traces for the slow hop. Classic culprits in this exact architecture: un-awaited promises at handler return, missing DLQ on an async trigger (failures silently exhausted retries), visibility timeout shorter than processing time (duplicate processing), and non-idempotent replays. Naming symptom → instrument → likely cause beats guessing a fix.

DynamoDB & OpenSearch

The JD names both because the architecture needs both: DynamoDB owns the truth about every asset, OpenSearch makes ten years of them findable. The interview tests whether you know which questions each one answers — and how they stay in sync.

YOU ALREADY KNOW THIS

You've keyed a Mongo collection by userId and fetched a document in one hop — that's DynamoDB's whole religion, with the schema flexibility swapped for guaranteed speed. And that search box you once faked with ILIKE '%jordan%' until it collapsed? The tool you needed was an inverted index — OpenSearch.

// the idea

  • DynamoDB thinks in access patterns, not entities: you list the queries FIRST ("assets by project, newest first", "asset by id", "assets by status"), then design keys to serve each in one Query. Partition key picks the shard; sort key orders within it; begins_with/between make the sort key do real work. Relational habits (normalize, then JOIN at read) literally cannot run here — there are no joins.
  • The numbers that design tables: items ≤400KB (store S3 keys, never bytes); a single partition sustains ~3,000 RCU / 1,000 WCU — beyond that, heavy keys must shard; Query beats Scan because Scan reads the table linearly (an O(n) tell in review). On-demand billing for spiky internal tools, provisioned + autoscaling for steady load.
  • Indexes, one line each: GSI = alternate PK/SK, its own capacity, eventually consistent — the "query by different attribute" answer. LSI = same PK, alternate SK, must exist at table creation, caps the partition at 10GB — rarely worth it; saying why you default to GSIs is the senior move.
  • Change data capture is the glue: DynamoDB Streams emit every write in order (per item); a Lambda consumes them to project into OpenSearch, fire notifications, or maintain aggregates. This is how search stays fresh without dual-writes — and dual-write inconsistency is a trap they may explicitly dangle.
  • OpenSearch is an index, not a database: documents are analyzed (tokenized, lowercased, stemmed) into an inverted index — term → posting list — which is why "contains word" is instant here and a table scan there. Relevance scoring (BM25), filters vs queries, aggregations for facets ("12 results in Footwear, 4 in Apparel"), and k-NN vector search for the AI bullet. It's rebuildable from the source of truth — treat losing it as an inconvenience, not a disaster.
  • The consistency sentence to volunteer: stream projection means search lags writes by a moment — fine for a creation tool, and you say so: "search is eventually consistent by a second or two; the asset detail page reads DynamoDB directly, so the truth is never stale."

How is data modeling in DynamoDB backwards from Postgres?

Relational: model entities normally, express queries later in SQL — the engine figures out joins. DynamoDB: enumerate every access pattern first, then build keys (and GSIs) so each is one Query; denormalize freely because storage is cheap and joins don't exist. The cost of the trade: ad-hoc questions you didn't design for need a new index or an export — say that honestly and you've given the complete answer.

Design keys for "all assets in a project, newest first".

PK = PROJECT#<id>, SK = <ISO timestamp>#<assetId> (the id suffix breaks timestamp ties and keeps keys unique). Query the PK with ScanIndexForward=false, Limit=N — one request, already sorted, paginated by LastEvaluatedKey. Follow-up they like: "and by status?" — a GSI whose PK is PROJECT#id#status, or an SK prefix like STATUS#review#ts, depending on whether status filtering is the common case.

GSI vs LSI — and which do you reach for by default?

GSI: any new PK/SK, own provisioned capacity, eventually consistent reads, add anytime — the workhorse. LSI: same PK with an alternate SK, strongly consistent reads possible, but only creatable with the table and it caps that partition's item collection at 10GB. Default to GSIs; reach for an LSI only when strong consistency on the alternate sort actually matters. Bonus point: GSIs need their own capacity thought — a hot GSI throttles writes to the base table.

What's a hot partition, how would you see it, and how do you fix it?

One partition key receiving traffic beyond a partition's ~3,000 RCU/1,000 WCU — think a "GLOBAL" counter or one giant project everyone hammers. You see throttling (ProvisionedThroughputExceeded) while table-level capacity looks fine; CloudWatch contributor insights names the key. Fixes: better key design (spread by natural dimension), write sharding (suffix #0–#9, fan-in on read), or a cache in front for hot reads. For an internal tool, also honestly: "at hundreds of users this may never trigger — but the design habit is free."

Why not just search DynamoDB? And why not make OpenSearch the primary store?

DynamoDB retrieves by key; "name contains 'mesh', tagged 2019, sorted by relevance" would be a full Scan plus client-side filtering — wrong tool. OpenSearch answers exactly that via the inverted index, plus facets and fuzziness. But it's not a system of record: no conditional-write transactions, mapping changes force reindexes, and its durability model assumes you can rebuild. The architecture sentence: DynamoDB is truth, OpenSearch is a derived, rebuildable projection — stream-fed, eventually consistent, disposable.

Walk the sync pipeline from a metadata edit to it being searchable.

Write hits DynamoDB → Streams records it (ordered per item) → a Lambda batch-consumes, transforms items to search documents, bulk-upserts into OpenSearch (idempotent by document id = asset id, so replays are safe) → visible in search within seconds. Failure honesty: DLQ on the stream consumer, and a periodic full-reindex job as the backstop that also enables mapping changes. Never dual-write from the API — the two stores WILL drift, and naming that anti-pattern unprompted is the flex.

How do you paginate a big result set — and why not offset?

DynamoDB hands back LastEvaluatedKey; you return it (opaquely encoded) as a cursor the client echoes to continue — stable under inserts, cost proportional to the page. Offset pagination re-reads and discards N rows per page (and shifts under concurrent writes) — DynamoDB doesn't even offer it, which is a hint about its cost elsewhere. Same cursor shape goes in your API design (API topic) — one consistent story across rounds.

Two designers edit the same asset's metadata simultaneously. Protect it.

Optimistic locking: items carry a version number; updates send ConditionExpression version = :expected and increment it; the loser gets ConditionalCheckFailed and the app refetches-and-merges or prompts. Cheap, no locks held, perfect for low-contention internal tools. If a change must span multiple items atomically, TransactWriteItems (up to 100 items) — but reach for it sparingly and say why: transactions cost double and most flows don't need them.

What does "API-first" change about how a team ships, concretely?

Order of operations: contract designed and reviewed with consumers first, mock server generated from it so frontend and backend build in parallel, types generated so drift is a compile error, and contract tests in CI so the spec stays true. Culturally: breaking the contract becomes a governance event, not a Tuesday. Contrast to code-first (the doc describes whatever shipped) and you've defined it by its opposite — which reads as experience.

PUT vs PATCH vs POST — the thirty-second version.

PUT replaces the whole resource at a known URL — idempotent, same request twice = same state. PATCH applies a partial change — not automatically idempotent (an increment run twice…), design accordingly. POST creates or triggers under the server's control — not idempotent, so retry-able clients send an Idempotency-Key the server dedupes on. The word "idempotent" appearing three times in your answer is not a bug; it's the theme of this whole stack.

Why cursor pagination over page numbers — especially here?

Offset pages shift when rows are inserted mid-scroll (skips and duplicates), and cost grows with depth since the store re-reads and discards. Cursors ("everything after this key") are stable under writes and constant-cost — and DynamoDB literally hands you the cursor as LastEvaluatedKey, so the API shape falls out of the storage engine. Encode it opaquely (base64) so clients can't build dependencies on its internals.

How do you evolve an API that other Nike teams already consume?

Additive by default: new optional fields and endpoints break nobody (consumers must tolerate unknown fields — say "tolerant reader"). Breaking changes: new version, both live in parallel, deprecation policy with dates, and usage telemetry per consumer so you chase the actual laggards instead of guessing. The differentiator sentence: "I treat removing a field like removing a public function — semver discipline, applied to HTTP."

Design auth for an internal creation tool at a global company.

SSO through the corporate IdP via OIDC — nobody makes a password for an internal tool. The SPA gets short-lived tokens (rotating refresh); API Gateway's authorizer verifies signature and claims before Lambda runs; fine-grained authorization (who can approve assets in project X) lives in the service against a roles/permissions model. Log identity on every mutation for audit. Close with the UI/API rule: hiding the button is UX; the API check is security.

When would you split a capability into its own service — and when not?

Split when team ownership, deploy cadence, scaling profile, or data isolation genuinely diverge — search indexing and asset CRUD are a real example (different load, different failure tolerance). Don't split for architectural fashion: every boundary adds a network hop, versioned contract, and distributed-failure mode. "I'd start modular in one deployable with hard internal boundaries, and split along the seams that prove painful" — the modular-monolith answer, delivered unapologetically, is a senior marker in 2026.

Where do async APIs fit — not everything is request/response.

Long work (asset processing) returns 202 + a status URL or pushes progress via events; cross-capability facts publish to EventBridge (AssetApproved) so consumers subscribe instead of being called; webhooks/event feeds for external integrators. Contract discipline applies to events too — schema-versioned payloads (EventBridge schema registry), at-least-once delivery documented so consumers dedupe. "Events are part of the API surface" ties this topic to the Step Functions one, and interviewers reward the cross-reference.

What makes an error response good?

Stable machine code the client can switch on, a human-safe message with no stack traces or table names, a correlationId that joins client report to server logs, and the right status class (4xx you-fix vs 5xx we-fix, 429 with Retry-After). Consistency across every endpoint matters more than any single field — consumers write ONE error handler. Mentioning that validation errors list per-field details (422 with an errors array) shows you've been on the consuming side.

How does Vue's reactivity actually differ from React's render model?

Tradeoff to volunteer: Vue's model means less manual optimization; React's means plainer JS semantics (no proxy edge cases). Bonus sentence: computed returns a read-only ref, so the same .value rules apply.

Translate: useEffect for data fetching → Vue. What improves, what to watch?

// the idea

  • The event lifecycle has three phases: capture (window → target, listeners with capture:true), target, bubble (target → window — where most listeners live). stopPropagation halts the walk; preventDefault cancels the browser's default action — different tools, commonly confused, and the confusion is a favorite probe. currentTarget is where your listener sits; target is what was actually hit.
  • Delegation is the pattern the phases exist for: one listener on the container, dispatch by e.target.closest('[data-action]') — survives re-renders, scales to any list length, one binding instead of thousands. Frameworks do a version of this for you; knowing the mechanism is what "working knowledge" means.
  • The observer family replaced polling: IntersectionObserver (lazy-load, infinite scroll sentinels, "seen" analytics), ResizeObserver (component-level response), MutationObserver (third-party DOM watching). Async, engine-scheduled, none of the per-scroll-tick main-thread cost of the listeners they replaced.

Long tasks drop frames; transform/opacity animate on the compositor (cheap) while width/top force layout (expensive); interleaved reads and writes of layout properties cause thrashing — batch reads, then writes, in requestAnimationFrame. Off-main-thread: web workers for compute (no DOM), and the honest note that postMessage serialization isn't free.
  • Network-ish platform APIs worth naming: fetch + AbortController (cancel stale searches — the autocomplete answer), navigator.sendBeacon (analytics on unload), Page Visibility (pause polling in hidden tabs), storage tiers (cookie/localStorage/IndexedDB — sync vs async, sent vs not), History API (what SPA routers wrap), BroadcastChannel (cross-tab sync for a tool people keep open in five tabs).

Walk a click through the event lifecycle.

The browser computes the propagation path, then walks it three ways: capture from window down to the target (only capture:true listeners fire), the target phase at the element itself, then bubble back up to window — where most handlers live, and what delegation exploits. stopPropagation ends the walk (stopImmediatePropagation also skips same-node listeners); preventDefault cancels the default action (navigation, submit) without affecting propagation. Distinguishing those two crisply is usually the entire point of the question.

Why is event delegation still worth knowing inside a framework?

Mechanically: one container listener + closest() dispatch means constant memory for unbounded lists, and handlers that survive DOM replacement — no rebinding after re-render. Inside frameworks: it's what your framework is doing conceptually, it's the escape hatch for content the framework doesn't own (CMS HTML, portals, third-party embeds), and it shows in interviews as platform fluency rather than framework dependence. Delegation caveat worth one sentence: events that don't bubble (focus, blur) need capture-phase delegation instead.

Type-ahead search: what goes wrong with the naive version, and what's the complete fix?

Naive: fetch per keystroke — request storms, and responses race so "me" can render after "mesh" (stale wins). Complete: debounce ~300ms (only the pause matters), AbortController to cancel in-flight on each new request (the race disappears at the source), cache by normalized query, min-length guard, and aria-live on the results count so the a11y floor holds. That's four platform primitives and zero libraries — which is precisely the JD's "browser APIs" bullet in action.

IntersectionObserver vs a scroll listener — why did the platform bother?

A scroll listener fires on the main thread per tick, and answering "is it visible?" forces getBoundingClientRect — which forces layout, per event: the jank generator. IntersectionObserver inverts it: the engine computes intersections off the hot path and calls you asynchronously with thresholds and rootMargin ("start loading 200px early") built in. Use cases to rattle off: image lazy-load, infinite-scroll sentinel, impression analytics, scrollspy — this page's own nav uses one.

The tool feels sluggish when dragging assets around. Diagnose, then fix.

Profile a drag in DevTools Performance first — the flame chart says which of three stories it is: long JS tasks in the move handler (fix: do nothing per-event but record position; render in requestAnimationFrame), layout thrashing from reading offsetTop/rect between style writes (fix: batch reads then writes), or paint storms from animating layout properties (fix: transform: translate, will-change sparingly). The structure — measure, attribute, then the matching fix — is the answer; the specific fix is just the payoff.

Where does each kind of client-side data live, and why?

Cookies: tiny, sent with every request, httpOnly-able — session/auth concerns, mostly set by the server. localStorage: small synchronous KV that survives restarts — preferences, theme (this page uses it); never tokens if XSS is in your threat model. sessionStorage: per-tab scratch. IndexedDB: async and large — drafts, offline queues, cached search results for a tool designers keep open all day. Axes to name: sync vs async, sent-to-server vs not, size — then match the data to the axes instead of memorizing pairings.

LCP (main content painted, ≤2.5s), INP (worst interaction latency, ≤200ms), CLS (layout stability, ≤0.1) — Google's field metrics for user experience. function debounce(fn, wait) {
  let t;
  return function (...args) {            // not an arrow: callers' `this` flows in
    clearTimeout(t);
    t = setTimeout(() => fn.apply(this, args), wait);
  };
}

async function retryWithBackoff(fn, retries = 3, base = 200) {
  for (let attempt = 0; ; attempt++) {
    try { return await fn(); }
    catch (err) {
      const retriable = !(err.status >= 400 && err.status < 500);
      if (!retriable || attempt === retries) throw err;   // never swallow
      const delay = base * 2 ** attempt * (0.5 + Math.random() / 2); // jitter
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

async function pool(jobs, limit = 5) {
  const results = new Array(jobs.length);
  let next = 0;
  async function worker() {
    while (next < jobs.length) {
      const i = next++;                  // single-threaded JS: no race here
      results[i] = await jobs[i]().catch(e => ({ error: e }));
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, jobs.length) }, worker));
  return results;                        // order preserved by index
}

// warm-up 1 of 4 — the symptom names the limit

Designers report: uploads of small images work, but every 3D model over a few MB fails instantly through the asset API (API Gateway → Lambda → S3). Which fix matches the actual constraint?

Why: "Works small, fails at a few MB, instantly" is a payload-size symptom, not a speed one — the synchronous invocation path caps the request body (~6MB through Lambda), and no configuration raises it. Memory (A) scales CPU and RAM, not payload; it's the most commonly pulled wrong lever. Compression (C) buys one factor-of-something and dies on the next texture-heavy model — a limit you can outgrow again isn't fixed. Timeout (D) mismatches the symptom: timeouts fail slowly, and these fail instantly. The presigned-URL pattern is the architectural answer AWS designed for exactly this — "pass keys, not bytes" — and recognizing when a limit is a design signal rather than a quota request is the warm-up's actual lesson.

// warm-up 2 of 4 — computed vs watch is a shape question

Two needs in a Vue component: (1) filteredAssets derived from assets + statusFilter, (2) calling the search API whenever query changes. Which pairing is right, and why?

Why: The dividing line is pure derivation vs side effect — the same line as useMemo vs useEffect in your React years. computed is a cached pure function: Vue tracks what it reads and recomputes only on change; putting an async API call inside one breaks both the purity contract and your ability to debounce/cancel it. watch exists for effects: explicit source, async body welcome, cleanup possible. A (watch everything) rebuilds computed's caching by hand and litters state with intermediate variables; D's template method re-runs on every render — the freshness it promises is just wasted work, since computed is never stale, only lazy. When an interviewer asks this, they're checking you can classify code by its nature, not recite the API table.

// warm-up 3 of 4 — keys are queries in disguise

Requirement: "list a project's assets, newest first, 50 at a time." Which DynamoDB shape serves it in a single efficient Query?

Why: Read the requirement as a query plan: "a project's assets" names the partition (all of them co-located under PROJECT#id), "newest first" names the sort key (range keys are stored ordered — descending reads are free), "50 at a time" names Limit + cursor. Option A shards assets randomly across partitions — listing a project would mean a full Scan. C's filter expression is the classic trap: filters run after the read — you pay for (and wait on) every scanned item, then discard. D works at toy scale and decays linearly — fetching 10,000 items to show 50 — plus pagination breaks, since you can't cursor into app-sorted data. "The sort key does the ordering" is the whole DynamoDB catechism in one line.

// warm-up 4 of 4 — which claim survives the follow-up?

Four claims about a clickable <div onclick="…"> vs a <button>. Which one would survive an interviewer's follow-up?

Why: The follow-up that kills A and B is one keyboard: Tab to it (divs aren't focusable), press Space (nothing happens — role="button" changes what's announced, not what works; behavior needs tabindex="0" plus keydown handling for Enter AND Space, with Space's scroll-default suppressed). That gap — ARIA describes, it never implements — is among the most-probed a11y misconceptions in frontend interviews, and this JD names accessibility explicitly. D inverts the cost: type="button" and one CSS reset line undo the defaults, which is nothing next to reimplementing focus and activation semantics per clickable div. The portable rule: "if it does something, it's a button; if it goes somewhere, it's a link; divs are for grouping."

// apply 1 of 4 — two workflows, two flavors

Two Step Functions workflows: (1) per-upload processing — seconds long, ~50k/month, steps are idempotent; (2) design approval — waits on humans for days, needs an audit trail. Which pairing do the constraints force?

Why: This is elimination by hard constraint, not preference: Express executions cap at 5 minutes, so the approval workflow can't run there at all — B and D die on arithmetic before any judgment is needed. Between A and C, the volume workflow decides it: 50k short executions/month on Standard pays per state transition for exactly-once orchestration the pipeline doesn't need (its steps are idempotent — replays are free by design), while Express's duration pricing is built for exactly this shape. D's "more reliable tier" reasoning is the tell to train away: Standard vs Express isn't a quality ladder, it's two different execution-semantics contracts. Matching guarantees to requirements — not "better vs worse" — is the whole question.

// apply 2 of 4 — keeping two stores honest

Asset metadata lives in DynamoDB; search runs on OpenSearch. Which write architecture keeps them from drifting apart?

Why: Dual writes (A) fail on the gap between them: crash after write one, and the stores disagree forever with nothing to reconcile them — under retries it also double-applies. B's "rollback" is a distributed transaction hand-rolled in a try/catch: the rollback itself can fail, and now you're worse off with more code. D inverts the trust hierarchy — OpenSearch trades away transactional guarantees to be a great index; mapping changes force reindexes, which is survivable for a projection and catastrophic for a system of record. The stream pattern wins because it changes the shape of the problem: one committed log, consumed asynchronously, idempotently, with replay as the universal repair tool. "Truth in one place; everything else is a rebuildable view" — that sentence generalizes to caches, materialized views, and half of system design.

// apply 3 of 4 — the deploy that hurt, autopsied

A Lambda deploy shipped a bug: 30 minutes of elevated 5xx before someone noticed a dashboard and manually redeployed the old zip. Which change most directly prevents the next one?

Why: Separate two failures: the bug shipping (prevention) and the bug running at 100% for 30 minutes (containment). More tests (A) improves prevention but has an asymptote — some bugs only exist against production traffic and data, so a plan that requires perfect pre-prod detection is a plan to have this incident again. The canary directly attacks containment: exposure starts small, detection is an alarm rather than a human's peripheral vision, and rollback is an automatic alias repoint measured in seconds. C adds a slow human gate that misses the same production-only bugs; D just schedules the incident politely. The senior deploy doctrine in one line: assume some bugs reach prod; engineer the blast radius and the recovery, not just the gate.

// apply 4 of 4 — one listener or ten thousand

A review queue renders up to 10,000 asset rows, each with approve/archive buttons. The current code attaches two listeners per row and rebinds after every re-render. What's the grounded fix?

Why: The problem is structural — listener count scaling with row count, plus rebinding churn per render — so the fix must change the structure: delegation exploits the bubble phase to make listener count O(1) in list size. The distractors all misapply real concepts: passive (B) is specifically about scroll-blocking events (touchmove/wheel) — it tells the browser "I won't preventDefault" so scrolling needn't wait; it does nothing for click volume. Capture (C) changes when in the propagation walk a handler runs — the ordering of a walk measured in microseconds, not responsiveness. Debounce (D) treats event frequency, but the cost here exists before anyone clicks at all. Each wrong option is a perf word attached to the wrong mechanism — exactly the confusion the JD's "working knowledge of event lifecycles" phrase exists to screen out.

// stretch 2 of 4 — the back-of-envelope they'll respect

The asset pipeline: ~50,000 uploads/month, each triggering ~5 Lambda invocations averaging 2 seconds. Someone objects: "won't we hit Lambda's ~1,000 default concurrency limit?" What does the arithmetic say?

Why: The estimation chain: 50k × 5 = 250k invocations/month; a month ≈ 2.6M seconds, so ~0.1 invocations/second; concurrency ≈ arrival rate × duration = 0.1 × 2s = 0.2. Even bursting 100× (all uploads in business hours, spikes on deadline days) gives ~20 concurrent — noise against 1,000. Option A commits the unit error the question exists to catch: comparing a monthly count to a simultaneity limit. C is learned helplessness dressed as rigor — load tests refine estimates, they don't replace the ability to make one, and "can't be estimated" fails the interview's actual test. D invents serialization Step Functions doesn't impose (Map states fan out concurrently by design). Little's law at cocktail-napkin precision — rate × duration = concurrency — settles half of all capacity arguments; carry it in.

// stretch 3 of 4 — trace the reactivity, not the vibes

Vue 3: const state = reactive({ count: 0 }); let { count } = state; count++; — then a template renders {{ state.count }}. What does the UI show, and why?

Why: Mechanism over memory: Vue 3's reactivity is a Proxy wrapping the object — get/set traps fire when you touch state.count through state. Destructuring is an ordinary JavaScript read: it fires the get trap once, hands you the primitive 0, and from then on count is just a local number with no tether — JS has no "live bindings" for destructured values (A invents one) and no proxy can follow a primitive (B misunderstands what "deep" reactivity deepens — nested objects, not extracted values). D fabricates an error mechanism; the code runs fine, which is what makes this bug nasty — it fails silently in exactly the way a React engineer's spread-happy habits invite. The fixes fall out of the mechanism: toRefs() wraps each property in a ref (an object, so the tether survives), or skip reactive() for refs from the start. If you can narrate THIS trace, the "why bet on you for Vue" question answers itself.

The day-of playbook

Six moves that apply to every round of this loop. Read it the morning of, not the night before.

01 · speak the JD's language back

"API-first", "capabilities", "idempotent", "modular" — their own vocabulary, used naturally, tells the panel you understood the assignment. Never recite it; deploy it where it belongs.

02 · every answer ends with a tradeoff

"Express Step Functions here — cheaper at volume, and we accept at-least-once because the steps are idempotent." A decision with its price is engineering; without it, it's fashion. One sentence, unprompted, every time.

03 · size the problem before solving it

"50k uploads a month is about 2 a minute — so this is an operability problem, not a throughput one." Thirty seconds of honest arithmetic reframes the entire question and is the rarest habit in the room.

04 · anchor in what you shipped

"…and we did exactly this for our uploads pipeline" is double-weighted evidence. Mine your own systems all interview — hypotheticals are half-price.

05 · own the Vue gap before they find it

If your Vue is crossover-level, say so with a plan: "React-deep, Vue-conversant — here's my two-week ramp, and here's the dictionary I already speak." Honesty with a plan beats bluffing every time.

06 · hand the wheel back

"Want me deeper on the data model, or shall I cover failure handling?" Checking in respects the clock, shows meeting-running instincts, and gets the follow-ups you want. Monologues lose rounds that knowledge won.
