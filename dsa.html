Big O notation

One question every interviewer asks: "what's the complexity?" Big O is how you answer — it describes how work grows as input grows.

YOU ALREADY KNOW THIS

You've felt the difference between a MongoDB query that hits an index and one that scans the whole collection. That's O(log n) vs O(n). Interviews just want that production instinct, with names attached.

// the three rules

  • Drop constants. Looping twice is O(2n) → still O(n). Big O cares about the shape of growth, not the exact count.
  • Keep only the dominant term. O(n² + n) → O(n²). At scale, the biggest term is all that matters.
  • Different inputs get different letters. Looping over two separate arrays is O(a · b), not O(n²). Saying this earns instant credibility.
the-whole-idea.js
// O(n) — scans elements one by one until it finds a match
const user = users.find(u => u.id === id);

// O(1) — jumps straight there, no matter how big the map gets
const sameUser = usersById.get(id);

// growth at n = 1,000 items

// space complexity, in one line

  • Same notation, applied to extra memory you allocate (the input itself doesn't count). A lookup Map over the input is O(n) space; two pointer variables are O(1).

// warm-up — name the Big O, then check

users.find(u => u.id === id)

O(n) — worst case it checks every element before finding (or not finding) a match.

usersById.get(id)

O(1) — hash lookup. The map's size is irrelevant.

a.filter(x => b.includes(x))

O(a · b) — .includes() is a hidden loop inside a loop. Classic accidental quadratic; a Set fixes it.

[...arr].sort((x, y) => x - y)

O(n log n) — the floor for any comparison sort. Say this number whenever you sort.

while (n > 1) n = Math.floor(n / 2)

O(log n) — anything that halves the problem each step is logarithmic. Remember this shape; it's binary search.

Arrays & the two-pointer pattern

You know arrays. What's new is knowing what each method costs, and the pincer trick that turns O(n²) pair-hunting into O(n).

YOU ALREADY KNOW THIS

Every users.map(...) in a route handler is an O(n) traversal. Two pointers is just traversing from both ends at once — the same walk, half the wasted work.

// what your daily methods cost

  • O(1): arr[i], push, pop.  O(n): shift/unshift (everything re-indexes), includes, indexOf, find, splice.  O(n log n): sort.
  • Two pointers, opposite ends: l starts left, r starts right; move them toward each other based on a rule. On sorted input, this replaces a nested loop.
  • Reader/writer variant: a slow pointer marks where to write, a fast one scans ahead — the standard move for "remove/compact in place".
  • "In place" means O(1) extra space. Say those words out loud when you do it — interviewers are listening for them.
two-pointers.js
// Is the string a palindrome? O(n) time, O(1) space.
function isPalindrome(s) {
  let l = 0, r = s.length - 1;
  while (l < r) {
    if (s[l] !== s[r]) return false; // mismatch — done early
    l++;
    r--;
  }
  return true;
}

// spot it in the wild

  • "sorted array" + "find a pair that sums to…"two pointers from the ends
  • "palindrome", "reverse in place"two pointers from the ends
  • "remove duplicates / move zeroes in place"slow writer + fast reader
  • "max area / container between lines"two pointers, move the smaller side

Sliding window

A moving subarray with a left and right edge. Grow the right side every step; shrink the left only when the window breaks a rule.

YOU ALREADY KNOW THIS

express-rate-limit keeps a rolling window of request timestamps per IP: new ones enter on the right, expired ones fall off the left. Same mechanic, same efficiency.

// the idea

  • Two flavors: fixed size k ("max sum of any 3 consecutive days") and dynamic ("longest substring such that…"). Dynamic is the one interviews love.
  • Why it's O(n): each element enters the window once and leaves once. The inner while looks nested but can only run n times total.
  • Pair it with a Set or Map so the window always knows what it contains — that's the bridge to the next topic.
  • It only works on contiguous runs. If the problem allows picking scattered elements, the window is the wrong tool.
sliding-window.js
// Longest substring with no repeated characters. O(n).
function lengthOfLongestSubstring(s) {
  const seen = new Set();
  let left = 0, best = 0;

  for (let right = 0; right < s.length; right++) {
    // rule broken (duplicate)? shrink from the left until it's fixed
    while (seen.has(s[right])) {
      seen.delete(s[left]);
      left++;
    }
    seen.add(s[right]);
    best = Math.max(best, right - left + 1);
  }
  return best;
}

// spot it in the wild

  • "contiguous subarray / substring"sliding window
  • "longest / shortest … with at most k …"dynamic window
  • "every window of exactly size k"fixed window
  • "minimum window containing all of X"window + need/have counters

Hash maps & sets

The single highest-ROI tool in interviews. The core trade: spend O(n) memory to make every lookup O(1) — and delete a nested loop.

YOU ALREADY KNOW THIS

This is {}, new Map(), and every Redis GET key you've ever cached. You reach for these daily to avoid slow lookups — interviews reward exactly that reflex.

// the idea

  • The reflex: any time you're about to scan an array inside another scan, ask "can a Map/Set remember this for me?" Nine times out of ten: yes, and O(n²) becomes O(n).
  • Map vs {}: use Map when keys aren't strings or you'll add/remove a lot; Set for pure "have I seen this?"; plain objects are fine for string keys.
  • Frequency counter: one pass to count items into a Map, then compare counts instead of re-scanning. Solves most anagram/duplicate problems.
  • Check-then-store: the one-pass idiom below — look for your complement before inserting yourself. Memorize it; it's the most-asked question on Earth.
two-sum.js
// The most famous interview question. O(n) time, O(n) space.
function twoSum(nums, target) {
  const seen = new Map(); // value -> index

  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i); // store AFTER checking — no self-match
  }
}

// spot it in the wild

  • "have I seen this before?", "contains duplicate"Set
  • "count occurrences", "valid anagram"frequency Map
  • "pair summing to target" (unsorted)Map of complements
  • "group items by some property"Map of arrays, computed key

Stacks & queues

Two disciplines for one pile of items: last-in-first-out (stack) or first-in-first-out (queue). The discipline is the whole data structure.

YOU ALREADY KNOW THIS

The call stack you scroll in DevTools is a stack — that's why it's named that. The event loop's task queue, where your setTimeout callbacks wait, is a queue. You debug both weekly.

// the idea

  • Stack in JS: a plain array with push/pop — both O(1). Reach for it when you must remember the most recent unfinished thing: open brackets, undo history, nested calls.
  • Queue in JS: arr.shift() is O(n). In an interview, say so — then either use a moving index pointer instead of shifting, or mention a linked list makes dequeue O(1). Saying it is the point.
  • Queues power BFS (tomorrow): anything processed in arrival order or "level by level".
  • Monotonic stack: keep the stack sorted by popping smaller items as you push. It cracks every "next greater element" question in O(n) — know the name even if you only skim it.
valid-parentheses.js
// Are the brackets balanced and properly nested? O(n).
function isValid(s) {
  const stack = [];
  const pairs = { ')': '(', ']': '[', '}': '{' };

  for (const ch of s) {
    if (!pairs[ch]) stack.push(ch);                   // opener — remember it
    else if (stack.pop() !== pairs[ch]) return false; // closer must match the LAST opener
  }
  return stack.length === 0; // nothing left dangling open
}

// spot it in the wild

  • "valid brackets", "matching pairs", "nesting"stack
  • "undo", "back button", "most recent first"stack
  • "next greater / next warmer element"monotonic stack
  • "process in arrival order", "level by level"queue

Linked lists

Nodes holding a value and a pointer to the next node. The exact inverse of an array: slow to reach a position, instant to splice once you're there.

YOU ALREADY KNOW THIS

Express middleware: each layer holds a reference to the next and calls next() to walk the chain. You've been writing linked-list traversal for years — React Fiber is one too.

// the idea

  • A node is just { val, next }. No indexes — reaching position i costs O(n), but inserting or removing at a known spot is O(1). That trade is the whole reason it exists.
  • Fast & slow pointers: fast moves two steps, slow moves one. When fast hits the end, slow is at the middle. If they ever meet, the list has a cycle (Floyd's algorithm).
  • Dummy head: const dummy = new ListNode(0, head) then work from dummy and return dummy.next. Deletes the entire class of "what if I modify the first node" edge cases.
  • Draw boxes and arrows on paper before coding. Everyone does — pointer bugs are visual bugs.
reverse-list.js
class ListNode {
  constructor(val, next = null) {
    this.val = val;
    this.next = next;
  }
}

// Reverse in place — THE classic. O(n) time, O(1) space.
function reverseList(head) {
  let prev = null, curr = head;
  while (curr) {
    const next = curr.next; // 1. save the rest of the list
    curr.next = prev;       // 2. flip this arrow backwards
    prev = curr;            // 3. step both pointers forward
    curr = next;
  }
  return prev; // prev ends up as the new head
}

// spot it in the wild

  • "find the middle"fast & slow pointers
  • "is there a cycle?"fast & slow — do they meet?
  • "O(1) get + put with eviction (LRU)"Map + doubly linked list

Recursion

A function that calls itself on a smaller piece of the problem, plus a base case that stops it. Trees, graphs, backtracking, and DP all run on this.

YOU ALREADY KNOW THIS

A <Comment /> component that renders child <Comment />s. JSON.stringify walking a nested object. A script recursing through directories. You've shipped recursion — you just called it "handling nested data".

// the idea

  • Two mandatory parts: a base case (when to stop) and a recursive case (same problem, smaller input). Forget the base case and you get Maximum call stack size exceeded — an error you've definitely met.
  • The leap of faith: assume the recursive call already works correctly for smaller input, and reason about one level only. Trying to mentally trace five levels deep is how people get lost.
  • Every pending call sits on the call stack, so depth = space cost: n-deep recursion is O(n) space even if you allocate nothing.
  • If the same subproblem gets recomputed (fib!), cache it in a Map — that's memoization, and it's the door into dynamic programming tomorrow.
recursion.js
// Every recursive function = base case + a smaller version of itself
function sumNested(arr) {
  let total = 0;
  for (const item of arr) {
    total += Array.isArray(item)
      ? sumNested(item) // recursive case: a smaller subproblem
      : item;           // base case: a plain number
  }
  return total;
}

sumNested([1, [2, [3, 4]], 5]); // 15 — the same walk JSON.stringify does

  • "nested / arbitrarily deep structure"recursion
  • defined by smaller versions of itself (fib, pow)recursion + memo Map
  • "explore every option / combination"recursion → backtracking (day 2)

Binary search

On anything sorted, halve the search space every step. A million items → found (or ruled out) in ~20 checks.

YOU ALREADY KNOW THIS

git bisect finds one bad commit among thousands in ~a dozen checkouts — that's binary search. MongoDB's B-tree indexes make the same halving move on every query you've optimized.

// the idea

  • Requirement: the search space must be sorted — or at least monotonic (all falses, then all trues).
  • Template discipline: lo <= hi, compute mid, move lo = mid + 1 or hi = mid - 1. This exact shape can't infinite-loop. Memorize it once, reuse it forever.
  • The pro move — search the answer, not the array: "minimum speed / capacity / days that satisfies…" — if feasibility flips once from false to true, binary search finds the boundary. This unlocks a whole question family.
  • Off-by-ones are where everyone dies. Trace a 2-element array by hand before you say "done".
binary-search.js
function binarySearch(nums, target) {
  let lo = 0, hi = nums.length - 1;

  while (lo <= hi) {
    const mid = (lo + hi) >> 1; // fast Math.floor((lo + hi) / 2)
    if (nums[mid] === target) return mid;
    if (nums[mid] < target) lo = mid + 1; // answer lives right of mid
    else hi = mid - 1;                    // answer lives left of mid
  }
  return -1; // not present
}

  • "must run in O(log n)"they're telling you: binary search
  • "rotated sorted array"binary search, pick the sorted half
  • "minimum X that satisfies…"binary search on the answer

Trees, BFS & DFS

Nodes branching into children. Two ways to walk one: deep-first on the call stack (DFS), or wide-first on a queue (BFS). This pair carries the whole interview.

YOU ALREADY KNOW THIS

You live inside trees: the DOM, your React component tree, the file system, a Mongo B-tree index. React reconciliation is literally an algorithm that diffs two trees. document.querySelector? A DFS.

// the idea

  • Vocabulary (interviewers use these): root, leaf, depth, height, subtree. Binary tree = at most two children. BST = everything left < node < everything right — which makes inorder traversal come out sorted.
  • DFS = recursion. Preorder/inorder/postorder just name when you visit the node — but ~90% of problems reduce to "recurse into both children, combine the results" like maxDepth below.
  • BFS = a queue. Process a whole level before the next. It's the answer to anything phrased "level by level" or "minimum steps to reach".
  • Most tree answers are 5–8 lines of recursion. The real skill is yesterday's leap of faith: trust that maxDepth(root.left) already returns the right number.
tree-traversal.js
class TreeNode {
  constructor(val) {
    this.val = val;
    this.left = this.right = null;
  }
}

// DFS — recursion rides the call stack. O(n) time, O(height) space.
function maxDepth(root) {
  if (!root) return 0; // base case: empty subtree
  return 1 + Math.max(maxDepth(root.left), maxDepth(root.right));
}

// BFS — a queue processes level by level. O(n).
function levelOrder(root) {
  if (!root) return [];
  const result = [], queue = [root];

  while (queue.length) {
    const level = [];
    for (let i = queue.length; i > 0; i--) { // exactly one level's worth
      const node = queue.shift();
      level.push(node.val);
      if (node.left) queue.push(node.left);
      if (node.right) queue.push(node.right);
    }
    result.push(level);
  }
  return result;
}

Heaps / priority queues

A structure with one job: hand you the smallest (or largest) item instantly, and stay cheap to update. The tool for anything "top K".

YOU ALREADY KNOW THIS

BullMQ priority jobs: the highest-priority job pops out next without re-sorting the whole backlog on every insert. That efficient "always know the extreme" trick is exactly what a heap is.

// the idea

  • A binary tree flattened into an array, where every parent ≤ its children (min-heap). Only the extreme is instantly visible — the rest is loosely ordered, and that looseness is why updates stay O(log n).
  • When: you repeatedly need the min/max while items keep arriving. Re-sorting each time is O(n log n) per insert; a heap does it in O(log n).
  • The Top-K template: keep a min-heap capped at size k — push each item, pop whenever size exceeds k. What survives is the k largest. O(n log k), and it beats sorting.
  • JS has no built-in heap. In the interview say: "in production I'd use a library — want me to implement one or simulate with sorting?" Naming the gap is a senior move; the class below is your implementation.
min-heap.js
class MinHeap {
  constructor() { this.a = []; }
  size() { return this.a.length; }
  peek() { return this.a[0]; }

  push(v) {
    this.a.push(v);
    let i = this.a.length - 1;
    while (i > 0) {                        // bubble the new value up
      const parent = (i - 1) >> 1;
      if (this.a[parent] <= this.a[i]) break;
      [this.a[parent], this.a[i]] = [this.a[i], this.a[parent]];
      i = parent;
    }
  }

  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.a.length) {                   // sink the moved value down
      this.a[0] = last;
      let i = 0;
      while (true) {
        let s = i;
        const l = 2 * i + 1, r = 2 * i + 2;
        if (l < this.a.length && this.a[l] < this.a[s]) s = l;
        if (r < this.a.length && this.a[r] < this.a[s]) s = r;
        if (s === i) break;
        [this.a[s], this.a[i]] = [this.a[i], this.a[s]];
        i = s;
      }
    }
    return top;
  }
}

  • "merge K sorted lists / streams"min-heap of current heads

Graphs

Trees without the rules: nodes connect freely, cycles allowed. Same two traversals as trees — plus one new obligation: track where you've been.

YOU ALREADY KNOW THIS

node_modules is a dependency graph. A "circular dependency detected" warning is cycle detection. Working out migration or build order is topological sort. You've been operating graphs the whole time.

// the idea

  • The one new rule vs trees: cycles exist, so you must keep a visited set or you'll loop forever. That's genuinely the only addition.
  • Step one is always representation: interviews hand you edge pairs or a grid — convert to an adjacency list (node → neighbors) before anything else. Snippet below.
  • Same two traversals: DFS for connectivity, regions, "explore everything"; BFS for shortest path in unweighted graphs — it's the only one that guarantees it.
  • A grid is a graph in disguise. Each cell is a node; its 4 neighbors are edges. Islands, flood fill, mazes — all graph traversal.
graphs.js
// Interviews hand you edges — you build the adjacency list first:
const graph = {};
for (const [a, b] of edges) {
  (graph[a] ??= []).push(b);
  (graph[b] ??= []).push(a); // drop this line if edges are directed
}

// Number of Islands — DFS where the grid IS the graph. O(rows · cols)
function numIslands(grid) {
  let count = 0;

  const sink = (r, c) => {
    if (r < 0 || c < 0 || r >= grid.length ||
        c >= grid[0].length || grid[r][c] === '0') return;
    grid[r][c] = '0';               // mark visited — never revisit
    sink(r + 1, c); sink(r - 1, c); // flood all 4 directions
    sink(r, c + 1); sink(r, c - 1);
  };

  for (let r = 0; r < grid.length; r++)
    for (let c = 0; c < grid[0].length; c++)
      if (grid[r][c] === '1') { count++; sink(r, c); } // new island found

  return count;
}

  • "clone / traverse a network of nodes"BFS or DFS + visited map

Backtracking

DFS over choices instead of nodes: build a candidate decision by decision, and when a branch dead-ends, undo the last choice and try the next one.

YOU ALREADY KNOW THIS

Generating every valid combination of feature flags for a test matrix: set a flag, recurse into the remaining flags, unset it, try the next value. Choose → explore → un-choose.

// the idea

  • The template below is ~90% of every backtracking answer. Per problem, only three things change: what counts as a choice, when you record a result, and when you prune a branch early.
  • One shared path array, mutated with push/pop, copied only when recorded — that's what keeps it fast. Never rebuild arrays per call.
  • Complexity is exponential by nature — O(2ⁿ) subsets, O(n!) permutations. Say that up front; the interviewer knows, and wants to hear that you know.
  • Pruning is the optimization: the moment a partial candidate can't possibly become valid, return early instead of exploring further.
subsets.js
// All subsets — THE template. O(2^n), inherently.
function subsets(nums) {
  const result = [], path = [];

  function backtrack(start) {
    result.push([...path]);              // record a copy of current choices
    for (let i = start; i < nums.length; i++) {
      path.push(nums[i]);                // 1. choose
      backtrack(i + 1);                  // 2. explore with that choice made
      path.pop();                        // 3. un-choose — try the next option
    }
  }

  backtrack(0);
  return result;
}

Dynamic programming

The scariest name for the simplest fix: it's recursion where subproblems repeat, plus a cache. That is genuinely the entire secret.

YOU ALREADY KNOW THIS

useMemo, React.memo, a Redis cache in front of an expensive computation — "never compute the same thing twice" is a pattern you already deploy. DP is that pattern applied to recursion.

// the idea

  • The interview script is the 3-step ladder below: write the brute recursion, point out the repeated subproblems, add a memo. Walking through it out loud is the answer they want.
  • Framework for any 1-D DP — say all three explicitly: (1) define what dp[i] means in plain words, (2) state the transition (how dp[i] is built from earlier answers), (3) state the base cases.
  • Bottom-up tables are the optional flex: same logic, loop instead of recursion, often lets you shrink space to O(1) by keeping only the last couple of values.
  • Realistic 48-hour goal: recognize DP and execute the memoization step cleanly. Hard multi-dimensional DP goes in the "know it exists" bucket — see Safe to Skip.
climbing-stairs.js
// Climbing Stairs: take 1 or 2 steps — how many ways to the top?

// 1) Naive recursion — O(2^n). Recomputes the same inputs forever.
const climbNaive = n => n <= 2 ? n : climbNaive(n - 1) + climbNaive(n - 2);

// 2) Memoized — O(n). The useMemo move: cache the answer by input.
function climbMemo(n, memo = new Map()) {
  if (n <= 2) return n;
  if (memo.has(n)) return memo.get(n);
  const ways = climbMemo(n - 1, memo) + climbMemo(n - 2, memo);
  memo.set(n, ways);
  return ways;
}

// 3) Bottom-up — O(n) time, O(1) space. Roll two values forward.
function climbStairs(n) {
  if (n <= 2) return n;
  let [a, b] = [1, 2];
  for (let i = 3; i <= n; i++) [a, b] = [b, a + b];
  return b;
}

The interview playbook

The algorithm for the interview itself. Interviewers grade the process as much as the code — a clean run through these seven steps with a decent solution beats a silent perfect one every time.

Restate & clarify

Repeat the problem in your own words, then ask: how big is the input? duplicates? negatives? empty? already sorted? Ninety seconds here prevents solving the wrong problem.

Work a tiny example by hand

Four to six elements, on paper or in a comment. If you can't produce the answer manually, you can't code it yet.

Say the brute force + its Big O

Out loud, even when it's obvious: "brute force is nested loops, O(n²)." It's your safety net if time runs out, and it shows structured thinking.

Name the pattern

Scan the trigger words against the pattern matcher: "sorted plus pair-sum — I'll try two pointers." Naming the tool earns points before you've typed a character.

Code it clean

Real names (left, seen, queue), small helper functions, early returns. You write production code every day — let that show.

Trace & test

Walk your example through the code line by line, then hit the edges: empty input, one element, all duplicates. Find your own bug before they do.

State final complexity, unprompted

Time and space. This is the close of the answer — never make them ask.

// javascript-specific gotchas — each one is a free point

.sort() lies by default

It sorts lexicographically: [10, 9, 1].sort() gives [1, 10, 9]. Always pass the comparator: .sort((a, b) => a - b).

no integer division

Use Math.floor(a / b) — there's no int type. The idiom (lo + hi) >> 1 is a fast floor for midpoints.

Map beats {} for non-string keys

Object keys silently coerce to strings. Map preserves key types, tracks .size, and iterates in insertion order.

strings are immutable

You can't edit s[i]. Convert: s.split('') → mutate the array → .join('').

no built-in heap or deque

The sanctioned line: "in production I'd pull a library — here I'll implement it / simulate with sort." Saying it is the senior signal.

default-param memo

function f(n, memo = new Map()) keeps recursive signatures clean — callers never see the cache.

Safe to skip (this weekend)

These appear rarely in product-company interviews and cost more than 48 hours can afford. Know the name and one sentence each — that's enough to stay composed if one appears.

  • Tries (prefix trees) — power autocomplete. If it appears: "prefix lookups — I'd reach for a trie; I can sketch the node shape."
  • Union-Find — near-instant "are these connected?" across many merges. Name-drop it for dynamic-connectivity problems; solve with DFS instead.
  • Dijkstra / weighted graphs — BFS's big sibling for weighted shortest paths (BFS + a min-heap, conceptually). Only study if the role screams graphs.
  • Segment / Fenwick trees — fast range queries. Effectively absent from product interviews. Skip without guilt.
  • Bit manipulation — know the one famous trick: XOR-ing everything finds the single non-duplicate, because x ^ x === 0.
  • Hard multi-dimensional DP — edit distance, 2-D grids. Recognize it, attempt the memoized recursion, and don't pre-grieve: partial credit for a clean setup is real.

Reading is not practicing. Type every snippet, solve with a timer, narrate out loud. Do the two days, then two problems a day until the onsite.
