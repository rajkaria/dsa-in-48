JavaScript under the hood

Closures, scope, this, prototypes, coercion. You use every one of these before your first coffee — this block attaches the vocabulary interviewers listen for.

YOU ALREADY KNOW THIS

Every event handler that reads a variable from the component around it is a closure. Every onClick={() => ...} arrow you write exists because of how this works. You've debugged undefined is not a function enough times to have earned this vocabulary already.

// the idea

  • Types: seven primitives (string, number, bigint, boolean, undefined, symbol, null) plus object. Primitives copy by value; objects copy the reference by value — which is why mutating a "copied" object mutates the original.
  • Coercion: == converts operands before comparing; === never does. The safe rule you can say out loud: always ===, except the idiom x == null to catch both null and undefined.
  • Scope & hoisting: var is function-scoped and hoisted as undefined; let/const are block-scoped and hoisted into the temporal dead zone — alive but unusable until their line runs. const freezes the binding, not the object.
  • Closures: a function keeps a live reference to the scope it was created in, even after that scope's function has returned. It's how debounce timers, event handlers, and module-private state all work — and it's the #1 asked JS question.
  • this is decided at call time, not write time: obj.fn() → obj; plain fn() → undefined in strict mode; new Fn() → the fresh object; fn.call(x) → x. Arrow functions don't have their own this — they capture the enclosing one, which is why they're perfect for callbacks.
  • Prototypes: property lookups walk up the prototype chain until they hit null. class is syntax over exactly this — there are no "real" classes, just objects delegating to objects.

// THE closure question: what does this log?
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));      // 3, 3, 3 — one shared i
}
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));      // 0, 1, 2 — fresh i per loop
}

// closures as private state — say "debounce" and mean it
function debounce(fn, ms) {
  let timer;                              // lives on between calls
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

// `this` is about the CALL, not the function
const user = {
  name: 'Ada',
  hello() { return `hi ${this.name}`; },
};
user.hello();                // 'hi Ada'    — called through user
const f = user.hello;
f();                         // this === undefined (strict) — detached!
f.call(user);                // 'hi Ada'    — this supplied explicitly

// rapid-fire — answer out loud, then reveal

What's a closure — and where have you used one this week?

A function bundled with the lexical scope it was created in, so it can read/write those variables after the outer function returned. Real answer-ender: "our debounced search input — the timer variable lives in a closure."

== vs ===?

== coerces types before comparing ('1' == 1 is true), === compares type + value. Use === everywhere; the one respectable == is x == null. Bonus point: NaN === NaN is false — use Number.isNaN().

What does typeof null return, and why?

'object' — a bug from the first JS engine, kept forever for backwards compatibility. Check null with x === null, never typeof.

var vs let vs const in three sentences?

var: function-scoped, hoisted as undefined, re-declarable — avoid. let: block-scoped, TDZ before its line, reassignable. const: same but the binding can't be reassigned — the object it points at is still mutable.

Is JavaScript pass-by-value or pass-by-reference?

Always pass-by-value — but for objects, the value is the reference. So a function can mutate the object you passed, but reassigning its parameter does nothing to your variable.

Why do arrow functions fix the classic "lost this" bug?

They don't bind their own this — they capture the enclosing scope's, at definition time. So a callback written as an arrow inside a method keeps the instance's this, no .bind(this) needed. Tradeoff: they can't be used as constructors or rebound with call/apply.

What is prototypal inheritance, in two sentences?

Every object has an internal link to a prototype object; failed property lookups walk up that chain until found or null. class ... extends is sugar that wires exactly these links.

Shallow copy vs deep copy — and how do you do each?

Shallow ({...obj}, Object.assign) copies one level; nested objects are still shared references. Deep copies everything — modern answer is structuredClone(obj); JSON.parse(JSON.stringify()) is the old hack that drops functions, dates, undefined.

The event loop & async

"In what order does this log?" is the question that decides JS screens. Ninety minutes here makes the answer mechanical instead of a coin flip.

YOU ALREADY KNOW THIS

You've felt every rule already: the UI that froze during a heavy .map() (something blocked the loop), the state update that "hadn't happened yet" (it was queued), the two fetches you sped up with Promise.all. This block just names the machinery.

// the idea

  • JavaScript runs on one thread with an event loop: run a task to completion → drain the microtask queue → maybe render → take the next task. Nothing interrupts running code; long sync work freezes everything.
  • Two queues, strict priority. Macrotasks: setTimeout, I/O, clicks. Microtasks: promise callbacks, queueMicrotask. All pending microtasks run after every task, before the next task or timer — that's the entire trick behind ordering questions.
  • A promise is a one-shot state machine: pending → fulfilled or rejected, then frozen. .then always fires asynchronously (as a microtask), even on an already-settled promise.
  • async/await is promise sugar: an async function returns a promise; await pauses that function (not the thread), parking the rest as a microtask continuation. try/catch around await replaces .catch.
  • The combinators: Promise.all — parallel, fail-fast on first rejection. allSettled — waits for every result, never rejects. race — first to settle wins (timeouts). any — first to fulfill. Sequential awaits in a loop are the classic accidental slowdown.
  • setTimeout(fn, 0) means "run after the current task + all microtasks, at least 0ms later" — never "now". Browsers also clamp nested timers (~4ms floor).
order-of-logs.js
// The screen question. Say the order BEFORE reading the answer.
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// → A, D, C, B
//   sync first (A, D), then microtasks (C), then the timer task (B)

// Sequential vs parallel — the perf question hiding inside async
const a = await getUser(1);          // 300ms
const b = await getUser(2);          // +300ms  → 600ms total
const [x, y] = await Promise.all([   // both in flight at once
  getUser(1),
  getUser(2),
]);                                  // → ~300ms total, fail-fast

// Retry with backoff — say this shape, don't memorize syntax
async function retry(fn, tries = 3, delay = 500) {
  for (let i = 0; i < tries; i++) {
    try { return await fn(); }
    catch (err) {
      if (i === tries - 1) throw err;
      await new Promise(r => setTimeout(r, delay * 2 ** i));
    }
  }
}

// rapid-fire — answer out loud, then reveal

JS is single-threaded — so how does it handle 100 concurrent requests without freezing?

The slow parts (network, timers, disk) run outside the JS thread — in browser APIs or Node's libuv. JS just registers callbacks and keeps going; the event loop feeds completions back one at a time. Concurrency without threads, as long as your own code never blocks.

Microtask vs macrotask — and why does the difference matter?

Microtasks (promise callbacks) all run immediately after the current task, before timers or rendering; macrotasks (setTimeout, I/O) each wait for the next loop turn. It decides every "what order does this log" question — and an infinite microtask chain can starve rendering entirely.

What does await actually do?

Unwraps a promise: suspends this function, schedules the rest of it as a microtask for when the promise settles, and returns control to the caller. The thread never blocks — that's the difference from "waiting".

Promise.all vs Promise.allSettled — when each?

all rejects the moment any promise rejects — right when the results are all-or-nothing (parallel queries for one page). allSettled always resolves with per-item status — right for independent jobs where partial success is fine (sending 50 emails).

Why is await inside a for loop a code smell — and when is it correct?

It serializes independent requests: n × latency instead of ~1 ×. Fix with Promise.all(items.map(...)). It's correct when order matters or you must limit pressure on a downstream — then say "I'd batch with a concurrency limit".

How do you time out a fetch?

Two idioms: Promise.race([fetchPromise, rejectAfter(5000)]), or the real-world one — AbortController, passing its signal to fetch and calling abort() in a timer. AbortController actually cancels the request; race just stops waiting.

What's an unhandled promise rejection, and how do you prevent them?

A rejected promise with no .catch/try-catch on its chain — crashes modern Node processes. Prevention: every chain ends in a catch, async route handlers are wrapped (or Express 5 / a wrapper forwards to the error middleware), plus a last-resort process.on('unhandledRejection') log.

Callback → promise: how, and what's the pattern called?

Wrap it: new Promise((resolve, reject) => legacyFn(args, (err, data) => err ? reject(err) : resolve(data))) — "promisification"; Node ships util.promisify for exactly this.

Modern JS + a dash of TypeScript

Nobody asks "what is destructuring" anymore — they watch whether you reach for it. This hour is about sounding like you write 2020s JavaScript, plus the four TypeScript questions every JS screen now includes.

YOU ALREADY KNOW THIS

Your last PR almost certainly contained const { data } = await res.json(), a spread, an optional chain, and a .map(). The screen version of this topic is just being able to say why those beat the older forms.

// the idea

  • Destructuring + spread/rest: pull fields out of objects/arrays in one line; { ...obj } shallow-merges (later keys win) — the immutably-update idiom React state depends on.
  • ?. and ??: optional chaining short-circuits to undefined instead of throwing; nullish coalescing falls back only on null/undefined — unlike ||, which also swallows 0, '', and false. That difference is a real bug class and a favorite question.
  • Array fluency: map/filter/reduce return new arrays (immutability); forEach returns nothing — it's for side effects. Know that sort mutates (use toSorted when fresh).
  • ESM vs CommonJS: import/export is static — analyzable at build time, enabling tree-shaking; require is a dynamic function call. Node speaks both; the ecosystem has converged on ESM.
  • TypeScript in four beats: it's compile-time only (erased at runtime); interface vs type — interfaces merge/extend and suit object shapes, type aliases do unions and everything else, pick one style and be consistent; unknown over any — any turns the checker off, unknown forces you to narrow first; generics = type-level function parameters (function first<T>(xs: T[]): T).
  • Structural typing: TS compares shapes, not names — any object with the right fields satisfies the interface. That's why it fits JS so naturally.

// rapid-fire — answer out loud, then reveal

?? vs || — when does the difference bite?

|| falls back on any falsy value — so 0, '', and false get replaced; ?? only on null/undefined. Classic bite: a page size or toggle legitimately set to 0/false gets silently overwritten by the default.

map vs forEach?

map transforms and returns a new array — use when you want the result; forEach returns undefined — use only for side effects. Saying "map for data, forEach for effects" is the fluency signal.

What does spreading an object actually do?

A shallow copy: top-level keys are copied, later keys win on conflict, but nested objects are shared references. That's why deep state updates need a spread per level (or Immer).

interface vs type in TypeScript?

Both describe shapes. Interfaces can extend and declaration-merge (good for public/object APIs); type aliases handle unions, intersections, primitives, and mapped types. Honest senior answer: "mostly interchangeable for objects — our lint rule picks one; unions force type."

any vs unknown — why does the distinction matter?

any switches type-checking off and spreads through everything it touches; unknown accepts any value but forbids use until you narrow it (typeof/in/instanceof or a schema like zod). For untrusted input — API responses, JSON.parse — unknown is the professional choice.

What is a generic, in one sentence + one example?

A type parameter that lets a function/type work over many types while keeping the relationship between input and output — function first<T>(xs: T[]): T returns exactly the element type it was given, no casting.

Does TypeScript exist at runtime?

No — types are erased at compile time; there's zero runtime validation. That's why API boundaries need a runtime validator (zod/joi) even in a fully typed codebase — a favorite senior follow-up.

ESM vs CommonJS — one practical difference that matters?

ESM imports are static, so bundlers can tree-shake unused exports and analyze the graph at build time; CommonJS require is a runtime call, so dead code can't be proven dead. Also: ESM has top-level await; CJS doesn't.

React: how rendering actually works

You've written React for years — but "walk me through what happens when state changes" is a mechanism question, and mechanisms are exactly what interviews probe. This is that mechanism, end to end.

YOU ALREADY KNOW THIS

Every list bug you've fixed by adding a proper key, every form you've wired with value + onChange, every "why did this child re-render" hunt in DevTools — those are the exam. You've done the lab work; today attaches the theory.

// the idea

  • The mental model: UI = f(state). You never mutate the DOM; you change state, and React re-derives what the UI should be. Every React question is this sentence plus detail.
  • JSX compiles to function calls that return plain objects — "React elements". A component is a function from props to elements. No magic, no templates.
  • Render vs commit: on a state change React re-runs your component (render — pure, cheap, can happen often), diffs the new element tree against the old (reconciliation), then touches the real DOM only where something changed (commit). "Virtual DOM" = the element tree that makes the diff possible.
  • Keys give list items identity across renders. With stable keys React matches items by identity; with index keys, deleting item 0 makes every item "become" its neighbor — state and focus land on the wrong rows. That's the whole keys question.
  • What triggers a re-render: your own setState, your parent re-rendering (children re-render by default — memo is the opt-out), or a context you consume changing. Props changing is really "parent re-rendered".
  • State updates are batched and setState is asynchronous-feeling: reading state right after setting it gives the old value; updates that depend on previous state use the functional form setCount(c => c + 1).
  • Controlled vs uncontrolled inputs: controlled = React state is the source of truth (value + onChange); uncontrolled = the DOM holds the value and you read it via a ref. Controlled is the default answer; uncontrolled for file inputs and simple/perf-sensitive forms.
rendering.jsx
// Batching + functional updates — a favorite "what does this show?"
function Counter() {
  const [n, setN] = useState(0);
  const wrong = () => { setN(n + 1); setN(n + 1); };      // +1  (same stale n)
  const right = () => { setN(c => c + 1); setN(c => c + 1); }; // +2
  return <button onClick={right}>{n}</button>;
}

// Keys: identity, not decoration
{todos.map(t => <TodoRow key={t.id} todo={t} />)}   // ✓ stable identity
{todos.map((t, i) => <TodoRow key={i} ... />)}      // ✗ delete #0 and
                                                     //   every row shifts state

// Controlled input — you own the value
function Search() {
  const [q, setQ] = useState('');
  return <input value={q} onChange={e => setQ(e.target.value)} />;
}

// rapid-fire — answer out loud, then reveal

What is the virtual DOM, and what problem does it solve?

A lightweight tree of plain objects describing the UI. On each render React diffs new tree vs old and applies only the minimal set of real-DOM mutations — because DOM writes (layout, paint) are the expensive part, not JS. It buys you declarative code at near-imperative cost.

Walk me through what happens when you call setState.

React schedules a re-render (batching multiple set-calls in the same event), re-runs the component function to get a new element tree, reconciles it against the previous tree, and commits the minimal DOM changes — then runs effects. Render is pure; commit touches the world.

Why is using the array index as a key a bug, and when is it fine?

Keys are identity. With index keys, inserting/deleting/reordering makes React match the wrong old item to each new position — component state, animations, and focus stick to the index, not the data. Fine only when the list never reorders and items have no state.

Props vs state?

Props are inputs from the parent — read-only; state is owned and mutated (via setter) by the component itself. If two components need it, lift it to the common parent and pass it down — "lifting state up".

Controlled vs uncontrolled components?

Controlled: React state drives the input (value+onChange) — validation, formatting, conditional UI all become trivial. Uncontrolled: DOM keeps the value, read it with a ref — less code, fewer renders, required for <input type="file">.

Why does my component render twice in development?

StrictMode intentionally double-invokes render (and mount effects) in dev only, to surface impure renders and missing effect cleanup. It's a lint at runtime, not a perf bug — knowing this instantly signals real React experience.

Can a child update its parent's state?

Only by calling a function the parent passed down as a prop — "state down, events up". That one-way data flow is the answer to half of all React architecture questions.

What's a fragment and why does it exist?

<>...</> groups siblings without an extra DOM node — because a component must return one root, and wrapper divs break flex/grid layouts and bloat the tree.

Hooks, deeply

Everyone can use useState. Interviews live one level down: why hooks can't be conditional, what the deps array really means, and the stale-closure bug you've definitely shipped.

YOU ALREADY KNOW THIS

The interval that kept logging a frozen counter value, the effect that fired twice, the lint rule yelling about missing deps — every hook gotcha in this block is a bug you have personally fought. Today you learn to explain them on purpose.

// the idea

  • Why the rules of hooks exist: React stores hook state in a list, matched to components by call order. Call a hook inside an if and render #2 reads render #1's slots off by one — that's why hooks live at the top level, unconditionally.
  • useEffect is for synchronizing with the outside world (network, subscriptions, DOM APIs, timers) — not for reacting to state you could derive during render. It runs after paint. Deps array: none → every render; [] → mount only; [a, b] → whenever a or b change (compared by Object.is).
  • Cleanup runs before the next effect and on unmount. Return a function that clears the timer / unsubscribes / aborts the fetch. Most "effect bugs" are missing cleanups.
  • Stale closures: an effect's callback captures the state values from the render it was created in. An interval created once ([]) sees the initial state forever — fix with a functional update, correct deps, or a ref.
  • useMemo/useCallback are about referential equality, not raw speed: they keep the same object/function identity between renders so memoized children and effect deps don't fire spuriously. Wrapping everything in them is cargo cult — measure first.
  • useRef is a mutable box that survives renders and never triggers one. Two jobs: holding DOM nodes, and stashing mutable values (latest callback, interval id) that aren't render data.
  • Custom hooks are just functions that call hooks — the reuse mechanism for stateful logic. useDebounce, useLocalStorage, useAuth: name starts with use so the linter can check the rules.
stale-closure.jsx
// THE hooks interview question. Why does this count stop at 1?
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);      // `count` is frozen at 0 — stale closure
    }, 1000);
    return () => clearInterval(id);   // cleanup: the part they check for
  }, []);                       // ran once → captured the first render
  return <h1>{count}</h1>;     // renders 1 and stays there
}

// Fix: functional update — no stale read at all
setCount(c => c + 1);

// A custom hook is just extraction — nothing magic
function useDebounce(value, ms) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), ms);
    return () => clearTimeout(id);
  }, [value, ms]);
  return debounced;
}

// rapid-fire — answer out loud, then reveal

Why can't you call a hook inside an if statement?

Hook state is stored positionally, by call order per component. A conditional call shifts the order between renders, so every later hook reads the wrong slot. The rule isn't style — it's the storage model.

useEffect with no deps array vs [] vs [x]?

No array: after every render. []: after mount only (plus cleanup at unmount). [x]: after renders where x changed by Object.is — which is why unstable object/function deps cause every-render firing.

What's a stale closure in a hook, concretely?

An effect/callback captures the state of the render that created it; if it runs later (interval, subscription, resolved fetch) it still sees those old values. Fixes: functional updates, listing the value in deps, or reading the latest through a ref.

useMemo vs useCallback — and when are they actually worth it?

useMemo(fn) caches a computed value; useCallback(fn) caches the function itself (≡ useMemo(() => fn)). Worth it when the result feeds a memoized child or a deps array, or the computation is provably heavy — otherwise it's overhead and noise.

When useRef over useState?

When the value must survive renders but changing it shouldn't cause one: DOM handles, interval ids, "latest value" mirrors, previous-props tracking. Rule: render data → state; instance data → ref.

How do you fetch data on mount, correctly?

Effect with an AbortController: start the fetch, setState on success, and return a cleanup that aborts — so an unmounted or re-run component never sets state from a dead request (the "race on fast navigation" bug). In production apps: React Query/SWR does this plumbing.

Why did my effect run twice on mount in dev?

StrictMode mounts → unmounts → remounts in development to prove your effect + cleanup pair is safe to re-run. If the double-run breaks something, the cleanup is missing or wrong — that's the signal it exists to send.

What makes something worth extracting into a custom hook?

Stateful logic used by more than one component (or crowding one): pair of state + effect + cleanup behind one clean return value. It's the hooks answer to "how do you reuse logic without HOCs/render props".

React at scale: state, context, performance

"Where does state live?" and "why is this page slow?" are the questions that separate senior from mid on a React screen. One hour on the decision rules.

YOU ALREADY KNOW THIS

You've drilled props three levels deep, reached for Context, watched everything re-render, and then pulled in Redux or React Query. That whole arc — and knowing when each step was actually justified — is precisely what this hour rehearses.

When does React.memo do nothing at all?

When props change identity every render anyway — inline objects, arrays, arrow functions recreated by the parent. memo does a shallow compare; new references defeat it. That's the marriage between memo and useCallback/useMemo.

Prop drilling — when is it fine, and what are the real fixes?

Two or three levels of explicit props is often the clearest code. Fixes when it hurts: component composition (pass children), context for stable globals, or a store for hot shared state. Jumping straight to a library is the red flag.

Why put server data in React Query instead of Redux?

Server data has concerns Redux doesn't solve out of the box: caching with staleness, request dedupe, background revalidation, retries, pagination. React Query treats "data on another machine" as its own problem class — Redux stays for genuinely client-owned state.

What is hydration — and what's a hydration mismatch?

The client runs React over server-rendered HTML, attaching event listeners instead of rebuilding the DOM. A mismatch is when client render ≠ server HTML (dates, random ids, browser-only branches) — React warns and patches, and the fix is making both renders deterministic.

SSR vs SSG vs ISR — one sentence each?

SSR renders per request (personalized, always fresh, costs a server). SSG renders at build (fastest, cacheable, for content that rarely changes). ISR is SSG that re-renders pages in the background on a timer/on-demand — the middle ground for mostly-static content.

How would you debug a slow React page, step by step?

React DevTools Profiler to find what re-renders and why → check state placement (colocate) → stabilize prop identities + memo the expensive subtree → virtualize long lists → split the bundle by route. Lead with "measure" — the order is the answer.

What are React Server Components, in one breath?

Components that run only on the server — they can query the DB directly and ship zero JS to the client; interactive "client components" opt in with 'use client'. It moves data-fetching to the server by default — the Next.js App Router model.

How do you code-split a React app?

React.lazy(() => import('./Page')) wrapped in <Suspense fallback>, split at route boundaries first — frameworks do it per-route automatically. Goal: first load ships only the code the first screen needs.

Node.js internals

Every Node interview contains "it's single-threaded — so how does it scale?" and one question about something blocking the loop. Both have precise, rehearsable answers.

YOU ALREADY KNOW THIS

You've run pm2 start -i max, streamed a big file after readFile ate the RAM, and watched one hot endpoint freeze every other request. You've operated all of Node's sharp edges — this block turns each scar into an answer.

// the idea

  • Node = V8 + libuv. Your JS runs on one thread; libuv handles async I/O with OS primitives (epoll/kqueue) and keeps a small thread pool (default 4) for fs, crypto, DNS. "Single-threaded" is true of your code, not the process.
  • Why it scales for I/O: a waiting request costs almost nothing — no thread per connection. Tens of thousands of concurrent sockets on one process is normal. The corollary: one CPU-heavy request blocks every other request. Node is I/O-bound heaven, CPU-bound hell.
  • The loop has phases — timers → pending callbacks → poll (I/O) → check (setImmediate) → close. Between every callback, Node drains process.nextTick then promise microtasks. Interview one-liner: "timers, poll, setImmediate — with nextTick and microtasks squeezed between every step."
  • CPU work escape hatches: worker_threads (real threads, shared nothing by default) for compute inside one process; the cluster module / PM2 (one process per core, sharing the port) for scaling requests across cores. Know which is which — it's a favorite pair question.
  • Streams process data in chunks with constant memory: readable → transform → writable via .pipe()/pipeline(). Backpressure — the consumer signalling "slow down" so the producer pauses — is handled for you by pipe; naming it is the senior tell. Buffers are the raw-bytes chunks streams carry.
  • Process hygiene: config via env vars, crash fast on unknown state, SIGTERM → stop accepting, drain, exit (graceful shutdown). require/ESM imports are cached — a module runs once, which is why "just export an object" is Node's singleton.

// The 2GB export, two ways.
import { createReadStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';

// ✗ loads the whole file into RAM, then starts sending
app.get('/export-bad', async (req, res) => {
  const all = await fs.readFile('huge.csv');   // 2GB in memory
  res.send(all);
});

// ✓ constant memory, backpressure handled by pipeline

  await pipeline(createReadStream('huge.csv'), res);
});

// rapid-fire — answer out loud, then reveal

Node is single-threaded — how does it serve 10,000 concurrent users?

Waiting costs nothing: I/O is delegated to the OS via libuv, so each idle connection is just a socket + callback, not a thread. The one thread only runs JS between I/O events. Caveat to volunteer: this dies the moment a request does heavy CPU work on the loop.

What blocks the event loop, and how do you find it in production?

Long synchronous work: big JSON.parse/stringify, sync fs/crypto calls, giant loops, catastrophic regex. Detect by measuring event-loop lag/utilization (built-in perf_hooks, APM dashboards, clinic.js); fix by chunking, streaming, or moving to worker threads.

cluster (PM2) vs worker_threads?

Cluster forks whole processes — one per core, sharing the listen port — to scale request throughput; memory is duplicated, crashes are isolated. Worker threads are threads inside one process for CPU-heavy jobs (image resize, parsing), passing data by message. Scale requests with processes; offload compute with threads.

When do you reach for a stream instead of readFile?

Whenever the data is big or unbounded, or you can start producing output before consuming all input: file uploads/downloads, CSV exports, proxying, ETL. Constant memory + lower time-to-first-byte; pipeline() wires error handling and backpressure.

What is backpressure?

When a fast producer outruns a slow consumer, the consumer's buffer fills and it signals "pause" upstream; the producer resumes on drain. pipe/pipeline implement it automatically — write your own write-loop and you must honor write() returning false.

process.nextTick vs setImmediate — and which is misnamed?

Both are misnamed, and saying so is the flex: nextTick runs immediately after the current operation (before promises, before any phase); setImmediate runs on the next loop iteration (check phase). Prefer setImmediate for "yield to the loop"; nextTick can starve I/O if abused.

How does require/import caching behave, and what pattern does it enable?

First load runs the module and caches its exports; every later require gets the same object. That makes a plain exported instance (db pool, config, logger) a natural singleton — and explains why mutating an imported object leaks state across the whole app.

What does a graceful shutdown look like in Node?

On SIGTERM: stop accepting new connections (server.close), let in-flight requests finish with a deadline, close DB pools/queues, then exit 0 — and the platform's load balancer has already stopped routing to you (that's why health checks exist). Kubernetes/ECS send SIGTERM then SIGKILL after the grace period.

Express & API design

The interview version of the code you write most: what middleware really is, which status code when, and the JWT-vs-session answer you'll give a dozen times in your career.

YOU ALREADY KNOW THIS

Your app.use(auth) line, the errorHandler at the bottom of app.js, the CORS error you fixed by listing the frontend origin — the entire topic is code you maintain today, asked back at you as "why".

// the idea

  • Middleware is a pipeline: each (req, res, next) function reads/annotates the request and either responds or calls next(). Registration order is execution order — auth before routes, error handler last. Forget next() and the request hangs forever.
  • Error handling is centralized: one (err, req, res, next) middleware at the end; everything else throws or calls next(err). In Express 5, rejected async handlers route there automatically; in Express 4 you wrap handlers (or a stray rejection kills the request silently).
  • REST semantics: nouns for resources (/orders/42), verbs from the method. GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes. Idempotent (safe to retry): GET, PUT, DELETE. POST isn't — which is why payment APIs take an idempotency key.
  • Status codes that matter: 200/201/204 (ok / created / no body), 400 (bad input), 401 unauthenticated vs 403 unauthorized, 404, 409 (conflict), 422 (validation), 429 (rate limited), 500 vs 503 (bug vs overloaded/down). Precision here is a cheap, loud competence signal.
  • Sessions vs JWT: session = random id in an httpOnly cookie, state on the server (Redis) — easy revocation, needs shared session store to scale. JWT = signed claims held by the client, verified statelessly — can't be revoked before expiry, so: short-lived access token + refresh token, and keep tokens in httpOnly cookies, not localStorage (XSS-readable). The tradeoff sentence is the whole question.
  • Edge discipline: validate input with a schema (zod/joi) before logic; rate-limit per user/IP; CORS is the browser enforcing which origins may read responses — the preflight OPTIONS is it asking permission for non-simple requests. CORS is not server security; authz is.
  • Pagination: offset/limit is simple but drifts under writes and slows at depth; cursor (keyset) — "after id X" — is stable and index-friendly. Version your API (/v1) before you need to.

// rapid-fire — answer out loud, then reveal

What is middleware, and why does order matter?

Functions in a chain, each seeing (req, res, next) — they compose cross-cutting concerns: parsing, auth, logging, rate limiting. Express runs them in registration order, so auth must precede routes and the error handler must come last; the order is the architecture.

401 vs 403?

401 Unauthorized actually means unauthenticated — "I don't know who you are; log in." 403 Forbidden means "I know exactly who you are, and no." Auth middleware sends 401; permission checks send 403.

PUT vs PATCH?

PUT replaces the whole resource (send everything, idempotent by definition); PATCH applies a partial change. Follow-up worth pre-empting: PATCH can be idempotent ("set status=paid") or not ("append item").

JWT vs server sessions — give the tradeoff, not a winner.

Sessions: server-held state, instant revocation, but every node needs the session store. JWT: stateless verification anywhere (great for microservices/mobile), but revocation before expiry needs a denylist — so short access tokens + refresh rotation. Then the kicker: either way the browser copy lives in an httpOnly cookie.

Why is localStorage the wrong place for tokens?

Any XSS — yours or a compromised npm dependency's — can read localStorage and exfiltrate the token. httpOnly cookies are invisible to JS; pair with SameSite and CSRF protection. "XSS steals localStorage; CSRF rides cookies; each store has its counter" is the complete answer.

What actually triggers a CORS preflight, and what is CORS protecting?

Non-simple requests — methods beyond GET/POST-with-form-encoding, custom headers like Authorization, JSON content-type — make the browser send OPTIONS first. CORS protects users from malicious origins reading cross-site responses in their browser; it does nothing against curl. Server auth is still doing the real guarding.

What is an idempotency key and when do you need one?

A client-generated unique id sent with a non-idempotent request (POST /payments); the server stores the result per key and replays it on retry instead of re-executing. Needed wherever retries + money/side effects meet — networks fail after the server succeeded.

Offset vs cursor pagination?

OFFSET n scans and discards n rows (slow at depth) and shifts when rows are inserted mid-scroll (duplicates/skips). Cursor: "WHERE (created, id) < last-seen ORDER BY … LIMIT k" — stable under writes, uses the index. Offset is fine for small admin tables; cursors for feeds.

How do you secure an Express API — the 30-second checklist?

HTTPS everywhere; helmet for headers; schema-validate every input; parameterized queries; authn middleware then per-route authz; rate limiting; httpOnly+SameSite cookies; secrets in env/secret manager; audit deps; central error handler that never leaks stacks. Rattling this off calmly is the senior signal.

PostgreSQL: queries, joins, transactions

SQL screens have a canon: one join question, one NULL trap, one "explain ACID". All three are fully rehearsable, and the join question is nearly always the same join question.

YOU ALREADY KNOW THIS

Every Prisma include is a join; every "why is this user missing from the report" you've debugged was an INNER join that should've been LEFT; every double-clicked checkout you've guarded was a transaction. The ORM has been writing this exam for you for years.

// the idea

  • Joins: INNER keeps only matching rows; LEFT keeps every left row, NULL-padding the misses; RIGHT is LEFT flipped; FULL keeps both sides. The canonical trap: a LEFT JOIN row-count question — one order per user duplicates the user row per order.
  • The anti-join — "users with NO orders" — has two canonical spellings: LEFT JOIN … WHERE o.id IS NULL, and NOT EXISTS (SELECT 1 …). Knowing both, and that NOT IN silently breaks when the subquery yields a NULL, is the whole question.
  • NULL is three-valued logic: NULL = NULL is not true — any comparison with NULL is unknown, and WHERE keeps only true. Hence IS NULL/IS DISTINCT FROM, and why NULLs vanish from COUNT(col) but not COUNT(*).
  • GROUP BY buckets rows; HAVING filters the buckets. WHERE runs before grouping (can't see aggregates), HAVING after. "Customers with more than 5 orders" = GROUP BY + HAVING COUNT(*) > 5.
  • Transactions are ACID: atomic (all or nothing), consistent (constraints hold), isolated (concurrent transactions don't see each other's partials), durable (committed survives crash). Anything that moves value between rows — transfer, checkout, inventory — belongs in one.
  • Isolation levels, PG edition: default is Read Committed — no dirty reads ever, but two reads in one transaction can disagree (non-repeatable). Repeatable Read gives a frozen snapshot; Serializable makes concurrent transactions behave as if run one-by-one (retry on serialization failure). PG does this with MVCC — writers make new row versions, readers read old ones, so readers and writers never block each other.
  • Constraints are the last line of defense: primary keys, foreign keys, NOT NULL, UNIQUE, CHECK. App code has races; a UNIQUE index does not. "Enforce it in the schema, not just in JS" is a senior refrain.
the-canon.sql
-- Q: every user and how many orders they have — INCLUDING zero.
SELECT u.id, u.name, COUNT(o.id) AS orders     -- COUNT(o.id), not (*):
FROM users u                                    -- NULLs must count as 0
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name
HAVING COUNT(o.id) > 5;        -- HAVING: filter AFTER grouping

-- Q: users with NO orders — both canonical forms
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

// rapid-fire — answer out loud, then reveal

INNER vs LEFT JOIN — and the report-bug version of the question?

INNER drops rows with no match; LEFT keeps them with NULLs. The bug version: "why did users disappear from the report?" — someone joined users to orders with INNER, silently excluding everyone with zero orders.

Why does WHERE deleted_at = NULL return zero rows?

Comparisons with NULL evaluate to unknown, never true — NULL isn't a value, it's "absent". You must write IS NULL. Bonus: this same rule is why NOT IN with a NULL in the list matches nothing.

WHERE vs HAVING?

WHERE filters rows before grouping — it can't see aggregates; HAVING filters groups after. Perf note worth adding: push every condition you can into WHERE so fewer rows get grouped at all.

What is ACID — with one real example?

Atomicity, Consistency, Isolation, Durability. Example that always lands: checkout decrements stock and inserts an order — in one transaction, either both happen or neither, constraints stay true, concurrent checkouts don't see half of mine, and once committed it survives a crash.

Postgres's default isolation level, and what anomaly does it allow?

Read Committed. Dirty reads are impossible, but non-repeatable reads aren't: read a row, someone commits a change, read again in the same transaction — different answer. Repeatable Read fixes that with a snapshot; Serializable removes anomalies entirely at the cost of retries.

What is MVCC, in two sentences?

Multi-Version Concurrency Control: every update writes a new row version instead of overwriting, and each transaction reads the versions visible to its snapshot. Readers never block writers and vice versa — and dead versions are why Postgres needs VACUUM.

DELETE vs TRUNCATE?

DELETE removes rows one by one — WHERE-able, fires triggers, fully transactional and slower. TRUNCATE deallocates the whole table's storage — instant, no per-row triggers, optionally RESTART IDENTITY (still transactional in PG). Prod rule: TRUNCATE is for test fixtures, not for tables with FKs pointing at them.

Why store money as NUMERIC and not FLOAT?

Floats are binary approximations — 0.1 + 0.2 ≠ 0.3 — and rounding errors compound in sums. NUMERIC is exact decimal arithmetic. Alternative correct answer: integer cents. Anyone who's shipped billing says this instantly, which is why it's asked.

Indexes, EXPLAIN & the N+1 problem

Every backend interview reaches "the endpoint is slow — walk me through it." The answer is a ritual: EXPLAIN, index, and the N+1 you already know from your ORM.

YOU ALREADY KNOW THIS

An index is the back-of-the-book kind: sorted, small, points at pages. You've also met N+1 — it's the endpoint that got slower with every customer, because the loop did one query per row. You fixed it with include; today you get to say why that worked.

// the idea

  • A B-tree index is a sorted structure over one or more columns: equality and range lookups in O(log n) instead of scanning every row. The costs: extra writes on every INSERT/UPDATE (each index must update) and disk — which is why you don't index everything.
  • Composite index (a, b) obeys the leftmost-prefix rule: serves WHERE a and WHERE a AND b — not WHERE b alone. Order columns by how you query: equality columns first, then the range/sort column.
  • When indexes don't fire: leading-wildcard LIKE '%foo' (nothing sorted to walk), functions on the column (lower(email) — unless you build that expression index), low-selectivity columns (a boolean where half the table matches — a scan is genuinely cheaper), tiny tables.
  • EXPLAIN shows the plan; EXPLAIN ANALYZE runs it and shows reality: Seq Scan vs Index Scan, estimated vs actual rows (a huge gap = stale stats), and loops — a nested query executing thousands of times is your N+1 in plan form. Read the innermost expensive node first.
  • N+1: fetch 100 posts (1 query), then authors in a loop (100 queries). Fixes: JOIN, or batch WHERE id IN (...) — ORMs call this include/eager loading; GraphQL calls it DataLoader. Symptom: latency scales with result count.
  • Connection pooling is non-negotiable: each PG connection is a whole server process, and Postgres has a max. One shared pool per app process, sized modestly (start ~10); serverless multiplies clients, hence PgBouncer / RDS Proxy in front.
  • The slow-endpoint ritual (say it in this order): reproduce → find the query (logs/APM, pg_stat_statements) → EXPLAIN ANALYZE → fix the shape (index / rewrite / batch the N+1) → only then consider caching. Cache-first answers read as junior.

EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

--         → reads ALL rows, sorts, keeps 20

-- after:  Index Scan using idx_orders_user_created (actual time=0.04..0.09)
--         → walks straight to user 42's newest rows. ~4000x.

const posts = await db.post.findMany({ take: 100 });

// rapid-fire — answer out loud, then reveal

How does a B-tree index make a query fast — one sentence?

It's a sorted tree over the column, so the database binary-searches to the matching entries and follows pointers to just those rows — O(log n) instead of reading the table.

Why not add an index to every column?

Every write must update every index — inserts and updates slow down, disk grows, and the planner gains nothing from indexes on low-selectivity or never-queried columns. Index what your WHERE/JOIN/ORDER BY actually use, and check usage stats before adding more.

Index on (user_id, created_at): which queries can use it?

WHERE user_id = ?, and WHERE user_id = ? ORDER BY created_at (equality then sort — the ideal). Not WHERE created_at > ? alone — leftmost prefix rule. This exact question is the composite-index interview in miniature.

What is the N+1 problem and how do you spot it without reading code?

One query for a list, then one more per item — 1+N round trips. Spot it from symptoms: endpoint latency grows linearly with result size, and query logs show the same statement repeated with different ids. Fix: JOIN/eager-load or batch with IN.

EXPLAIN vs EXPLAIN ANALYZE?

EXPLAIN shows the planner's estimated plan; ANALYZE actually executes and reports real times and row counts. The gold is comparing estimated vs actual rows — a 1000x gap means stale statistics (run ANALYZE) or a query the planner can't reason about.

Why can't LIKE '%smith' use a normal index — and what can?

A B-tree is sorted from the string's start; a leading wildcard means there's no prefix to seek to. Options: trigram index (pg_trgm GIN) for substring search, or full-text search — naming either one is a strong senior tell.

When is a Seq Scan the RIGHT answer?

Small tables (the whole thing fits in a few pages) and low-selectivity queries returning a big fraction of rows — sequential reads beat millions of random index hops. "Seq scan isn't automatically bad" earns instant credibility.

Why do serverless functions + Postgres need PgBouncer or RDS Proxy?

Each function instance opens its own connections, and PG connections are expensive processes with a hard cap — a traffic spike exhausts them. A pooler multiplexes thousands of client connections onto a few dozen real ones.

  • Compute ladder: EC2 — a VM you patch and scale yourself. ECS/Fargate — run containers, no servers to patch. Lambda — a function per event, scales to zero and to thousands, you give up long-running processes (15-min cap) and eat cold starts. The interview move is picking by workload: steady traffic → containers; spiky/event-driven glue → Lambda.
  • S3 is an object store, not a filesystem: PUT/GET whole objects by key, effectively infinite, famously durable (the "11 nines" line), versioning + lifecycle rules to cheaper tiers. It serves your SPA build, stores uploads, backs your backups. Presigned URLs let clients upload/download directly, bypassing your servers — the standard uploads answer.
  • RDS is managed Postgres: AWS runs backups, patching, failover. Two knobs interviews test: Multi-AZ = synchronous standby in another AZ for availability (failover, not extra speed); read replicas = async copies for read scaling (slightly stale, and your app must route reads). Say "Multi-AZ for uptime, replicas for reads" and the question is over.
  • IAM: identities (users/roles) + JSON policies = who can do what to which resource. The two rules that matter: least privilege, and roles, not keys — code on EC2/Lambda assumes a role and gets rotating temporary credentials; an access key in an env var (or worse, a repo) is the classic breach story.
  • VPC in one breath: your private network; public subnets hold load balancers, private subnets hold apps and databases; security groups are stateful per-resource firewalls (allow rules only); a NAT gateway lets private things call out without being reachable in. RDS goes in a private subnet — "the database has no public IP" is a sentence that wins security questions.
  • CloudWatch collects logs + metrics and fires alarms; that's how you know you're down before Twitter does.

// rapid-fire — answer out loud, then reveal

EC2 vs Lambda — how do you choose?

By traffic shape and runtime: steady/long-running/predictable → EC2 or containers (cheaper at constant load, no cold starts, any process model); spiky, event-driven, or glue work → Lambda (scales to zero, no ops, but 15-min cap and cold starts). Most real systems: containers for the API, Lambda for events.

What is S3 actually good for — and what should never go in it?

Good: static assets, user uploads, backups, data-lake files — cheap, durable, infinitely scalable objects. Wrong: anything needing partial updates, low-latency queries, or filesystem semantics — that's a database's job. "S3 is not a database" gets a knowing nod.

Multi-AZ vs read replica — the one-sentence-each answer?

Multi-AZ: synchronous standby, automatic failover, zero extra read capacity — it's for availability. Read replica: asynchronous copy you point SELECTs at, slightly stale — it's for scale. They compose: Multi-AZ primary + replicas is the standard prod shape.

Why IAM roles instead of access keys in env vars?

Roles issue short-lived, auto-rotated credentials to the compute that assumes them — nothing to leak, commit, or rotate manually. Long-lived keys in env/repos are the #1 real-world AWS breach vector. Follow with "and least-privilege policies per service".

How do users upload a 500MB video without melting your API?

API issues a presigned S3 URL (scoped, expiring); the client PUTs directly to S3; S3 event (→ SQS/Lambda) triggers post-processing. Your servers never touch the bytes. This exact flow is the most-asked AWS design question at product companies.

Security group vs NACL?

Security group: stateful firewall on the resource — allow rules only, return traffic automatically permitted; it's the one you actually use daily. NACL: stateless allow/deny at the subnet boundary, both directions explicitly. Answer "SGs for everything, NACLs for coarse subnet guardrails".

Where do secrets live, and how does the app get them?

Secrets Manager (rotation built in) or SSM Parameter Store (simpler/cheaper); the app's IAM role grants read at boot or the platform injects them. Never in the repo, never baked into images, never in plaintext env files on servers.

Your RDS is in a private subnet — how do you, a human, connect to it?

Not by giving it a public IP: a bastion host, or the modern answer — SSM Session Manager port-forwarding through an instance/agent, with access logged by IAM. Shows you've actually operated a locked-down VPC.

Scaling, queues & the bill

The difference between "has an AWS account" and "has run things on AWS" is three topics: how it scales, what the queue is for, and what surprised you on the invoice.

YOU ALREADY KNOW THIS

You've already scaled horizontally the day you ran two PM2 workers — and hit the classic wall when in-memory sessions broke, which you fixed with Redis. That exact story, retold with an ALB and an Auto Scaling Group, is the whole scaling interview.

// the idea

  • Horizontal scaling requires statelessness: any instance must serve any request, so sessions live in Redis/JWT, uploads in S3, state in the DB. Then an ALB spreads traffic over an Auto Scaling Group (or ECS service) that adds/removes instances on CPU/request metrics, across AZs. Health checks pull sick instances out automatically.
  • Queues decouple: SQS between "accept the request" and "do the slow thing" (emails, exports, video processing) — producers and consumers scale independently, spikes become backlog instead of outage, retries are built in, and poison messages land in a dead-letter queue instead of retrying forever. SNS is pub/sub fan-out — one event, many subscribers; the classic combo is SNS → multiple SQS queues.
  • Lambda operational truths: cold start = first-invocation latency for a new instance (bigger with heavy bundles and VPC attachment; mitigations: smaller functions, provisioned concurrency); per-invocation concurrency limits; and every Lambda talking to Postgres needs the pooler story from the last topic.
  • CloudFront (CDN) caches at edge locations worldwide: static assets get long max-age + hashed filenames; it also fronts APIs for TLS termination and DDoS absorption. "Cache at the edge, invalidate by deploying new hashes" is the modern answer.
  • Deploys without downtime: rolling (replace a few at a time), blue/green (run both fleets, flip traffic, instant rollback), canary (1% first, watch, then ramp). Know which your team runs and why.
  • The bill, honestly: the classics that surprise people — NAT gateway data processing, cross-AZ/egress transfer, unattached EBS volumes and idle load balancers, over-provisioned RDS, S3 without lifecycle rules. Levers: right-size, autoscale to zero where possible, reserved/savings plans for the steady floor, budgets + alerts so you find out in days not months.
  • Observability minimum: structured logs with request ids → CloudWatch; RED metrics (rate, errors, duration) per endpoint; alarms on error rate and p99, wired to a human. If you can say "our p99 was X and here's how I knew", you're hired-adjacent.

// rapid-fire — answer out loud, then reveal

How do you make an API horizontally scalable — the full sentence?

Make instances stateless (sessions in Redis or JWT, files in S3), put an ALB in front of an auto-scaling group across ≥2 AZs, scale on request/CPU metrics, health-check instances out when they fail. Every clause earns a point; "stateless" is the load-bearing one.

SQS vs SNS?

SQS is a queue — messages wait until one consumer processes each, buffering work over time. SNS is pub/sub — one message pushed to all subscribers immediately, no storage. Fan-out pattern: publish once to SNS, deliver into several SQS queues so each consumer gets its own buffered copy.

What's a dead-letter queue and why does every queue need one?

Where messages go after N failed processing attempts. Without it, a poison message retries forever, burning compute and blocking insight; with it, bad messages park for inspection and an alarm fires. It's the difference between an incident and a mystery.

Why must queue consumers be idempotent?

Queues guarantee at-least-once delivery — crashes and visibility timeouts cause redelivery. Processing twice must be safe: dedupe by message/business id, or make the operation naturally re-runnable ("set status=sent", not "increment counter").

What is a Lambda cold start and how do you reduce it?

Latency to spin up a fresh execution environment — load runtime + your bundle — before the first invocation; subsequent calls reuse the warm instance. Reduce: smaller bundles, lighter runtimes, provisioned concurrency for latency-critical paths, and don't put chatty init in the handler path.

Blue/green vs rolling deploy?

Rolling swaps instances a few at a time — cheap, but two versions serve traffic simultaneously and rollback is another roll. Blue/green stands up the new fleet beside the old and flips traffic — instant rollback, costlier, needs backward-compatible DB migrations. Canary = blue/green with a 1% toe in the water.

What typically surprises teams on their first real AWS bill?

Data transfer — NAT gateway processing charges and cross-AZ/egress traffic — plus zombie resources: unattached EBS, idle ALBs, forgotten snapshots, oversized RDS. Naming NAT gateway specifically is the "has actually seen the invoice" tell.

How do you know your service is down before users tell you?

Health checks at the LB, CloudWatch alarms on error rate and p99 latency wired to a pager/Slack, and an external synthetic check hitting the real endpoint from outside — because internal dashboards can be green while DNS or certs are broken.

The tech-screen playbook

Knowledge questions are graded on shape as much as substance. These six moves apply to every question on this page.

01 · definition → example → tradeoff

Three sentences, always: what it is, where you've used it, what it costs. "An index is a sorted lookup; we added one on orders.user_id and cut a report from 4s to 40ms; the price is slower writes." Complete, calm, done.

02 · trace out loud, never guess

On "what does this log?" questions, silence reads as guessing. Narrate the machine: "sync runs first, so A and D… the .then is a microtask, so C before the timer's B." A wrong answer with right reasoning scores better than a lucky guess.

03 · "I'd have to check the syntax" is a power move

Said confidently about an argument order or config key, it signals you know what matters. Never say it about mechanisms — the event loop, indexes, and JWT tradeoffs are exactly what you're being paid to carry in your head.

04 · don't bluff — redirect

Interviewers probe until they find the edge; bluffing moves the edge to a lie. Instead: "I haven't run Kafka — our scale fit SQS, and here's the queue reasoning I do own." Honest edges + strong adjacent ground beats fake coverage every time.

05 · volunteer the follow-up

Every canned question has a planned follow-up. Beat them to it: JWT answer ends "…the catch is revocation", index answer ends "…and writes pay for it". You're answering the next question — that's what senior sounds like.

06 · after every real screen

Five minutes, same day: write down every question asked. Anything you fumbled goes into your copy of the bank with the answer you wish you'd given. Three screens in, you've seen 80% of the deck.

The rapid-fire bank

Fifty-six more questions — the ones screens actually ask, grouped by area, answers hidden until you commit. These deliberately don't repeat the topic questions above; together they're the full deck. Night-before ritual: run one group per stack area you'll be quizzed on, out loud.

// javascript & the browser

What's the difference between null and undefined?

undefined = never assigned (missing params, absent properties); null = deliberately empty, set by a human. JSON has only null; typeof disagrees on them; x == null catches both.

Debounce vs throttle — and one real use of each?

Debounce: wait for quiet, then fire once — search-as-you-type. Throttle: fire at most every N ms during activity — scroll/resize handlers. Both are closures around a timer.

What is event delegation and why does React make it feel free?

One listener on a parent catches bubbled events from all children — fewer listeners, works for future children. React does this internally: your onClicks attach to the root, not each node.

localStorage vs sessionStorage vs cookies?

localStorage: ~5-10MB, persists, JS-only, never sent to server. sessionStorage: same but per-tab, dies with it. Cookies: ~4KB, sent with every request, and the only one the server can set httpOnly — which is why auth lives there.

How does garbage collection work in JS, one sentence?

The engine periodically frees anything unreachable from the roots (globals, the stack, closures) — so "memory leak" in JS means an accidental reference: a forgotten listener, a growing module-level cache, a detached DOM node held in a closure.

What is a WeakMap actually for?

Keys are objects, held weakly — when the object dies, the entry is collected with it. Use: attaching metadata/caches to objects you don't own without leaking them. (Same idea powers per-object private state.)

Why does 0.1 + 0.2 !== 0.3, and what do you do about it?

IEEE-754 binary floats can't represent decimal tenths exactly. Handle money in integer minor units or a decimal library; compare floats with an epsilon; never float columns in the DB for money.

What does use strict change — and why do you rarely write it now?

Throws on silent errors: undeclared globals, bad deletes; plain-call this becomes undefined instead of the global object. ES modules and class bodies are strict automatically — so modern code is strict without the pragma.

// react

useEffect vs useLayoutEffect?

useEffect runs after paint (async, doesn't block); useLayoutEffect runs after DOM mutation but before paint — for measuring or repositioning without visible flicker (tooltips, scroll restoration). Default to useEffect; layout only when you saw the flicker.

What's an error boundary, and what does it NOT catch?

A component that catches render-phase errors in its subtree and shows a fallback instead of unmounting the app. Doesn't catch: event handlers, async/awaited code, SSR. Handlers use try/catch; there's no hook — it's a class component (or your framework's errorElement).

What are portals for?

Rendering children into a DOM node outside the parent hierarchy — modals, toasts, tooltips escaping overflow/z-index traps — while keeping React context and event bubbling intact.

Controlled form library question: why do Formik/React Hook Form exist?

Per-keystroke setState across a 30-field form = 30 re-renders of everything. RHF keeps values in refs (uncontrolled), re-rendering only what's touched, and layers validation on top. Knowing the "controlled forms don't scale" reason is the point.

What is Suspense, beyond code-splitting?

A declarative "while this subtree isn't ready, show the fallback" boundary. With React.lazy it waits for code; with RSC/React Query integrations it waits for data — streaming SSR sends the shell first and fills Suspense holes as they resolve.

How do you test React components — what's the philosophy that gets you hired?

React Testing Library: render, interact via roles/labels like a user, assert visible outcomes — never internals or instance state. "Test behavior, not implementation" plus one story about a refactor that didn't break tests = full marks.

What's the key difference between state in React and a variable in the component?

A plain variable resets every render and changing it triggers nothing; state persists across renders and its setter schedules the re-render. If it should survive renders but not cause them — that's the third option, a ref.

Two components need the same fetched data — what's wrong with fetching in both?

Nothing, if you're using React Query/SWR — same key dedupes to one request and one cache. Hand-rolled effects would double-fetch and drift; lifting to a parent couples layout to data. Naming the cache-key answer shows current-era React.

// node & apis

npm install vs npm ci — and why does CI use the second?

install resolves ranges and may update the lockfile; ci installs exactly the lockfile (deleting node_modules first) and fails if lockfile and package.json disagree — deterministic, faster, no surprise upgrades in CI.

What does ^4.2.1 in package.json actually allow?

Semver: any 4.x.y ≥ 4.2.1 — minor + patch, never major (5.0.0). Tilde ~4.2.1 = patch only. Majors signal breaking changes; the lockfile is what actually pins.

How do you find a memory leak in a Node service?

Confirm with RSS/heap metrics over time, then take two heap snapshots (Chrome DevTools via --inspect, or heapdump) minutes apart and diff what's growing — usually a module-level array/map, listeners never removed, or unbounded cache. Say "snapshot diff" and you pass.

REST vs GraphQL — the calibrated answer?

REST: simple, cacheable by URL, the default for service APIs. GraphQL: clients pick fields and traverse relations in one round trip — earns its complexity with many client shapes (mobile+web+partners) atop many services; costs: caching, N+1 resolvers (DataLoader), query cost control. "We'd start REST" is a fine answer with reasons.

WebSockets vs SSE vs polling — pick for a notifications feature?

Server→client only: SSE — plain HTTP, auto-reconnect, cheap. Two-way (chat, games): WebSockets. Polling: fine at low frequency, simplest infra. Most "real-time notifications" interviews want you to say SSE and explain why not WS.

How do env-specific configs work in a 12-factor app?

Config lives in the environment, not the code: same artifact deployed everywhere, behavior differs only by env vars/secrets injected per environment. No config files per env checked into the repo, no NODE_ENV branching for secrets.

What is a health check endpoint supposed to check?

Two flavors: liveness — "process is up" (cheap, always 200 unless wedged); readiness — "can serve traffic" (DB/queue reachable). LBs and orchestrators route on readiness and restart on liveness; conflating them causes restart storms during DB blips.

How would you version and retire an API endpoint?

Version at the path (/v1) or header; add v2 alongside, migrate consumers with metrics on v1 usage, deprecate with sunset headers + comms, remove when traffic hits zero. The word "metrics" is what makes this answer real.

// http & the web

What happens when you type a URL and hit enter — the 60-second version?

DNS resolves the name (cache → resolver → authoritative) → TCP handshake → TLS handshake (certs, keys) → HTTP request → CDN/LB routes to an app server → app queries DB, returns HTML/JSON → browser parses, fetches assets, builds DOM/CSSOM, renders, hydrates. Practice until fluid — it's the most-asked breadth question in existence.

HTTP is stateless — what does that mean and how do apps fake state?

Each request stands alone; the server keeps no per-connection memory. Continuity comes from tokens the client re-sends: cookies/session ids/JWTs — that's the entire reason auth headers and cookies exist.

What do Cache-Control, ETag, and 304 do together?

Cache-Control sets freshness (max-age, public/private, no-store); when stale, the browser revalidates with If-None-Match: etag; unchanged → 304 empty body, cache reused. Assets: hashed filenames + max-age=1yr, immutable. HTML: no-cache (revalidate every time).

HTTP/1.1 vs HTTP/2 in one line each?

1.1: one request at a time per connection → head-of-line blocking, browsers open ~6 sockets. 2: one connection, many multiplexed streams + header compression — bundling/spriting hacks became obsolete. (3/QUIC: same idea over UDP, kills TCP-level blocking.)

What's the same-origin policy?

Scripts can only read responses from their own scheme+host+port; everything cross-origin is blocked unless the target opts in via CORS headers. It's the browser's core security boundary — CORS is the relaxation valve, not the wall.

GET request with a body — why is it a bad idea even though it's "possible"?

Semantics: GET promises safety and cacheability keyed on URL; intermediaries (caches, LBs, CDNs) may drop or ignore GET bodies. Search with complex filters → POST /search, or encode in query params. Shows you think about the infrastructure between client and server.

What is DNS TTL and how does it bite during migrations?

How long resolvers may cache a record. Cutting over with a 24h TTL means a day of traffic split between old and new. Ritual: drop TTL to 60s well before, migrate, restore. A one-sentence war story here is gold.

What's a CDN cache invalidation strategy that doesn't hurt?

Don't invalidate — version: hashed asset filenames mean every deploy is new URLs, old ones stay valid; HTML stays short-TTL/no-cache. Purge APIs are for emergencies, not the deploy path.

// sql & data modeling

Normalization vs denormalization — the working engineer's answer?

Normalize (each fact once, FKs) for integrity by default; denormalize (duplicate a name/count onto rows that need it) when read paths hurt — accepting you now maintain the copy. "Third normal form until measured pain" is the calibrated line.

SQL vs NoSQL — when is Postgres NOT the answer?

Genuine key-value/document scale-out (Dynamo/Mongo), heavy ephemeral caching (Redis), search ranking (Elasticsearch), analytics over billions of rows (columnar warehouses). For the app's system of record with relations and transactions, Postgres wins by default — say that, then the exceptions.

What's a CTE and when do you use one?

WITH name AS (SELECT …) — a named subquery for readability and reuse within one statement; recursive CTEs walk trees (org charts, categories). Modern PG inlines them, so the old "optimization fence" caveat is mostly history.

Window functions in one sentence + the classic use?

Aggregates that see a "window" of related rows without collapsing them: ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) = "latest order per user", also running totals and ranks. Naming that exact query is the flex.

UNION vs UNION ALL?

UNION dedupes (costs a sort/hash); UNION ALL just concatenates. If duplicates are impossible or acceptable, ALL is strictly faster — the follow-up they're fishing for.

View vs materialized view?

A view is a saved query — always fresh, no storage, runs on read. A materialized view stores the result — fast reads, but stale until you REFRESH (in PG, manually or via cron). Dashboard aggregations = the materialized use case.

UUID vs serial integer primary keys?

Serial: small, fast, index-friendly — but guessable and awkward across services. UUID: generatable anywhere, safe to expose — bigger, and random v4 scatters B-tree inserts (v7/time-ordered fixes that). Modern default: UUIDv7 externally, or serial internally + public UUID.

How do schema migrations work safely on a live table?

Versioned, incremental, reversible files (Prisma/Knex/Flyway) run in CI before deploy; expand-and-contract for breaking changes: add nullable column → backfill → dual-write → switch reads → drop old. Never DROP in the same deploy that stops writing.

// aws & devops

Horizontal vs vertical scaling — one line + the catch of each?

Vertical: bigger box — zero code changes, hard ceiling, still one failure point. Horizontal: more boxes — near-unlimited, needs statelessness and a load balancer. Real systems: vertical until it's silly, horizontal by design.

Docker container vs VM?

VMs virtualize hardware and boot a full OS each; containers share the host kernel and isolate processes with namespaces/cgroups — MBs not GBs, ms not minutes. "Same image runs identically on my laptop and ECS" is the why.

What's in a good CI/CD pipeline for a Node app?

On PR: install (npm ci) → lint + typecheck → unit tests → build. On merge: build the artifact/image once → deploy staging → smoke/e2e → promote the same artifact to prod (canary/rolling) → alarms watch the rollout. "Build once, promote the artifact" is the phrase that scores.

Infrastructure as code — why, in two sentences?

Terraform/CDK make infra reviewable, repeatable, and recoverable — the environment is a pull request, not a memory. Click-ops means the staging/prod drift and the "only Dave knows why that SG exists" problem.

Where do you put a feature you must ship dark?

Feature flags: deploy the code off, enable per user/percent, kill instantly without a deploy. Decouples deploy from release — also the honest answer to "how do you ship risky changes".

ElastiCache Redis — name three distinct jobs it does?

Session store (the horizontal-scaling enabler), hot-data cache (cache-aside with TTLs), and coordination primitives: rate-limit counters, distributed locks, pub/sub, queues. Bonus caveat: cache invalidation is the hard part — TTL + explicit bust on write.

What is cache-aside, and its classic failure?

Read: try cache → miss → read DB → write cache with TTL. Failure: stale data after DB writes (bust or update the key on write), and stampedes when a hot key expires (jittered TTLs, lock-and-refresh). Naming the stampede is senior.

Kubernetes in one honest sentence for a screen?

Declarative container orchestration — you state desired replicas/resources, it schedules, heals, and scales across nodes. Honest add-on if true: "we didn't need it at our scale; ECS/Fargate was less to operate" — that's judgment, not a gap.

// security

XSS — attack and the three defenses?

Injected script runs in victims' browsers (stored/reflected/DOM). Defend: escape/encode output (React does by default — dangerouslySetInnerHTML is the named escape hatch), sanitize any rich HTML, CSP as backstop, httpOnly cookies so stolen JS context can't read the session.

CSRF — attack and the modern defense?

Another site triggers a state-changing request that rides the user's auto-sent cookies. Defend: SameSite=Lax/Strict cookies (the modern default that mostly kills it), CSRF tokens for forms, and never mutate on GET. If auth is a header token, CSRF largely doesn't apply — trade discussed under XSS.

SQL injection — and why ORMs don't make you immune?

Untrusted input concatenated into SQL. Defense: parameterized queries — the driver sends structure and data separately. ORMs parameterize by default, but every raw-query API ($queryRawUnsafe, string-built WHERE clauses) reopens the door.

How do you store passwords?

Never encrypted, never SHA-256 — slow adaptive hashes: bcrypt/argon2 with per-password salt (built into the format), cost tuned so brute force is expensive. Everything else — reset flows, 2FA, rate limits on login — assumes this floor.

What does HTTPS actually protect, and what not?

Encrypts and authenticates the pipe: no reading or tampering in transit, cert proves the server. Doesn't touch: XSS, SQLi, authz bugs, leaked tokens — everything inside the app. "TLS everywhere is the floor, not the security story."

A dependency you use gets compromised — what limits the blast radius?

Lockfiles + npm ci (no silent upgrades), audit/Dependabot for known CVEs, least-privilege runtime (the app's IAM role can't read all of S3), secrets in a manager not env-committed, and CSP/httpOnly limiting what injected client code can steal.

Rate limiting — where and how?

At the edge (ALB/CloudFront/WAF) for blunt abuse, in-app per user/API-key for fairness — token bucket in Redis is the standard implementation; return 429 + Retry-After. Login and OTP endpoints get their own, much tighter limits.

What secrets hygiene do you actually practice?

Secrets in a manager (not the repo — with git history scanned to prove it), injected at runtime via IAM, rotated on departure/leak, different per environment, and never logged. One honest sentence about a .env near-miss makes this answer human and credible.
