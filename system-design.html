How to run these two days

Each topic is a timed block: a 5-minute idea, one snippet or diagram to internalize, and drills you do on paper, out loud. System design is graded on how you think — so the practice is talking and drawing, not typing.

01 · draw everything

Boxes and arrows on paper for every single drill. The interview is a whiteboard; the muscle you're building is drawing while talking. Reading diagrams is not drawing diagrams.

02 · numbers before boxes

Never draw a component until you've said the scale out loud. "10M DAU → ~100 RPS average" takes 20 seconds and decides half the design.

03 · say the tradeoff

Every component you add costs something. The sentence interviewers wait for is "I'm choosing X, which buys me A but costs me B." Practice it from hour one.

04 · the 25-minute rule

Stuck on a drill past 25 minutes? Look up a reference design, understand it, close it, re-draw it blind. This weekend you're studying patterns, not inventing them.

05 · only have one day?

Do numbers, caching, databases, the framework, and the URL shortener. That's the spine of every answer — the rest is elaboration.

06 · the night before

Nothing new. Re-draw the URL shortener and the feed from memory, re-read the component picker, sleep. Recall beats coverage on the day.

Numbers & back-of-envelope estimation

Every design decision downstream — cache or not, shard or not, queue or not — is decided by numbers you can compute in 30 seconds. Round aggressively; nobody wants precision.

YOU ALREADY KNOW THIS

You've eyeballed a DevTools waterfall and thought "that request is slow" — that's the latency ladder. You've sized a database plan against row counts — that's capacity math. Interviews just want it out loud, with round numbers.

// the idea

  • The one conversion that matters: a day is ~86,400 seconds — round to 10⁵. So 1M requests/day ≈ 12 RPS. Say this in every interview; most "huge" numbers collapse into small ones.
  • Peak ≠ average. Multiply average RPS by 2–5× for peak. Design for peak, state the multiplier.
  • Storage math is multiplication: items/day × size/item × days. Keep every number to one significant digit — the point is the exponent, not the digits.
  • Read/write ratio is the first question to ask of any system. 100:1 read-heavy (feeds, catalogs) → caching wins. Write-heavy (metrics, chat) → queues and partitioning win.
  • Know the latency ladder (table in reference): memory ~100ns, SSD ~100µs, same-region network ~1ms, cross-continent ~100ms. Every design trick is just moving work up the ladder.
back-of-envelope.js
// The only math you need. Do it OUT LOUD, round hard.
const SECONDS_PER_DAY = 100_000;      // really 86,400 — round it

// "10M requests a day" — sounds scary, isn't:
const avgRps  = 10_000_000 / SECONDS_PER_DAY;   // ≈ 100 RPS
const peakRps = avgRps * 3;                     // ≈ 300 RPS — one good server

// "10M posts/day at ~1 KB each" — storage:
// 10M × 1 KB = 10 GB/day  →  ×365 ≈ 3.6 TB/year. A single disk. Relax.

// The exponent is the answer. 10× more users = new design conversation.

// warm-up — answer out loud, then check

1M DAU, each making 20 requests/day. Average RPS?

20M / 10⁵ = ~200 RPS. Peak ~600. One beefy box could survive; a small LB pool is comfortable.

100M photos/day at 2 MB. Storage per day? Per year?

200 TB/day, ~70 PB/year. The exponent says: object storage + CDN, never a database.

Which is bigger: 1 memory read or 1 same-region network hop?

The network hop, by ~10,000× (100ns vs ~1ms). That gap is why caching in-process or in Redis beats "just query the DB again".

A request's journey: DNS → CDN → LB → app

Everything between the user's thumb and your Express route. Learn this path once and the left half of every whiteboard diagram draws itself.

YOU ALREADY KNOW THIS

Deploying to Vercel gave you all of it invisibly: DNS on their nameservers, a CDN at the edge, TLS termination, and a fleet of stateless functions behind a router. The interview version is just drawing what Vercel hid from you.

// the idea

  • The path, in order: DNS resolves the name → TLS handshake → CDN serves static & cached content from a nearby edge → load balancer spreads the rest across app servers → your handler runs. Draw it left-to-right, always.
  • CDN rule: anything that's the same for many users (JS bundles, images, public API responses) belongs on the edge. It's the single biggest latency win because it beats the speed of light — by moving bytes closer.
  • Load balancer: spreads traffic (round-robin / least-connections), health-checks instances, and hides deploys. L4 balances TCP; L7 reads HTTP and can route by path. Saying "L7 so I can route /api and /ws differently" is a senior line.
  • The prerequisite is statelessness: the LB can only send a request anywhere if any server can handle it — so sessions live in Redis or a JWT, uploads in object storage, never on an instance's disk. This one habit is what makes horizontal scaling possible.
  • Two of anything behind an LB also buys you availability — deploys and crashes stop being outages.
nginx.conf
# The load balancer you may have already configured without the title
upstream app {
  least_conn;               # send each request to the least-busy instance
  server 10.0.0.1:3000;     # instances are STATELESS —
  server 10.0.0.2:3000;     # any of them can take any request
}
server {
  listen 443 ssl http2;                 # TLS terminates here
  location /static/ { expires 30d; }    # ...but really: put a CDN in front
  location /        { proxy_pass http://app; }
}

  • "users all over the world", "assets load slowly"CDN at the edge

  • "users get logged out when we scale"externalize sessions (Redis / JWT)
  • "route /api and websockets differently"L7 load balancer

Databases: indexes, replication, SQL vs NoSQL

The database is the bottleneck in ~every design, because it's the part that remembers. Three levers: index it, replicate it, and (last) shard it.

YOU ALREADY KNOW THIS

You've run .explain() on a slow Mongo query and seen COLLSCAN, added an index, and watched it drop from seconds to milliseconds. And a Mongo replica set — primary takes writes, secondaries serve reads — is leader-follower replication. You've operated this chapter.

// the idea

  • Indexes are B-trees (binary search's production cousin — same halving idea). Reads go O(n) → O(log n); the cost is slower writes and more RAM per index. Index what you query, nothing else.
  • Replication: one leader takes writes, followers copy the log and serve reads. Buys read throughput + a hot standby. The catch is replication lag — a follower can be seconds behind, so a user might not see their own write. Name that; it's the classic follow-up.
  • SQL vs NoSQL, honestly: relational buys you joins, transactions, and constraints; document stores buy flexible schema and easy horizontal scale. The senior answer: "either works here — what matters is the access patterns" — then pick one and justify it.
  • Transactions: "these writes succeed or fail together." Money, inventory, bookings → you want them (SQL's home turf). Likes and view counts → you don't.
  • Order of operations when the DB is slow: index → cache → replicas → shard. Jumping straight to sharding is the classic junior tell.
indexes.js
// You have met this in production:
db.orders.find({ userId }).explain()
// "COLLSCAN"  → reads EVERY document. O(n). Fine at 1k rows, an outage at 100M.

db.orders.createIndex({ userId: 1, createdAt: -1 })
// "IXSCAN" → walks a B-tree. O(log n). Compound index serves
// "orders for user, newest first" in one shot.

// The trade: every index slows every write and eats RAM.
// Rule: indexes mirror your queries — never speculate.

// spot it in the wild

  • "this query got slow as the table grew"missing index — check the plan
  • "reads vastly outnumber writes"read replicas (+ cache first)
  • "user doesn't see their own update"replication lag — read-your-writes
  • "payments / bookings / inventory"transactions → SQL comfort zone

day 1 · 13:45 · 60 min~1ms hit vs ~30ms DB read

Caching

The highest-ROI component in system design, exactly like hash maps were in DSA — and it's the same trade: spend memory, skip repeated work.

YOU ALREADY KNOW THIS

useMemo, Cache-Control headers, Redis in front of a slow query — you've cached at three layers already. The interview version adds two questions you must always answer: when does it expire, and how does it get invalidated?

// the idea

  • Cache-aside is the only pattern you need: read cache → miss → read DB → write cache with a TTL. On updates: write the DB, then delete the key (recompute on next read — don't try to patch cached values in place).
  • Always say the TTL out loud. "Cached for 5 minutes" is a product decision disguised as an infra decision — it states how stale you're willing to be.
  • What to cache: read-heavy + rarely-changing + expensive to compute. Profile pages, product listings, rendered feeds. Never cache what must be exact (balances, stock counts).
  • Thundering herd: a hot key expires and 10k requests hit the DB at once. Fixes: per-key lock ("one flight refills, the rest wait"), staggered TTLs, or serving stale while refreshing. Naming this unprompted is a strong-signal moment.
  • Eviction: memory fills → something must go → LRU by default. (You built exactly this in DSA — LRU Cache. It was Redis all along.)
cache-aside.js
// Cache-aside — the pattern behind every "we added Redis" war story
async function getProduct(id) {
  const hit = await redis.get(`product:${id}`);
  if (hit) return JSON.parse(hit);                       // ~1 ms

  const product = await db.products.findById(id);        // ~30 ms
  await redis.set(`product:${id}`, JSON.stringify(product),
    'EX', 300 + Math.floor(Math.random() * 60));         // TTL + jitter
  return product;
}

// On update: write DB, then DELETE the key. Next read refills it.
async function updateProduct(id, patch) {
  await db.products.updateOne({ _id: id }, { $set: patch });
  await redis.del(`product:${id}`);
}

// spot it in the wild

  • "same data requested over and over"cache-aside + TTL
  • "DB melts when the cache restarts"thundering herd — lock / stale-while-refresh
  • "users see stale data — how stale is OK?"the TTL conversation
  • "memory is full — what do we drop?"LRU eviction

day 1 · 14:45 · 90 minthe shard key decides everything

Scaling & sharding

The escalation ladder for "more traffic than one machine can take" — and the last rung, splitting the data itself, where the only real decision is the key.

YOU ALREADY KNOW THIS

PM2 cluster mode fanning your Express app across CPU cores is horizontal scaling in miniature — same app, many copies, work spread between them. Sharding applies the identical idea to the data instead of the compute.

// the idea

  • Scale vertically first. A bigger box is boring, cheap, and has zero new failure modes. Saying "I'd scale up before scaling out" is a senior move, not a cop-out — modern single machines handle enormous load.
  • Horizontal = clones behind an LB — works only because the app tier is stateless (day-1 morning). App servers scale trivially; the database is what's hard, which is why the ladder is: index → cache → replicas → shard.
  • Sharding: split rows across machines by a key — hash(userId) % N spreads evenly. Each shard is smaller, faster, and independently scalable. Costs: no cross-shard joins/transactions, and resharding pain.
  • The shard key is the whole decision. Good: high-cardinality, evenly-accessed (userId). Bad: low-cardinality or skewed (country, date) — one shard gets the traffic. The follow-up is always the hot key: one celebrity's data melting one shard. Answer: cache the hot entity, or split it further.
  • Consistent hashing, one sentence: keys and nodes hash onto a ring, each key belongs to the next node clockwise — so adding a node moves only ~1/N of keys instead of nearly all of them under naive % N.
sharding.js
// Sharding = deciding which machine OWNS a row. The key decides everything.

shard = hash(userId) % N       // even spread — but going N=4 → 5
                               // remaps ~ALL keys. Migration nightmare.

// Consistent hashing: nodes + keys hash onto a ring;
// a key belongs to the next node clockwise.
// Add a node → only ~1/N of keys move. This is the whole trick.

// GOOD shard key: userId    (high cardinality, even traffic)
// BAD  shard key: country   (5 shards do 90% of the work)
// BAD  shard key: createdAt (ALL writes hammer today's shard)

  • "one user/tenant melts a shard"hot key — cache it, split it

Queues & async work

A queue is a buffer between "accepted" and "done". It absorbs spikes, survives crashes, and lets you answer the user before the slow work happens.

YOU ALREADY KNOW THIS

If you've pushed a BullMQ job for a welcome email instead of awaiting nodemailer in the request handler, you've made the exact architectural move this chapter is about — and the event loop's task queue has been teaching you the mental model all along.

// the idea

  • When to reach for a queue — any of: the work is slow (video encode, email), the traffic is spiky (flash sale), or the downstream is fragile (third-party API). Producer enqueues, responds immediately; workers chew through at their own pace.
  • The contract is at-least-once. A worker can crash after doing the work but before acking — the queue redelivers. Therefore every job must be safe to run twice: idempotency keys, upserts, "already processed?" checks. This is the #1 follow-up question.
  • Queue vs pub/sub: a queue gives each job to one worker (work distribution); pub/sub gives each event to every subscriber (fan-out of notifications). Kafka-style streams = pub/sub with replayable history — one sentence is enough.
  • Dead-letter queue: after N failed retries a job goes to the DLQ for humans. Mentioning it says "I've operated this", loudly.
  • Backpressure: queue depth growing = consumers can't keep up. Monitor depth, scale workers on it, and shed or reject load before the queue eats all your memory.
queue.js
// Respond NOW, work later
app.post('/signup', async (req, res) => {
  const user = await db.users.create(req.body);
  await queue.add('welcome-email', { userId: user.id },
    { jobId: `welcome:${user.id}` });   // same jobId = enqueued once, ever
  res.status(201).json(user);           // user is gone before the email exists
});

// Worker — written to be safe to run TWICE (at-least-once delivery)
worker.process('welcome-email', async (job) => {
  const user = await db.users.findById(job.data.userId);
  if (user.welcomeSentAt) return;       // redelivered? no-op.
  await sendEmail(user.email, 'welcome');
  await db.users.update(user.id, { welcomeSentAt: new Date() });
});

  • "traffic spikes 50×, downstream can't"queue as shock absorber
  • "we charged / emailed them twice"idempotency key
  • "several services care about one event"pub/sub, not a queue

The interview framework

A system design interview is 45 unstructured minutes — unless you bring the structure. This six-step script is the structure. It works for literally every prompt.

YOU ALREADY KNOW THIS

It's the same discipline as a good sprint kickoff: agree scope before touching anything, size the work, define the interfaces, then build. You run this meeting at work — now run it solo, at a whiteboard, in 45 minutes.

// the idea

  • You drive. The single biggest failure mode is waiting to be led. Announce the plan in the first 30 seconds: "I'll clarify requirements, do quick numbers, sketch the API, draw the high level, then we deep-dive wherever you like."
  • Scope ruthlessly. "Design WhatsApp" means three features: 1:1 messages, delivery status, online presence. Say what you're cutting ("no calls, no stories") — cutting scope earns points.
  • Draw the boring baseline fast: client → LB → stateless app tier → cache → DB, queue hanging off the side. It's 80% of every answer. Spend your brilliance on the deep dive, not on rediscovering this shape.
  • Deep-dive where they point. When the interviewer nudges ("what about the feed for celebrities?") — that's the graded section. Follow the nudge, always.
  • Checkpoint out loud every ~10 minutes: "That's the write path; want me to do the read path or dig into storage?" It reads as collaboration, and it is.
the-script.txt
1. REQUIREMENTS  (5 min)   functional: the top 3 features, cut the rest
                           non-functional: scale, latency, consistency needs
2. NUMBERS       (3 min)   DAU → RPS → storage → read/write ratio
3. API + DATA    (5 min)   core endpoints + core entities. Sketch, don't gold-plate
4. HIGH LEVEL    (10 min)  client → LB → app → cache → db  (+ queue if async work)
5. DEEP DIVE     (15 min)  the hard part — theirs if they point, yours if not
6. WRAP          (5 min)   bottlenecks, single points of failure, what you'd do next

CAP, consistency & availability

The vocabulary of tradeoffs. You don't need the theory — you need to sort any feature into "must be correct" vs "must be up", and know what each costs.

YOU ALREADY KNOW THIS

You've seen a like count jump backwards on refresh and thought nothing of it — but you'd file a P0 if a checkout charged twice. Congratulations: you already sort features into eventual vs strong consistency. This chapter just names the sort.

// the idea

  • CAP without mysticism: when the network between replicas breaks (it will), you choose per-system: CP — refuse some requests, stay correct; or AP — answer everyone, possibly stale. It's not "pick 2 of 3"; it's "what breaks first when a partition happens".
  • Strong consistency = every read sees the latest write (banking, inventory, seat booking). Eventual = replicas converge in seconds (likes, follower counts, feeds). Most products are eventual almost everywhere — say so, feature by feature.
  • Read-your-writes is the special case users actually notice: after I post, I must see it — everyone else can wait. Cheap fix: read the author's own data from the leader (or their cache), everything else from replicas.
  • Availability math: 99.9% ≈ 8.7 hours down/year; 99.99% ≈ 52 minutes. Each nine roughly means "another instance of everything, in another failure domain" — redundancy, health checks, automatic failover. Nines are bought, not declared.
  • The audit ritual for step 6: point at each box and ask "what happens when this dies?" One LB, one DB leader, one queue broker — each is a single point of failure until it has a partner.
cap.txt
Network partitions WILL happen. When one does, each system chooses:

  CP  — refuse some requests, never be wrong     bank balance, seat #14C
  AP  — answer everyone, maybe slightly stale    like counts, feeds, DNS

The interview move: sort each FEATURE, not the whole product.
  checkout      → CP  (refuse > double-charge)
  product page  → AP  (stale price for 5s beats a blank page)

Nines:  99.9% = 8.7 h/yr down   99.99% = 52 min/yr   each nine ≈ 10× effort

// warm-up — CP or AP? decide, then check

A bank transfer between two accounts

CP. Refusing the transfer during a partition is annoying; letting balances disagree is a headline. Transactions, leader-only writes.

The retweet counter on a viral post

AP. Nobody can verify 1.2M vs 1.200003M. Serve stale, converge later, never block reads on it.

Booking the last seat on a flight

CP at the moment of purchase (two people cannot both get seat 14C) — even though browsing seats can be AP. Same product, different features, different choices — that's the whole skill.

APIs, rate limiting & idempotency

Your home turf, upgraded with the three details interviewers actually probe: pagination that scales, limits that protect, and writes that are safe to retry.

YOU ALREADY KNOW THIS

You've designed REST APIs for years, and if you've used express-rate-limit or retried a Stripe call with an Idempotency-Key header, you've consumed both of today's patterns. Now you get to produce them.

// the idea

  • Cursor pagination beats offset and interviewers love hearing why: OFFSET 100000 makes the DB walk 100k rows to throw them away, and rows shifting between requests makes pages skip or repeat. A cursor ("everything after id X / time T") is O(log n) with an index and stable under inserts.
  • Rate limiting = token bucket: a bucket per user refills at R tokens/sec up to burst B; each request spends one; empty bucket → 429. Distributed version: the bucket lives in Redis so all API servers share it.
  • Idempotency: networks retry, users double-click. The client sends an Idempotency-Key; the server stores the result under it and replays the stored response on repeats. Every payment discussion must include this.
  • Auth in one line: JWTs make auth stateless (any server verifies the signature — perfect behind an LB) at the cost of awkward revocation; sessions in Redis revoke instantly at the cost of a lookup. Naming that trade is the point, not picking a winner.
  • Webhooks — flip side of APIs: you're the caller now. Sign the payload, retry with backoff, and expect the receiver to see duplicates (their idempotency problem now).
token-bucket.js
// Token bucket — THE rate limiter. Refill R/sec, burst up to B.
const R = 2, B = 10;
const buckets = new Map();   // in prod: Redis, keyed rl:{userId}

function allow(userId) {
  const now = Date.now();
  const b = buckets.get(userId) ?? { tokens: B, last: now };
  b.tokens = Math.min(B, b.tokens + ((now - b.last) / 1000) * R);
  b.last = now;
  if (b.tokens < 1) { buckets.set(userId, b); return false; }  // → 429
  b.tokens -= 1;
  buckets.set(userId, b);
  return true;
}
// Why bucket over a fixed window: it allows honest bursts
// and can't be gamed at the window boundary.

  • "one client hammers the API"token bucket in Redis
  • "double-click bought two subscriptions"idempotency keys
  • "auth across 20 stateless servers"JWT — and name the revocation cost

day 2 · 12:45 · 60 minclassic #1 — the Two Sum of system design

Classic: URL shortener

The most-asked design on Earth because it's small enough to finish and deep enough to grade. Learn it cold — it's also the template every "simple" design follows.

YOU ALREADY KNOW THIS

It's a CRUD app with one POST and one very hot GET — an Express route, a Mongo lookup, a redirect. Every skill from Day 1 slots in: numbers say read-heavy, so cache; the ID design is the only genuinely new thought.

// the walkthrough — say it in this order

  • Requirements + numbers: shorten + redirect (cut: auth, custom domains). Say the ratio: reads dwarf writes ~100:1 — that one sentence drives the whole design. 100M new links/month ≈ 40 writes/sec; redirects maybe 4k reads/sec.
  • The ID is the design: 7 chars of base62 ≈ 3.5 trillion combinations. Generate from an auto-increment counter → base62-encode. Counter is a SPOF? Hand out ranges to each server (server A gets 1–1M, B gets 1M–2M) — no coordination per request.
  • Storage: one table: code → longUrl, createdAt. 500B × billions = single-digit TB — one primary + replicas is plenty. If pushed: shard by hash(code).
  • The read path is the product: redirect must be fast → cache-aside on hot codes (Zipf: a tiny fraction of links get almost all clicks). 302 not 301 — 301 lets browsers cache the redirect forever and your analytics go blind. Interviewers ask this exact thing.
  • Analytics without slowing redirects: fire a click event onto a queue, aggregate async. The redirect path never waits for the write.
base62.js
// 62^7 ≈ 3.5 trillion — 7 chars is enough forever
const ALPHA = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';

function encode(n) {
  let s = '';
  while (n > 0) { s = ALPHA[n % 62] + s; n = Math.floor(n / 62); }
  return s || '0';
}
encode(125_500_299_003);  // "29zoWFK" — your short code

// GET /:code  →  cache hit? redirect 302.
//             →  miss? DB lookup, fill cache, redirect 302.
//             →  publish {code, ts, ua} to the analytics queue. Never await it.

// the follow-ups they will ask

  • "why not hash the URL to make the code?"collisions + same-URL dupes — counter wins

day 2 · 13:45 · 90 minclassic #2 — the fan-out problem

Classic: news feed

"Design Twitter/Instagram." One real question hides inside: when someone posts, who does the work — the writer, or every reader? That decision is the interview.

YOU ALREADY KNOW THIS

Precompute-vs-compute-on-request is a call you've made before: SSG vs SSR. Fan-out on write is static generation (build the feed ahead of time); fan-out on read is server rendering (assemble on request). Same instinct, new noun.

// the idea

  • Fan-out on write (push): when Alice posts, push the post id into a cached feed list for each follower. Posting costs O(followers); reading is one Redis read — perfect for read-heavy social apps.
  • The celebrity problem: 100M followers × one tweet = 100M writes. Fan-out on write dies exactly here — and every interviewer steers you into it on purpose.
  • The hybrid (the expected answer): normal users fan out on write; celebrities don't — their posts are merged in at read time from a small "celebrity posts" cache. Reads do a k-way merge of (my precomputed feed) + (posts from the few celebrities I follow) — the exact merge-k-sorted-lists pattern from DSA heaps.
  • Feed storage: a capped list of post ids per user in Redis (ids only — hydrate post bodies from a post cache). A few hundred ids × 8 bytes × millions of users fits in memory fine — say the math.
  • Do the fan-out on a queue — posting must return in ms; pushing to a million follower lists happens in workers. A feed being seconds stale is invisible (AP, eventual — yesterday's vocabulary).
fanout.js
// Fan-out on write — runs in queue workers, not in the POST handler
async function fanOut(post) {
  if (await isCelebrity(post.authorId)) return;   // celebrities skip fan-out

  const followers = await getFollowerIds(post.authorId);
  for (const chunk of chunks(followers, 1000)) {
    await Promise.all(chunk.map(f =>
      redis.lpush(`feed:${f}`, post.id)           // feed = capped list of IDs
        .then(() => redis.ltrim(`feed:${f}`, 0, 799))));
  }
}

// Read path: one list read + merge in celebrity posts + hydrate
// GET /feed  →  ids = LRANGE feed:{me}  +  recent posts of followed celebrities
//            →  k-way merge by timestamp → MGET post bodies → return

  • "ranking, not chronological?"same plumbing — score at merge time

day 2 · 15:15 · 90 minclassic #3 — real-time + state

Classic: chat

"Design WhatsApp." The twist vs everything so far: servers hold live connections, which means state, which means routing messages to the right box.

YOU ALREADY KNOW THIS

If you've run socket.io with the Redis adapter, you have built this system: sockets pinned to instances, pub/sub carrying events between them, rooms as channels. The interview version just adds persistence and delivery guarantees.

// the idea

  • WebSockets, not polling — chat needs server-push. A socket is a long-lived TCP connection pinned to one server, so the chat tier is stateful: the design problem is "which server holds Bob's socket?"
  • The shape: chat servers hold sockets; a session registry (Redis: userId → serverId) tracks who's where; servers talk to each other over pub/sub. A → server-1 → publish to Bob's channel → server-7 (holding Bob's socket) → B.
  • Persist first, then deliver. Write the message to the DB before pushing it — sockets drop; the DB is the source of truth. Offline? No socket anywhere → push notification + deliver on reconnect from the store.
  • Delivery states = ✓ sent (server persisted) ✓✓ delivered (device acked) ✓✓ blue (read receipt). Each tick is just an ack event flowing back the same path. Message ordering: per-conversation sequence numbers — global ordering doesn't exist and nobody needs it.
  • Group chat = fan-out again (yesterday's pattern, smaller): one message → lookup members → route to each member's server. Presence ("online 2m ago") = heartbeats updating a TTL'd Redis key — don't broadcast every flicker; batch it.

// reference · run this script in every interview

The interview playbook

The meta-algorithm for the room. System design grades judgment, not memory — a modest design defended with clear tradeoffs beats an exotic one you can't justify.

Scope ruthlessly

Restate the prompt as three features and say what you're cutting. "I'll do messages, delivery states, and presence — no group calls." Cutting scope is a skill being graded, not a dodge.

Numbers before boxes

DAU → RPS → storage → read/write ratio, rounded hard, out loud. Ninety seconds that decide cache-vs-not, shard-vs-not, queue-vs-not.

API + data model, briefly

Core endpoints and core entities on the board. It forces clear thinking and gives the interviewer hooks to steer with. Don't gold-plate it.

Draw the boring baseline

Client → LB → stateless app tier → cache → DB, queue off the side. Every system starts here; drawing it fast signals fluency and buys deep-dive time.

Scale by bottleneck, not buzzword

Point at the component that breaks first at your numbers and fix that. "At 4k reads/sec the DB is the bottleneck, so…" — never add Kafka because it sounds impressive.

Go deep where they point

The interviewer's nudge marks the graded section. Follow it even if you'd planned otherwise — depth on their topic beats breadth on yours.

Close with failure modes

Walk the diagram asking "what dies, and what happens?" Then name what you'd do next with more time. This is the strongest possible ending — never make them ask.

// sentences that earn points — each one, said naturally, is a signal

"that's a read-heavy workload"

Names the ratio before choosing components. The single fastest way to sound like you've done this before.

"this is a single point of failure"

Say it about your own diagram, unprompted — then fix it. Self-critique reads as seniority.

"the cache needs an invalidation story"

Anyone can add Redis. Naming TTL + invalidation before being asked is what separates the answer.

"at-least-once, so this must be idempotent"

The queue sentence. It preempts the #1 follow-up and shows you've been paged for the alternative.

"I'd scale up before scaling out"

Vertical first is the experienced move. Distributed systems are a cost you pay, not a badge you earn.

"the shard key decides everything"

If sharding comes up, this sentence + a hot-key example is the whole conversation.

Safe to skip (this weekend)

Real topics, wrong weekend. Know the name and one honest sentence each — enough to stay composed and redirect if one appears.

  • Consensus protocols (Paxos, Raft) — "they keep replicas agreed on who's leader; I'd use a battle-tested store (etcd/ZooKeeper) rather than implement one."
  • Dynamo internals (vector clocks, Merkle trees, gossip, hinted handoff) — the machinery inside AP databases. Name-drop only if asked how Cassandra works.
  • Kafka internals (partitions, ISR, consumer rebalancing) — "a distributed, replayable append-only log" is the whole sentence you need.
  • Kubernetes internals — "schedules containers across machines and restarts what dies." Interviewers want your architecture, not your YAML.
  • Geo-distributed writes / multi-leader conflicts — CRDTs, last-write-wins. Genuinely hard; punt gracefully: "single write region first, multi-region reads via replicas."
  • Exotic estimation — memorizing beyond the latency ladder. Six numbers and confident rounding beat a memorized table every time.
